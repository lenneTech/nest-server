# Migration Guide: 12.8.6 → 12.8.7

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None. The deployed behaviour does not change |
| **New Features** | `@UnifiedField` warns at start for a field whose type the SWC dev start and the tsc build read differently; the package bin `nest-check-unified-field-types` finds those fields and with `--fix` writes the declared type (§1, §2) |
| **Bugfixes** | Under the SWC dev start an enum field took the enum object as its type — `@UnifiedField({ enum: Status, mongoose: true })` crashed the schema build; it is now read as `String` / `Number` like in the tsc build (§1). Documentation: §14 of the 12.0 guide no longer claims the TypeScript loader matches the tsc build for decorator metadata. The 12.1 guide names the pnpm 10 deploy effect of the `typeorm` devDependency |
| **Migration Effort** | Recommended: run `nest-check-unified-field-types --fix` once and add it to `check` / `check:fix` (§2). 12.9.0 refuses such fields at boot |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.7
pnpm run update                                  # nest-server-starter based projects
pnpm exec nest-check-unified-field-types --fix   # npm mode; vendor mode: §2
pnpm run format
pnpm run build
pnpm test
```

## 1. The dev start and the build can read a field's type differently

Without `type`, `@UnifiedField` takes a field's type from the `design:type` metadata the compiler writes. The tsc
build writes it with the type checker. The TypeScript loader of the dev start (`ts-compiler.js`, SWC) writes it per
file, without type information:

| Field | SWC (dev start) | tsc (build, `strict: false`) |
|---|---|---|
| `max?: null \| number`, `count?: number \| undefined` | `Object` | `Number` |
| `kind?: Kind` (a type alias, local or imported) | `Object` | `String` / `Number` |
| `status?: Status` (an enum) | the enum object — read as `String` / `Number` since 12.8.7 | `String` / `Number` |
| `status?: Status \| null` | `Object` | `String` / `Number` |
| `flag?: boolean \| null` | `Object` | `Boolean` |
| `state?: 'ok' \| 'error'` (written in place), `number`, `string`, `boolean`, `Date`, a class imported as a value | same as tsc | |
| `meta?: Record<string, unknown>`, an interface, `string \| number` | `Object` | `Object` |

`Object` makes `@UnifiedField` validate the field as a nested object. In the dev API `max: 5` is refused, Swagger
documents the field as `type: object` and the generated app client types it `{ [key: string]: unknown }` — while the
deployed build accepts `max: 5`. Projects in strict mode (`strictNullChecks`) get `Object` for `null | number` from
tsc too, so there the deployed API refuses it as well.

**What is new:**

- `@UnifiedField` reads the enum object SWC writes for an enum field as `String` / `Number`, like the tsc build. Until
  12.8.6 it became the field's type: the Mongoose path type of `@UnifiedField({ enum: Status, mongoose: true })`, which
  `SchemaFactory` refused — the dev start crashed while the build booted.
- `@UnifiedField` warns once per field at start when the type comes only from metadata that says `Object` and neither
  `type`, `isAny` nor `enum` is set:
  `[@UnifiedField] "InputRequestCreateInput.max" has no explicit type, and the compiler metadata says only "Object". …`
- The package bin `nest-check-unified-field-types` (file `bin/check-unified-field-types.js`) uses the project's
  TypeScript type checker to find every such field. With `--fix` it writes the type the field declares —
  `type: () => Number`, `String`, `Boolean`, `Date` or the class, referenced the way the file imports it. Without
  `strictNullChecks` that is the type the tsc build already uses, so the deployed behaviour stays as it is and the dev
  start matches it. **With `strictNullChecks`** the tsc build writes `Object` for a union with `null` / `undefined`
  too: the check marks such a field `[changes the deployed build]`, because the written type changes how the deployed
  API validates it (as the declared type instead of as an object) — review those fields. Fields without a runtime class (an interface, a `Record`, a mixed union, `any`, a class imported
  only as a type) are reported with what to declare: `type: () => Object` for a free-form object, `isAny: true` for
  any value, or a class for a nested structure.

```typescript
// Before: the dev start reads Object, the build reads Number
@UnifiedField({ description: 'Upper limit', isOptional: true })
max?: null | number;

// After `nest-check-unified-field-types --fix`
@UnifiedField({ description: 'Upper limit', isOptional: true, type: () => Number })
max?: null | number;
```

## 2. Running the check

| Mode | Command |
|---|---|
| npm mode | `nest-check-unified-field-types` (package bin, e.g. `pnpm exec nest-check-unified-field-types --fix`) |
| vendor mode | `node ./bin/check-unified-field-types.js` once the lt CLI copies the file next to `bin/migrate.js`; until then a one-off `npx -p @lenne.tech/nest-server@12.8.7 nest-check-unified-field-types --fix` in the API project |

Options: `--fix` writes the types, `--project <tsconfig>` (default `tsconfig.json`), `--include <dir>` (default `src`,
repeatable). Exit code 1 when fields remain (with `--fix`: the ones it cannot fix), 2 on a usage error. Spec and test
files are skipped (checked since 12.9.0).

nest-server-starter adds it as `check:unified-field-types` to `check` (fails on a finding) and with `--fix` to
`check:fix`, before `format`, so `lt fullstack update` brings it to every starter-based project. A project of its own:

```jsonc
"check:unified-field-types": "nest-check-unified-field-types",
// in "check": … && pnpm run check:unified-field-types && …
// in "check:fix": … && pnpm run check:unified-field-types -- --fix && pnpm run format && …
```

## 3. Outlook

12.9.0 turns the warning of §1 into an error at boot (`12.8.x-to-12.9.x.md`), as `@UnifiedField` already refuses an array field
without `type`. A project that runs `check:unified-field-types` in its `check` is ready for it.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `[@UnifiedField] "X.y" has no explicit type …` at start | §1 | `nest-check-unified-field-types --fix` (vendor mode: `node ./bin/check-unified-field-types.js --fix`), or declare `type` / `isAny` / `enum` by hand |
| The dev API refuses `max: 5` with "must be an object", the deployed API accepts it | §1 | as above |
| The check reports `(a type-only import)` | the class is imported with `import type` | import it as a value, then `type: () => X` |
| A fixed field is marked `[changes the deployed build]` | `strictNullChecks`: the build validated it as an object until now | review it; the written type is the one the field declares |
| `tsconfig not found` (exit code 2) | the check runs outside the API project | run it in the API project, or pass `--project` |
