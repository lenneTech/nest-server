# Migration Guide: 11.42.2 → 11.42.3

## Overview

| Category             | Details                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Security**         | An open GraphQL WebSocket loses what its user lost — membership, tenant, role, session — instead of keeping it until reconnect (§1) |
| **Security**         | IAM sign-out ends the session on the server, not only in the browser (§2)                                                       |
| **Bugfix**           | The IAM WebSocket handshake accepts a valid bearer token (§3)                                                                   |
| **Security**         | The legacy WebSocket handshake verifies the token's signature and expiry, as HTTP does (§4)                                     |
| **New option**       | `graphQl.subscriptionRevalidationMs` (default 30000) (§1)                                                                       |
| **Migration Effort** | None for most projects — `pnpm update`. Check §1 if you replaced `onConnect` yourself                                           |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick up the core update. No configuration change is required.

## 1. Open WebSockets are re-checked, and closed when the rights behind them changed

A GraphQL WebSocket was authorized once: `onConnect` validated the token and recorded the user, the
subscribe wrapper resolved the tenant, and every event and operation on the socket ran on that
snapshot until the client reconnected. Removing someone from a tenant, switching a tenant off,
withdrawing a role or ending a session took effect on every new request and on none of the sockets
that were already open — for a browser tab, often hours.

Since 11.42.3 every connection `CoreModule`'s `onConnect` accepts is registered with the rights it was
authorized with, and checked again:

| Trigger                                                                                                                                                 | When                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `CoreTenantGuard.invalidateUser()` / `invalidateTenant()` / `invalidateAll()`, `CoreUserService.setRoles()`, an `update()` of `roles` / `verified` / `emailVerified`, the legacy password reset | at once                                                                               |
| Better-Auth deleting a session: sign-out, a revoked session, a reset with `revokeSessionsOnPasswordReset`                                               | at once                                                                               |
| A change nobody invalidated (a membership edited directly in the database, an expired session)                                                         | before the next event or operation, once `graphQl.subscriptionRevalidationMs` has passed |

A connection whose rights changed is closed with **4403**. The graphql-ws client retries that code: it
reconnects, resubscribes and continues with the rights the user holds now, or is refused at the
handshake when the session is gone. Nothing changes for a connection whose rights did not change.

```typescript
// config.env.ts — optional, the default is 30000
graphQl: {
  subscriptionRevalidationMs: 30000, // 0 = re-check on every event and operation, false = only on invalidation
},
```

**If you replaced `onConnect`** through `graphQl.driver.subscriptions`, register what you accept, or
your connections keep the old "checked once" behaviour:

```typescript
import { registerWsConnection } from '@lenne.tech/nest-server';

onConnect: async (context) => {
  const user = await authenticate(context); // your own handshake
  context.extra.user = user;
  registerWsConnection({
    carrier: context.extra,
    reauthenticate: () => authenticate(context), // the user the token belongs to NOW, or null
    socket: context.extra.socket,
    user,
  });
  return context.extra;
},
```

**If your client does not use graphql-ws** (or turned its retries off), make sure it reconnects after a
4403 close; otherwise the user's live updates stop until the page is reloaded.

A dropped event is checked after graphql-js executed it and before it is sent: the reads made while
computing it happened, but nothing of it reaches the client. Subscription resolvers should not write.

## 2. IAM sign-out ends the session on the server

`CoreBetterAuthService.revokeSession()` — used by `POST /iam/sign-out` and the `betterAuthSignOut`
mutation — passed the session token to Better-Auth's `signOut` only as an `Authorization` header.
Better-Auth reads that header only with its `bearer` plugin, which the framework does not install. The
sign-out therefore answered `{ success: true }`, cleared the cookies, and deleted nothing: the session
stayed valid server-side, and the same token kept authenticating requests until it expired.

The token is now passed as the signed session cookie Better-Auth reads, and the header is kept for
projects that added the bearer plugin themselves. **No action is needed.** Sessions signed out before
the update are still valid until they expire; if that matters for your deployment, delete them from the
`session` collection.

## 3. The IAM WebSocket handshake accepts a valid bearer token

Both IAM driver builders authenticated the handshake through `getSession()` with an `Authorization`
header — the same header Better-Auth ignores without its `bearer` plugin. Every IAM WebSocket handshake
with a bearer token was refused as `Invalid or expired session`, so authenticated subscriptions did not
work in IAM-only projects at all.

The handshake now resolves the token the way the HTTP middleware does for the same header: a Better-Auth
JWT first, then the session store, and `getSession()` as the last resort. If you built a workaround
(for example a custom `onConnect`), you can remove it — and register the connection as shown in §1 if
you keep it.

## 4. The legacy WebSocket handshake verifies the token

Legacy access tokens are verified on HTTP by passport-jwt: signature and expiry. The legacy WebSocket
handshake read them with `decodeJwt()` instead, which checks neither — only the payload's `tokenId` had
to match the device. An expired token, or a copy of one re-signed with any key, therefore kept opening
sockets for as long as the device's refresh token was not rotated.

The handshake, and the re-check from §1, now use `CoreAuthService.verifyJwt()`, which applies passport's
rule: `jwt.secretOrKeyProvider` when configured, else `jwt.secretOrPrivateKey || jwt.secret`. A token
that is not a JWT at all is refused as unauthorized instead of closing the socket with 4500 and a
TypeError as the reason.

**What this changes for a legacy WebSocket client:** a connection now ends when its token does — at
expiry, or when the client refreshes its tokens (a refresh rotates the device's `tokenId`, which already
invalidated the old token on HTTP). The socket is closed with 4403 and graphql-ws reconnects, so pass
the CURRENT token on every connect rather than the one the client had at start-up:

```typescript
createClient({
  url,
  connectionParams: () => ({ Authorization: `Bearer ${getCurrentAccessToken()}` }), // a function, not an object
});
```

The same holds for an IAM client that authenticates its socket with a Better-Auth JWT (§3): the JWT
expires after `betterAuth.jwt.expiresIn` (15 minutes by default). A session token lives as long as its
session.

An AuthService passed to `CoreModule.forRoot()` that does not extend `CoreAuthService` may lack
`verifyJwt()`; it keeps the unverified read and logs a warning once. Extend `CoreAuthService` to close it.

## Troubleshooting

| Symptom                                                                    | Cause                                                          | Fix                                                  |
| -------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| A client's WebSocket closes with 4403 after a role or membership change    | Intended: the rights behind the connection changed             | Let the client reconnect (graphql-ws does by default) |
| Live updates stop after a role change and never resume                     | The client does not reconnect after a 4403 close               | Enable reconnects (graphql-ws `retryAttempts`)       |
| Revoked access still receives events on a project with its own `onConnect` | The custom `onConnect` does not register the connection        | Call `registerWsConnection()` (§1)                   |
| IAM subscriptions are refused with `Invalid or expired session`            | 11.42.2 or older                                               | Update to 11.42.3                                    |
| A WebSocket reconnects and is refused shortly after a token refresh or expiry | The client reconnects with the token it had at start-up      | Pass `connectionParams` as a function (§4)           |
| `has no verifyJwt()` warning at the first legacy WebSocket                  | The AuthService does not extend `CoreAuthService`             | Extend `CoreAuthService` (§4)                        |
