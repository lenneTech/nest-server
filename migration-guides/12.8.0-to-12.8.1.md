# Migration Guide: 12.8.0 → 12.8.1

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | `CoreBetterAuthService.isPersistedUser()`, `CoreBetterAuthUserMapper.mapUnstoredSessionUser()` and `equalizeLegacyPasswordSync()` |
| **Bugfixes** | Security: a sign-up for an already registered address changed the existing account (§1). Defense in depth: the IAM API middleware decides on the path Better-Auth routes (§2) |
| **Migration Effort** | Update. Projects that had `requireEmailVerification: true` or `autoSignIn: false` with open sign-up check their accounts (§1) |

12.8.1 is a security patch for 12.8.0. The same fix ships in 12.6.6 (`latest-12.6`) and 11.44.1 (`latest-11`).

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.1
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. A sign-up for an already registered address changes nothing

**Why:** with `emailAndPassword.requireEmailVerification: true` or `emailAndPassword.autoSignIn: false` (set through
`betterAuth.options`), Better-Auth 1.5.0 and later answers a sign-up for a known address like a new one, so the
response does not reveal which addresses have an account. That answer carries a placeholder user: a generated id and
the given address, stored nowhere. The core's sign-up paths took it for the new user:

- **REST `POST /iam/sign-up/email`** (`CoreBetterAuthController.signUp()`, also without a project override) linked the
  placeholder to the real account it found by address. That account's `iamId` then pointed at the placeholder, it got
  `verified: false`, its **legacy password was set to the one the caller chose**, and the answer carried its roles.
- **GraphQL `betterAuthSignUp`** linked it the same way and answered with the real account's id and roles.
- **The legacy sign-up with IAM enabled** (`/auth/signup`, GraphQL `signUp`) linked it, overwrote the password and
  returned the real account, and the caller received its tokens.

With the legacy endpoints open, the overwritten legacy password let the caller sign in as the account owner. For a
legacy user without an IAM credential account, the next IAM sign-in with that password migrated the account to it.

**What changed:** a user Better-Auth returns from a sign-up is written only once `CoreBetterAuthService.isPersistedUser()`
confirmed it through Better-Auth's own adapter. For a placeholder, nothing is linked and no password is synced. The
answer stays that of a new sign-up: its own id, no roles, not verified, and the same bcrypt round as a real sign-up,
so neither the body nor the response time tells the address exists. The legacy sign-up answers a known address with
`Email address already in use`, as it always did without IAM.

**Who was affected:** a project running better-auth 1.5.0 or later (nest-server 11.18.0 and later pin it) whose
Better-Auth options set `requireEmailVerification: true` or `autoSignIn: false`, with sign-up open
(`emailAndPassword.disableSignUp: true` refused the request before it reached Better-Auth). Without those options
Better-Auth answers a known address with an error, and the core answered `EMAIL_ALREADY_EXISTS` without writing.

**Your project:** update. If the conditions above applied, the traces an attack leaves on an account do not list every
affected one: `iamId` no longer matching the account's own id, and `verified: false` next to `emailVerified: true`, are
written back by the owner's next IAM sign-in, while the overwritten legacy password stays. Take the time the options
were active as the window and:

- **Accounts that still carry a trace:** remove the legacy `password`, end their sessions (IAM sessions and legacy
  refresh tokens) and send a password reset.
- **Every account with a Better-Auth credential account:** remove the legacy `password`. IAM sign-in does not read it,
  only the legacy endpoints do. Where `auth.legacyEndpoints` keeps those open (closed by default since 11.38.0), send
  these accounts a password reset instead.
- **Credential accounts created in the window for a user who existed before it:** a legacy user's first IAM sign-in
  creates one with the password used for that sign-in, after an attack the caller's. End those sessions and send a
  password reset.

Better-Auth logs a sign-up for a known address ("Sign-up attempt for existing email") only at `logger.level: 'info'` or
lower. Its default is `warn`, so there is usually no log trail. A project test that stubs `CoreBetterAuthService` for
the sign-up needs `isPersistedUser`.

## 2. The IAM API middleware decides on the routed path

`CoreBetterAuthApiMiddleware` leaves the routes `CoreBetterAuthController` serves to the controller and hands everything
else to Better-Auth. It now decides on the canonical path (`canonicalRequestPath()`), the one Better-Auth routes after
`new URL()` resolved `.`, `..` and `%2e` segments. Before, it decided on the raw URL. On 12.x the path guard (12.3.0)
already refuses such paths with 400 before this middleware runs. This keeps the middleware correct where the guard is
not registered, as the rate limiter already does. Nothing to do.
