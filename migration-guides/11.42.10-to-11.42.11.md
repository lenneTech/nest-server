# Migration Guide: 11.42.10 → 11.42.11

## Overview

| Category             | Details                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| **Framework API**    | No change                                                                                                |
| **Test tooling**     | e2e low-resource cap fixed for Vitest 4, e2e run governor hardened, two `check.mjs` false greens closed (§1–§3) — reaches your project only through this guide |
| **Tests**            | A race in tests that upload to a route a role guard refuses (§4)                                         |
| **Documentation**    | `lt dev` exports `NSC__MONGOOSE__URI`, never `MONGODB_URI`; two older guides corrected (§5)              |
| **Dependencies**     | `nodemailer` 10.1.0 (minor, no API change); dev tooling (§6)                                             |
| **Breaking Changes** | None                                                                                                     |
| **Migration Effort** | None for the package. Starter-derived projects older than starter 11.42.10 should port §1 and §2         |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required for the
framework itself.

**Why the rest of this guide exists:** `tests/`, `scripts/` and `vitest-e2e.config.ts` do not ship in the npm
tarball and are not part of the vendor file set. They are template files: `nest-server-starter` ships them,
and every project generated from it holds a private copy that no update channel touches. The sections below
say which starter version already carries each fix, so you can tell whether your copy needs it.

## 1. e2e low-resource mode: `maxWorkers` instead of `poolOptions` (Vitest 4)

Already in projects generated from **starter 11.42.10 or later**.

Vitest 4 removed `test.poolOptions`. The low-resource mode in `vitest-e2e.config.ts` still set
`poolOptions.forks.maxForks`, so the worker cap was announced on stderr and then discarded — measured: a run
logging `maxForks=2` used 8 workers on a 12-core machine, the same run with `maxWorkers` used 2. Low-resource
mode only raised the timeouts, and overlapping e2e runs (several sessions, `lt dev test` next to `check`) kept
starving each other into spurious 401s and timeouts.

```typescript
// Before
...(LOW_RESOURCE ? { poolOptions: { forks: { maxForks: LOW_RESOURCE_FORKS, minForks: 1 } } } : {}),

// After
maxWorkers: LOW_RESOURCE ? LOW_RESOURCE_FORKS : undefined,
```

`undefined` leaves Vitest's default in place for a normal run. `minWorkers` does not exist in Vitest 4 — drop
`minForks` rather than translating it. Also rename the option in the stderr announcement, so the one line that
reports the cap names an option that exists.

A type check does not catch this: under `module: commonjs`, Vitest's config type collapses to `any`, so a
removed option compiles cleanly. The starter pins it with `tests/unit/vitest-e2e-config.spec.ts`.

**Not for your project: the framework's GitHub-runner exception.** nest-server additionally skips the cap when
the load signal is the only trigger and `RUNNER_ENVIRONMENT === 'github-hosted'`: a GitHub-hosted runner runs
one job per VM, so the load it sees is the job's own unit step, and the cap measurably slowed every build
(133 s → 198 s mean e2e time). A shared GitLab runner sets `CI` but not `RUNNER_ENVIRONMENT`, and there the
load is real contention — keep the cap.

## 2. e2e run governor (`tests/e2e-run-slots.ts`) hardened

Already in projects generated from **starter 11.42.10 or later**.

The slot directory under `os.tmpdir()` is shared by every lt project on the machine. Three fixes, each pinned
by a test in `tests/unit/e2e-run-slots.spec.ts`:

| Defect | Fix |
| ------ | --- |
| A slot whose PID was recycled by an unrelated long-lived process counted as an active run forever | Reclaim a slot older than six hours even when its PID answers |
| On a multi-user Linux host (`/tmp` world-writable) a planted `<pid>.slot` symlink made the write follow it | Create the directory `0o700`, unlink the own path first, write with `flag: 'wx', mode: 0o600` |
| An unwritable slot directory threw out of `acquireRunSlot()` and aborted the suite, despite the documented fail-open | Catch the claim; the run proceeds ungoverned |

The easiest port is to copy `tests/e2e-run-slots.ts` and its spec from the current starter; the file has no
project-specific content.

## 3. `scripts/check.mjs`: two false greens

Already in projects generated from **starter 11.40.0 or later**. nest-server's own copy caught up in this
release.

- **The "Vulnerabilities" summary line tested `audit.counts` before `audit.degraded`.** A silent audit outage
  (exit 0, all-zero JSON, advisory service unreachable) keeps `counts` set, so the summary printed
  `critical 0 · high 0 · …` for a run that never reached the service. Test `degraded` first.
- **The CLI guard compared `resolve(process.argv[1])` with the module's own path.** Node resolves the main
  module's symlinks for `import.meta.url` but keeps `argv[1]` as typed, so a start through a symlink — on macOS
  any absolute path under `/tmp` — skipped the pipeline and exited 0. Compare both sides through
  `realpathSync`, and exit 1 when the entry cannot be resolved.

## 4. Tests that upload to a refused route: send no file

Already in projects generated from **starter 11.41.9 or later** (for the avatar upload test).

When a role guard refuses a multipart upload route, it answers before the file interceptor reads the body. A
test that still attaches a file races that answer: the 401/403 arrives while the client is writing the
multipart body, and the write fails with `EPIPE` (observed 1 run in 14 in this repository with retries off).
The file cannot change the guard's answer, so send none — an open route then answers 400 for the missing file,
so the test still fails if the guard is gone:

```typescript
// Before
await testHelper.rest('/files/upload', { attachments: { file: local }, statusCode: 401 });

// After
await testHelper.rest('/files/upload', { method: 'POST', statusCode: 401 });
```

Search your `tests/` for `attachments:` next to `statusCode: 401` or `403`.

## 5. Documentation corrections: `NSC__MONGOOSE__URI`, not `MONGODB_URI`

`lt dev` exports `NSC__MONGOOSE__URI` (and `DATABASE_URL`); it has never set `MONGODB_URI`. The guides
[11.36.3 → 11.36.4](./11.36.3-to-11.36.4.md) and [11.27.2 → 11.27.3](./11.27.2-to-11.27.3.md) named
`MONGODB_URI` where a starter-derived project's `tests/global-setup.ts` reads `NSC__MONGOOSE__URI`. Both are
corrected. The steps in them were right for your project — only the variable name was wrong, so nothing needs
redoing unless you adapted a script to the wrong name.

## 6. Dependency updates

- **`nodemailer` 10.0.16 → 10.1.0** — minor release: hardened message streams, SMTP connection and pool
  handling, SMTP and encoding fixes. No API change; the framework's real-SMTP round-trip test passes. A project
  that carries a lock-step `nodemailer` override (nest-server-starter does) should raise it:

  ```yaml
  # Before
  overrides:
    'nodemailer@<10.0.16': '10.0.16'

  # After
  overrides:
    'nodemailer@<10.1.0': '10.1.0'
  ```

- **Development tooling only:** `@aws-sdk/*` 3.1149.0, `bullmq` 6.3.12, `smtp-server` 3.19.19, `vite` 8.3.4,
  `@types/node` 26.6.5, `@types/lodash` 4.17.26. If your project pins `@types/node` exactly, raise it to 26.6.5
  so a fresh install does not keep two copies.

Unchanged on purpose: `express` stays 5.2.1, because `@nestjs/platform-express` 11.2.7 pins it exactly — a
direct bump would put two copies of express into your tree. `better-auth` stays on 1.7.7, the current release.

## Troubleshooting

**`[e2e] low-resource mode: … -> maxForks=…` in your log**
Your copy still sets `poolOptions` — the cap is not applied. Port §1.

**`[e2e-governor] could not claim a slot (…) — proceeding without the governor.`**
The slot directory is not writable (owned by another user, read-only tmpdir). The run continues, ungoverned.
Point `LT_E2E_SLOT_DIR` at a writable directory to get the governor back.
