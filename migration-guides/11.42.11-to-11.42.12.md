# Migration Guide: 11.42.11 → 11.42.12

## Overview

| Category             | Details                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| **Security**         | Password-reset and verification links are no longer printed on deployed `develop` / `test` stages (§1); auth cookies carry `Secure` on every https deployment, whatever the environment is called (§2) |
| **Framework API**    | Additive only: `isLocalEnv()`, `CoreBetterAuthService.usesSecureCookies()`, optional `secureTransport` / `baseUrl` arguments on the cookie helpers |
| **Dependencies**     | None for the package. The repository's own audit suppression for GHSA-ch52-4w7c-c8xp is gone (§3)        |
| **Breaking Changes** | None                                                                                                     |
| **Migration Effort** | None for most projects. Check §1 if you read auth links from a log outside `local` / `ci` / `e2e`, and §2 if you override a cookie-writing method |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required unless one
of the checks in §1 or §2 applies to you.

## 1. Auth links are printed only in local environments

`CoreBetterAuthEmailVerificationService.logAuthUrlForDevelopment()` prints the verification and password-reset
link to stdout so a developer can follow it without a mail server. The URL carries a live bearer token — a reset
link changes the password outright.

Until this release the link was printed everywhere except `production` and `staging`. The deployed `develop` and
`test` stages of a starter-based project are neither, so they wrote live reset links into their log pipeline,
where read access to the logs was enough to take over an account.

| Environment (`env`, else `NODE_ENV`) | Before | After |
| ------------------------------------ | ------ | ----- |
| `local`, `ci`, `e2e`                 | printed | printed |
| `develop`, `test`, `development`, any other name, none at all | printed | **not printed** |
| `production`, `staging`, `NODE_ENV=production` | not printed | not printed |

`LT_LOG_AUTH_URLS` gained a value:

| Value | Effect |
| ----- | ------ |
| unset | the table above |
| `1`   | also print in an environment that is not in the list — for a developer machine with a different environment name |
| `0`   | print nowhere, not even locally |

`production` and `staging` never print, whatever the variable says.

**What to check:**

- **Your local environment has another name** (e.g. `development`): set `LT_LOG_AUTH_URLS=1` in your local
  `.env`. Never set it on a deployment.
- **A script or CI job reads `[EMAIL VERIFICATION]` / `[PASSWORD RESET]` from the API log** — fine as long as it
  runs the API as `local`, `ci` or `e2e` (`lt dev up`, `lt dev test` and the starter's e2e scripts do). Against a
  deployed stage, read the mail instead (Hub mailbox, Mailpit), which is what that stage should have been doing.

The decision uses the new exported helper `isLocalEnv(env)`, which reads the existing `LOCALHOST_URL_ENVS`
(`local`, `ci`, `e2e`). The SSRF guard's private-target allowance (`privateOutboundTargetsAllowed()`) now reads
the same helper; its behaviour is unchanged.

## 2. Auth cookies carry `Secure` on every https deployment

The session cookie is written by two paths: Better-Auth's own handlers (2FA, social callback, passkey) and the
framework's cookie helper (sign-in and sign-up through `CoreBetterAuthController`, the API middleware, and the
legacy `token` / `refreshToken` cookies). Better-Auth sets `Secure` from an `https://` base URL. The framework
helper set it only for `production` / `staging` — so on an https `develop` or `test` stage the cookie that
establishes the session went out without `Secure`, while Better-Auth's handlers set it on the same deployment.

Now:

| Cookie | `Secure` when |
| ------ | ------------- |
| Better-Auth session cookie written by the framework | Better-Auth's own cookies are secure (read off the instance: `CoreBetterAuthService.usesSecureCookies()`), or the environment is production-like |
| Legacy `token` / `refreshToken` | `baseUrl` starts with `https://`, or the environment is production-like |

`Secure` is only ever added, never removed. A project that switched it off on purpose
(`betterAuth.options.advanced.defaultCookieAttributes.secure: false`) keeps that outside production and staging.

**What to check:**

- **A deployment whose `baseUrl` says `https://` but whose browsers reach the API over plain http** now loses the
  framework-written session cookie too — browsers drop a `Secure` cookie received over http. Better-Auth's own
  handlers already behaved this way, so such a deployment had broken 2FA and social sign-in before. Fix the
  `baseUrl` or serve https.
- **You override a cookie-writing method.** The new inputs reach the helpers only if the caller passes them:

  ```typescript
  // A CoreAuthController / CoreAuthResolver subclass that overrides processCookies()
  const baseUrl = this.configService.getFastButReadOnly<string>('baseUrl');
  return setLegacyAuthCookies(res, result, cookiesConfig, env, baseUrl);

  // Code that builds its own Better-Auth cookie helper
  createCookieHelper(basePath, { ...options, secureTransport: this.betterAuthService.usesSecureCookies() });
  ```

  Without the argument the helper keeps the previous, environment-only rule — nothing breaks, the fix just does
  not reach that path.
- **Your tests stub `CoreBetterAuthService`**: no change needed. The controller calls `usesSecureCookies()`
  optionally, so a stub without it keeps the previous behaviour.

## 3. Audit suppression GHSA-ch52-4w7c-c8xp removed (repository only)

This repository no longer lists GHSA-ch52-4w7c-c8xp (`http-cache-semantics <= 4.2.0`, dev tooling only:
`@swc/cli` > … > `cacheable-request`) in `auditConfig.ignoreGhsas`. Its lockfile now resolves 4.3.0, which
`cacheable-request`'s `^4.2.0` takes on any fresh resolve. Nothing here reaches the published package.

4.3.0 is **not a fix**: its max-stale code is identical to 4.2.0's. It only lies outside the advisory's declared
range, because the advisory was written as "up to the newest release" and never followed. The maintainer disputes
the report (kornelski/http-cache-semantics#56); a withdrawal request is open (github/advisory-database#10139),
and an independent re-test there reproduces the behaviour through 4.3.0, so a range extension is possible.

**For starter-derived projects** that carry the same entry (nest-server-starter 11.41.7 – 11.42.11):

- Lockfile on 4.3.0 (`pnpm why http-cache-semantics`): remove the entry from `ignoreGhsas` together with its row in
  `tests/unit/audit-suppression-scope.spec.ts`. On 4.3.0 the entry hides nothing and would swallow the advisory
  unseen the day its range is extended; without it, that day turns `pnpm audit` red, which is the moment to
  re-argue the dev-only case.
- Lockfile still on 4.2.0: `pnpm update http-cache-semantics` first, then as above. Keep the entry instead if
  your resolve cannot move.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| npm-mode and vendor-mode projects without cookie-related overrides | Nothing to do |
| `lt dev up` / `lt dev test` / starter e2e scripts reading auth links from the log | Unchanged — they run as `local` / `e2e` |
| Subclass overriding `processCookies()` (legacy) | Pass `baseUrl` (§2), otherwise unchanged behaviour |
| Custom `createCookieHelper()` call | Pass `secureTransport` (§2), otherwise unchanged behaviour |
| Test stubs of `CoreBetterAuthService` | Compatible |

## Troubleshooting

**The `[PASSWORD RESET]` / `[EMAIL VERIFICATION]` line disappeared from your local log**
Your environment is not named `local`, `ci` or `e2e`. Set `LT_LOG_AUTH_URLS=1` locally (§1).

**After the update, sign-in succeeds but the next request is anonymous on a non-production stage**
The browser dropped the now-`Secure` session cookie because the page or API is served over http while `baseUrl`
says https. Serve https or correct `baseUrl` (§2).
