# Migration Guide: 11.41.8 → 11.41.9

## Overview

| Category              | Details                                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **New Features**      | A custom TUS service via `TusModule.forRoot({ service })`, and an overridable `onUploadCreate()` (§1)                                                                    |
| **Behaviour Changes** | Only with `multiTenancy` configured: TUS uploads record the validated tenant, and a tenant header naming a tenant the caller does not belong to is refused with 403 (§2) |
| **Breaking Changes**  | None for projects without `multiTenancy`                                                                                                                                 |
| **Migration Effort**  | None — `pnpm update`. Projects that want upload rules (quota, validation) adopt §1                                                                                       |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm run build && pnpm test
```

Vendor-mode projects pick up the core update; nothing else to change.

## What's New in 11.41.9

### 1. A custom TUS service, and a hook before the first byte

Until now `TusModule` constructed `CoreTusService` directly in both of its provider factories, so a
project could not plug in a subclass at all — and `onUploadCreate` sat inline inside a private method,
so even a subclass could not have changed it. Both are open now:

```typescript
import { CoreTusService } from '@lenne.tech/nest-server';
import { Upload } from '@tus/server';

export class TusService extends CoreTusService {
  protected override async onUploadCreate(req: any, upload: Upload) {
    const quota = this.options?.moduleRef?.get(QuotaService, { strict: false });
    if (!(await quota?.hasRoomFor(req, upload.size))) {
      const error = new Error('Storage quota exceeded');
      (error as any).status_code = 413;
      throw error;
    }
    return super.onUploadCreate(req, upload);
  }
}

// server.module.ts
TusModule.forRoot({ controller: TusController, service: TusService });
```

`onUploadCreate(req, upload)` runs once per upload, after the client declared `Upload-Length` and
before anything is stored — the one point at which a quota can refuse an upload without the store
having grown first.

Three rules, all in the TUS [INTEGRATION-CHECKLIST](../src/core/modules/tus/INTEGRATION-CHECKLIST.md)
Step 2:

- **Keep the constructor signature `(connection, options?)`.** The module constructs the service
  itself, with exactly those arguments. Project providers are reached at call time through
  `this.options?.moduleRef`, which the module now passes in.
- **Return `super.onUploadCreate()`.** It records the owner and the tenant and enforces
  `allowedTypes`; skipping it produces owner-less uploads and accepts every file type.
- **Throw an `Error` with `status_code`** to refuse — that is how `@tus/server` turns it into a
  response.

### 2. With multi-tenancy: TUS uploads carry their tenant

**Projects without `multiTenancy` see no change** — no header is read, no field is written.

With `multiTenancy` configured (and not `enabled: false`), TUS uploads used to carry no tenant at
all: the routes carry `@SkipTenantCheck()`, the file stores sit outside Mongoose, and so every
TUS-uploaded file bypassed tenant filtering and any per-tenant storage accounting. Now an upload that
sends the tenant header is validated against the caller's active memberships — the same check
GraphQL subscriptions use — and the finished file gets `metadata.tenantId`:

| Request                                              | 11.41.8               | 11.41.9                 |
| ---------------------------------------------------- | --------------------- | ----------------------- |
| No tenant header                                     | tenant-less           | tenant-less (unchanged) |
| Header naming a tenant the caller belongs to         | tenant-less           | `metadata.tenantId` set |
| Header naming a tenant the caller does NOT belong to | accepted, tenant-less | **403**, nothing stored |

**Send the header from the TUS client.** A tenant header added by an interceptor of the project's
generated API client does not reach `tus-js-client`. Without it the upload silently stays tenant-less,
outside tenant filtering and per-tenant quotas. Pass it explicitly, e.g.
`useLtTusUpload({ headers: { 'X-Tenant-Id': currentTenantId } })`.

The tenant is recorded under the framework-owned metadata key `TUS_TENANT_METADATA_KEY`
(`ltTenantId`), next to the owner key. Like the owner key it is always overwritten, so a client
cannot put a tenant into its own `Upload-Metadata`.

**What this changes downstream:** the file module's `'tenant'` access preset and any
`checkRights()` rule reading `metadata.tenantId` now see the tenant on TUS-uploaded files. Under the
`'tenant'` preset such files used to be refused for every non-admin (no tenant on the file); new
uploads are now readable within their tenant. Files uploaded before 11.41.9 keep no tenant.

## Compatibility Notes

| Pattern                                                               | Status                                                            |
| --------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `TusModule.forRoot()` / `forRoot({ controller })`                     | Unchanged                                                         |
| Project without `multiTenancy`                                        | Unchanged — nothing read, nothing written (§2)                    |
| Multi-tenant client sending a tenant header it is a member of         | Works; files now carry `tenantId` (§2)                            |
| Multi-tenant client sending a header for a foreign tenant             | Now 403 (§2)                                                      |
| Own `TusModule` replacement that provides a `CoreTusService` subclass | Keeps working; `forRoot({ service })` is now the simpler way (§1) |

## Troubleshooting

| Symptom                                              | Cause                                                                  | Fix                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------- |
| TUS `POST` answers 403 after the update              | The tenant header names a tenant the caller is not an active member of | Send the caller's own tenant, or no header (§2)   |
| An `onUploadCreate` override never runs              | The subclass is not registered                                         | `TusModule.forRoot({ service: TusService })` (§1) |
| Dependencies are `undefined` in the service subclass | Declared as constructor parameters                                     | Resolve via `this.options?.moduleRef` (§1)        |
| Uploads have no `ownerId` after adding an override   | `onUploadCreate` override does not call `super`                        | `return super.onUploadCreate(req, upload)` (§1)   |
