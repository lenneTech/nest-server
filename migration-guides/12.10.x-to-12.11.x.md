# Migration Guide: 12.10.x → 12.11.x

> **This minor contains breaking changes** (see "Breaking Changes"): a Better-Auth JWT is bound to its session and
> stops working when the session ends; Passkey and two-factor are off in projects without e-mail and password sign-in;
> a client-submitted id token no longer signs in; `NSC__` environment values are read differently; unnamed list enums
> no longer share an OpenAPI schema `Array`. The MAJOR digit follows NestJS, so a breaking change ships as a minor here
> — read this guide before updating.

## Overview

| Category | Details |
|----------|---------|
| **Breaking Changes** | (1) A Better-Auth JWT is refused once the session it was issued from is signed out, revoked, expired or its user deleted; a JWT issued before 12.11.0 is refused once (§1). (2) With `emailAndPassword.enabled: false` and no plugin sign-in route of the project's own (sign-in through a provider alone), Passkey and two-factor are off unless switched on explicitly (§2). (3) `POST /iam/sign-in/social` and `/iam/link-social` with a client-submitted `idToken` answer `ID_TOKEN_NOT_SUPPORTED` unless the provider sets `disableIdTokenSignIn: false` (§3). (4) `NSC__` values: empty = not set, `true` / `false` in any case, `enabled` keys take only `true` / `false` / `1` / `0` (§4). (5) A plain list given as `@UnifiedField({ enum: [...] })` without `enumName` stays inline in the OpenAPI document instead of becoming a schema `Array` (§5) |
| **Security fixes** | §1 to §3: nothing the framework offers keeps someone signed in after a sign-out or after a sign-in provider withdrew the assignment — the JWT outlived a sign-out by up to 15 minutes, a passkey registered once kept working after the withdrawal, and an id token kept from an earlier sign-in signed its owner in again for about an hour. A JWT client's `POST /iam/sign-out` ended no session at all. §4: an off switch written as empty, `0`, `FALSE` or `off` left the feature on |
| **New Features** | `betterAuth.session` (fixed session lifetime, §6); `emailAndPassword` in `GET /iam/features` and `betterAuthFeatures` (§2); `CoreCronJobs.rescheduleCronJob()`, SSE streams re-checked in place (`registerHttpStream()`, the sync hints stream), a readiness endpoint `GET /health-check/ready` and `CoreHealthCheckService.additionalHealthIndicators()` (§7) |
| **Bugfixes** | `POST /iam/sign-out` with a JWT ends the JWT's session; Better-Auth's plugin routes act on the JWT's own session instead of the user's newest one (§1). `CronJobConfig.utcOffset` is typed as a number (minutes), as cron expects it — it was typed as a boolean by mistake |
| **Dependencies** | NestJS 12.6.0 and patch updates; keep `@apollo/server` at 5.5.1 (§8) |
| **Migration Effort** | ~10 minutes: check JWT clients (§1), SSO-only projects (§2), native apps with id token sign-in and the starter's Microsoft example test (§3), deployment variables (§4) and generated API clients (§5) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.11.x
pnpm run update   # only if you use the starter's update script
pnpm run build
pnpm test
```

No new dependency is required.

## 1. Breaking (security): a Better-Auth JWT is bound to its session

Up to 12.10.x the API accepted a Better-Auth JWT on its signature and expiry alone. Measured in a project: after
`POST /iam/sign-out` the session cookie answered 401 at once, while the JWT kept reading and writing for 14 min 57 s of
its 15 — and so did any copy of it. A session revoked by an administrator, an expired session and a deleted user were
no different. Two more defects sat on the same path: a JWT client's `POST /iam/sign-out` read the session from the
cookie alone, found none, ended nothing and answered `{ success: true }`; and the middleware handed Better-Auth's
plugin routes the user's NEWEST session for a JWT request, so a sign-out on one device ended another one.

Since 12.11.0:

- The JWT carries the id of the session it was issued from (claim `sid`), next to Better-Auth's default payload.
- The API accepts it only while that session exists, belongs to the token's subject and has not expired. The answer is
  cached for 10 seconds; when Better-Auth deletes the session (sign-out, revoke, password reset with
  `revokeSessionsOnPasswordReset`, user deletion) it is forgotten at once — with `redis` on every replica, without it on
  this one and on the others within 10 seconds. A session removed directly in the database is caught by the interval.
- `POST /iam/sign-out` with a JWT ends the JWT's own session, and plugin routes (2FA, passkey, …) act on it.

**What changes for clients:**

| Situation | Since 12.11.0 | What to do |
|---|---|---|
| A JWT issued before the update | `401` on its next request | With a session cookie (the default `cookies: true`): nothing for `@lenne.tech/nuxt-extensions` / `@lenne.tech/ng-base`, they fetch a new JWT with the session on the 401; other clients fetch `GET /iam/token` with the session again. **With `cookies: false` the client holds the JWT alone and cannot renew it: every user signs in once more after the update** |
| Sign-out, revoked session, deleted user | The session's JWTs answer `401` at once | — |
| Enabling 2FA (the first `verify-totp`) | Better-Auth replaces the session; the old JWT answers `401`. The answer's `token` is the JWT of the new session | A JWT client continues with that `token` (or fetches a new one on the 401) |
| Disabling 2FA (`POST /iam/two-factor/disable`); enabling it with `method: 'otp'` or `skipVerificationOnEnable` | Better-Auth replaces the session; the old JWT answers `401`. **Since 12.11.1** the answer carries `token`, the JWT of the new session (`{ status: true, token }`, `{ method: 'otp', token }`). 12.11.0 answered without it, so with `cookies: false` turning 2FA off signed the user out | Update to 12.11.1; a JWT client continues with that `token`, like after `verify-totp` |
| Several devices | Each JWT follows its own session; signing out one leaves the others signed in | — |

A JWT is still verified without a call to the identity provider, and the session check costs at most one lookup per
session and 10 seconds per replica. Before 12.11.0 the middleware looked up the user's newest session on every JWT
request; that lookup is gone.

**A project that verifies Better-Auth JWTs itself** (`jwtVerify()` against the JWKS) checks the signature only — call
`CoreBetterAuthService.verifyJwtToken()` instead, which checks the session.

## 2. Breaking (security): Passkey and two-factor follow e-mail and password sign-in

**Who is affected:** projects that sign in through a single sign-on provider alone —
`betterAuth.emailAndPassword.enabled: false` and no plugin of the project with a sign-in route of its own. A project
that signs in by username or phone number (`username()`, `phoneNumber()` in `betterAuth.plugins`) keeps both on, since
two-factor is what enforces the second factor on those routes. Every other project keeps both on, as before.

Passkey and two-factor were on whatever `emailAndPassword` said. Whoever signed in through Microsoft once and registered
a passkey kept signing in with it after Entra withdrew the assignment: the provider no longer decided who gets in.

Since 12.11.0 both are off while sign-in runs through a provider alone. Their routes answer `404`, also for a passkey
registered earlier, and `GET /iam/features` reports `passkey: false` / `twoFactor: false`. The boot names what it
switched off — as a warning when the factor carried settings of its own (`twoFactor: { appName }`). To keep one
deliberately:

```typescript
betterAuth: {
  emailAndPassword: { enabled: false },
  passkey: true,                               // or { enabled: true, rpName: '…' }
  twoFactor: { appName: 'My App', enabled: true },
}
```

An object without `enabled: true` (a `twoFactor: { appName }` kept from a password setup) does not switch it on.

`GET /iam/features` (and the GraphQL `betterAuthFeatures`) report `emailAndPassword` since 12.11.0, so a login page
can hide the e-mail form instead of subclassing the controller for it.

## 3. Breaking (security): no sign-in with a client-submitted id token

`POST /iam/sign-in/social` accepts `{ provider, idToken: { token } }`: the client submits the provider's id token, and
Better-Auth checks its signature, audience and expiry — and asks the provider nothing. `GET /iam/list-accounts` and
`POST /iam/get-access-token` hand a signed-in user the id token of their last sign-in, so within its lifetime (about an
hour at Microsoft) that token signed its owner in again after Entra had withdrawn the app role or the assignment. Proven
end to end against a mock of the Entra endpoints.

Since 12.11.0 every social provider gets `disableIdTokenSignIn: true` unless the project sets it to `false`. Such a
request answers `ID_TOKEN_NOT_SUPPORTED`, on `/iam/link-social` too. The redirect flow (`signIn.social` with a
`callbackURL`, what the lenne.Tech frontends use) never uses this path and keeps working.

**Native apps and Google One Tap** send the provider's id token themselves. Open it for that provider:

```typescript
betterAuth: {
  socialProviders: {
    google: { clientId, clientSecret, disableIdTokenSignIn: false },
  },
},
```

Only the boolean `false` opens it; any other value keeps it closed. nest-server-starter's Microsoft example sets
`disableIdTokenSignIn: true` since 12.10.1 — that line can stay, it states the default now.

**Projects created from nest-server-starter 12.10.1 or later** carry `tests/unit/microsoft-sign-in-example.spec.ts`.
Its third case removes the option and expects the id token to be verified, so after the update it fails with
`expected 'ID_TOKEN_NOT_SUPPORTED' not to be 'ID_TOKEN_NOT_SUPPORTED'`. Open the path explicitly there, as the starter
does:

```typescript
it('would verify a submitted ID token with the option set to false, so the option is what closes the path', async () => {
  const code = await idTokenSignInCode({ ...EXAMPLE, disableIdTokenSignIn: false });
  expect(code).toBeDefined();
  expect(code).not.toBe('ID_TOKEN_NOT_SUPPORTED');
});
```

## 4. Breaking: `NSC__` environment values

Deployments set the configuration through `NSC__…` variables. Two ways of writing an off switch left the feature on:

| Variable | Up to 12.10.x | Since 12.11.0 |
|---|---|---|
| `NSC__X__ENABLED=` (empty, or spaces) | `0` — `enabled !== false` reads it as **on** | not set: the default applies, and no object is created along the path (`NSC__REDIS__HOST=` no longer creates `redis: {}`, which switches Redis on) |
| `NSC__X__ENABLED=FALSE`, `=False`, `= false ` | the text `"FALSE"` — **on** | `false` |
| `NSC__X__ENABLED=0` / `=1` | `0` / `1` — both **on** | `false` / `true` |
| `NSC__X__ENABLED=off`, `=no`, `=yes` | text — **on** | **the start stops**: `NSC__X__ENABLED="off" is not a switch value: write true or false (1 or 0 work too)` |
| `NSC__X__ROLE=` | `"0"` | not set |
| any other key: `TRUE`, `True` | text | `true` |
| numbers, other text | unchanged | unchanged |

**Check before updating:** `env | grep '^NSC__'` on each stage. Empty variables now leave the default in place instead
of `0`; a key named `ENABLED` with any value but `true`, `false`, `1` or `0` must be corrected, or the service does not
start. A text value that must stay exactly `TRUE` or `False` (a password, say) is now a boolean — pass it through
`NEST_SERVER_CONFIG` or `config.env.ts` instead (exactly `true` / `false` were converted before as well).

## 5. Breaking: unnamed list enums in the OpenAPI document

`@UnifiedField({ enum: ['red', 'green'] })` without `enumName` named its OpenAPI schema after the list's constructor:
`Array`. Every such field of a project shared that one schema, and a client generated from the document declared
`export type Array = …`, shadowing the built-in type (36 type errors in one project).

Since 12.11.0 such an enum stays inline (`{ "enum": ["red", "green"] }`), as an unregistered TypeScript enum does, and
no schema is named after a built-in type. **Regenerate API clients** (e.g. `pnpm run generate-types` in an app): a
type `Array` disappears, fields that used it carry their own values. To keep a named schema, set `enumName` on the
field or register the enum with `registerEnum()`.

## 6. New: a fixed session lifetime (`betterAuth.session`)

Better-Auth's sessions last 7 days and are extended once a day while they are used — a session used every day never
ends, and a withdrawal at the sign-in provider never reaches it. A project that wants the provider to be asked again
after a fixed time:

```typescript
betterAuth: {
  session: { expiresInHours: 8, extendOnUse: false }, // sign in again after 8 hours, every time
},
```

| Option | Maps to | Default |
|---|---|---|
| `expiresInHours` | Better-Auth's `session.expiresIn` (seconds) | 168 (7 days) |
| `extendOnUse: false` | `session.disableSessionRefresh: true` | extended once a day of use |

A value of `expiresInHours` that is not a positive number is ignored with a warning (never "unlimited").
`betterAuth.options.session` still wins key by key.

## 7. New: cron schedules at runtime, SSE streams re-checked in place, health readiness

### `CoreCronJobs.rescheduleCronJob(name, schedule)`

Changes the schedule of a registered job without touching protected internals: a cron expression, a date,
`{ cronTime, timeZone }` or `{ cronTime, utcOffset }` (type `CronJobSchedule`). Only the schedule changes —
`distributed`, `runParallel`, the leases and `bullJobOptions` stay; `runOnInit` is not repeated. An invalid expression,
an unknown time zone, a date in the past or an unregistered job rejects and leaves the job as it was.

- **BullMQ** (with `redis`): the scheduler in Redis changes for the whole fleet; calling it on every replica is safe.
- **Local timer**: changes on the calling replica only — call it on every replica (from the settings change each one
  observes, and at startup).
- A reschedule is not stored: the next bootstrap schedules from the configuration again, so a project re-applies a
  stored schedule after `super.onApplicationBootstrap()`.

### SSE streams keep running while the rights are unchanged

A Server-Sent Events stream registered for re-checks (`endsOnRecheck`) ENDED on the first event after
`graphQl.subscriptionRevalidationMs`, and the client received that event only after reconnecting (about 3 s later). The
sync hints stream (`GET /sync/hints`) behaved that way. Since 12.11.0 a stream whose credential is a Better-Auth session
or JWT is re-checked in place, like a WebSocket: the request's bearer token, `lt-jwt-token` cookie or session cookie is
authenticated again, and the stream ends only when user, roles, verification or tenant scope changed (log lines
"User authorization changed", "Session no longer valid", "Tenant access changed"). Streams on legacy JWTs or API tokens
keep ending on every re-check, as before.

A project with its own SSE stream registers it with `registerHttpStream({ … })` (`http-stream-auth.helper.ts`) to get
the same behaviour; `CoreSyncService.recheckHintStreamInPlace()` is the protected override point of the hints stream.

### Health check: readiness endpoint and project checks

```typescript
healthCheck: {
  configs: { database: { enabled: true }, build: { enabled: true } },
  readiness: true, // GET /health-check/ready — or { checks: ['database'] }
},
```

- `GET /health-check/ready` runs the checks named in `readiness.checks` (default `['database', 'build']`, a list or a
  comma-separated string) and answers `503` while one is down — and `shutting_down` from the first SIGTERM / SIGINT on
  when `installGracefulShutdown(app)` handles the signals with a `shutdownDelayMs`, before that wait, so a load balancer
  polling readiness drains the replica while it still serves. Without
  `readiness` the route does not exist (404), and `GET /health-check` is unchanged. A project with a shutdown flow of
  its own (a preStop hook, its own signal handler) calls the exported `markShutdownDraining()` at its start.
- A project adds checks of its own by extending `CoreHealthCheckService` and overriding the protected
  `additionalHealthIndicators(kind: 'liveness' | 'readiness')`, registered with
  `CoreModule.forRoot(env, { healthCheck: { service } })` (`readinessController` overrides the readiness controller).

## 8. Dependencies

12.11.0 declares NestJS 12.6.0. `pnpm run update` raises these pins where a nest-server-starter based project already
declares them:

| Package | From | To |
|---|---|---|
| `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express`, `@nestjs/testing` | 12.5.1 | 12.6.0 |
| `@nestjs/cli` / `@nestjs/schematics` | 12.0.13 | 12.0.15 / 12.0.16 |
| `jose` | 6.2.17 | 6.2.18 |
| `nodemailer` | 10.6.0 | 10.6.1 |
| `mongoose` (MongoDB projects) | 9.12.2 | 9.12.3 |

Where declared, also the optional peers `bullmq` 6.7.8, `@aws-sdk/*` 3.1175.0 and `ai` 7.0.179. With NestJS 12.6.0 a
testing module's `createNestApplication()` applies its `logger` option like `NestFactory.create()` does, so an e2e
setup that passes `logger: true` (or a log level list) now logs. An override of a core handler declared with
`@Res({ passthrough: true })` (the IAM `signIn` / `signUp` / `signOut`, the sync routes) no longer inherits
`passthrough` when it re-declares a plain `@Res()`: its return value is no longer sent and the request hangs —
re-declare `@Res({ passthrough: true })`, as `INTEGRATION-CHECKLIST.md` shows.

**Keep `@apollo/server` at 5.5.1.** 5.5.2 caps `@graphql-tools/utils` below 12.0.2 (for Node 20) and brings back
GHSA-c4qx-w738-7hr3 (high); this package requires Node 22.15 or later and stays on 5.5.1.

**Refresh two transitive packages** of `@modelcontextprotocol/sdk` if your lockfile still holds older ones:
`@hono/node-server` 2.1.11 (GHSA-8wcc-wqxr-28qp, GHSA-qhm2-7mpr-ghjp) and `express-rate-limit` 8.7.5
(GHSA-cppf-2hm6-mrvm). Both sit inside the SDK's ranges; `pnpm update @hono/node-server express-rate-limit --depth
Infinity` lifts them. The advisories were published in the projects' own repositories, so `pnpm audit` may not report
them yet.

A project that mirrors this package's `minimatch@>=11.0.0 <11.0.9` override can drop it with `@nestjs/cli` 12.0.15,
which pins 11.0.9 itself.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Frontends on `@lenne.tech/nuxt-extensions` / `@lenne.tech/ng-base` in cookie mode | Unaffected |
| The same frontends in JWT mode | One extra token fetch after the update and after enabling 2FA (handled on the 401); with `cookies: false` one sign-in after the update |
| A backend-to-backend client holding a JWT | Fetch `GET /iam/token` again on a 401; a JWT dies with its session |
| A project with `emailAndPassword.enabled: false` that uses Passkey / 2FA and signs in through a provider alone | Set `passkey: true` / `twoFactor: { …, enabled: true }` (§2); with `username()` / `phoneNumber()` nothing changes |
| A native app / Google One Tap sign-in | Set `disableIdTokenSignIn: false` on that provider (§3) |
| A project verifying Better-Auth JWTs with its own `jwtVerify()` | Use `CoreBetterAuthService.verifyJwtToken()` (§1) |
| A maintenance line (12.6.x, 11.x) | Not backported (behavior changes). The switches a project sets itself: `passkey: false` / `twoFactor: false` for SSO-only, `disableIdTokenSignIn: true` per provider, `jwt: false` (cookie mode) or a shorter `jwt.expiresIn` |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Every JWT answers 401 right after the update | JWTs issued before 12.11.0 carry no session reference (§1) | Fetch a new one with the session (`GET /iam/token`); the frontend libraries do it on the 401. With `cookies: false` users sign in once more |
| 401 right after enabling 2FA in JWT mode | The first `verify-totp` replaced the session (§1) | Use the `token` of the `verify-totp` answer |
| Signed out right after turning 2FA off in JWT mode (`cookies: false`) | `two-factor/disable` replaced the session, and 12.11.0 answered without the new JWT (§1) | Update to 12.11.1 and use the `token` of the answer |
| Passkey or 2FA routes answer 404 | Sign-in through a provider alone: `emailAndPassword.enabled: false`, no plugin sign-in route (§2) | `passkey: true` / `twoFactor: { enabled: true }` |
| `ID_TOKEN_NOT_SUPPORTED` from a native app | Id token sign-in closed by default (§3) | `disableIdTokenSignIn: false` on that provider |
| `microsoft-sign-in-example.spec.ts` fails: `expected 'ID_TOKEN_NOT_SUPPORTED' not to be 'ID_TOKEN_NOT_SUPPORTED'` | The starter's test removes the option and expected an open path (§3) | Set `disableIdTokenSignIn: false` in that case instead of removing it |
| The start stops with `NSC__…ENABLED="…" is not a switch value` | An `enabled` variable holds neither `true`/`false` nor `1`/`0` (§4) | Write `true` or `false` |
| A feature configured as `NSC__…=` now uses its default instead of `0` | Empty values count as not set (§4) | Write the value you mean (`0`) |
| A generated client lost its type `Array` | Unnamed list enums stay inline (§5) | Regenerate the client; name the enum with `enumName` if you want a schema |
