# Migration Guide: 11.42.4 → 11.42.5

## Overview

| Category             | Details                                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| **New feature**      | `TestHelper.mcpSession()` / `TestHelper.mcp()` — MCP tests without hand-written SSE parsing (§1)            |
| **Tooling**          | `check:overrides` accepts a declared "fix exists, but this consumer cannot use it" suppression that expires by itself (§2) |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick up the core update; the new helpers arrive with `src/test/`. No configuration
change is required.

## 1. TestHelper: MCP tests without SSE parsing

Projects that enable the AI module's MCP server (`ai.mcp` in `config.env.ts`) should test their tools over
MCP as well as over REST/GraphQL: MCP has its own role filter and sessions, and a refused tool comes back as
a result with `isError: true`, not as an HTTP error. Until now such a test had to set the right `Accept`
header, carry the `mcp-session-id` header, and parse the SSE stream by hand. `TestHelper` now does that:

```typescript
const session = await testHelper.mcpSession({ token: userToken });

expect((await session.listTools()).map((tool) => tool.name)).not.toContain('delete_user');

const refused = await session.callTool('delete_user', { id });
expect(refused.isError).toBe(true);

const result = await session.callTool('find_users', { query: '@test.com' });
expect(result.json.data.length).toBeGreaterThan(0);

await session.close();
```

`testHelper.mcp(message, { statusCode, sessionId, token })` sends a single JSON-RPC message for the
HTTP-level cases (401 without a token, 404 for another user's session). Full reference: `src/test/README.md`
→ "MCP Testing".

The helpers are additive and build on `testHelper.rest()`, so `token` and `cookies` behave as there. They add
no dependency, so vendor-mode projects receive them with `src/test/`. A project with its own MCP module (not
the AI module's `/ai/mcp`) passes its endpoint as `path`.

## 2. `check:overrides`: a suppression for a fix the consumer cannot use

`auditConfig.ignoreGhsas` used to be usable only for advisories with no fix at all — the moment any fix
appeared, `check:overrides` failed with `FIX AVAILABLE`. That is right in the common case and a dead end in
one: the fix exists, but the package that pulls in the vulnerable version cannot use it (for example, a
patched major removed an export the consumer imports).

That case can now be declared next to the suppression:

```yaml
auditConfig:
  ignoreGhsas:
    - GHSA-x6jw-m9v5-85vh
  unusableFixConsumers:
    GHSA-x6jw-m9v5-85vh: '@nuxt/devtools@3.4.1 cannot use 4.0.1'
```

The declaration expires by itself: `check:overrides` fails with `RE-TEST` as soon as the consumer leaves the
tree or changes version, the advisory offers a patched version nobody assessed (a backport), or anything other
than exactly that consumer version pulls the vulnerable package — including a direct dependency of your own
project. An undeclared suppression of a fixed advisory still fails on sight.

This is a change to the guard script, not to the published runtime: projects created from
nest-server-starter or lt-monorepo receive it with their template update. Exhaust the remedies first (raise
the vulnerable package, raise or patch the consumer); the rules and the reasoning are in
`.claude/rules/package-management.md` → "When the fix exists and the consumer cannot use it".

## 3. Three steps added to the 11.42.3 → 11.42.4 guide

If you already applied [11.42.3 → 11.42.4](./11.42.3-to-11.42.4.md), check these — they were added after its
release:

1. **`source-map-js` < 1.2.2** ([GHSA-68fv-2mgg-jv7q](https://github.com/advisories/GHSA-68fv-2mgg-jv7q),
   high, dev tooling only) is also reported by `pnpm audit`: `pnpm update --depth Infinity source-map-js`.
2. **Commit `pnpm-workspace.yaml` and `pnpm-lock.yaml` together.** An override only reaches the lockfile through
   the `pnpm install` that follows it; a workspace file committed without the re-installed lockfile fails every
   `pnpm install --frozen-lockfile`, typically the Docker image build.
3. **Starter-based projects:** set `bodyParser` where both `localConfig()` and `deployedConfig()` see it (the
   starter ships a shared `PROJECT_BODY_PARSER` constant), or via `NSC__BODY_PARSER__JSON__LIMIT`. A value only
   in the deployed block leaves the e2e suite and `lt dev up` at 100 kB.

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| `check:overrides` fails with `RE-TEST` on a declared suppression | The consumer moved, a new patched version appeared, or another package (or your project directly) now pulls the vulnerable package | Re-assess: take the fix if it is now usable, otherwise update the declaration with what you re-checked (§2) |
| `check:overrides` fails with `FIX AVAILABLE` | A suppressed advisory gained a fix, and no declaration explains why it cannot be used | Take the fix; declare only after the remedies are exhausted (§2) |
| `session.callTool()` throws instead of returning `isError` | The JSON-RPC call itself failed (protocol error), not the tool | Assert on `session.request(...)` for protocol-level errors (§1) |
