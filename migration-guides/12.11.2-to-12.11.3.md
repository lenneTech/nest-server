# Migration Guide: 12.11.2 → 12.11.3

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None |
| **Bugfixes** | With `multiTenancy`, the tenant safety net answers a request nobody is signed in to with `401` instead of `403` — also a request whose session has expired (§1) |
| **Security** | None |
| **Migration Effort** | Package update. Only multi-tenant projects whose own tests or client code expect `403` for an anonymous request to tenant-scoped data adjust that expectation |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.11.3
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Bugfix: an expired session reaches the sign-in, also on tenant-scoped data

**No action needed** for most projects. A multi-tenant project whose tests assert `403` for an ANONYMOUS request that
reads tenant-scoped data changes them to `401`.

When a request reads tenant-scoped data without a valid tenant context, the tenant safety net
(`resolveTenantFilter()`, used by the Mongoose tenant plugin and the SQL stores) refuses it instead of returning
unfiltered rows. Up to 12.11.2 it answered `403` to everyone. A browser keeps sending the cookie of an expired
session, so a public route that reads tenant-scoped data answered such a user `403`, and the frontend showed
"data could not be loaded" instead of the sign-in: `@lenne.tech/nuxt-extensions` signs out on a `401` and on nothing
else.

The safety net now follows the rule every other permission layer already follows (`accessDeniedException()`):

| Caller | Since 12.11.3 | Before |
|---|---|---|
| A client request nobody is signed in to (no credential, an unknown or expired session, an expired JWT) | `401` | `403` |
| A signed-in caller without a tenant context | `403` | `403` |
| Server work inside a request context of its own (no client request) | `403` | `403` |

The message (`Tenant context required: …`) is unchanged, and the refusal is the same: only its status differs. The
role guards (`RolesGuard`, `BetterAuthRolesGuard`) and `CoreTenantGuard` already answered an expired or unknown session
with `401`; 12.11.3 adds tests that pin it on both guards, over REST and GraphQL, for an unknown session cookie, an
expired session, the JWT cookie of an expired session and an expired JWT.

## 2. Documentation: the first administrator of a project that signs in through a provider alone

`src/core/modules/better-auth/README.md` → "The first administrator" describes how the administrator created by
`POST /system-setup/init` reaches the project when `emailAndPassword` is off: the init password is a credential nobody
can use while e-mail and password sign-in is off (use a long random value and do not keep it), and the first provider
sign-in is linked to the administrator only when the provider reports the address as verified — Microsoft Entra ID
only with the optional ID token claim `verified_primary_email`. Do not make linking work through
`betterAuth.options.account.accountLinking.trustedProviders` or `emailVerified: true` from `mapProfileToUser`: both
skip that check, and an Entra tenant administrator can give any user any address.

## 3. Dependencies

| Package | 12.11.2 | 12.11.3 |
|---|---|---|
| `graphql-ws` | 6.4.1 | 6.4.3 |
| `better-auth`, `@better-auth/core`, `@better-auth/passkey` (required peers, tested version) | 1.7.23 | 1.7.28 |
| `mongoose` (optional peer) | 9.13.0 | 9.13.1 |
| `bullmq` (optional peer) | 6.7.8 | 6.7.10 |
| `@aws-sdk/client-s3`, `@aws-sdk/lib-storage`, `@aws-sdk/s3-request-presigner` (optional peers) | 3.1176.0 | 3.1177.0 |

Maintenance releases without advisories; every peer range is unchanged (`better-auth` stays `>=1.7.16 <1.8.0`). The
better-auth version is the one this release is tested against: a project keeps its own `better-auth` pin and may raise
it to 1.7.28, together with `@better-auth/passkey` and `@better-auth/core` and with the app's pin in a fullstack
project. `pnpm run update` raises `graphql-ws` and the optional peers a project declares.

## Compatibility Notes

| Pattern | Status |
|---|---|
| No `multiTenancy` | Unchanged |
| `multiTenancy`, signed-in requests | Unchanged (`403` where the tenant context is missing) |
| `multiTenancy`, anonymous request to tenant-scoped data (public route, expired session) | `401` instead of `403` |
| Code that catches `ForbiddenException` from the safety net for an anonymous request | Catch `UnauthorizedException` as well, or both via `HttpException` |
| `GET /iam/features` | Unchanged; `jwt` follows the JWT plugin registration (now pinned by a test) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| A project test expects `403` for an anonymous tenant-scoped read and now gets `401` | 12.11.3 answers the safety net by the requester's auth state | Expect `401` for the anonymous case, `403` for a signed-in caller |
| The frontend still shows a load error after the session expired | A project's own guard or exception answers `403` without a user | Throw `accessDeniedException(currentUser)` instead of a fixed `ForbiddenException` |
