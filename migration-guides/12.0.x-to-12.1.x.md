# Migration Guide: 12.0.x → 12.1.x

## This MINOR contains breaking changes

Per `.claude/rules/versioning.md` the MAJOR digit mirrors NestJS, so a breaking change ships as a MINOR. 12.1.0 is
one: **`mongoose`, `@nestjs/mongoose` and `mongodb` become optional peer dependencies** (§2). A MongoDB project keeps
working once it declares them itself — which a starter-based project already does for two of the three.

12.1.0 makes the framework **database-agnostic**: a project keeps its data in MongoDB (the default, unchanged), in
**PostgreSQL**, in **MySQL 8.4 / MariaDB 11.8** (§7), or in several of them, model by model. The framework's own
modules — users, Better-Auth, tenants, API tokens, the AI module, file metadata, locks, migrations, health check, Hub —
run on MongoDB and PostgreSQL behind one `CrudService` and one security pipeline, and the whole e2e suite runs on both;
on MySQL and MariaDB everything but Better-Auth runs, proven by the parity matrices. A project that stays on MongoDB changes nothing but
its dependency list.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | `mongoose`, `@nestjs/mongoose`, `mongodb` are optional peers — declare them (§2). `CorePersistenceModule.forFeature()` provides the model tokens itself instead of importing `MongooseModule` (§6). A `database` URL without explicit `mongoose` config no longer opens the fallback MongoDB connection (§5) |
| **New Features** | PostgreSQL data sources with TypeORM, Kysely or Drizzle (§3); MySQL 8.4 / MariaDB 11.8 data sources on the same three engines (§7); per-model routing (`database.models`, `@PersistedModel`); the data store port (`DataStore`, `@InjectStore()`); Better-Auth on PostgreSQL; framework-owned schema evolution and SQL migrations (§4); model decorators usable without MongoDB (`Schema`, `Prop`, `SchemaFactory`, `InjectModel` from `@lenne.tech/nest-server`) (§2); `findAndCount({ samples })` on SQL |
| **Bugfixes** | Found while making every suite pass on both databases, all fixed on MongoDB too: a legacy logout kept the device's refresh token; with legacy JWTs and `multiTenancy` the tenant guard answered every tenant route with 401; the passkey challenge cookie was looked up under the wrong name; the system-setup refusal log names the claim's real location |
| **Migration Effort** | MongoDB project: add three dependencies. PostgreSQL: a new project or a data move — see §3 |

## Quick Migration (a MongoDB project)

```bash
# npm mode: raise the framework and declare MongoDB's libraries yourself
pnpm add @lenne.tech/nest-server@12.1.0 mongoose@9.11.4 @nestjs/mongoose@12.0.0 mongodb@7.7.0

pnpm run build
pnpm test
```

Use the versions this release's `package.json` lists under `devDependencies` — they are the ones it is tested with.

**Vendor mode** (`src/core/` copied into the project): the vendored core names every SQL package in an `import()`,
which TypeScript resolves whatever database the project uses. Declare them, at least as `devDependencies`, or the
build fails with TS2307 — `mysql2` is new in this release:

```bash
pnpm add -D pg@8.23.1 @types/pg@8.23.1 mysql2@3.24.6 typeorm@1.1.2 kysely@0.29.7 drizzle-orm@1.0.0-rc.5
``` A
starter-based project already declares `mongoose` and `@nestjs/mongoose` in `dependencies`; **move `mongodb` from
`devDependencies` to `dependencies`**, because Better-Auth's MongoDB adapter loads it at runtime.

## 1. What changes for a MongoDB project

Nothing in behaviour. Every MongoDB code path is the one 12.0 ran: Mongoose models, the five Mongoose plugins, GridFS,
the 12.0 lock documents (an old and a new replica share them in a rolling deploy), the native collections. The new
security layer below the plugins — the **tenant row check**, which refuses a read result containing another tenant's
row with 403 — only refuses rows the tenant filter would already have removed, so a correct path never meets it.

## 2. MongoDB's libraries are optional peers

`@lenne.tech/nest-server` no longer installs `mongoose`, `@nestjs/mongoose` and `mongodb`. A project that keeps data in
MongoDB declares them (Quick Migration above); one on PostgreSQL alone installs none of them, and the framework loads,
boots and runs without them — proven on every release by `pnpm run check:without-mongodb` against the build. A
vendor-mode project on PostgreSQL keeps the three as `devDependencies`: the vendored core is compiled as the project's
own source and imports their types, so `tsc` needs them, while the running server loads none of them.

What a missing package looks like: a named `MongoPackagesMissingError` at boot, saying which feature needs MongoDB
(the `mongoose` configuration, GridFS, Better-Auth on MongoDB, a MongoDB migration) and what to install. Only one of
`mongoose` / `@nestjs/mongoose` installed is refused the same way.

**Model files.** A project that wants its models to work on either database imports the decorators from the framework
instead of `@nestjs/mongoose` — same names, same options:

```typescript
// Before (MongoDB only)
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
// After (MongoDB and PostgreSQL)
import { Prop, Schema, SchemaFactory } from '@lenne.tech/nest-server';
```

Where Mongoose is installed they apply `@nestjs/mongoose`'s decorators exactly as before; where it is not, they record
the declaration, and the framework builds the same model description from it. Also available: `InjectModel`,
`InjectConnection`, `getModelToken`, `getConnectionToken`, `raw`, `createSchema` (an inline schema), `objectIdType()`
(the ObjectId field type), `newObjectId()`, `isValidObjectId()`. Free-form fields are declared `{ type: Object }`
(Mongoose stores that as `Mixed`) rather than `Schema.Types.Mixed`.

`@InjectConnection()` receives `null` where no MongoDB is configured.

## 3. PostgreSQL

```typescript
// config.env.ts
database: {
  url: 'postgres://app_role@db/project',      // the application role: owns nothing, no BYPASSRLS
  ownerUrl: 'postgres://owner_role@db/project', // owns the schema, migrates it at boot
  sqlEngine: 'typeorm',                         // or 'kysely' / 'drizzle'
},
```

```bash
pnpm add pg typeorm   # or kysely / drizzle-orm@1.0.0-rc.5 — optional peers
```

- **Only models registered with `CorePersistenceModule.forFeature()` are routed.** The framework's own models are; a
  project's models move by replacing `MongooseModule.forFeature([...])` with `CorePersistenceModule.forFeature([...])`
  (same definitions). A model registered with `MongooseModule.forFeature()` stays on MongoDB.
- **Per-model routing:** `database.models: { Article: 'mongoose' }` keeps a model in the project's MongoDB (configure
  `mongoose` explicitly — it becomes the source `mongoose`), `@PersistedModel({ dataSource })` declares it in code.
- **Better-Auth follows the user model.** With the user model on PostgreSQL, Better-Auth runs there too: one `users`
  row per user, its tables in snake_case. Nothing is copied from MongoDB — moving existing users is a data migration.
- **Tenant isolation in the database.** Every tenant-scoped table gets forced row-level security; a query without a
  tenant scope fails (403) instead of reading every tenant. The application role must not be superuser, have
  `BYPASSRLS`, own a framework table or be allowed to `TRUNCATE` one — the boot refuses it.
- **PostgreSQL 15+** (unique indexes are `NULLS NOT DISTINCT`, as MongoDB treats missing values).
- **Health check:** with `healthCheck.configs.database` every SQL source answers as `<key>:<source>`.
- **Hub:** a Persistence panel shows each model's source; the Migrations panel reads `lt_migrations`.

Choosing between the databases: `docs/choosing-a-database.md`.

## 4. Schema evolution and SQL migrations

The framework creates and evolves the tables from the model descriptions at boot, as the owner role: new tables,
columns, indexes and grants are applied automatically. A change that could lose or reject data — a type change, a new
unique index, a rename collision, a table losing tenant isolation — stops the boot with the suggested statements:

```bash
migrate create <name> --sql      # a migration that runs SQL (runSqlMigration())
```

`@UnifiedField({ renamedFrom: 'oldName' })` declares a renamed field. The migration state lives in `lt_migrations`
(`createMigrationStore(<owner URL>)`); the Hub refuses to run migrations while that table is empty and the MongoDB
collection still lists applied ones (a `migrate.js` still writing MongoDB).

## 5. A `database` URL without `mongoose` configuration opens no MongoDB

Until 12.0, `CoreModule.forRoot()` merged a fallback `mongoose.uri` (`mongodb://localhost/nest-server-default`) into
every configuration and connected to it, whatever `database` said. Since 12.1.0 MongoDB is connected only when a source
uses it: `mongoose` configured explicitly, or `database` naming MongoDB, or `database` absent (today's single MongoDB).
A project that set `database` to PostgreSQL **and relied on the implicit fallback** for models registered with
`MongooseModule.forFeature()` configures `mongoose` explicitly — those models were on a database nobody configured.

## 6. `CorePersistenceModule.forFeature()` provides the model tokens itself

It used to import `MongooseModule.forFeature()`. It now registers the same providers itself (the shape `@nestjs/mongoose`
uses: `connection.model(name, schema, collection)`, discriminators included) and exports `getModelToken(name)` plus the
store token. `@InjectModel()` keeps resolving. Without a MongoDB connection the model token is a stand-in whose data
methods refuse with a named error — a `CrudService` runs on the routed store either way. A test module that relied on
the re-exported `MongooseModule` imports `MongooseModule.forRoot()` itself, as before.

## 7. MySQL and MariaDB

```typescript
// config.env.ts — the scheme names the server the URL reaches: mysql:// or mariadb://
database: {
  url: 'mysql://app_account@db/project',      // the application account: SELECT, INSERT, UPDATE, DELETE only
  ownerUrl: 'mysql://owner_account@db/project', // creates and migrates the schema, grants the application account
  sqlEngine: 'typeorm',                         // or 'kysely' / 'drizzle'
},
```

```bash
pnpm add mysql2 typeorm   # or kysely / drizzle-orm@1.0.0-rc.5 — optional peers
```

The same models, routing and store as on PostgreSQL (§3, §4). What differs, and belongs in the project's own
documentation:

- **No row-level security.** Tenant isolation is the store's (the before-layer and the row check after every read).
  A query through `store.native()`, `store.raw()` or a connection of the project's own reaches every tenant's rows
  unless it filters by `tenantId` itself; the boot warns once per source.
- **Better-Auth is refused at boot** while the user model (`users`) lives on MySQL / MariaDB. Keep it on PostgreSQL or
  MongoDB (`database.models: { User: '<source>' }`), or sign in through the legacy endpoints only.
- **An indexed text field holds at most 255 characters** (a longer value answers 400). Indexing an existing text field
  later is a type change — a reviewed SQL migration. A lookup index over four or more text fields indexes a prefix of
  each; such a unique index is refused.
- **Updates:** two operators on one path, or on a path and a path inside it, are refused — MongoDB's own rule.
- **Unique indexes:** a missing value counts as a value, as on MongoDB; a sparse unique index (or a partial one on
  "field exists") lets records without the value through. Any other partial unique index stops the boot — MySQL has
  no partial indexes, and a uniqueness checked nowhere must not look like one that holds.
- **Schema runs are not transactional:** MySQL commits every DDL statement on its own. A failed change leaves the
  statements before it applied and names the one that failed; the next boot completes the rest. The same holds for
  `runSqlMigration()` — write such a migration so it can run again.
- **The application account** may only read and write rows; the boot refuses one that may alter, drop, index, trigger
  or grant, a server older than MySQL 8.4 / MariaDB 11.8, and a scheme that names the other server.
- Leases, migration state (`createMigrationStore(<owner URL>)`), the expiry sweep, health check and Hub work as on
  PostgreSQL.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Services extending `CrudService` with `@InjectModel()` | Compatible — the service follows its model's store |
| Direct `this.mainDbModel.find(…)` on a model routed to SQL | Refused with a named error; use `this.dataStore` |
| `Model.create()` / `findByIdAndUpdate().lean()` in hot paths (MongoDB) | Compatible; the store (`this.dataStore.insert()` / `updateById()`) is the neutral fast path |
| `getNativeCollection(reason)` / `getNativeConnection(reason)` | MongoDB only; on SQL `store.native(reason)` / `store.raw(reason)` (RLS still binds) |
| Custom Mongoose plugins on the connection | MongoDB only; their logic does not run on a SQL store |
| GridFS (`file.storage: 'gridfs'`) | MongoDB only; on a SQL default source the derived driver is `filesystem` (or `s3`) |
| `@nestjs/mongoose` decorators in project models | Compatible on MongoDB; switch to the framework's exports for PostgreSQL |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `MongoPackagesMissingError: … needs MongoDB, and its libraries are not installed` | A MongoDB feature is configured, the peers are missing | Install `mongoose`, `@nestjs/mongoose`, `mongodb` (Quick Migration) |
| `SchemaMigrationRequiredError` at boot | A schema change needs review | Write the suggested statements into `migrate create <name> --sql`, run it |
| Boot refuses the application role | Superuser, `BYPASSRLS`, owner of a framework table, or `TRUNCATE` right | Use a role that owns nothing; the owner goes into `ownerUrl` |
| `X.find() reaches MongoDB, but X is stored on postgres` | Code calls the Mongoose model of a model routed to SQL | Use `this.dataStore` / `@InjectStore()` |
| 403 on a tenant read on PostgreSQL | No tenant scope for a tenant-scoped table (RLS) | Run inside a request with a tenant, or as system work (`RequestContext.runWithBypassTenantGuard()`) |
| `Better-Auth cannot run on MySQL yet` at boot | The user model is routed to a MySQL / MariaDB source | Route `User` to PostgreSQL or MongoDB, or switch Better-Auth off |
| `The application account … holds ALTER, …` at boot | `database.url` connects as an account with schema rights | Connect as a DML-only account; the owner goes into `ownerUrl` |
| `Updating the path "…" would create a conflict` on MySQL | Two update operators on one path | One operator per path, as on MongoDB |
| 400 `a value is longer than its column allows` on MySQL | A text field in an index got more than 255 characters | Shorten the value, or leave the field out of the index |
