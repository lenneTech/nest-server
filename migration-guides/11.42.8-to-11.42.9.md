# Migration Guide: 11.42.8 → 11.42.9

## Overview

| Category             | Details                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| **New Feature**      | `setupSwagger()` documents every HTTP interface the server makes usable — Better-Auth's own routes, `/ai/mcp`, the MCP OAuth endpoints (§1) |
| **Bugfix**           | …and only those: routes the running configuration makes fail for every caller leave the document (§2)          |
| **New Feature**      | `@ApiMethods()` — the HTTP methods an `@All()` handler actually serves (§3)                                     |
| **Bugfix**           | The `tus` key in the server configuration takes effect — it was never read (§5). **Check your `tus` block**     |
| **Bugfix**           | TUS: upload URLs work below a global prefix and a project route, a `path` naming a new route moves the endpoint, `termination: false` / `creation: false` are enforced, new `relativeLocation` (§5) |
| **Bugfix**           | `healthCheck.enabled: false` leaves the health check endpoints out (§6)                                         |
| **Breaking Changes** | None in the API. A `tus` block in `config.env.ts` that did nothing before now applies (§5)                      |
| **Migration Effort** | Review a `tus` block in `config.env.ts` if you have one (§5.1); a proxy that renames the tus route or relative upload URLs need a look (§5.2). Regenerate a client built from `/api-docs-json` if you keep one (§4) |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update.

## 1. Everything usable is documented

The document is built from the running application, so it follows the server configuration and every
project module automatically: a module that is registered appears, one that is not stays out. Three
kinds of interface used to be invisible to `@nestjs/swagger` because they have no Nest handler:

| Interface | Documented since 11.42.9 |
| --- | --- |
| Routes Better-Auth serves itself under `/iam` — whatever the configured plugins add (two-factor, passkey, sessions, password change, …), including plugins a project adds via `betterAuth.plugins` | from Better-Auth's own OpenAPI generator, under your Better-Auth controller (§1.1) |
| `/ai/mcp` (MCP server, `ai.mcp`) | POST/GET/DELETE, with the bearer requirement the endpoint enforces itself |
| MCP OAuth endpoints (`mountAiMcpOAuth()` in `main.ts`) | exactly the endpoints the call mounted (`/.well-known/…`, `/authorize`, `/token`, `/register`) |

### 1.1 Better-Auth routes

- Documented under your Better-Auth controller: same tags, and `operationTags` receives them with
  `controller` set to that controller's class name (`handler` is Better-Auth's operation id).
- Operation ids: `<Controller>_betterAuth_<betterAuthOperationId>`, e.g.
  `BetterAuthController_betterAuth_changePassword`. Unique and stable across builds.
- Schemas Better-Auth refers to are added as `BetterAuthUser`, `BetterAuthSession`, … so they cannot
  collide with your own `User` model; Better-Auth's OpenAPI 3.1 constructs are converted to 3.0.
- Security: what Better-Auth enforces. A route behind one of its session middlewares (or one of the
  social-account routes that check the session in their handler) carries the global requirement —
  bearer or the session cookie; every other route is public (`security: []`): sign-in, password reset,
  get-session, the two-factor verification steps of a sign-in. Better-Auth's own generator marks every
  route bearer-only, so this is read from the live instance, not from the generator. Routes of plugins
  you add yourself (`admin()`, `organization()`, …) always carry the global requirement.
- With API tokens configured they carry "API tokens: not allowed on this route" and never appear in the
  API-token view.
- Under a global prefix or URI versioning Better-Auth's own routes are not reachable (the API
  middleware does not forward them); they are then not documented, and a warning says why.

**Behind it:** Better-Auth exposes its generator only through its `openAPI()` plugin, so nest-server
registers that plugin itself (`disableDefaultReference: true`). Its own route,
`/iam/open-api/generate-schema`, is not part of your API: its endpoints are marked server-only, so
Better-Auth never routes them and they answer 404, as before this release. If you registered `openAPI()`
in `betterAuth.plugins` yourself, nothing changes — your registration replaces the internal one.

## 2. Only what can succeed is documented

A route that answers an error to every caller under the running configuration is left out. Each rule
reads the switch the handler itself reads:

| Configuration | Left out |
| --- | --- |
| `auth.legacyEndpoints` keeps REST closed (the default since 11.38.0) | legacy `/auth/signin`, `/auth/signup`, `/auth/logout`, `/auth/refresh-token` (they answer 410) |
| `betterAuth.emailAndPassword.enabled: false` | `/iam/sign-in/email`, `/iam/sign-up/email` |
| `betterAuth.emailAndPassword.disableSignUp: true` | `/iam/sign-up/email` |
| `betterAuth.emailAndPassword.passwordReset: false` | `/iam/request-password-reset`, `/iam/reset-password`, `/iam/reset-password/{token}` |
| Better-Auth's own options, read from the live instance — so `betterAuth.options` counts too | e.g. POST `/iam/get-session` without `session.deferSessionRefresh`, social routes without a provider, two-factor OTP routes without `otpOptions.sendOTP`, `/iam/delete-user` without `user.deleteUser.enabled`, `/iam/change-email` without `user.changeEmail.enabled`, `/iam/update-session` without session fields that accept input |
| A Hub panel switched off (`hub.collectors.*`, `hub.mailbox`, `hub.emailPreview`, `hub.db`, `hub.migrations`) | its `*.json` endpoint and actions, which would only answer `{ available: false }` or 400 |

A project controller extending a core controller is covered too — the rules go by the handler, not by
the class name.

## 3. `@ApiMethods()` for `@All()` handlers

`@nestjs/swagger` documents an `@All()` handler as eight operations (GET … SEARCH), whatever it serves.
The TUS handlers now declare theirs, so `/tus` shows POST and `/tus/{id}` HEAD/PATCH/DELETE. Use the
decorator on your own catch-all handlers:

```typescript
import { ApiMethods } from '@lenne.tech/nest-server';

@All(':id')
@ApiMethods('get', 'delete')
async handle(@Req() req: Request, @Res() res: Response) { … }
```

It affects the document only, never routing.

## 4. Generated clients

A client generated from `/api-docs-json` (hey-api, openapi-generator, …) gains functions for the newly
documented routes and loses those for routes your configuration switches off (and the eight
`/iam/{path}` catch-all functions since 11.42.8). Regenerate and let the compiler point at anything that
used a removed function.

## 5. TUS: the configuration takes effect

### 5.1 The server configuration's `tus` key is read

`TusModule.forRoot()` without a `config` of its own now reads the `tus` key of the server configuration
(`config.env.ts`, `NSC__TUS__*`) — the zero-config rule `BetterAuthModule.forRoot()` already follows. An
explicit `TusModule.forRoot({ config })` still wins. **Before this release that key was never read**:
TUS ran with the defaults whatever it said.

What that means for you, if `config.env.ts` has a `tus` block:

| You set | Before | Now |
| --- | --- | --- |
| `tus: false` | TUS enabled anyway | `/tus` is not registered |
| `allowedTypes` | every type accepted | other types answer 415 at creation |
| `maxSize` | 50 GB | your limit (413 above it) |
| `roles` | `[S_USER]` | your roles |
| `termination`, `creation`, `path`, `expiration`, … | defaults | your values (see 5.2 / 5.3) |

These are the values the block was written to enforce, so this is the behaviour you asked for — but it
starts on this upgrade. Check that the allowed types cover what your clients upload before you deploy.

### 5.2 `path` and upload URLs

Before this release `path` only changed the URL handed to a client for a new upload (`Location`); the
endpoint itself always stayed where the controller declared it. Every setup that works today keeps
working:

| `path` | Since 11.42.9 |
| --- | --- |
| unset | The upload URL is built from the path the upload was created at — so resuming now also works below a global prefix, a URI version or a project controller's own route, where it answered 404 before |
| ends with the controller's route — `'/api/tus'` (global prefix) or `'/files/tus'` (a proxy that strips `/files`) | Unchanged: the controller stays, upload URLs use this path. This was the workaround for the old behaviour and needs no change |
| a new route — `'/uploads'` | The controller is now mounted there (a project controller too, as `roles` already did). Before, the endpoint stayed at `/tus` while clients were sent to `/uploads/…`, so no upload could ever be resumed |

Like any controller route, a new route sits below the global prefix and the URI version.

Two cases need a look:

- **A proxy that renames the route** (public `/files/upload` forwarded as `/tus`): `path: '/files/upload'`
  now moves the endpoint. Remove `path` and override `uploadCollectionPath(req)` in your
  `CoreTusService` subclass to return the public path.
- **Relative upload URLs.** The framework now builds the upload URL itself, which takes precedence over
  `@tus/server`'s `relativeLocation`. Use `tus.relativeLocation: true` (new); a `relativeLocation` you
  pass to the tus server yourself — in a vendored core, for example — is honoured as well.

### 5.3 Switched-off extensions are enforced

`@tus/server` itself ignores the extension flags. Since this release:

| Setting | Effect |
| --- | --- |
| `termination: false` | DELETE answers 501, OPTIONS no longer advertises `termination` |
| `creation: false` | POST answers 501, OPTIONS no longer advertises the creation extensions |
| `creationWithUpload: false` | a POST carrying data answers 501 |

`checksum` and `concatenation` have no effect: neither built-in store supports them. The boot log now
lists the extensions the server actually offers.

## 6. `healthCheck.enabled: false`

The flag was declared and ignored: any `healthCheck` object registered `GET /health-check` and the
`healthCheck` query. `enabled: false` now leaves both out (and out of the Swagger document).

## Compatibility Notes

- The Swagger work changes nothing at runtime. Better-Auth's `openAPI()` plugin is now registered, but
  kept off the router, so `/iam/open-api/*` answers 404 exactly as before. The runtime changes of this
  release are the ones in §5 and §6.
- A `CoreTusService` subclass that overrides `onUploadCreate()` keeps the extension checks of §5.3: they
  run before the hook, whether or not the override calls `super`.
- The description of Better-Auth's routes is prepared once at application bootstrap
  (`CoreBetterAuthService.onApplicationBootstrap()`). A project service extending
  `CoreBetterAuthService` that overrides `onApplicationBootstrap()` must call `super` to keep it.
- An explicit `@ApiBearerAuth()` / `@ApiSecurity()` on a route the guards admit to everybody now keeps
  its security requirement instead of being documented as public.
