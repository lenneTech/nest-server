```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required — the filter is

## 1. Malformed ids answer 404 / 400 instead of 500

A malformed id in a route parameter (`GET /users/not-an-id`, `/ai/connections/abc`) reached Mongoose, which throws
`mongoose.Error.CastError`. That is not an `HttpException`, so it escaped `HttpExceptionLogFilter`
(`@Catch(HttpException)`) and Nest answered **500 Internal server error** for what is simply "this resource does not
exist". In a typical project that affected every `:id` route, including the framework's own `/users/:id` and the AI
module's routes.

`CoreModule` now registers `MongooseCastErrorFilter` as `APP_FILTER`. It decides by where the value that failed to
cast came from:

| Value of the failed cast | REST | GraphQL |
| ------------------------ | ---- | ------- |
| a route parameter / a top-level argument (`getUser(id: …)`) | **404** `#LTNS_0400: Resource not found` | same |
| the query string or an update / filter body / a value nested in an input | **400** `#LTNS_0302: Invalid field format [<path>]` | same |
| not in the request (a broken stored id, a value computed by server code) | **500**, unchanged — Nest's body, logged as an error | unchanged |

The third row is deliberate: a cast failure on a value the request does not contain is a data or code defect, and
answering it as a client error would hide it from monitoring. The Mongoose message is never sent to the client — it
names the model. REST bodies have the same shape as every other error `HttpExceptionLogFilter` answers.

**What to check:**

- **A test or client expected 500 for a malformed id:** it now gets 404 (route parameter) or 400 (query / body).
  A well-formed id that matches nothing keeps answering 404 as before, so 404 now means the same for both.
- **A project filter already handled `CastError`:** a catch-all filter registered with `app.useGlobalFilters()` is
  consulted before this one and keeps winning. One registered as `APP_FILTER` in the project's root module is
  consulted after it — set `security.mongooseCastErrorFilter: false` if your own filter must see every `CastError`
  (for example a Sentry filter that reports them).
- **You want the previous behaviour:** `security.mongooseCastErrorFilter: false` restores the 500.

**Not covered — both stay a 500:**

- A malformed id in a document being **created** (`save()`, `Model.create()`, `insertMany()` — the path
  `CrudService.create()` takes). Mongoose reports that as a `ValidationError` wrapping the `CastError`. Validate
  reference ids in the input instead:

  ```typescript
  import { IsMongoId } from 'class-validator';

  @UnifiedField({ isOptional: true, type: () => String, validator: () => [IsMongoId()] })
  owner?: string = undefined;
  ```

- A `BSONError` from `new Types.ObjectId(bad)` in service code. It carries no value to classify; check the id
  before converting it, as `CoreFileService.isMalformedFileId()` does.

## 2. Development tooling and the `@graphql-tools/utils` override

Nothing here reaches the published package's runtime dependencies. Worth mirroring in your own project:

- **`vitest` and `@vitest/coverage-v8` 4.1.12** fix two `@vitest/mocker` advisories published on 2026-10-16
  (GHSA-qxg6-89mg-rqv8, GHSA-xp26-3454-mjgp, both medium). Development tooling only. `pnpm audit` may not list them
  yet, so raise both together without waiting for it: `@vitest/coverage-v8` peer-requires the exact vitest version.
- **`@graphql-tools/utils` override:** if your project carries its own entry for GHSA-7mx3-vvmw-hjmv (overrides do
  not reach consumers, so many do), raise it:

  ```yaml
  # pnpm-workspace.yaml
  overrides:
    '@graphql-tools/utils@>=12.0.0 <12.1.0': '12.1.0'   # was: '<12.0.3': '12.0.3' / '<12.0.4': '12.0.4'
  ```

  The old target still clears the advisory, but `@graphql-tools/schema` 10.1.5 (pulled in by `@apollo/server`)
  requests `^12.1.0`, so a lower target leaves two copies of `@graphql-tools/utils` in the tree.
  See [`docs/security-overrides.md`](../docs/security-overrides.md).

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| `main.ts` with `app.useGlobalFilters(new HttpExceptionLogFilter())` | Unchanged; both filters coexist (they catch different classes) |
| A project catch-all filter via `app.useGlobalFilters()` | Unchanged; it still sees every `CastError` |
| A project catch-all filter as `APP_FILTER` in the root module | No longer sees `CastError` — opt out if it must (§1) |
| Tests built with `Test.createTestingModule({ imports: [ServerModule] })` | Get the filter automatically |
| `security.mongooseCastErrorFilter: false` | Previous behaviour (500) |

## Troubleshooting

**A malformed id still answers 500**
Check where it fails. A create path raises `ValidationError` (see "Not covered" above); a `new Types.ObjectId(bad)` in
service code raises `BSONError`; a value from a header or from stored data is not in the request and stays a 500 on
purpose. The server log names the cast at debug level (`MongooseCastErrorFilter`) when the filter answered 404 / 400.

**A 400 names a field the client did not send**
The path in brackets is the schema path Mongoose failed to cast. For a filter on `id` it reads `[_id]`.
