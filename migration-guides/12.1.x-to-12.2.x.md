# Migration Guide: 12.1.x → 12.2.x

## No breaking change

12.2.0 adds **offline sync**: mobile apps (React Native, Capacitor) with SQLite, web apps and PWAs with IndexedDB, and
desktop or Node clients read and write while disconnected and reconcile with the server afterwards. It is opt-in in
two places — the `sync` configuration and a declaration per model — and **without both nothing changes**: no field,
index, route or code path is added, and a project's test suite stays as it is (protocol §13). It is a MINOR because of
its size, not because anything existing moves.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | Synchronized models: `version`, tombstones, live-only unique indexes, a change order on every database (§2). The sync module: `GET/POST /sync/{model}` with cursor pull, idempotent push, conflict strategies, client ids, resync (§3). Change hints over SSE and GraphQL, tombstone purge, the `syncUpdate` migration helper (§4). `ServiceOptions.expectedVersion` for conditional changes of a synchronized model (§2) |
| **Bugfixes** | None that change existing behaviour |
| **Migration Effort** | None for an update. Offering a model to offline clients: about an hour per model, plus the client (§5) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.2.0
pnpm run build
pnpm test
```

No dependency of a project changes. **Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual; the new
module is `src/core/modules/sync/`.

## 1. What changes for an existing project

Nothing, unless it switches offline sync on. The framework's own models are not synchronized, the `CrudService` keeps
its behaviour for every model that does not declare `sync`, and no route is registered without the `sync`
configuration.

## 2. Synchronized models

A model takes part in offline sync when it is declared with `sync` and registered with
`CorePersistenceModule.forFeature()`:

```typescript
@PersistedModel({
  sync: {
    roles: { create: [RoleEnum.S_USER], delete: [RoleEnum.S_CREATOR], pull: [RoleEnum.S_USER], update: [RoleEnum.S_CREATOR] },
    strategy: 'merge',
  },
})
@Schema({ timestamps: true })
@ObjectType()
export class Note extends CorePersistenceModel { … }
```

The store then keeps three system fields on every write path — `version`, `deletedAt` and the change position
(`syncSeq` on SQL, `syncAt` on MongoDB) — never settable through an input:

- **Deletes leave tombstones**: `CrudService.delete()` and every port delete keep the record as a tombstone without
  content, so clients learn of the deletion. Reads leave tombstones out.
- **Unique indexes apply to live records only**, so delete-then-recreate with the same value works.
- **Conditional changes**: `ServiceOptions.expectedVersion` on `update()` / `delete()` is one statement with the
  version as its condition; another version answers `409` (`VersionConflictError`). Only a synchronized model has a
  `version`: on any other model `expectedVersion` throws `UnsupportedCapabilityError`.

**Making an EXISTING model synchronized is a migration** on every database — the boot refuses with the statements to
run (SQL: the new column and live-only indexes; MongoDB: `SyncMigrationRequiredError`, dropping the old unique indexes
and stamping every document). Details: `.claude/rules/persistence.md` → "Synchronized models".

## 3. The sync module

```typescript
// config.env.ts
sync: {
  cursorSecret: process.env.SYNC_CURSOR_SECRET, // else SECRETS_ENCRYPTION_KEY; required in production/staging
},
```

```typescript
@SyncService({ createInput: NoteCreateInput, model: Note, updateInput: NoteInput })
@Injectable()
export class NoteService extends CrudService<Note, NoteCreateInput, NoteInput> { … }
```

- `GET /sync/{model}`: one page of changes after an opaque, signed cursor; `410` with a reason when the client must
  resync (`invalid`, `horizon`, `access`).
- `POST /sync/{model}`: items processed in order, each atomic; idempotent through mutation ids; client-generated ids
  (ObjectId-hex with a random tail, or uuidv7 for new models); strategies `reject`, `lww`, `merge` (`@SyncField()` for
  fields), `custom` (`resolveSyncConflict()` on the service).
- Every pull and push runs through the model's `CrudService` with the roles from `sync.roles` — the roles of the
  project's own routes do not apply here, and an operation without roles is ADMIN only.
- Without `X-Tenant-Id` a request spans every tenant the caller belongs to.

The protocol for client authors: `docs/offline-sync-protocol.md`. The module: `src/core/modules/sync/README.md`.

## 4. Hints, purge, data migrations

- **Hints**: `GET /sync/hints` (Server-Sent Events, event `change`) and the GraphQL subscription `syncHint(models)` tell
  a client "pull now" — `{ model, at }` only, to callers with the pull roles and access to the tenant. With `redis`
  every replica's subscribers receive them. `sync.hints: false` switches them off.
- **Purge**: tombstones older than `sync.retention.tombstonesDays` (90) are deleted every hour on one replica, after
  the retention horizon moved past them; a client behind it resyncs.
- **Data migrations** of a synchronized SQL table: `runSqlMigration(ownerUrl, [{ syncUpdate: { table, set, where } }])`
  raises `version` and numbers the rows like a store write. A bare `UPDATE` would let a stale client overwrite the
  migrated value without a conflict.
- **Writes past the CrudService** (data store, native API) call `CoreSyncService.notifyChange()` for hints and
  `bumpAccessEpoch()` when a record changes tenant or owner.

## 5. Offering a model to offline clients — checklist

Follow `src/core/modules/sync/INTEGRATION-CHECKLIST.md`. In short:

1. Declare `@PersistedModel({ sync: { roles, strategy } })` and register the model with `CorePersistenceModule.forFeature()`.
2. Put `@SyncService({ model, createInput, updateInput })` on its `CrudService`.
3. Add `sync: {}` (with a `cursorSecret` for deployed stages) to the configuration.
4. Give the client its duties: delete every local record, cursor and unsent change on logout and on an account switch
   (`src/core/modules/sync/SECURITY.md`).

The reference model is `src/server/modules/sync-note/`; the framework's own test clients (a PWA on IndexedDB and a Node
client on SQLite, `tests/clients/` in the framework repository) show a complete client in a few hundred lines.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Project without `sync` configuration | Unchanged |
| Model without `sync` in a project with `sync` | Unchanged; not reachable under `/sync` |
| `CrudService.delete()` on a synchronized model | Leaves a tombstone; a hard delete is the purge's alone |
| Project controller extending `CoreSyncController` | Fine — the hint route is `CoreSyncHintsController`'s, registered first, so re-declaring `pull()` cannot shadow it |
| TTL index on a synchronized model | Refused at registration — an expired record would vanish without a tombstone |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Boot fails: `cursorSecret` missing | Production / staging without `sync.cursorSecret` or `SECRETS_ENCRYPTION_KEY` | Set one of them |
| Boot fails with SQL statements or `SyncMigrationRequiredError` | An existing model was declared `sync` | Run the printed migration (§2) |
| Warning "declares no sync roles" | `sync.roles` missing an operation | Declare roles per operation; otherwise ADMIN only |
| `400` on a push | `Content-Type` is not `application/json` | Send JSON |
| `403` on a cookie push | `Sec-Fetch-Site: cross-site` or an untrusted `Origin` | Push from a trusted origin (`appUrl`, `baseUrl`, `cors.allowedOrigins`) |
| Every cursor answers `410 invalid` | `cursorSecret` changed | Expected: clients resync once |
| Hints only on one replica | No `redis` configured | Configure `redis`; hints are never a correctness signal |
