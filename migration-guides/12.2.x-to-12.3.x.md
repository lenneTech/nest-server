# Migration Guide: 12.2.x → 12.3.x

## 12.3.0 contains breaking changes

The version number moves only the MINOR digit (the MAJOR follows NestJS). Read §1–§3 before you update: none of them
needs code in a typical project, but each one changes what a running application does.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | E-mail verification no longer signs the user in (§1). A prompt continues only the caller's own AI conversation, `CoreAiConversationService.appendMessage()` takes the owner and the protected `CoreAiService.persistTurn()` the run as a third parameter (§2). Non-canonical paths under the Better-Auth base path answer 400, and the IAM rate limit tells routes apart, with half the limit on sign-in and sign-up (§3) |
| **New Features** | None |
| **Bugfixes** | Login CSRF through a forwarded verification link (§1), turns written into another user's AI conversation (§2), rate limiter bypass through dot segments and an IAM rate limit that never told routes apart over HTTP (§3), a planned end of the SSE hint stream logged as a lost session (§4), a sync push that applied a change chained to a refused one in the same request on another writer's version (§5) |
| **Migration Effort** | Usually none. A frontend whose verify page expects a session: one redirect. A project calling `appendMessage()` or overriding `persistTurn()`: one argument. A deployment with a tight `betterAuth.rateLimit.max`: check the value (§3) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.3.0
pnpm run build
pnpm test
```

No dependency of a project changes. **Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Auto sign-in after e-mail verification is off by default

`betterAuth.emailVerification.autoSignInAfterVerification` defaulted to `true`; it is now `false`, which is
Better-Auth's own default.

With the option on, `GET /iam/verify-email` creates a session for the account the link belongs to in whatever browser
opens the link. A verification link travels by mail, so it can be forwarded: someone who signs up with their own
address and sends the unopened link to someone else has that person's browser signed in to the sender's account, and
what the recipient enters there (payment data, documents, messages) lands with the sender (login CSRF).

**What changes:** after clicking the link the user is verified but not signed in, and signs in once.
`CoreBetterAuthEmailVerificationService.shouldAutoSignIn()` answers `false` accordingly.

**What to check:** a frontend whose verify page assumes a session afterwards should send the user to the sign-in, for
example with a "verified, please sign in" message. The nuxt-base-starter's verify page already does ("Jetzt
anmelden").

**To keep the previous behaviour** — only where a verification link reaches nobody but its owner:

```typescript
// config.env.ts
betterAuth: {
  emailVerification: {
    autoSignInAfterVerification: true,
  },
},
```

Only the boolean `true` switches it on (`NSC__*` variables turn `true` into a boolean). Any other value — the string
`"true"` in `NEST_SERVER_CONFIG`, `1`, `yes` — is read as off, in what Better-Auth receives and in what
`shouldAutoSignIn()` answers alike.

## 2. A prompt continues only the caller's own AI conversation

`POST /ai/prompt`, `POST /ai/stream` and the GraphQL `aiPrompt` accepted any `conversationId` and wrote the new turns
into that conversation, also when it belonged to another user. Now a `conversationId` the caller did not create —
another user's, or one that does not exist — counts as no conversation: the run reads no history, writes nothing, uses
no conversation-scoped tool grants, and its response carries no `conversationId`. **Administrators are no exception**:
they still read every conversation (`getAiConversation`, `findAiConversations` with `all`), but continue only their
own.

`CoreAiConversationService.appendMessage()` checks the owner itself and has a third parameter:

**Before:**
```typescript
await this.conversationService.appendMessage(conversationId, { content, role: 'user' });
```

**After:**
```typescript
// The id of the user the turn belongs to; anyone else's turn is not written.
await this.conversationService.appendMessage(conversationId, { content, role: 'user' }, currentUser.id);
```

A call without it fails to compile (TS2554). A subclass that overrides `appendMessage()` and does not call `super`
must check the owner itself — `isOwnedBy(id, userId)` is the new public helper for it.

The protected `CoreAiService.persistTurn()`, which calls `appendMessage()`, takes the run as a third parameter for the
same reason — the owner comes from `run.currentUser`:

```typescript
// Before: protected async persistTurn(input, response)
protected override async persistTurn(input: CoreAiPromptInput, response: CoreAiResponse, run: AiRunContext) {
  // … your own steps …
  await super.persistTurn(input, response, run);
}
```

An override that still calls `super.persistTurn(input, response)` fails to compile (TS2554).

## 3. Requests under the Better-Auth base path

### Non-canonical paths answer 400

Every check under the base path (`/iam` by default) — rate limiter, controller routes, the forwarding to Better-Auth —
read the path as sent, while Better-Auth routes the path after `new URL()` resolved it. `/iam/callback/../sign-in/email`
therefore passed the rate limiter as a skipped OAuth callback and ran as a sign-in.

`CoreBetterAuthPathGuardMiddleware` now runs first under the base path and answers **400** (`#LTNS_0305: Invalid
request path`) for a path with a `.` or `..` segment (also `%2e`-encoded), a backslash, an encoded `/` or `\`, or a
`#`. No Better-Auth route needs any of them; a client that sends one has a bug. It is registered by
`CoreBetterAuthModule` itself — nothing to add.

### The IAM rate limit tells routes apart

The rate-limit middleware read `req.path`, which is `/` for a middleware Nest mounts under the base path. So every IAM
request of a client shared one counter with the full limit, the skip list (`/session`, `/callback`) and the halved
limit for sign-in, sign-up and the password routes never applied over HTTP.

Now a client IP has one counter per route NAME — the last path segment — so `/sign-in/email` and `/sign-up/email` (both
`email`) share one counter. `/session` and `/callback` are not counted, and the strict routes (sign-in, sign-up, the
password reset and change routes) get half of `betterAuth.rateLimit.max`, rounded up. The skip and strict lists match
whole path segments, case-insensitively, as Express routes.

**What to check:** a deployment that set `betterAuth.rateLimit.max` (the nest-server-starter reads it from
`IAM_RATE_LIMIT_MAX`) gets half of it for the e-mail sign-in and sign-up now, and the two count together — with
`max: 10`, five attempts per window for both combined. Behind a shared NAT or proxy, sign-ups use up the same budget as
sign-ins. Raise the value if that is too tight. A single-page app that polls `/iam/session` no longer uses up the
limit.

## 4. SSE hint stream: a planned end logs on debug

`GET /sync/hints` ends its stream on every re-check (`graphQl.subscriptionRevalidationMs`) and the client reconnects.
Every such planned end logged `Closing GraphQL WebSocket of user …: Session no longer valid` at log level. It now logs
`Closing SSE hint stream of user …` on debug; an end an invalidation causes (role change, sign-out) stays at log level.

`registerWsConnection()` takes two optional fields for a long-lived channel of a project's own: `channel` (the name in
the log line, default `GraphQL WebSocket`) and `endsOnRecheck` (every re-check ends the connection). GraphQL WebSockets
log as before.

## 5. Sync push: a change chained to a refused one is held back

A client sends the changes of one record with chained base versions, also in one push (protocol §6.2). The server
applied every item on its own: when the first item conflicted with another writer's version 2, the second — base
`2` — matched that version and was stored on data the client never saw, while the client dropped it locally.

Once an item of a record is not stored (`conflict`, `rejected`, `not_found`, `retry`), the later items of that record
in the same push are now held back: answered `retry` behind a `retry`, otherwise `conflict` with the current record
(`not_found` when the caller may not see one). Items of other records are unaffected.

The server holds back within one request only. Protocol §11 now says what a client does across requests: it sends a
later change of a record only in the same request as the change before it, or after that one came back `applied` or
`merged`, and drops or rebases the later changes of a record whose change was `rejected` or `not_found`. **Check your
client** if it splits its queue into several requests (the protocol caps a push at
`sync.push.maxItems`, 100 by default): after a `retry` it must keep the record's later changes back until the next
sync. A client that sent a single change per record and request to avoid the defect may send chains in one request
again; across requests it still waits for each answer.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Frontend verify page that leads to the sign-in | Unchanged |
| Frontend verify page that expects a session after the link | Redirect to the sign-in, or set `autoSignInAfterVerification: true` (§1) |
| Project calling `appendMessage()` | Pass the owner id (§2) |
| Project subclass of `CoreAiService` overriding `prompt()` | Call `super.prompt()`, or the conversation is not scoped (§2) |
| Project subclass of `CoreAiService` overriding `persistTurn()` | Take `run` as third parameter and pass it to `super` (§2) |
| Project controller extending `CoreBetterAuthController` | Unchanged; the path guard runs before it |
| Custom `betterAuth.rateLimit.skipEndpoints` / `strictEndpoints` | Matched by whole segments now: `/session` no longer covers `/sessions-export` |
| Sync client pushing chained changes of one record in one request | Unchanged; behind a refused item the rest of the chain is answered `conflict` (or `retry`) instead of being applied (§5) |
| Sync client splitting a record's changes across requests | Keep a later change back until the one before it was stored, drop it after `rejected` / `not_found` (§5, protocol §11) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| User not signed in after clicking the verification link | §1 | Expected; lead to the sign-in, or opt in |
| TS2554 on `appendMessage()` or `super.persistTurn()` | §2 | Pass the owner id, or the run, as third argument |
| A continued AI conversation answers without history, no `conversationId` in the response | The conversation belongs to another user (also for admins) | Continue only conversations the caller created |
| 400 `#LTNS_0305` on an IAM request | The path carries a dot segment, a backslash, an encoded separator or a `#` | Fix the client's URL |
| 429 on sign-in earlier than before | The strict limit (half of `max`) applies now, shared by e-mail sign-in and sign-up | Raise `betterAuth.rateLimit.max` |
