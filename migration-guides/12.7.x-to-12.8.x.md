# Migration Guide: 12.7.x → 12.8.x

## 12.8.0 changes behaviour

The version number moves only the MINOR digit (the MAJOR follows NestJS). Two security defaults change what a request
may carry:

- A request value that is a plain **object** where a route declares `string`, `number` or `boolean`
  (`@Body('token') token: string`, likewise `@Query` and `@Param`) is answered with **400** (`#LTNS_0306`) before the
  route runs (§1).
- Cookie values that are not strings — what cookie-parser makes of a `j:`-prefixed cookie — are removed from
  `req.cookies` before any middleware or guard reads them (§2).

Neither affects a client that sends what the route declares. Both have a switch.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | An object at a `string` / `number` / `boolean` parameter answers 400 instead of reaching the route (§1). Non-string cookie values are dropped (§2) |
| **New Features** | `security.mapAndValidatePipe.rejectObjectsForPrimitiveTypes` and `security.stringCookiesOnly` (both default `true`); error code `LTNS_0306` `INVALID_PARAMETER_TYPE`; `receivesObjectForPrimitive()`, `dropNonStringCookies()`, `StringCookiesMiddleware` exported |
| **Bugfixes** | The email-verification link derives the app URL from `baseUrl` instead of pointing at `http://localhost:3001` when `appUrl` is not set (§3) |
| **Migration Effort** | Usually none. Check that no client sends an object into a parameter typed `string` / `number` / `boolean`, and that the project writes no object cookies (§1, §2) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.0
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. An object at a primitive parameter answers 400

**Why:** a controller parameter declared `@Body('token') token: string` has the metatype `String`, and
`MapAndValidatePipe` returned basic-type values unchecked — TypeScript types are erased at runtime. A JSON body
`{ "token": { "$ne": null } }` therefore reached the service as an object, and a MongoDB filter read it as an operator.
That is how a password-reset token set somebody else's password before 11.39.0 (DEV-4143), and the same shape reached
the session lookup through a cookie until 12.7.3 (DEV-4138). Both were fixed per query; this closes the class for every
route at once, including routes in your project.

**What changed:** the pipe answers `400 Bad Request` with `#LTNS_0306: Invalid parameter type [<parameter>]` when the
value is a **plain object** and the parameter is declared `string`, `number` or `boolean` — for `@Body(…)`, `@Query(…)`
and `@Param(…)`, and for a whole-body `@Body() body: string`.

| Value at `@Body('x') x: string` | 12.7.x | 12.8.0 |
|---|---|---|
| `"abc"`, `7`, `true` | passed | passed |
| `null`, missing | passed | passed |
| `["a", "b"]` (also a repeated query key) | passed | passed |
| `{ "$ne": null }`, `{}` | **passed to the route** | **400 `#LTNS_0306`** |

`null` passes on purpose (clearing an optional field is legitimate), and so do arrays (a repeated query key arrives as
one, and an array selects nothing as a filter value). Express 5's default query parser cannot produce an object from a
query string; JSON and form bodies can.

**Not covered — keep the guards at the query:**

- a parameter typed as a **union** the compiler emits as `Object`: `tsc` with `strictNullChecks` does so for
  `locale: string | undefined`, and the pipe cannot tell (SWC and `tsc` without `strictNullChecks` emit `String`, and
  the parameter is covered);
- a **number** at a `string` parameter (`{ "token": 7 }`): it passes on purpose, because a client may send a numeric
  code as a number. MySQL and MariaDB compare a number numerically (`token = 7` matches every token starting with
  `7`), so a lookup there checks its value with `isQueryableString()`;
- a parameter typed as a **class** whose DTO field has **no type validator** (`@UnifiedField({ isAny: true })`, a custom
  `validator` that does not check the type) — the DTO decides what it accepts;
- `any`, and values a project reads from `req.body` / `req.query` itself;
- values that end up in an **aggregation pipeline** (`$match`, `$lookup` stages built from request data);
- GraphQL arguments of a JSON scalar type (`String` arguments are safe: the scalar refuses objects).

For those, check the value where it reaches the database: `isQueryableString()` is exported from
`@lenne.tech/nest-server`. The framework's own query guards from 11.39.0 and 12.7.3 stay in place.

**Your project:** usually nothing. A client that sends an object into a parameter typed `string`, `number` or
`boolean` now gets 400 — that was a type mismatch before, and it reached your code unchecked. To find such routes:

```bash
grep -rnE "@(Body|Query|Param)\('[a-zA-Z_]+'\) [a-zA-Z_]+\??: (string|number|boolean)" src/
```

Switch: `security.mapAndValidatePipe.rejectObjectsForPrimitiveTypes: false` restores the old behaviour (only an
explicit `false` counts). With `security.mapAndValidatePipe: false` the whole pipe is off, this check included.

## 2. Cookies carry strings only

**Why:** cookie-parser turns a cookie value starting with `j:` into the parsed JSON. A client sending
`iam.session_token=j:{"$ne":null}` therefore put an object into `req.cookies`, and on MySQL / MariaDB a number (`j:7`)
is compared numerically (`token = 7` matches every token starting with `7`). Until 12.7.3 that signed a request in as
the owner of a stored session (DEV-4138).

**What changed:** `StringCookiesMiddleware`, registered by `CoreModule` for all routes right after the request context,
removes every non-string value from `req.cookies`, and from `req.signedCookies` everything but strings and `false`
(cookie-parser's marker for a cookie whose signature did not verify). Every middleware, guard and route after it sees
string cookies only. The framework writes only string cookies. Nest middleware runs on the routes Nest serves: an
Express router a project mounts itself with `app.use()`, or a path outside the global prefix, reads `req.cookies` as
cookie-parser left them — check a cookie value there before it reaches a query.

**Your project:** nothing, unless it writes object cookies with `res.cookie(name, { … })` and reads the object back from
`req.cookies`. Then switch it off with `security.stringCookiesOnly: false`, or — better — write a string
(`JSON.stringify`) and parse it where it is read.

## 3. The verification link follows the app URL (DEV-4140)

**Why:** a relative `betterAuth.emailVerification.callbackURL` (the default `/auth/verify-email`) was resolved against
`appUrl || 'http://localhost:3001'`. A deployed stage without `NSC__APP_URL` therefore mailed a verification link to
localhost, although `NSC__BASE_URL` names the app and the password-reset link already derived it from there.

**What changed:** the link uses the same resolver as the reset link — explicit `appUrl`, the localhost default in
`local` / `ci` / `e2e`, else derived from `baseUrl` (`https://api.example.com` → `https://example.com`) unless
`cors.deriveAppUrl` is `false`. When nothing resolves, the mail keeps Better-Auth's own link to the API (token sealed)
and the service warns once.

**Your project:** nothing. `NSC__APP_URL` still wins where it is set.
`CoreBetterAuthEmailVerificationService.buildFrontendVerificationUrl()` now returns `string | undefined`; an override
that returns a string stays compatible.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `@Body('x') x: string` receiving a string, number or boolean | Unchanged |
| `@Body() input: SomeInput` (DTO class) | Unchanged — validated by the DTO as before |
| `@Body() body: any` | Unchanged — not covered by §1, guard at the query |
| `@Query('x') x: string \| undefined` receiving an object | Depends on the compiler (§1): 400 under SWC and `tsc` without `strictNullChecks`, unchanged under `tsc` with it — guard at the query either way |
| `@Body('code') code: string` receiving the number `7` | Unchanged — a number passes; on MySQL / MariaDB guard the lookup (§1) |
| `@Query('ids') ids: string` with `?ids=a&ids=b` | Unchanged — an array passes |
| `@Body('x') x?: string` receiving `null` | Unchanged — `null` passes |
| A multipart form with bracketed field names (`title[a]=x`) into a `string` parameter | 400 — multer builds an object from it |
| Cookies written by nest-server, nuxt-extensions, ng-base or the starters | Unchanged — all are strings |
| `req.signedCookies.x === false` (invalid signature) | Unchanged — `false` is kept |
| Project code reading an object cookie written with `res.cookie(name, {…})` | Gone — see §2 |
| GraphQL arguments | Unchanged — scalars validate their type |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `400 #LTNS_0306: Invalid parameter type [x]` after the update | A client sends an object for a parameter typed `string` / `number` / `boolean` | Send the declared type, or declare the parameter as a DTO class that describes the object (§1) |
| A cookie the project set is `undefined` in `req.cookies` | It was written as an object (`res.cookie(name, {…})`) | Write a string and parse it, or `security.stringCookiesOnly: false` (§2) |
| The verification link points at the API instead of the app | No `appUrl`, and `baseUrl` gives none (or `cors.deriveAppUrl: false`) | Set `NSC__APP_URL`; the boot log carries a warning (§3) |
