# Migration Guide: 11.41.x → 11.42.x

## Why this is a MINOR

Per `.claude/rules/versioning.md` the MAJOR mirrors NestJS, so **MINOR is where breaking changes
live**. Two behaviour changes hit multi-tenant projects only: with `multiTenancy.adminBypass: false`
a platform administrator can no longer set a tenant account's e-mail address or password (§4), and
the AI tool registry resolves tool roles by the membership role of the request's tenant (§3). A call
that used to succeed can now be refused, so this is `11.42.0` rather than a patch.

**Projects without `multiTenancy` see no behaviour change.** Everything else in this release is
opt-in.

## Overview

| Category                                    | Details                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **New (opt-in)**                            | `outboundFetch()` and friends — an SSRF guard for URLs a user entered (§1)                                 |
| **New (opt-in)**                            | `multiTenancy.isTenantActive` — a deactivated tenant stops working (§2)                                    |
| **New**                                     | `assertTenantRole()` / `hasTenantRole()` — tenant roles enforced in services, on every entry point (§3)    |
| **Behaviour change** (multi-tenancy)        | AI tool roles (chat and MCP) resolve like `@Roles()` in the tenant guard (§3)                              |
| **Behaviour change** (`adminBypass: false`) | No credential changes of other accounts through `updateUser`; no ADMIN bypass in the AI tool registry (§4) |
| **Dependency**                              | `undici` 7.30.0 is a runtime dependency (§1) — nothing to do                                               |
| **Migration Effort**                        | None without multi-tenancy. With it: check §3 and §4; adopt §1–§3 where they apply                         |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm run build && pnpm test
```

Vendor-mode projects pick up the core update; `undici` reaches them through `dependencies`.

## What's New in 11.42.0

### 1. SSRF guard for user-entered URLs

When the server calls a URL a USER entered — a webhook, an export target, an ERP address — it calls it
from inside its own network. Without a check, a user points it at the database, other containers or
the cloud metadata service (`169.254.169.254`) and reads the answer back.

```typescript
import { outboundFetch, OutboundUrlBlockedError } from '@lenne.tech/nest-server';

const response = await outboundFetch(webhook.url, { body, headers, method: 'POST' });
// an ERP in the same network, freed explicitly:
await outboundFetch(target.url, init, { allowedHosts: ['erp.internal:8443'] });
```

- **Only for user-entered URLs.** Configured targets (AI providers, SMTP, S3, Redis, Brevo) do not use
  it; nothing is applied globally.
- Checked twice: on the URL before sending (`OutboundUrlBlockedError`, readable) and on every
  connection — the only place that sees a redirect's next hop and DNS rebinding. A refusal on a later
  hop surfaces as undici's `TypeError: fetch failed` with the `OutboundUrlBlockedError` as `cause`.
- Internal targets are allowed in `local`, `e2e` and `ci`, refused elsewhere — including the deployed `test` stage.
  `security.allowPrivateOutboundTargets` (`NSC__SECURITY__ALLOW_PRIVATE_OUTBOUND_TARGETS=true|false`)
  decides explicitly.
- `assertOutboundUrlAllowed(url)` checks without sending; `createOutboundDispatcher()` returns the
  guarded undici `Agent` for code that uses undici directly. `outboundFetch()` uses undici's own
  `fetch`: Node 22's built-in `fetch` bundles a different undici major than the agent.

### 2. Deactivated tenants stop working

`CoreTenantGuard` validated the membership only, so a tenant a project switched off kept working for
its members, its API tokens and every request without a tenant header. Tell the guard:

```typescript
// config.env.ts
multiTenancy: {
  isTenantActive: async (tenantId, { connection }) =>
    (await connection.collection('tenants').findOne({ _id: new Types.ObjectId(tenantId) }))?.active !== false,
}
```

Then call `tenantGuard.invalidateTenant(tenantId)` right after switching a tenant on or off (answers are
cached for `cacheTtlMs`; the call broadcasts to every replica with Redis). Effects: 403 on header paths
and for tenant tokens, no tenant context on public routes, the tenant dropped from the header-less
tenant list, no tenant for a new WebSocket subscription (one already open keeps its tenant until the client reconnects — the same holds today for a removed membership). A platform administrator under `adminBypass` still gets in.
Asked after the membership check, so a non-member learns nothing. A function cannot come through
`NSC__*` — set it in `config.env.ts`.

**If your project already has its own "tenant active" guard**, it can stay; the hook additionally
covers the header-less tenant list, which such a guard usually misses.

### 3. Tenant roles on every entry point — services, MCP and AI chat

`@Roles()` protects a route. MCP tools, AI tools, queue processors and other services call a service
directly and never pass it. Enforce a tenant role in the service:

```typescript
import { assertTenantRole, DefaultHR } from '@lenne.tech/nest-server';

async updateSettings(input: SettingsInput, serviceOptions?: ServiceOptions) {
  assertTenantRole(DefaultHR.OWNER, 'Only owners may change the settings');
  // …
}
```

Signed in without the role → 403; anonymous client request → 401; system work (cron, migration, seed —
no client request) → passes. The last two are told apart by the new `RequestContext.fromRequest`,
which `RequestContextMiddleware` and the GraphQL WebSocket context set. **If you build a
`RequestContext` yourself for a client operation** (a custom transport), set `fromRequest: true`.

**Behaviour change, multi-tenancy only:** the AI tool registry (chat and `/ai/mcp`) now resolves a
tool's `roles` like the tenant guard resolves `@Roles()` — a global role against `user.roles`, a tenant
role against the membership role in the request's tenant (by hierarchy), and no ADMIN bypass where
`adminBypass: false`. Before, every role was compared with the global `user.roles`. If a tool lists a
TENANT role and a user relied on holding that name globally, the tool now follows the membership
instead. An AI client acts within the signed-in user's rights and tenant scope — never beyond.

**MCP sessions follow the current user.** A session used to keep the user object from its `initialize`
request for its whole life, so a role revoked mid-session kept working over MCP until the client
reconnected. The controller now refreshes the session's user on every request, and
`CoreAiMcpService.createServer()` receives a **getter** (`() => AiToolUser`) instead of the user object.
A project that overrides `createServer(user)` must accept the getter (a plain object is still accepted
when you call it yourself) and read it per request, not once.

### 4. `adminBypass: false` holds for credentials

With multi-tenancy and `adminBypass: false`, `PATCH /users/:id` / `updateUser` now refuse (403) a change
of another account's e-mail address or password — whoever asks, including the account's creator
(`S_CREATOR` may update, and the e-mail field is open to every updater). Changing the address and
requesting a reset was a way to take over a tenant account that `adminBypass: false` exists to rule
out.

Unaffected: the account itself, profile fields, an unchanged address sent along, deletion, and
system work without a current user (invitation, password reset). Administrator accounts are NOT
exempt as targets — an administrator may write `roles`, so "promote to ADMIN, then change the address"
would otherwise open every account in two requests. Support for a
tenant user goes through the password-reset flow. A project that needs a different rule overrides
`CoreUserService.assertCredentialChangeAllowed()`.

## Compatibility Notes

| Pattern                                             | Status                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------- |
| Project without `multiTenancy`                      | Unchanged                                                             |
| `multiTenancy` with `adminBypass` on (default)      | Unchanged except §3 (AI tool roles follow the membership)             |
| `multiTenancy` with `adminBypass: false`            | §3 and §4 apply                                                       |
| Project-own tenant-active guard                     | Keeps working; the hook adds the header-less path                     |
| Project-own SSRF check                              | Keeps working; consider `outboundFetch()` for redirects and rebinding |
| Custom `RequestContext.run()` for client operations | Set `fromRequest: true` (§3)                                          |
| Override of `CoreAiMcpService.createServer(user)`   | Receives a getter now — call it per request (§3)                      |

## Troubleshooting

| Symptom                                                        | Cause                                                                   | Fix                                                                 |
| -------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `403` when an admin changes a tenant user's e-mail or password | `adminBypass: false` (§4)                                               | Let the user change it, or use the reset flow                       |
| An AI tool disappeared for some users                          | Tool roles follow the membership under multi-tenancy (§3)               | List the tenant role the users hold in the tenant, or a global role |
| `Tenant is inactive` (403)                                     | `isTenantActive` returned `false`                                       | Reactivate, then `invalidateTenant(tenantId)`                       |
| A reactivated tenant is still refused                          | Cached answer                                                           | `tenantGuard.invalidateTenant(tenantId)`                            |
| `OutboundUrlBlockedError` locally                              | `security.allowPrivateOutboundTargets: false` set, or a non-local `env` | Unset it, or list the host in `allowedHosts`                        |
| `TypeError: fetch failed` from `outboundFetch()`               | A redirect or DNS answer pointed inside                                 | Inspect `error.cause`                                               |
