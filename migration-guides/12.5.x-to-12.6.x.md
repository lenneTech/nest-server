# Migration Guide: 12.5.x → 12.6.x

## 12.6.0 contains breaking changes

The version number moves only the MINOR digit (the MAJOR follows NestJS). Two changes can stop something that worked:

- Read §1 if your project has an email-verification page: the link in the verification mail no longer carries the
  address (`&email=`), so a page that offers "send a new email" only when `?email=` is present stops offering it until
  it uses the new endpoint. The nuxt-base-starter page follows in its release after 12.6.0 (lock-step); until a project
  has taken that over, §1 applies to the starter's page too.
- Read §3 if your project is based on nest-server-starter: from its 12.6.0 release on, a `NODE_ENV` without a block in
  `src/config.env.ts` no longer starts, and the required-variable check runs for every environment that is not local.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | The verification link carries the token only and sealed, no `email` parameter (§1). Starter: a `NODE_ENV` without a block in `config.env.ts` no longer starts, the required-variable check covers every non-local environment (§3) |
| **New Features** | `POST /iam/resend-verification-email`: a new verification mail for the token of a link, an expired one included; `resendVerificationByToken` in `GET /iam/features` (§1) |
| **Bugfixes** | A system setup killed halfway (SIGKILL, OOM) left a user without the admin role and the setup locked for good; the next boot now finishes it (§2) |
| **Migration Effort** | One change on the verification page (§1), or taking over the `verify-email` page of the nuxt-base-starter release that follows 12.6.0. Starter-based projects: check the boot line of every stage before taking over the starter change (§3) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.6.0
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The verification link carries no address — resend with the token

**Why:** the address stood in the URL of the mail, in the browser history and in every access log of the app.

**What changed:** `buildFrontendVerificationUrl()` builds `<callbackURL>?token=…` and nothing else, and the token is
sealed: Better-Auth's own token is a readable JWT with the address and the user id in it, so the link carries it
encrypted. Pass it on unchanged — `GET /iam/verify-email?token=…` opens it before Better-Auth verifies, and a plain
token from a mail sent before the update still works. Do not decode the token on the page: there is nothing to read
any more. Instead of the address, a page sends the token of the link to a new endpoint:

```http
POST /iam/resend-verification-email
Content-Type: application/json

{ "token": "<the token of the link, also when it has expired>" }
```

| Answer | When |
|---|---|
| `200 { "email": "k***@example.com", "success": true }` | the token carries Better-Auth's signature (expired or not). A new mail goes out only to an existing, unverified account; the answer is the same either way |
| `200 { "email": null, "success": true }` | the token is invalid, forged or missing its claims |
| `400` | no `token` in the body |
| `429 LTNS_0020` | more than 3 requests for one token, or more than 10 invalid tokens from one client address, within an hour |

The endpoint never verifies, signs in or creates a session. `GET /iam/features` reports
`resendVerificationByToken: true` while email verification is enabled.

**Your page (if it is not the current nuxt-base-starter one):**

```typescript
// Before: the button needed the address from the URL
const email = route.query.email as string | undefined;
async function resend() {
  await $fetch('/iam/send-verification-email', { body: { email }, method: 'POST' });
}

// After: the token of the (expired) link is enough
const token = route.query.token as string | undefined;
async function resend() {
  const { email } = await $fetch<{ email: null | string; success: boolean }>('/iam/resend-verification-email', {
    body: { token },
    method: 'POST',
  });
  // Show `email` (masked) as "a new mail is on its way to k***@example.com"
}
```

Keep an address field only as the fallback for a page opened without a token, or for a server that does not report
`resendVerificationByToken`. A project that overrides `buildFrontendVerificationUrl()` and still appends the address
should stop doing so.

### The development log line of auth links

Verification and password-reset links are printed to stdout only in `local`, `ci` and `e2e` now. `LT_LOG_AUTH_URLS=1`
no longer opens the line in any other environment: an environment name says nothing reliable about whether it is a
laptop, and the line carries a live token. `LT_LOG_AUTH_URLS=0` still suppresses it. The line reads
`[<LABEL>] User: <masked>, UserKey: <16 hex>, URL: <url>`; `UserKey` is the first 16 hex characters of SHA-256 over
the trimmed, lower-cased address. A test helper that found its token by decoding the JWT in the URL (the token is
sealed now) matches its line by `UserKey` instead.

The process's `NODE_ENV` must agree: it is unset (the `local` default) or itself `local`, `ci` or `e2e`.
`getEnvironmentConfig()` answers a `NODE_ENV` that has no block in `config.env.ts` with the `local` block, so such a
stage used to claim `env: 'local'` and print the links. It prints nothing now — but it still runs on the `local`
block. Look for the boot line `Configured for: local (requested: <NODE_ENV>)`; if a deployed stage shows it, give
that `NODE_ENV` a block of its own. A starter-based project refuses to start in that state from the starter's 12.6.0
release on (§3).

## 2. An interrupted initial-admin setup is finished at the next boot

No action needed. The admin role is now written together with the user, and with `systemSetup.initialAdmin` set, the
boot finishes a setup that was killed halfway, for that address only:

- an administrator without any login account gets the configured password;
- the leftover of an older version (no role, no administrator in the system, and no account or only a credential
  account with the configured password) gets the role.

A user with another password, a social account, a second account or a legacy password (`users.password`) is never
touched, and the anonymous `POST /system-setup/init` still refuses once users exist. Remove the `initialAdmin`
variables after the first deployment to close this path too.

## 3. Starter: a NODE_ENV without a block in `config.env.ts` no longer starts

From the nest-server-starter release 12.6.0 on, a starter-based project refuses to start when `NODE_ENV` names an
environment that has no block in `src/config.env.ts`:

```
NODE_ENV='staging' has no block in src/config.env.ts (known: local, e2e, ci, develop, test, production, preview). Use one of them, or add a block for this env to the matrix.
```

Until now `getEnvironmentConfig()` answered such a `NODE_ENV` with the `local` block (`config[env] || config.local`).
A stage started with `NODE_ENV=development`, `dev`, `staging` or `preview` therefore ran on the local baseline: public
dummy secrets, the anonymous `POST /system-setup/init`, an open `GET /config`. The required-variable check never ran,
because it keys on the resolved env and the local block carries `env: 'local'` whatever `NODE_ENV` asked for.

The same starter release makes two more changes:

- The required-variable check runs for every env that is not local (`local`, `ci`, `e2e`), not only for `develop`,
  `test` and `production`.
- The starter gains a `preview` block on the deployed baseline, because the lt CLI writes `migrate:preview:up` into
  every project.

**Am I affected?**

- **A stage on an env without a block.** Its boot log shows `Configured for: local (requested: <NODE_ENV>)`.
- **A stage or job on `NODE_ENV=preview`.** It ran on the local block too (same boot line), `migrate:preview:up`
  included. After the takeover it runs on the new `preview` block.
- **A block of your own besides `develop`, `test` and `production`**, for example `staging`. Its boot line looks
  correct (`Configured for: staging`), but the required-variable check never ran for it. Now it does.

**What to do, before taking over the starter change:**

- For a stage on an env without a block, either set `NODE_ENV` to an env the matrix has (`develop`, `test`,
  `production`, `preview`), or add a block next to the others:
  `staging: deployedConfig('staging', { brandSuffix: 'Staging' }),`
- Any stage that moves off the local block, including one already on `NODE_ENV=preview`, needs every variable
  `.env.example` lists as required — and so does its `migrate:<env>:up` job, which loads the same config. On a fresh
  instance it also needs a first-admin route: the anonymous setup page is closed on every deployed block, so set
  `NSC__SYSTEM_SETUP__INITIAL_ADMIN__*`.
- For a block of your own, check that its stage sets every required variable. Otherwise it stops with
  `Missing required environment variables for NODE_ENV='<env>'`.
- On a developer machine, a shell that exports such a `NODE_ENV` (for example `development`) now stops `pnpm start`
  and `lt dev up` at their migrate step, which inherits the shell environment. Unset the variable or set it to `local`.

A project that keeps its own `config.env.ts` can copy the guard in front of `getEnvironmentConfig()` and the
`!isLocalEnv(resolved.env)` condition from nest-server-starter PR #59
(https://github.com/lenneTech/nest-server-starter/pull/59). The condition alone does not catch a `NODE_ENV` without a
block, because the resolved env is then `local`; the guard does.

## Compatibility Notes

| Pattern | Status |
|---|---|
| nuxt-base-starter `verify-email` page of the release that follows 12.6.0 | Uses the new endpoint |
| A page that reads the token's JWT payload (for example to show the address) | Gets nothing: the token is sealed. Use the masked `email` of the resend answer |
| A page that reads `route.query.email` for its resend button | Shows no button for an expired link until it uses the token (§1) |
| `POST /iam/send-verification-email` with `{ email }` | Unchanged — still the fallback when the user types the address |
| A project subclass of `CoreBetterAuthEmailVerificationService` | `buildFrontendVerificationUrl(token)` takes one argument; a second one is ignored |
| `systemSetup.initialAdmin` left set on a running deployment | Read at every boot; changes nothing for a finished setup (§2) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Expired link, no "send a new email" button | The page still waits for `?email=` | Send the token to `POST /iam/resend-verification-email` (§1) |
| The resend answers 200 but no mail arrives | The account is verified or unknown, the resend cooldown is active, or email verification is off | Intended: the answer never says which. Check the server log at debug level |
| `429` on the resend | 3 requests for one token, or 10 invalid tokens from one address, in an hour | Wait, or sign in and request a new mail |
| Log line `Finished an interrupted initial-admin setup` | A previous setup was killed halfway | Nothing to do; the administrator can sign in |
| `NODE_ENV='<env>' has no block in src/config.env.ts` at startup (starter-based project) | The stage ran on the `local` block until now | Set `NODE_ENV` to an env the matrix has, or add a block for it (§3) |
| `Missing required environment variables for NODE_ENV='<env>'` after the starter update | The check now covers every non-local env, `preview` and own blocks included | Set the variables `.env.example` lists as required (§3) |
