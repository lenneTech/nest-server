# Migration Guide: 12.8.1 → 12.8.2

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None. On a stage with `NODE_ENV=test` Better-Auth's origin and CSRF checks now run, as they always did elsewhere (§1) |
| **New Features** | None |
| **Bugfixes** | Security: on a stage with `NODE_ENV=test`, Better-Auth's origin check, CSRF check and `callbackURL` / `redirectTo` validation were off, so a password-reset mail could carry its token to a page the caller chose (§1). Documentation named `betterAuth.options.plugins` for custom plugins, which replaces the built-in ones (§2). A project's `betterAuth.options.user` replaced the framework's `user` block (§3). An address change that differed only in case ended every session (§4). One client could fill the IAM rate limiter's store with paths nobody serves, after which new clients were refused at their first sign-in (§5) |
| **Migration Effort** | Update. A test stage whose frontend origin is missing from `trustedOrigins` answers 403 `INVALID_ORIGIN` now, as production already does (§1). Plugins registered through `betterAuth.options.plugins` move to `betterAuth.plugins` (§2) |

12.8.2 is a security patch for 12.8.1. The same fix ships in 12.6.7 (`latest-12.6`) and 11.44.2 (`latest-11`).

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.2
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The origin check runs whatever the environment is called

**Why:** Better-Auth decides its origin check itself while `advanced.disableOriginCheck` is unset. Its `isTest()`
(`NODE_ENV === 'test'`, or a truthy `TEST` variable) switches the check off. With it go:

- the CSRF check (Better-Auth keeps them coupled for backward compatibility),
- the validation of `callbackURL`, `redirectTo`, `errorCallbackURL` and `newUserCallbackURL` against `trustedOrigins`.

The nest-server-starter names its deployed test stage `test`, so every such stage ran without these checks. The worst
consequence: `POST /iam/request-password-reset` is unauthenticated and took any `redirectTo`. The core's reset mail
(`betterAuth.emailVerification.passwordResetLink`, default since 11.38.0) uses the caller's `redirectTo` because
Better-Auth normally validates it first. A request for somebody else's address with
`redirectTo: 'https://attacker.example/reset'` therefore sent that person a genuine mail whose link carried a valid reset
token to the attacker's page.

**What changed:** for every config environment that is not `local`, `ci` or `e2e` (an unknown or missing one
included), the core passes `advanced.disableOriginCheck: false` to Better-Auth, so `NODE_ENV` no longer decides the check
there. `local`, `ci` and `e2e` keep Better-Auth's own decision: vitest sets `TEST=true`, so test suites still run without
the check, as before. A suite that wants it (CSRF, foreign origins, `redirectTo`) sets
`betterAuth.options.advanced.disableOriginCheck: false` itself, as `tests/better-auth-signin-csrf.e2e-spec.ts` does. A
project that sets `betterAuth.options.advanced.disableOriginCheck` keeps its own value; an explicitly `undefined` value
counts as not set. While a project switches the check off (`true`, or a list of paths),
the core's reset mail no longer takes the caller's `redirectTo` at all and links to the default page
(`<appUrl>/auth/reset-password`), because nothing validated the URL.

**Who was affected:** every project with Better-Auth that ran a deployed stage with `NODE_ENV=test` or a truthy `TEST`
variable. Stages with `NODE_ENV=develop` or `production` were not affected.

**Your project:** update. Then check:

- **Frontend origins of the test stage.** A browser request that carries cookies is checked against `trustedOrigins`
  now. If the test stage's frontend runs on an origin the configuration does not name (`appUrl`, `cors.allowedOrigins`,
  `betterAuth.trustedOrigins`), sign-in through Better-Auth's own routes, 2FA and passkeys answer 403 `INVALID_ORIGIN`
  there. Production behaves this way already; add the origin to the same setting.
- **Password resets on test stages.** A reset link requested while the stage ran an affected version may have carried
  its token to a foreign page. Whoever held the token could set a new password, so ending sessions alone does not
  lock them out again. Where test stages hold accounts that matter, take the time the stage ran an affected version as
  the window, and for every account whose password changed in it:
  - make the password unusable and have the owner set a new one through a reset on the fixed version;
  - remove what was added in the window: passkeys, 2FA enrolments, a changed e-mail address, API tokens;
  - then end its sessions.

  What shows such a reset: `POST /iam/reset-password` in the access logs, and credential accounts (`account`,
  `providerId: 'credential'`) whose `updatedAt` falls in the window. The `redirectTo` itself is a body field, which
  access logs do not record, and Better-Auth logged nothing for it while the check was off.

## 2. Documentation: custom Better-Auth plugins belong in `betterAuth.plugins`

The descriptions of `emailAndPassword.disableSignUp` (interface, README, guide 12.2.x → 12.3.x) named
`betterAuth.options.plugins` as the place for a project's own plugins. The framework appends `betterAuth.plugins` to its
own (JWT, 2FA, passkey). `betterAuth.options` is spread over the generated configuration, so `options.plugins`
**replaces** that list, and JWT, 2FA and passkey stop working without an error.

**Your project:** if you register plugins through `betterAuth.options.plugins`, move them to `betterAuth.plugins`. A
plugin that creates users itself (Magic Link, Generic OAuth) does not follow `emailAndPassword.disableSignUp`. Give it
its own option, for example `magicLink({ disableSignUp: true, … })`.

## 3. `betterAuth.options.user` is merged

The framework gives Better-Auth `user: { modelName: 'users', additionalFields }`. That is the collection or table it
shares with the user model, plus the fields `betterAuth.additionalUserFields` declares, among them the `input: false` locks
on `roles`, `verified` and `twoFactorEnabled`. `betterAuth.options` was spread over that configuration, so a project
that set `options.user` for its own reason (`changeEmail`, `deleteUser`) replaced the whole block. Better-Auth then read
and wrote a `user` collection the framework never sees, and knew none of the additional fields.

**What changed:** `options.user` is merged. `modelName` stays `users` unless the project names another one. A project
field of the same name as a framework field does not replace it; change those through `betterAuth.additionalUserFields`.
A project field under another name that maps to a locked column (`fieldName: 'roles'`) is locked as well.

**Your project:** nothing, unless you set `betterAuth.options.user`. Then check whether a `user` collection or table holds
records written while the options were replaced.

## 4. An address that differs only in case is no change

`CoreUserService.update()` syncs an address change to IAM, and that sync ends every session of the account. It compared
the stored address with the submitted one as typed, while the address is stored trimmed and in lower case. A profile
form sending `Foo@Example.com` back for `foo@example.com` therefore signed the user out everywhere without changing
anything. The comparison now uses the stored form. Nothing to do.

## 5. The IAM rate limiter keys its counters by a bounded set of names

Only with `betterAuth.rateLimit` configured (the nest-server-starter reads `IAM_RATE_LIMIT_MAX`). Since 12.3.0 a
counter was keyed by the last segment of the path as sent, and the limiter runs for every path under the base path,
existing or not. One client sending `/iam/x1`, `/iam/x2`, … created one counter per request, and none of them reached the
limit. Once the store held `maxEntries` counters (10,000 by default, the Redis store likewise), every new client fell
into the shared overflow buckets the attacker had filled, and was refused at its first sign-in.

**What changed:** a counter is keyed by a route name the base path serves (taken from the running Better-Auth instance and
the controller, so plugin routes are included), by the matching strict entry for a strict route under an unknown name
(`/reset-password/<token>`), or by one `other` counter per client for everything else. Real routes keep their counters
as before: `/sign-in/email` and `/sign-up/email` still share one, `/get-session` and `/two-factor/enable` still have one
each. Nothing to do.
