# Migration Guide: 12.8.1 → 12.8.2

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None. On a stage with `NODE_ENV=test` Better-Auth's origin and CSRF checks now run, as they always did elsewhere (§1) |
| **New Features** | None |
| **Bugfixes** | Security: on a stage with `NODE_ENV=test`, Better-Auth's origin check, CSRF check and `callbackURL` / `redirectTo` validation were off, so a password-reset mail could carry its token to a page the caller chose (§1). Documentation named `betterAuth.options.plugins` for custom plugins, which replaces the built-in ones (§2) |
| **Migration Effort** | Update. A test stage whose frontend origin is missing from `trustedOrigins` answers 403 `INVALID_ORIGIN` now, as production already does (§1). Plugins registered through `betterAuth.options.plugins` move to `betterAuth.plugins` (§2) |

12.8.2 is a security patch for 12.8.1. The same fix ships in 12.6.7 (`latest-12.6`) and 11.44.2 (`latest-11`).

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.2
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The origin check runs whatever the environment is called

**Why:** Better-Auth decides its origin check itself while `advanced.disableOriginCheck` is unset. Its `isTest()`
(`NODE_ENV === 'test'`, or a truthy `TEST` variable) switches the check off. With it go:

- the CSRF check (Better-Auth keeps them coupled for backward compatibility),
- the validation of `callbackURL`, `redirectTo`, `errorCallbackURL` and `newUserCallbackURL` against `trustedOrigins`.

The nest-server-starter names its deployed test stage `test`, so every such stage ran without these checks. The worst
consequence: `POST /iam/request-password-reset` is unauthenticated and took any `redirectTo`. The core's reset mail
(`betterAuth.emailVerification.passwordResetLink`, default since 11.38.0) uses the caller's `redirectTo` because
Better-Auth normally validates it first. A request for somebody else's address with
`redirectTo: 'https://attacker.example/reset'` therefore sent that person a genuine mail whose link carried a valid reset
token to the attacker's page.

**What changed:** for every config environment that is not `local`, `ci` or `e2e` (an unknown or missing one
included), the core passes `advanced.disableOriginCheck: false` to Better-Auth, so `NODE_ENV` no longer decides the check
there. `local`, `ci` and `e2e` keep Better-Auth's own decision: vitest sets `TEST=true`, so test suites still run without
the check, as before. A suite that wants it (CSRF, foreign origins, `redirectTo`) sets
`betterAuth.options.advanced.disableOriginCheck: false` itself, as `tests/better-auth-signin-csrf.e2e-spec.ts` does. A
project that sets `betterAuth.options.advanced.disableOriginCheck` keeps its own value; an explicitly `undefined` value
counts as not set. While a project switches the check off (`true`, or a list of paths),
the core's reset mail no longer takes the caller's `redirectTo` at all and links to the default page
(`<appUrl>/auth/reset-password`), because nothing validated the URL.

**Who was affected:** every project with Better-Auth that ran a deployed stage with `NODE_ENV=test` or a truthy `TEST`
variable. Stages with `NODE_ENV=develop` or `production` were not affected.

**Your project:** update. Then check:

- **Frontend origins of the test stage.** A browser request that carries cookies is checked against `trustedOrigins`
  now. If the test stage's frontend runs on an origin the configuration does not name (`appUrl`, `cors.allowedOrigins`,
  `betterAuth.trustedOrigins`), sign-in through Better-Auth's own routes, 2FA and passkeys answer 403 `INVALID_ORIGIN`
  there. Production behaves this way already; add the origin to the same setting.
- **Password resets on test stages.** A reset link requested while the stage ran an affected version may have pointed
  at a foreign page. Where test stages hold accounts that matter, end the sessions of accounts whose password was reset
  in that time and look at the access logs for `POST /iam/request-password-reset` with a `redirectTo` outside your
  origins.

## 2. Documentation: custom Better-Auth plugins belong in `betterAuth.plugins`

The descriptions of `emailAndPassword.disableSignUp` (interface, README, guide 12.2.x → 12.3.x) named
`betterAuth.options.plugins` as the place for a project's own plugins. The framework appends `betterAuth.plugins` to its
own (JWT, 2FA, passkey). `betterAuth.options` is spread over the generated configuration, so `options.plugins`
**replaces** that list, and JWT, 2FA and passkey stop working without an error.

**Your project:** if you register plugins through `betterAuth.options.plugins`, move them to `betterAuth.plugins`. A
plugin that creates users itself (Magic Link, Generic OAuth) does not follow `emailAndPassword.disableSignUp`. Give it
its own option, for example `magicLink({ disableSignUp: true, … })`.
