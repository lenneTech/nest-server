# Migration Guide: 11.42.6 → 11.42.7

## Overview

| Category             | Details                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| **New Feature**      | `setupSwagger()` — a Swagger document that says how each route is reached: security, API-token scopes, tenant header (§1) |
| **New Feature**      | Optional second document with only the routes an API token may call (§2)                                        |
| **Dependencies**     | `nodemailer` 10.0.15, `@modelcontextprotocol/sdk` 1.32.1, dev: `oxlint` 1.87.0 (§3)                             |
| **Breaking Changes** | None                                                                                                            |
| **Migration Effort** | Optional. Switching `main.ts` to the helper replaces the hand-built `DocumentBuilder` block with one call        |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Nothing changes until `main.ts` calls the new helper. Vendor-mode projects pick it up with the core
update.

## 1. `setupSwagger()` instead of a hand-built `DocumentBuilder`

The starters built the document like this:

```typescript
const config = new DocumentBuilder().setTitle('…').addBearerAuth().build();
SwaggerModule.setup('swagger', server, () => SwaggerModule.createDocument(server, config, { … }), {
  jsonDocumentUrl: '/api-docs-json',
});
```

`addBearerAuth()` registers a scheme but attaches it to no route. A token entered under "Authorize" is
therefore sent with almost no request: in one project 10 of 158 operations carried a security entry.
And what a caller needs to know — is the route public, which API-token scope does it release, does it
read the tenant header — lived only in decorators.

```typescript
import { setupSwagger } from '@lenne.tech/nest-server';

setupSwagger(server, {
  description: 'API of my project',
  documentOptions: {
    extraModels: [CoreUserModel, CoreAuthModel, User, PersistenceModel, CorePersistenceModel, FilterArgs],
  },
  title: 'My Project API',
  version: packageJson.version,
});
```

Paths stay as before (`/swagger`, `/api-docs-json`) unless `path` / `jsonDocumentUrl` say otherwise.
What the document now contains, read from the same metadata the guards read:

| Feature in the config | In the document |
| --- | --- |
| always | `bearer` as a global security requirement — "Authorize" applies to every route. Public routes (no `@Roles`, or `S_EVERYONE`) carry `security: []` |
| `betterAuth` + `cookies` on | the session cookie (`iam.session_token`, or the name `COOKIE_PREFIX` / `basePath` produce) as a second, alternative requirement |
| `apiTokens` on | per operation `x-api-token-scopes` and a description line: "allowed with scope `read`" or "not allowed on this route". `@ApiTokenScopes()` on the method replaces the class declaration, exactly as in `assertApiTokenScopes()` |
| `multiTenancy` on | a reusable `TenantHeader` parameter (`X-Tenant-Id`, or `multiTenancy.headerName`) on every operation except public ones and `@SkipTenantCheck()`; its description says which callers need it (sessions and personal tokens) and which may omit it (company tokens) |

Optional:

- `operationTags: (operation) => string[] | undefined` regroups operations by use case instead of by
  controller; `tags: [{ name, description }]` orders and describes them.
- `configureBuilder: (builder) => builder` adds servers, contact or further schemes.
- `customOptions` is passed to `SwaggerModule.setup()` for both documents.

Each operation is mapped to its handler through the default operation id (`<Controller>_<method>`, with
`[<n>]` for a handler serving several paths). An own `operationIdFactory` is therefore refused. Two different controller classes with the same name
cannot be told apart; their operations are left as Swagger built them, with a warning.

## 2. A document for API-token callers

```typescript
setupSwagger(server, { …, apiTokenView: true });
// or: apiTokenView: { path: 'swagger-partner', title: 'Partner API' }
```

Serves a second document (default: UI `swagger-api-tokens`, JSON `/api-docs-api-tokens-json`) with only
the operations that release a scope, the bearer scheme as the only requirement and without the schemas
nothing refers to any more. Keep its path outside the path of the full UI, which serves its assets below
its own path.

The tenant header stays in this view while personal (user) tokens are enabled (`apiTokens.userTokens`,
the default): such a token without a company restriction chooses the company like a session does, and
without the header it is checked against its global roles and refused on company routes. With company
tokens only (`userTokens: false`) the header is dropped — a company token carries its company.

## 3. Dependency updates

Patch-level maintenance, no code changes required:

| Package | Old | New | Section |
| --- | --- | --- | --- |
| `nodemailer` | 10.0.14 | 10.0.15 | dependencies |
| `@modelcontextprotocol/sdk` | 1.32.0 | 1.32.1 | dependencies |
| `oxlint` | 1.86.0 | 1.87.0 | devDependencies |

A project that pins `oxlint` itself should raise it to 1.87.0 alongside the framework —
`pnpm run update` in starter-based projects does this. A project that carries a `nodemailer`
override matching the framework's version (the starter does) should raise it to `10.0.15`.

## Compatibility Notes

- The helper is additive. `DocumentBuilder` + `SwaggerModule.setup()` keep working unchanged.
- The document is built on the first request, as before.
- `buildSwaggerDocument()` and `buildApiTokenSwaggerDocument()` are exported for tests: a project can
  assert in its e2e suite that a route documents the scope it enforces.
