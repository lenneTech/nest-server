# Migration Guide: 11.41.7 → 11.41.8

## Overview

| Category              | Details                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- |
| **Security**          | better-auth 1.7.7 is now the minimum — critical account takeover in < 1.7.7 (§1)                |
| **Breaking Changes**  | None at runtime: 11.41.8 still works on better-auth 1.7.1 (§2). The peer floor rises to 1.7.7, so pnpm reports an unmet peer until you raise the pins |
| **Data**              | Nothing to migrate. The boot drops one index that better-auth 1.7.0–1.7.2 left behind (§2)        |
| **Tooling**           | The override guard reports unused overrides; husky and its hooks are gone (§3)                  |
| **Migration Effort**  | Raise three pins in the API — and two in the app of a fullstack project, in the same change     |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm add better-auth@1.7.7 @better-auth/passkey@1.7.7 @better-auth/core@1.7.7
pnpm run build && pnpm test
```

Fullstack projects raise the app in the same change — `@lenne.tech/nuxt-extensions` 1.18.4 and
`better-auth` / `@better-auth/passkey` 1.7.7 in `projects/app` — see §1.

Vendor-mode projects pick up the core update, and raise the same pins.

## What's New in 11.41.8

### 1. better-auth 1.7.7 is the minimum

[GHSA-965c-763c-88jm](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm)
(critical): an OAuth state value can be used as a Magic Link to sign in as another user. It covers
`better-auth >= 1.4.0-beta.18, < 1.7.7`; 1.7.7 is fixed. A project is exposed when it registers the
`magicLink` plugin — through `betterAuth.options.plugins` — next to a social or Generic OAuth
provider, with OAuth state stored in the database (the default when a database is configured). An
attacker who knows a user's email address then gets a normal session for that user, without access
to the mailbox.

At the time of writing the advisory lives only in better-auth's own repository, not yet in the
database `pnpm audit` reads, so **your audit does not report it**. Do not wait for it to.

The framework's peer range is now `>=1.7.7 <1.8.0` for `better-auth`, `@better-auth/passkey` and
`@better-auth/core` (the floor is forced anyway: `@better-auth/passkey` 1.7.7 itself requires
`better-auth ^1.7.7`). A project still on 1.7.1 gets an unmet-peer warning, and stays vulnerable
if it uses Magic Link.

**What to do:**

```bash
# projects/api (or a standalone API)
pnpm add better-auth@1.7.7 @better-auth/passkey@1.7.7 @better-auth/core@1.7.7

# projects/app of a fullstack project — in the SAME change
pnpm add @lenne.tech/nuxt-extensions@1.18.4 better-auth@1.7.7 @better-auth/passkey@1.7.7
```

API and app must resolve the same better-auth version: they speak one protocol, and a split
breaks flows like 2FA activation with errors that name neither side. In a monorepo,
`check-workspace-consistency` fails the check when they differ.

Upstream's upgrade note for 1.7.7, worth passing on to whoever deploys: upgrade every server that
shares verification storage at the same time, have users request new Magic Links, and expect
OAuth / SAML sign-ins that were in progress during the deploy to need a restart. No database
migration is required. Custom `verification.storeIdentifier.overrides` rules, and storage code that
inspects verification identifiers, must now expect the `magic-link:` and `auth-state:` prefixes.

### 2. better-auth dropped its issuer schema again — what that means for your data

better-auth 1.7.0 keyed accounts by `(issuer, accountId)`, and nest-server 11.37–11.41.7 followed:
every account it wrote carried an `issuer`, and the boot backfilled it on older rows. better-auth
1.7.3 restored the 1.6 schema — accounts keyed by `(providerId, accountId)` — and no longer reads or
writes the field. 11.41.8 follows whichever line is INSTALLED, so the upgrade stays compatible in
both directions:

| You run | nest-server 11.41.8 does |
| ------- | ------------------------ |
| better-auth 1.7.7 (the target) | writes no `issuer`; on boot drops the unique `(issuer, accountId)` index better-auth 1.7.0–1.7.2 left behind, and forgets the old backfill marker |
| better-auth 1.7.1 (pins not raised yet) | behaves exactly like 11.41.7: writes the `issuer`, runs the backfill. Still vulnerable (§1) — raise the pins |

**Why the index has to go.** With the field no longer written, the index treats every new account
as having the same, missing issuer, so a user who holds the same account ID at two providers can no
longer link the second one. MongoDB has no `NOT NULL`, so dropping the index is the whole cleanup —
upstream's 1.7 upgrade guide says the same. The log shows it once:
`Dropped the unique index "account_issuer_accountId_uidx" on account(issuer, accountId)`.

**Existing `issuer` values stay.** better-auth 1.7.3+ ignores them, and keeping them is what makes a
rollback safe.

**Rolling back to 11.41.7** (better-auth 1.7.1) works for password users: that version's backfill
runs again on boot — 11.41.8 deleted its completion marker for exactly this — and gives the issuer
back to every credential account written in the meantime. better-auth recreates its index on first
use. Social accounts LINKED while on 11.41.8 stay without an issuer; 11.41.7 reports them at boot,
and they need the issuer set per provider before their next social sign-in.

**Vendor mode on better-auth 1.7.1** builds as well: the core compiles against both lines.

**Code that imported `createLocalAccountIssuer`** from `@better-auth/core/db` stops compiling with
better-auth 1.7.3+, which removed it. Remove the call; accounts no longer carry an issuer.

### 3. Tooling (this repository)

- **The override guard reports unused overrides again.** `scripts/check-overrides.mjs` searched the
  whole lockfile, where pnpm echoes every override into a top-level `overrides:` block — so an
  override whose package had left the tree still counted as "in the tree". It now reads only the
  resolved part. A project that copied the guard (nest-server-starter ships it since 11.41.7) may
  see new `UNUSED` lines after updating it: warnings, not failures — remove the dead entry.
- **husky is gone.** Its `prepare` script had been removed in 2024, so the hooks never ran; the
  `check` script is the gate. `.husky/`, `.lintstagedrc.json`, `extras/sync-version.ts` and the
  devDependencies `husky` and `find-file-up` (used only by that hook) were removed. Nothing ships
  in the package from any of them.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| `better-auth` / `@better-auth/*` pinned at 1.7.1 | Unmet peer — raise to 1.7.7 (§1) |
| API on 1.7.7, app still on 1.7.1 | Breaks auth flows — raise both in one change (§1) |
| `magicLink` plugin with an OAuth provider, on < 1.7.7 | Account takeover — raise now (§1) |
| nest-server 11.41.8 with better-auth still at 1.7.1 | Works as before (§2); unmet-peer warning, still vulnerable |
| Rollback to 11.41.7 after upgrading | Works — the backfill runs again (§2) |
| Own code calling `createLocalAccountIssuer` | Remove it — gone in better-auth 1.7.3+ (§2) |

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| `unmet peer better-auth@">=1.7.7 <1.8.0": found 1.7.1` | Old pin | `pnpm add better-auth@1.7.7 @better-auth/passkey@1.7.7 @better-auth/core@1.7.7` |
| 2FA activation or passkey sign-in fails with a generic client error after updating | API and app on different better-auth versions | Pin the same version in both |
| `check-workspace-consistency` fails on better-auth | Same | Same |
| New `UNUSED` lines from `check:overrides` | The guard sees dead overrides now (§3) | Remove the entry it names |
| `Could not drop the legacy unique (issuer, accountId) index` at boot | The database user may not drop indexes | `db.account.dropIndex("account_issuer_accountId_uidx")` once, by hand |
| `E11000 duplicate key … account_issuer_accountId_uidx` when linking an account | The legacy index is still there | Same |
