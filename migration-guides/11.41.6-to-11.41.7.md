# Migration Guide: 11.41.6 → 11.41.7

## Overview

| Category              | Details                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------- |
| **Breaking Changes**  | None in npm mode. Vendor mode: one package to install (§1)                                  |
| **Bugfixes**          | Uploads to S3 are no longer read into memory — a large upload could OOM-kill the container. A known length above 5 GiB (TUS) no longer fails on AWS S3. MCP clients reconnect on their own after a restart (§4) |
| **New optional peer** | `@aws-sdk/lib-storage` — uploads of unknown length go to S3 in parts                        |
| **New field**         | `FileUploadSource.size` — the exact file length, when the caller knows it                   |
| **Migration Effort**  | `pnpm run update` (raises the `@nestjs/*` pins, §6). Projects using the S3 driver: install one package. Starter-based projects: assess two dev-only advisories (§5) |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm run update            # starter-based projects: raises the @nestjs/* pins to 11.2.7 (§6)
pnpm add @aws-sdk/lib-storage@<your @aws-sdk/client-s3 version>   # only with file.storage 's3'
pnpm run build && pnpm test
```

**Vendor-mode projects must install it, whether they use S3 or not.** The vendored core is compiled
as project code, and `core-s3.service.ts` now references the types of `@aws-sdk/lib-storage` — the
same way it already references `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`. Without the
package the typecheck fails with `Cannot find module '@aws-sdk/lib-storage'`. A project converted to
vendor mode from now on gets it from the CLI's import scan; the core update of an EXISTING vendor
project does not add packages, so add it there yourself, next to `@aws-sdk/client-s3`, at the same
version.

## What's New in 11.41.7

### 1. Uploads reach S3 as a stream

Until now the S3 driver read every upload into a Buffer before sending it: `createFile()` did so for
every GraphQL and multer upload, and `CoreS3Service.putObject()` for every stream without a length.
The memory cost of an upload was therefore its size. A multi-GB file threw
`Array buffer allocation failed` or got the container OOM-killed at 100 % progress — taking every
other request on that replica with it.

Now nothing on that path buffers:

| Length | Request | Memory |
| ------ | ------- | ------ |
| known, up to 5 GiB — `size` on the upload, a TUS upload, a buffer | one streamed `PutObject` | constant |
| known, above 5 GiB | multipart upload via `@aws-sdk/lib-storage` | at most four parts |
| unknown — every GraphQL and streamed REST upload | multipart upload via `@aws-sdk/lib-storage` | at most four 5 MiB parts |
| `@aws-sdk/lib-storage` not installed | as before: an unknown length is read into memory, a known one is one `PutObject` | the file's size (unknown length) |

The second row is a fix in its own right: AWS S3 refuses a single `PutObject` above 5 GiB
(`EntityTooLarge`). A TUS upload that large — the default `tus.maxSize` is 50 GiB — used to fail at
finalization, after the client had sent every byte, on every retry. MinIO and RustFS accept such a
request, which is why test setups never showed it.

The length recorded for an upload of unknown length is read back from the stored object.

**What to do:** with `file.storage: 's3'` (or an `s3` config that makes it the derived driver),
install `@aws-sdk/lib-storage` at the same version as your `@aws-sdk/client-s3`:

```bash
pnpm add @aws-sdk/lib-storage@3.1145.0   # match your @aws-sdk/client-s3
```

Without it nothing breaks — uploads keep the previous behaviour, and the boot log says once:

```
Streaming an S3 upload of unknown length falls back to buffering it in memory because the optional
peer dependency "@aws-sdk/lib-storage" is not installed. Run: pnpm add @aws-sdk/lib-storage
```

Use an S3-compatible store that supports multipart uploads (AWS S3, MinIO and RustFS do). Give the
bucket a lifecycle rule that aborts incomplete multipart uploads: a failed upload is aborted by the
framework, but a process killed mid-upload leaves its parts behind, and S3 keeps them until something
removes them.

### 2. `FileUploadSource.size`

A caller that knows the file's EXACT length can say so, and the S3 driver then uses one streamed
request instead of a multipart upload (up to 5 GiB; above that it stays a multipart upload, with
parts sized to the total):

```typescript
await fileService.createFile({
  createReadStream: () => createReadStream(path),
  filename,
  mimetype,
  size: (await stat(path)).size,
});
```

Leaving it out is always safe — it only costs the multipart round trips — and for data that is
already in memory it is the better choice: the multipart path sends Buffer parts, which the SDK
retries after a transient S3 error, while one streamed request is attempted once.
`multerFileToUpload()` therefore does not set it.

**Never pass the `Content-Length` of a multipart/form-data request.** It counts the whole envelope
(boundaries, part headers, other fields) and is always larger than the file, and a wrong length
breaks the upload. Anything but a positive integer is treated as unknown.

### 3. `CoreS3Service.statObject()`

New: size and content type of an object, or `null` when it does not exist — one HEAD request.
`objectExists()` now delegates to it.

### 4. MCP clients recover from a restart

`/ai/mcp` keeps its sessions in process memory, so every restart — every deploy — forgets the
session ids its clients still hold. A request carrying such an id used to get a fresh transport,
which answered the client's next call (a `tools/call`, never an `initialize`) with
`400 Bad Request: Server not initialized`. Clients do not recover from a 400: every connected
client stayed dead until somebody reconnected it by hand.

Such a request now gets **404** `Unknown or expired MCP session` — the status the MCP specification
tells clients to answer with a new `initialize`, and what the SDK's own server returns. An
`initialize` carrying a stale id still starts a new session. With `redis` configured, a session
that lives on another replica of the same user still answers **409**, as before.

Nothing to do. A client or proxy that treated the old 400 as "session gone" sees 404 instead.

### 5. Two advisories without a fix in the dev tooling

Two HIGH advisories surfaced in the audit on 2026-10-03, and neither has a patched release
anywhere yet:

| Advisory | Package | Reaches a project through |
| -------- | ------- | ------------------------- |
| GHSA-ch52-4w7c-c8xp | `http-cache-semantics` <= 4.2.0 | `@swc/cli` (also via `@nestjs/cli`) — its binary downloader |
| GHSA-vfj7-8cjw-p6xm | `braces` <= 3.0.3 | `nodemon` > `chokidar@3`; `cpy-cli` > `micromatch` |

Both paths are dev tooling, and no override can help while no fixed version exists. So
`pnpm audit` — and every `check` that runs it — is red in a starter-based project until you
assess them.

**What to do:** confirm neither package is in your production tree
(`pnpm why http-cache-semantics --prod`, `pnpm why braces --prod` — both must print nothing),
then suppress them in `pnpm-workspace.yaml` with the reasoning next to each entry. The starter's
file shows the shape:

```yaml
auditConfig:
  ignoreGhsas:
    - GHSA-ch52-4w7c-c8xp   # http-cache-semantics, dev-only via @swc/cli
    - GHSA-vfj7-8cjw-p6xm   # braces, dev-only via nodemon / cpy-cli
```

A suppression hides the advisory everywhere and for good, so nest-server-starter 11.41.7 also
ships the two guards that keep one honest: `scripts/check-overrides.mjs` (wired into `check` as
`check:overrides`; it fails once a patched version exists) and
`tests/unit/audit-suppression-scope.spec.ts` (fails once a suppressed package reaches the
production tree). Copy both along with the entries. A project generated as a monorepo already
has the first one at its root, from lt-monorepo.

### 6. Dependency updates

| Package | 11.41.6 | 11.41.7 |
| ------- | ------- | ------- |
| `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express` | 11.2.6 | **11.2.7** |
| dev: `@nestjs/testing` | 11.2.6 | 11.2.7 |
| dev / optional peers: `@aws-sdk/client-s3`, `@aws-sdk/lib-storage` (new), `@aws-sdk/s3-request-presigner` | 3.1143.0 | 3.1145.0 |
| dev: `@swc/core`, `@types/node`, `bullmq`, `vite` | 1.16.12, 26.6.3, 6.3.10, 8.3.1 | 1.16.13, 26.6.4, 6.3.11, 8.3.2 |

**Raise the `@nestjs/*` pins together with the framework.** Starter-based projects:
`pnpm run update` does it. A project that pins them itself must move all four to 11.2.7 — a
project still on 11.2.6 next to the framework's 11.2.7 gets two copies of `@nestjs/common`, and
then `CronJobs extends CoreCronJobs` stops type-checking with an error that does not name the cause.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| GraphQL / multer uploads with the S3 driver | Streamed — multipart with `@aws-sdk/lib-storage`, buffered without it |
| `CoreS3Service.putObject(key, stream)` without a length | Same as above |
| `CoreS3Service.putObject(key, stream, type, length)` | Unchanged up to 5 GiB: one streamed `PutObject`. Above: multipart (with `@aws-sdk/lib-storage`) |
| TUS uploads | Unchanged up to 5 GiB. Above, on AWS S3: fixed — they failed at finalization with `EntityTooLarge`, now multipart (with `@aws-sdk/lib-storage`) |
| GridFS and filesystem drivers | Unchanged — they always streamed |
| A subclass overriding `CoreS3Service.collect()` | Called only when `@aws-sdk/lib-storage` is missing |
| `@nestjs/common` / `core` / `platform-express` / `testing` pinned at 11.2.6 | Raise to 11.2.7 with the framework (§6) |
| An MCP request with a session id the process no longer knows | 404 instead of 400 — the client re-initializes (§4) |
| `pnpm audit` red on GHSA-ch52-4w7c-c8xp / GHSA-vfj7-8cjw-p6xm | No fix exists yet; dev-only — suppress with the guards (§5) |

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| Boot warning about `@aws-sdk/lib-storage` | The optional peer is not installed | `pnpm add @aws-sdk/lib-storage` |
| Peer warning: `@aws-sdk/lib-storage` wants a newer `@aws-sdk/client-s3` | The two packages are on different AWS SDK releases | Install both at the same version |
| S3 upload fails or never completes when `size` is passed | `size` is not the file's length — e.g. a request's `Content-Length` | Pass the file's own length, or leave `size` out |
