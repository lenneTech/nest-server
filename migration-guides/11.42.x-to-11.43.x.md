# Migration Guide: 11.42.x → 11.43.x

## Why this is a MINOR

Per `.claude/rules/versioning.md` the MAJOR mirrors NestJS, so **MINOR is where breaking changes
live**. Two behaviour changes can turn a call that used to succeed into a refusal: a browser sign-in
or sign-up from an origin Better-Auth does not trust now answers **403** in every project (§5), and
with `ai.mcp.oauth` enabled a deployed environment without a signing secret or without `baseUrl`
now fails the boot instead of signing tokens with the public development key (§1, §4). So this is
`11.43.0` rather than a patch.

**Projects whose frontends sign in from `appUrl` or an origin in `cors.allowedOrigins`, and that do
not use `ai.mcp.oauth`, see no behaviour change.** Server-side clients (scripts, seeders, SSR
routes, API tests) are not affected either (§5).

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. **Every project:** check that each browser origin that signs in is
trusted (§5). **With `ai.mcp.oauth: true`:** also §1 and §4.

## 1. The MCP OAuth endpoints are mounted by `CoreModule`

The OAuth 2.1 endpoints for MCP clients (`/.well-known/oauth-authorization-server`,
`/.well-known/oauth-protected-resource/ai/mcp`, `/authorize`, `/token`, `/register`) are an Express router. The
documentation said to mount it in `main.ts` **after** `app.init()`:

```typescript
// main.ts — what the documentation prescribed until 11.42.16
await app.init();
await mountAiMcpOAuth(app);
```

That never worked in a Nest application. Nest registers its not-found handler inside `app.init()`; a router added
afterwards sits behind it and is never reached. Every OAuth endpoint answered Nest's 404, so no MCP client could
discover the server, register or get a token.

Since 11.43.0 `CoreAiMcpOAuthInitializer` (registered by `CoreAiModule` together with the MCP endpoint) mounts the
router during `app.init()` whenever `ai.mcp.oauth` is `true`: behind every Nest middleware (security headers, request
context, CORS) and the Nest routes, ahead of the not-found handler. It needs no `main.ts` code and works the same
under `Test.createTestingModule()`. Guards and interceptors do not run for it — the SDK's handlers authenticate the
client and rate-limit per IP themselves.

```typescript
// main.ts — remove the call; it is a no-op now and logs that it can go
await mountAiMcpOAuth(app);
```

The protected MCP resource is described at the path Nest registered `/ai/mcp` at — global prefix and its exclusions,
URI versioning and a `RouterModule` path included. The issuer is the server's `baseUrl`, or the new
`ai.mcp.oauthBaseUrl` when MCP clients reach the server under another URL (its origin is added to Better-Auth's
trusted origins automatically, so the consent page can sign users in there; it replaces the `baseUrl` option of
`mountAiMcpOAuth()`, which is ignored with a warning once the router is mounted).

**What to check:**

- **A deployed environment without `baseUrl` now fails the boot** when `ai.mcp.oauth` is `true` — before, only the
  `mountAiMcpOAuth()` call failed. Set `NSC__BASE_URL` (or `ai.mcp.oauthBaseUrl`). `local` / `ci` / `e2e` keep the
  `http://localhost:3000` default.
- **The endpoints now exist.** With `ai.mcp.oauth: true`, dynamic client registration (`/register`) is reachable,
  rate-limited per IP by the SDK — configure `trustProxy` behind a proxy, or all clients share one bucket — and so is
  the consent page (§4): users can now authorize MCP clients.
- **CORS.** A project's `enableCors()` runs before the router, so a browser-based MCP client on an origin it does not
  allow is refused at the preflight. Native clients (Claude Code, Claude Desktop) are unaffected.
- **Express only.** `ai.mcp.oauth` on another HTTP adapter fails the boot with a named error.
- **A route of your own at `/token`, `/register` or `/authorize`** now wins over the OAuth router, which comes after
  the Nest routes.

## 2. Refusals answer `400 invalid_grant`, not `500`

The SDK's handlers answer an error with its OAuth code only when it is one of the SDK's own `OAuthError` classes;
anything else becomes `500 server_error`. The provider refused with plain `Error('invalid_grant')`, so an unknown,
rotated or foreign refresh token, or a code issued to another client, was answered with a 500. MCP clients discard
their stored tokens only on `invalid_grant`: on a 500, Claude Code kept the dead token, retried the refresh on every
start and never asked the user to sign in again.

Now: `invalid_grant` (400) for refresh tokens and codes, `invalid_client` for a missing client, `invalid_token` from
`verifyAccessToken`, and `access_denied` when an API token tries to approve a consent (the client is redirected back
with `error=access_denied` instead of `server_error`). `verifyAccessToken` also returns `expiresAt`, which the SDK's
bearer middleware requires. A code presented by another client is no longer deleted on the way to the refusal: the
exchange consumes only a code issued to the presenting client (`consumeAuthorizationCode(code, clientId)`), so the
owner can still redeem it.

**What to check:** code that matched the error MESSAGE (`/invalid_grant/`) — the code is in `error.errorCode` now, the
message is a description. An `authorizeConsent()` of your own must refuse the same way:

```typescript
const { AccessDeniedError } = await this.loadOAuthErrors();
throw new AccessDeniedError('The user declined');
```

## 3. The MCP 401 points at the metadata document

`POST /ai/mcp` without credentials answered `WWW-Authenticate: Bearer resource_metadata="<request host>/ai/mcp"` — the
endpoint itself, built from the caller-controlled `Host` header. RFC 9728 §5.1 wants the URL of the protected resource
METADATA. It is now exactly the document the mounted router serves
(`https://api.example.com/.well-known/oauth-protected-resource/ai/mcp`), and a plain `Bearer` without OAuth, where no
such document exists.

**What to check:** a test or client that parsed the old header value.

## 4. A built-in consent page

`/authorize` needs a consent step: the page on which a user decides whether an MCP client may act for them. The
documentation told projects to override `authorizeConsent()` for it, but `CoreAiModule` offered no way to register a
subclass, so no project had one and no authorization could ever complete. The framework now brings the page itself:

- **Nobody signed in** → e-mail + password and the two-factor step (TOTP or backup code), against Better-Auth's own
  endpoints on the API origin, then a reload of the pending request. Passkey and social login through the app's login
  page: `ai.mcp.oauthLoginUrl`, default `<appUrl>/auth/login`, opened next to the consent page. A user already signed in
  to the API origin skips this.
- **Signed in** → the account first (with "use another account"), which client asks, where the code goes; Allow /
  Deny as a form POST. Allow counts only after intent on the page (visible, focused, a pointer move / key / touch at
  least 600 ms later), against double-clickjacking; without JavaScript nothing can be approved.
- **Allow** issues the code only with the page's CSRF token, signed and bound to user, client, redirect URI and PKCE
  challenge (10 minutes). **Deny** → `access_denied`.

The page sets its own CSP (nonces, `frame-ancestors 'none'`), `X-Frame-Options: DENY` and `Cache-Control: no-store`,
escapes every value from outside (the client's name comes from whoever registered it), and speaks German to a German
browser. It needs Better-Auth active; without it the boot warns.

**A signed-in session is not consent.** Dynamic registration is open, so anybody can register a client with their own
redirect URI and start the flow — PKCE is then theirs too. A GET to `/authorize` is what any link produces, and it
carries the SameSite=Lax session cookie. The framework therefore refuses a code saved while answering a GET to
`/authorize`: the client is sent back with `error=server_error`, and the server log names the refusal. That applies to
a consent page of your own as well.

**Your own page** (optional): override `renderConsentPage(view)` to restyle, or `authorizeConsent(client, params, res)`
to replace it, and register the subclass:

```typescript
CoreModule.forRoot(envConfig, { ai: { mcpOAuthService: McpOAuthService } })
```

Two checks stay outside the overridable methods: an API token can never approve a consent, and the production secret
check runs again before the endpoints are mounted. Without a signing secret, every environment except `local`, `ci` and
`e2e` now refuses to boot with `ai.mcp.oauth` — and refuses to sign or verify tokens at all — instead of falling back
to the public development key. That includes the DEPLOYED `develop` and `test` stages of a starter-based project:
before, anybody who knew a user id could forge that user's MCP access token there.

## 5. IAM sign-in and sign-up run Better-Auth's login-CSRF protection

Better-Auth protects `sign-in/email` and `sign-up/email` itself (`formCsrfMiddleware`): it refuses a cross-site
navigation (`Sec-Fetch-Site: cross-site` + `Sec-Fetch-Mode: navigate`, i.e. a form a hostile page submits) and checks
a present `Origin` / `Referer` against `trustedOrigins`. It reads both from the request — and
`CoreBetterAuthController` called `api.signInEmail()` / `api.signUpEmail()` without one, so the check never ran. A
hostile page could sign a visitor in to an account of the attacker's choosing (login CSRF); whatever the visitor did
next, approving an MCP client on the consent page included, happened in the attacker's account.

The controller now hands Better-Auth those headers (`Origin`, `Referer`, `Sec-Fetch-*` — not the cookie, see below). A
refused request answers **403** (`#LTNS_0101`, `ErrorCode.ACCESS_DENIED`) instead of a session, and the server logs the reason.

**What to check:**

- **Every origin that signs in from a browser must be trusted.** Trusted by default: the API's own origin, `appUrl`,
  every origin in `cors.allowedOrigins` (merged with `appUrl` and `baseUrl`) and, with `ai.mcp.oauth`, the origin of
  `ai.mcp.oauthBaseUrl`. A frontend on any other origin — a second web app, a native app's web view
  (`capacitor://localhost`, `http://localhost`), a preview deployment — now answers 403 where it used to succeed.
  Add it to **`cors.allowedOrigins`**; it needs that entry for credentialed CORS anyway. `cors.allowAll: true` does not
  trust arbitrary origins for sign-in — an origin check has no "allow everything" mode.
- **Do not reach for `betterAuth.trustedOrigins` for this unless you list everything.** An explicit list REPLACES the
  derived one: `['capacitor://localhost']` alone stops trusting `appUrl` and `cors.allowedOrigins`, and every sign-in from
  the main web app then answers 403 — with the project's test suite still green (see "Test runners" below). If you set
  it, include `appUrl` and every other frontend origin.
- **Non-browser clients are unaffected:** a request without `Origin`, `Referer` and `Sec-Fetch-Site` (server-to-server,
  API tests, mobile HTTP clients, scripts and SSR routes using Node's built-in `fetch`) is not checked. Node's `fetch`
  sends a lone `Sec-Fetch-Mode: cors`; that is not a browser signal and is not forwarded, because Better-Auth would read
  it as a browser request missing its origin. The cookie is deliberately not forwarded either: its presence alone makes
  Better-Auth demand an `Origin`, which would refuse such clients when they keep a cookie jar.
- **Test runners:** Better-Auth skips this check under a test runner by default (`isTest()`), so project test suites
  behave as before; set `betterAuth.options.advanced.disableOriginCheck: false` in a spec that must see production
  behaviour.
- A subclass overriding `signIn()` / `signUp()` that calls `super` keeps the protection; one that calls
  `api.signInEmail()` itself should pass `request: this.csrfCheckedRequest(req, '/sign-in/email')` and
  `asResponse: false` the same way.
