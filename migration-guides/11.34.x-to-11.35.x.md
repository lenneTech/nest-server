# Migration Guide: 11.34.x → 11.35.x

## Why this is a MINOR

Per `.claude/rules/versioning.md` the MAJOR mirrors NestJS, so **MINOR is where breaking changes
live**. This release makes a previously-accepted (and always-wrong) input fail loudly: `roles`
values with the `s_*` system-role prefix are now rejected with a validation error (400). A request
that used to succeed can now fail, so it is `11.35.0` rather than a `11.34.1` patch.

## Overview

| Category | Details |
|----------|---------|
| **Security** | `CoreUserInput.roles` rejects `s_*` values — the framework rule "NEVER store S_ roles in user.roles" is now enforced, not just documented (§1) |
| **Breaking Changes** | `POST /users`, `PATCH /users/:id`, `updateUser`/`createUser` mutations (and every project input extending `CoreUserInput`) answer 400 for `roles` containing an `s_*` value. Previously the value was silently stored — and acted as a grant (§1) |
| **Migration Effort** | None for correct data. If any stored user document already carries an `s_*` role, remove it (it was always a misconfiguration — and an exploitable one) |

## 1. Security: `s_*` values in `user.roles` are rejected

### What happened

`roles` in `CoreUserInput` was an unvalidated `string[]`. The `@Restricted(INPUT, ADMIN)` on the
field limits **who** may send it, but nothing limited **what** it may hold. `hasRole()` is a plain
string intersection, so a stored `'s_self'` satisfied every `S_SELF` check — for the core user
module that includes `updateUser` / `deleteUser` on **arbitrary** users (mail/password change →
account takeover), without the account carrying `admin`. The rule "NEVER store S_ roles in
user.roles" existed only as documentation.

The actor must already be an admin (no escalation from below), but a typo or copy-paste in an
admin tool was enough to mint a dormant skeleton key.

### What changed

```ts
// CoreUserInput.roles
validator: () => [Matches(/^(?!s_)/i, { each: true, message: 'System roles (s_*) must never be stored in user.roles' })],
```

Every `s_*`-prefixed value (case-insensitive) fails validation with the usual
`Validation failed for 1 field: roles (matches)` / 400. All other values — including
project-specific custom roles — remain allowed; consumers keep full control over their own role
vocabulary.

### What you should do

- **Nothing**, if your data is clean. Custom roles are unaffected.
- **Audit once**: `db.users.find({ roles: /^s_/i })` — any hit was always a misconfiguration and,
  depending on your endpoints, an exploitable one. Remove those values before upgrading (the
  upgrade does not touch stored data; it only refuses to write new violations).
- **Optional hardening**: narrow the accepted values further to your project's own assignable
  set with an `IsIn([...], { each: true })` override of `roles` in your project's user inputs —
  the framework cannot know your role vocabulary, so the strict allowlist stays project-side.
