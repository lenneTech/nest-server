# Migration Guide: 12.3.0 → 12.3.1

## Overview

| Category             | Details                                                                                                                                                                                                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Security**         | better-auth 1.7.16: closes the better-auth advisories published on 2026-11-03 — social sign-in, passkeys, e-mail change, revoked sessions with a session cache — and brings better-call 1.4.5 (§1) |
| **New Features**     | `GET /ai/status`: a public answer whether the AI module is on and whether MCP runs (§2)                                                                                                                                                                                       |
| **Bugfixes**         | `betterAuth.passkey.userVerification`, `residentKey` and `authenticatorAttachment` take effect — they never reached the passkey plugin before (§3). The HTTP safety net strips secret fields under their SQL column names too, so a native SQL row returned by a route no longer hands out `password_reset_token` and the other secrets (§4)                                                                                                                             |
| **Breaking Changes** | The better-auth peer range starts at 1.7.16 (was 1.7.12). A project pinning an older version gets a peer warning, and keeps the vulnerability, until it raises the pin (§1). A project that set one of the three passkey options now gets what it configured (§3)            |
| **Migration Effort** | Raise the better-auth trio to 1.7.16 in the API **and** in the app, in the same change (§1). Check §3 if your `betterAuth.passkey` block sets `userVerification`, `residentKey` or `authenticatorAttachment` |

## Quick Migration

```bash
# API (projects/api)
pnpm add better-auth@1.7.16 @better-auth/passkey@1.7.16 @better-auth/core@1.7.16
pnpm add @lenne.tech/nest-server@12.3.1
pnpm run update   # nest-server-starter based projects

# App (projects/app) — together with @lenne.tech/nuxt-extensions, see its release notes
pnpm add better-auth@1.7.16 @better-auth/passkey@1.7.16

pnpm run build && pnpm test
```

Vendor-mode projects pick it up with the core update (`/lt-dev:backend:update-nest-server-core`) and raise the trio in
their own `package.json`.

## 1. better-auth 1.7.16 (security)

better-auth 1.7.16 closes the better-auth advisories published on 2026-11-03. Whether one reaches your project depends
on the features it uses; the ones that can matter for a nest-server project:

| Advisory              | Affects you when                                                  |
| --------------------- | ----------------------------------------------------------------- |
| GHSA-fvxx-76fc-893x   | revoked sessions stayed valid with secondary storage or the cookie cache |
| GHSA-9hm7-xhfp-cx58   | social sign-in (`socialProviders`): an unverified provider e-mail counted as verified |
| GHSA-gv75-j3v8-3crm   | passkeys: origin and user verification were not enforced         |
| GHSA-hwq2-v29r-p69r   | e-mail change: links stayed valid after the address changed hands |
| GHSA-48c2-w96j-mv3m   | the Kysely / Drizzle adapter on MySQL with serial ids (nest-server uses ObjectId hex ids) |

It also pins better-call 1.4.5, which fixes GHSA-23w8-wx9r-vm57 (values a router middleware returns were shared between
requests). That one is not reachable through nest-server, on 1.7.12 as on 1.7.16: better-auth's handler, which
nest-server calls for every `/iam/*` request it forwards, builds a new router around a per-request copy of its context,
so no two requests share one, and nest-server's direct `api.*` calls do not go through a router at all. 1.4.5 is a
second layer there, not the reason for this release.

**Raise all three packages in the API and in the app together.** better-auth is a wire protocol between nest-server
and nuxt-extensions; the two ends must not run different minors, and the peer ranges of both libraries now start at
1.7.16. `pnpm run update` does not raise these pins — the project owns them.

**Installing before 2026-11-04 21:24 UTC.** pnpm's `minimumReleaseAge` (24 h) refuses the new versions until then.
To take the fix the same day, exempt exactly these versions in `pnpm-workspace.yaml` (each carries SLSA provenance
from the projects' own GitHub Actions) and drop the entries with your next maintenance — after that time they change
nothing:

```yaml
minimumReleaseAgeExclude:
  - '@better-auth/core@1.7.16'
  - '@better-auth/drizzle-adapter@1.7.16'
  - '@better-auth/kysely-adapter@1.7.16'
  - '@better-auth/memory-adapter@1.7.16'
  - '@better-auth/mongo-adapter@1.7.16'
  - '@better-auth/passkey@1.7.16'
  - '@better-auth/prisma-adapter@1.7.16'
  - '@better-auth/telemetry@1.7.16'
  - better-auth@1.7.16
  - better-call@1.4.5
```

Never override `better-call` alone instead: better-auth pins it exactly, and an override puts a combination into the
tree that nobody tested.

## 2. `GET /ai/status`

A frontend asks before anybody signs in whether it shows the assistant at all:

| Server                         | Answer                         |
| ------------------------------ | ------------------------------ |
| `ai` configured, `ai.mcp` off  | `200 { "mcp": false }`         |
| `ai` configured, `ai.mcp` on   | `200 { "mcp": true }`          |
| no `ai` (or `enabled: false`)  | `404` — the route does not exist |

The route is public and names no user data; every other `/ai` route keeps its roles. A project controller extending
`CoreAiController` inherits it. nuxt-extensions reads it through its AI status composable. Nothing to configure.

## 3. Passkey options take effect

`betterAuth.passkey.userVerification`, `residentKey` and `authenticatorAttachment` were handed to the passkey plugin
at the top level of its options, where it never reads them: it takes them from `authenticatorSelection`. Every project
therefore ran on the plugin's defaults (`residentKey` and `userVerification` `"preferred"`, no attachment), whatever it
configured. Since 12.3.1 the framework passes them where the plugin reads them.

Nothing changes for a project that sets none of the three. A project that sets one gets what it configured, and
better-auth 1.7.16 now enforces `userVerification: 'required'`: a passkey that answers without user verification (no
biometric or PIN check) is refused at registration and at sign-in. That is the point of the setting — check it is what
you want before you update:

```typescript
// config.env.ts
betterAuth: {
  passkey: {
    userVerification: 'required',          // refuses passkeys without biometric/PIN verification
    residentKey: 'required',               // registration creates a discoverable credential
    authenticatorAttachment: 'platform',   // only built-in authenticators (Touch ID, Windows Hello)
  },
},
```

## 4. Secret fields are stripped under their SQL column names too

`CheckSecurityInterceptor` removes the fields of `security.secretFields` (`password`, `verificationToken`,
`passwordResetToken`, `refreshTokens`, `tempTokens`, `apiKeyEncrypted`, … plus your own) from every response as
a safety net. It compared the field names only. A row read through `store.native(reason)` or `store.raw(reason)`
on a SQL source carries the snake_case columns (`password_reset_token`), so a route that returned such a row
unchanged — a `SELECT *` or `RETURNING *` — dropped `password` (spelled alike) and handed every other secret to
the client.

Since 12.3.1 each secret field is also stripped under its column name, your own entries in `security.secretFields`
included. Nothing to change. Still: a route should map a native row to the fields the client needs rather than rely
on the safety net — see `.claude/rules/persistence.md` → "Native access in three tiers".

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| `ERR_PNPM_NO_MATURE_MATCHING_VERSION` for better-auth 1.7.16 | installed before 2026-11-04 21:24 UTC | add the `minimumReleaseAgeExclude` entries from §1, or wait |
| `unmet peer better-auth@">=1.7.16 <1.8.0"` | the project still pins an older better-auth | raise the trio (§1) |
| The app shows no assistant although `ai` is configured | the API answers `/ai/status` with 404 — it runs a version before 12.3.1 | update the API |
| Passkey registration or sign-in fails after the update for some users | `betterAuth.passkey.userVerification: 'required'` now takes effect, and their authenticator answered without user verification | keep `'required'` and let those users use a verifying authenticator, or set `'preferred'` |
