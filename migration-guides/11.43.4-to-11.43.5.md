# Migration Guide: 11.43.4 → 11.43.5

A security patch for projects that still run on 11.x. It is published under the npm dist-tag `latest-11`, not `latest`:
12.x stays the version a plain install resolves to, and moving every project to 12.x remains the goal. This release
carries only urgent security fixes; functional fixes from 12.x are not backported.

## Overview

| Category             | Details                                                                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bugfixes**         | None in the framework code                                                                                                                    |
| **New Features**     | None                                                                                                                                          |
| **Framework API**    | Unchanged                                                                                                                                     |
| **Dependencies**     | `follow-redirects` 1.16.1 → 1.16.2, transitive (§1)                                                                                          |
| **Breaking Changes** | None                                                                                                                                          |
| **Migration Effort** | Raise the version, refresh one transitive package (§1); decide on two advisories that have no usable fix yet (§2)                          |

## Quick Migration

```bash
# npm mode: the version is pinned exactly, and `latest` is 12.x, so name the version
pnpm add @lenne.tech/nest-server@11.43.5
pnpm update --depth Infinity follow-redirects
pnpm audit --prod
pnpm test
```

Vendor-mode projects update the core to the tag `11.43.5` with the core updater and refresh `follow-redirects` the same
way.

## 1. follow-redirects 1.16.2

[GHSA-mrwp-f3q8-3g9p](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p) (high, CVSS 5.9): `sensitiveHeaders` arrays
from another realm are discarded, so custom credentials can follow a redirect to another host. It covers 1.16.0 and
1.16.1, patched in 1.16.2.

nest-server reaches it through `node-mailjet > axios > follow-redirects`. axios requests a caret range, so no override is
needed, but an existing lockfile keeps 1.16.1 until it is refreshed (the command in Quick Migration). Projects that
reach axios on another path are covered by the same refresh.

## 2. minimatch and glob: fixed only in a new major

[GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) (minimatch `< 11.0.1`, moderate, DoS through
globparts amplification) and [GHSA-3g3m-2fjr-6pw4](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) (glob `9.0.0` to
`14.0.1`, moderate, AbortSignal cancellation bypass) were published on 2026-10-30. Both fixes exist only in new majors
(minimatch 11.0.1, glob 14.0.2), and none of their consumers in the 11.x tree can take them: `@nestjs/cli` 11.0.24, the
newest 11.x, pins glob 13.0.6 and fork-ts-checker-webpack-plugin 9.1.0 (minimatch ^3) exactly; ts-morph, nodemon,
`@swc/cli`, glob 13 and rimraf 6 are on their newest releases and request the older majors. An override across the
major is no way out: minimatch 11 removed `makeRe()` and `Minimatch#regexp`.

`pnpm audit --prod` in a project reports minimatch: ts-morph is a dependency of nest-server (the Permissions module's
scanner), so the path `@lenne.tech/nest-server > ts-morph > @ts-morph/common > minimatch` reaches every production
tree. That scanner matches globs the developer writes, never request input. glob is dev tooling in nest-server's own
tree.

What a project does depends on its audit gate:

- **No blocking `pnpm audit` gate:** nothing to do. Re-check when the consumers move to minimatch 11 / glob 14.
- **A blocking gate:** check `pnpm why minimatch --prod` and `pnpm why glob --prod` first. Your tree may reach either
  package on a path that does take request input; then that path is a finding of its own. If every path matches
  patterns the developer writes, suppress both advisories with the reason next to them. A project that carries
  `scripts/check-overrides.mjs` (starter-based projects do) declares them in `unusableFixConsumers`, so the guard
  reports the day a consumer moves:

```yaml
# pnpm-workspace.yaml of the project — list the consumers YOUR lockfile shows, at their versions
auditConfig:
  ignoreGhsas:
    - GHSA-g3hv-75wg-m249
    - GHSA-3g3m-2fjr-6pw4
  unusableFixConsumers:
    GHSA-g3hv-75wg-m249: '@swc/cli@0.8.1 + @ts-morph/common@0.29.0 + fork-ts-checker-webpack-plugin@9.1.0 + glob@13.0.6 + nodemon@3.1.14 cannot use 11.0.1'
    GHSA-3g3m-2fjr-6pw4: '@nestjs/cli@11.0.24 + rimraf@6.1.3 cannot use 14.0.2'
```

nest-server's own repository carries exactly these entries, with the reasoning in `pnpm-workspace.yaml` and a scope
guard (`tests/unit/audit-suppression-scope.spec.ts`) that fails if glob reaches the production tree or minimatch reaches
it through any parent other than `@ts-morph/common`.

## 3. `check:overrides`: the guard of 12.x (projects that copied it)

Only relevant for a project that carries a copy of `scripts/check-overrides.mjs`. The guard on `release/11.x` is now the
one 12.x runs, which the declarations in §2 need:

- `unusableFixConsumers` takes several consumers, joined with ` + `, each at its assessed version. A listed consumer
  that no longer pulls an affected version fails the run.
- Only edges to an AFFECTED version count as consumers; a parent that already pulls the fixed release does not. An edge
  is matched by the package it pulls, not by its key (npm aliases).
- An advisory that names no patched version is looked up in the registry: a release outside every vulnerable range
  makes the suppression `FIX AVAILABLE`, a release younger than `minimumReleaseAge` is reported as `pending`.

Copy the file from the tag `11.43.5` to take these over. Nothing changes for a project without the guard.

## Not in this release

Fixes from 12.x that are not urgent security fixes stay there. They arrive with the move to 12:
`migration-guides/11.43.x-to-12.0.x.md`.
