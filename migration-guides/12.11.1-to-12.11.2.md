# Migration Guide: 12.11.1 → 12.11.2

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None. `resolveJwtCookieName()` and `DEFAULT_JWT_COOKIE_NAME` name the JWT cookie |
| **Bugfixes** | With `COOKIE_PREFIX`, the API reads a JWT-mode frontend's JWT cookie under `<prefix>-jwt-token`, the name `@lenne.tech/nuxt-extensions` writes (§1) |
| **Security** | None |
| **Migration Effort** | Package update. Only projects that set `COOKIE_PREFIX` and run in JWT mode (`cookies: false`) notice a difference |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.11.2
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Bugfix: the JWT cookie follows `COOKIE_PREFIX`

**No action needed.** Keep `COOKIE_PREFIX` (API) and `NUXT_PUBLIC_COOKIE_PREFIX` (app) equal, as before.

In JWT mode the frontend keeps the Better-Auth JWT in a cookie as well as sending it as a bearer token. A request that
carries the cookie but no `Authorization` header is authenticated by `CoreBetterAuthMiddleware` from that cookie: a
server-side rendered page that forwards the browser's cookies, a passkey request from the app, and the in-place re-check
of an SSE stream (`registerHttpStream()`).

`@lenne.tech/nuxt-extensions` names that cookie `<NUXT_PUBLIC_COOKIE_PREFIX>-jwt-token` when a prefix is set. Up to
12.11.1 the API read `lt-jwt-token` only. With a prefix such a request was anonymous, and Better-Auth's plugin routes
(passkey registration, two-factor) answered `401`.

| `COOKIE_PREFIX` | JWT cookie read since 12.11.2 | Before |
|---|---|---|
| not set | `lt-jwt-token` | `lt-jwt-token` |
| `acme` | `acme-jwt-token` | `lt-jwt-token` |

The prefix is sanitised by the same rule as on the frontend (`[A-Za-z0-9._-]`). The base path does not enter the name,
unlike the session cookie (`<prefix>.session_token`, else `iam.session_token`). There is no fallback to `lt-jwt-token`
while `COOKIE_PREFIX` is set: the prefix keeps the apps on one host apart, and the session cookie does not fall back
either.

## Compatibility Notes

| Pattern | Status |
|---|---|
| No `COOKIE_PREFIX` | Unchanged |
| `COOKIE_PREFIX` with cookies (the default `cookies: true`) | Unchanged; the session cookie already followed the prefix |
| `COOKIE_PREFIX` with `cookies: false` and a matching `NUXT_PUBLIC_COOKIE_PREFIX` | Fixed: the JWT cookie is read |
| A frontend that sets `COOKIE_PREFIX` on the API but writes `lt-jwt-token` | No longer authenticated through the cookie. Set the same prefix on both sides |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Passkey or 2FA routes answer `401` in JWT mode with a cookie prefix | 12.11.1 or older read only `lt-jwt-token` | Update to 12.11.2 |
| Still `401` after the update | The API and the app use different prefixes | Set `COOKIE_PREFIX` and `NUXT_PUBLIC_COOKIE_PREFIX` to the same value |
