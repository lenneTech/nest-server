# Migration Guide: 12.6.0 → 12.6.1

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None for the server API. A client that read the session token from a forwarded Better-Auth response gets none in cookie mode and a JWT in token-in-body mode (§1) |
| **New Features** | None |
| **Bugfixes** | Security: routes forwarded to Better-Auth (two-factor verify, passkey verify, OTP and magic-link sign-in, get-session) put the opaque session token into the response body, also in the default cookie mode (§1) |
| **Migration Effort** | None on the server. Check a frontend that stores a `token` from the second factor or a passkey sign-in (§1) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.6.1
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Forwarded Better-Auth responses follow the sign-in token policy

**Why:** the framework's own sign-in (`POST /iam/sign-in/email`) never hands the opaque session token to a script. In
the default cookie mode it lives in an httpOnly cookie only, and where the body may carry a token
(`cookies: false` or `cookies.exposeTokenInBody`) it is a JWT. Routes the framework forwards to Better-Auth's own
handler bypassed both. `POST /iam/two-factor/verify-totp`, `verify-backup-code` and `verify-otp` answered
`{ token: <session token>, user }`, passkey verify and `GET /iam/get-session` carried `session.token`. A frontend that
stored that token in a cookie or storage its scripts can read handed a 7-day session to any XSS.

**What changed:** every response the API middleware or the controller's catch-all forwards from Better-Auth now goes
through `CoreBetterAuthService.presentSessionTokens()`:

| Mode | Top-level `token` (the session token) | `session.token` |
|---|---|---|
| Cookie mode (default) | removed | removed |
| `cookies: false` or `exposeTokenInBody` | the JWT, as sign-in hands out (the token itself without the JWT plugin); a session-creating response without one (passkey verify) gains it | removed |

A `token` counts as the session token when the response sets it as the session cookie, when it equals `session.token`,
or when it is the token of a live session — the last covers a signed-in user who verifies a second factor again, which
Better-Auth answers with the session they already hold and no cookie.

Untouched: the session cookie Better-Auth sets, error responses, a JWT (`/iam/token` hands one out on purpose), arrays
(`list-sessions`) and a `token` that is not the session token.

**Your frontend:** in cookie mode, rely on the session cookie after the second factor or a passkey sign-in, as after
sign-in. Do not store a `token` from these responses; there is none any more. In token-in-body mode, the `token` is now
the same kind of JWT sign-in returns, so a client that already handles sign-in needs no change.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Cookie-based sign-in, second factor and passkey | Unchanged: the session cookie authenticates |
| A client storing `token` from `two-factor/verify-*` in cookie mode | Gets no `token` any more; use the cookie |
| A client reading `session.token` from `get-session` | Gets none any more, in every mode |
| A signed-in user verifying a second factor again (step-up, adding an authenticator) | The response names the session they already hold; it gets the same treatment (no `token` in cookie mode, a JWT otherwise) |
| `betterAuth.options.advanced.useSecureCookies` / a renamed session cookie | Covered: the session cookie is matched under the name the Better-Auth instance sets |
| `POST /iam/token` (JWT for a cookie session) | Unchanged |
| A project subclass of `CoreBetterAuthService` | `presentSessionTokens()` and `sendBetterAuthResponse()` are new public methods, `sessionCookieNameOfInstance()` a new protected one; keep the cookie-mode rule when overriding |
