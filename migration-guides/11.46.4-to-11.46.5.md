# Migration Guide: 11.46.4 → 11.46.5

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None in nest-server. NestJS 11.2.10, which `pnpm run update` installs, adds startup errors for configurations 11.2.7 ignored (§5) |
| **New Features** | Byte ranges from every file store: `getFileStream(id, { range })`, `CoreS3Service.getObject(key, { range })`, `resolveDownloadRange()`, `setDownloadRangeHeaders()`, `parseRangeHeader()`; `TestDownloadOptions.headers` |
| **Bugfixes** | `GET /files/id/:id` and `GET /files/:filename` answered every `Range` request with `200` and the whole file — Safari does not play a video from such a server (§1) |
| **Security** | NestJS 11.2.10 closes GHSA-c8fr-c7pf-58pf and GHSA-jgpx-8x6j-fcpf (high, process crashes; §5). `ws` GHSA-37g9-w4hg-h9qr (high, unauthenticated memory-exhaustion DoS through the GraphQL WebSocket) — one override in your `pnpm-workspace.yaml` (§6) |
| **Also fixed** | Every S3 download the client aborted logged `ERROR File download failed: aborted` (§4) |
| **Migration Effort** | Projects with their OWN route for video, audio or large downloads: answer `Range` (§2). Everyone: `pnpm run update` and the `ws` override (§6) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@11.46.5
pnpm run update   # nest-server-starter based projects
# replace the ws 8.x override in pnpm-workspace.yaml with the one from §6, then: pnpm install
grep -rn "pipeFileToResponse(" src/   # own download routes: serve ranges where media is delivered (§2)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The framework's download routes answer ranges

Safari refuses to play a video, and stalls audio, from a server that answers a `Range` request with `200` and the
whole file. Chrome plays it anyway, so the problem showed neither locally nor in a Chromium-based Playwright run — it
showed on the first iPhone. Until 11.46.4 the core could not read a byte range at all: `CoreS3Service.getObject()` sent
no `Range`, and `getFileStream()` always opened the whole file. A project could serve ranges from GridFS and the
filesystem with its own code, but not from S3, which every deployed stage with `s3` configured uses.

Since 11.46.5 both download routes answer ranges on every store, without any change in the project:

| Request | Answer |
|---|---|
| `Range: bytes=0-1` (one range inside the file) | `206`, `Content-Range: bytes 0-1/<length>`, `Content-Length: 2`, only those bytes |
| `Range: bytes=1000-` / `bytes=-500` | `206` with the rest of the file / its last 500 bytes |
| A range starting at or past the end of the file | `416`, `Content-Range: bytes */<length>`, `#LTNS_0503` |
| Several ranges, an invalid header, `If-Range` | `200` with the whole file, as before |
| No `Range` | `200` as before, now with `Accept-Ranges: bytes` |

The rights check runs first, as before: a refused or unknown file is `404` whatever the `Range` says. A `206` carries
`no-transform` in `Cache-Control` (`private, no-store, no-transform` by default), which keeps a `compression`
middleware from gzipping the partial body.

## 2. Own download routes

A route of your own that delivers media (or large files a client may resume) answers ranges with three calls:

```typescript
import {
  downloadAbortSignal,
  openDownloadStream,
  pipeFileToResponse,
  resolveDownloadRange,
  RESPONSE_GONE,
  setDownloadRangeHeaders,
} from '@lenne.tech/nest-server';

@Get('video/:id')
async video(@Param('id') id: string, @Res() res: Response, @CurrentUser() currentUser) {
  const serviceOptions = { abortSignal: downloadAbortSignal(res), currentUser };
  const resolved = await this.fileService.resolveFile(id, serviceOptions); // rights check, length, store
  if (!resolved) {
    throw new NotFoundException();
  }
  const range = resolveDownloadRange(res, resolved.info.length); // throws 416 past the end
  const stream = await openDownloadStream(res, () =>
    this.fileService.getFileStream(id, { ...serviceOptions, range }, resolved.store),
  );
  if (stream === RESPONSE_GONE) {
    return res;
  }
  if (!stream) {
    throw new NotFoundException();
  }
  res.header('Content-Type', resolved.info.contentType || 'video/mp4');
  res.header('Cache-Control', 'private, no-store');
  setDownloadRangeHeaders(res, range, resolved.info.length); // 206 + Content-Range, or Accept-Ranges only
  return pipeFileToResponse(stream, res);
}
```

- `resolveDownloadRange()` must run AFTER the rights check: a `416` confirms that the file exists.
- `setDownloadRangeHeaders()` goes after your own headers — it replaces `Content-Length` with the length of the range
  and appends `no-transform` to `Cache-Control`.
- The range reaches every store: S3 with a ranged `GetObject`, GridFS from the chunk holding the first byte, the
  filesystem from that offset — with the same idle guard and abort signal as a whole file, so an aborted range
  releases its S3 socket at once.

**A project that reads ranges itself** (GridFS `openDownloadStream(id, { start, end })`, `createReadStream({ start,
end })`, a hand-written Range parser) can switch to these functions and drop its own code — and gets S3, which such
code could not reach. Mind the end: `range.end` is INCLUSIVE, like HTTP and `createReadStream()`; GridFS counts it
exclusive, which `getFileStream()` translates.

Lower-level pieces, for code that does not go through `CoreFileService`:

- `CoreS3Service.getObject(key, { range: { start, end } })` — the result carries `contentRange` (S3's
  `bytes <start>-<end>/<total>`) and the range's `contentLength`.
- `parseRangeHeader(header, length)` — the pure parser (`{ start, end }`, `'unsatisfiable'` or `undefined`), for a
  route that decides `If-Range` with a strong validator of its own.
- A malformed range (`start > end`, negative, not an integer) throws a `RangeError` before any store is asked.

## 3. Tests

`testHelper.download()` / `downloadBuffer()` take request headers:

```typescript
const res = await testHelper.download(`/files/id/${id}`, { headers: { Range: 'bytes=0-1' }, token });
expect(res.statusCode).toBe(206);
expect(res.headers['content-range']).toBe(`bytes 0-1/${length}`);
```

## 4. No ERROR for downloads the client aborts

A client that leaves while an S3 download is still streaming is normal traffic — a video player aborts the running
range on every seek. Each of them logged `ERROR [CoreFileController] File download failed: aborted` with a stack trace,
through the framework's download routes and every project route that delivers with `pipeFileToResponse()`.
`downloadAbortSignal(res)` registers its listeners first, aborts the S3 request when the client goes, and the SDK fails
the body inside that same dispatch — before `pipeFileToResponse()` saw the client leave.

Since 11.46.5 `pipeFileToResponse()` reads a stream error while the client is gone as the end of an aborted download:
nothing is sent, one debug line is logged. A store error while the client is still connected is an ERROR as before.
Nothing to change in a project.

## 5. Security: NestJS 11.2.10

11.46.5 declares NestJS 11.2.10 (`@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express`, `@nestjs/testing` (dev); from 11.2.7) — three patch releases of the 11.2 line (11.2.8 – 11.2.10). Besides the two advisories below they bring behaviour a REST / GraphQL application on Express can meet: a global guard, interceptor or pipe that cannot run (a class given as the `useValue` of `APP_GUARD`, one without `canActivate` / `intercept` / `transform`, or a class enhancer whose dependencies are request-scoped) and an invalid `forRoutes()` / `exclude()` entry now stop the application at startup — 11.2.7 dropped them silently, so they never took effect: correct or remove them. Middleware given to `forRoutes()` is also mounted on routes excluded from the global prefix, and multipart requests are capped at 1000 parts by default (`limits.parts` raises it). Boot the application once after the update. `pnpm run update` raises your pins to it.
NestJS's advisories of 2026-11-12 include two high ones for an application on Express that this release closes:

| Advisory | Package | What |
|---|---|---|
| [GHSA-c8fr-c7pf-58pf](https://github.com/nestjs/nest/security/advisories/GHSA-c8fr-c7pf-58pf) | `@nestjs/platform-express` | Process crash via a multipart request with many fields |
| [GHSA-jgpx-8x6j-fcpf](https://github.com/nestjs/nest/security/advisories/GHSA-jgpx-8x6j-fcpf) | `@nestjs/common` | Process crash via many files validated at once by `ParseFilePipe` |

They were not in GitHub's global advisory database on 2026-11-14, so `pnpm audit` does not report them yet. A project
that pins `@nestjs/*` itself below 11.2.10 stays affected whatever nest-server version it runs.

## 6. Security: one override for `ws`

[GHSA-37g9-w4hg-h9qr](https://github.com/websockets/ws/security/advisories/GHSA-37g9-w4hg-h9qr) (high): a client floods
ping frames without reading the replies, the server buffers the automatic pongs, and the process runs out of memory —
before any authentication, through the WebSocket every application with GraphQL subscriptions accepts. Patched in `ws`
8.23.0 (and 7.5.14). The GraphQL WebSocket server runs on `@nestjs/graphql`'s own `ws`, which 13.4.5 exact-pins at
8.21.3. nest-server's own `overrides:` do not reach your install (`docs/security-overrides.md`), so put the entry into
your project's `pnpm-workspace.yaml` and run `pnpm install`. A nest-server-starter based project already has two `ws`
entries, `'ws@>=8.0.0 <8.21.3': 8.21.3` and `'ws@>=7.0.0 <7.5.13': 7.5.13`: **replace both** with the two below. Do not
only raise their targets — pnpm matches the key against the requested exact version, and a key whose upper bound stays
below it leaves the vulnerable copy in the tree. 7.5.13 is itself covered by the advisory (patched 7.5.14).

```yaml
overrides:
  # GHSA-37g9-w4hg-h9qr (high): @nestjs/graphql 13.4.5 exact-pins ws 8.21.3. Keep key and target in lockstep
  # with the ws version @lenne.tech/nest-server declares (8.23.0 since 11.46.5). Remove once @nestjs/graphql pins ws >= 8.23.0.
  'ws@>=8.0.0 <8.23.0': '8.23.0'
  # The 7.x copy comes from @nestjs/graphql 13 > subscriptions-transport-ws, same advisory.
  'ws@>=7.0.0 <7.5.14': '7.5.14'
```

`pnpm why ws` must then show a single `ws@8.23.0` (and `ws@7.5.14` for the legacy transport). Until GitHub's global advisory database lists the
advisory, `pnpm audit` does not report the vulnerable version. A vendor-mode project adds the same entry.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ERROR [CoreFileController] File download failed: aborted` with `socketCloseListener` in the stack, one per aborted download | 11.46.3 – 11.46.4 on S3 | Update to 11.46.5 (§4) |
| `pnpm why ws` lists `ws@8.21.3` under `@nestjs/graphql` | The override from §6 is missing, or an older `ws` 8.x key was kept with only its target raised | Use exactly `'ws@>=8.0.0 <8.23.0': '8.23.0'`, `pnpm install` |
| A video plays in Chrome but not in Safari (iPhone, macOS) | The route answers `Range` with `200` and the whole file | Framework routes: update. Own route: §2 |
| `416` with `#LTNS_0503` | The client asked for bytes past the end of the file; `Content-Range: bytes */<length>` names the real size | Usually a player with a cached, outdated length — reload |
| `RangeError: Invalid byte range` | A `range` with `start > end`, a negative or fractional value reached `getFileStream()` / `getObject()` | Produce it with `resolveDownloadRange()` |
| `InvalidRange` from S3, or a GridFS stream error `Stream end (…) must not be more than the length of the file` | A `range` past the end of the file reached the store | Resolve it against the file's `length` with `resolveDownloadRange()`, which cuts it at the last byte |
