# Migration Guide: 11.42.12 → 11.42.13

## Overview

| Category             | Details                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| **Bugfixes**         | `CoreTenantGuard` refusals carry translatable error codes (§1); `GET /files/id/:id` answers 404 instead of 500 for an id that is not an ObjectId (§3) |
| **New Features**     | A finished TUS upload names the stored file in the `X-File-Id` response header (§2)                      |
| **Framework API**    | Additive only: `ErrorCode.NOT_TENANT_MEMBER` … `VERIFICATION_REQUIRED` (`LTNS_0103`–`LTNS_0107`), `TUS_FILE_ID_HEADER`, `CoreFileService.isMalformedFileId()` (protected) |
| **Dependencies**     | None for the package                                                                                     |
| **Breaking Changes** | None. Status codes and access decisions are unchanged; only the message text of five tenant refusals gains a prefix (§1) |
| **Migration Effort** | None for most projects. Check §1 if you compare a tenant refusal message for exact equality, and §2 if your frontend derives a file id from the TUS URL |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required unless one of
the checks below applies to you.

## 1. Tenant guard refusals are translatable

Five of the guard's 403 refusals were thrown as plain English strings. Without the `#LTNS_XXXX:` prefix the
frontend error translation could not map them, so users saw the raw English text in a toast.

| Code        | Message (unchanged wording)   | Refused because                                                                          |
| ----------- | ----------------------------- | ---------------------------------------------------------------------------------------- |
| `LTNS_0103` | `Not a member of this tenant` | the tenant header names a tenant the user has no active membership in                     |
| `LTNS_0104` | `Insufficient tenant role`    | the membership role does not satisfy the required tenant role                             |
| `LTNS_0105` | `Insufficient role`           | `user.roles` does not meet the required role (no header, or a `@SkipTenantCheck` route)   |
| `LTNS_0106` | `Tenant is inactive`          | `multiTenancy.isTenantActive` reports the header's tenant as switched off                 |
| `LTNS_0107` | `Verification required`       | an `S_VERIFIED` endpoint, and the user is not verified                                    |

The response `message` is now e.g. `#LTNS_0103: Not a member of this tenant`. Status code (403), exception class
and the decision itself are unchanged. German and English translations ship in the error catalog
(`GET /i18n/errors/:locale`), so `nuxt-extensions` translates them without any change.

**What to check:**

- **You compare the message for exact equality** (`toBe('Insufficient role')`, `message === '…'`): switch to a
  substring match or, better, to the code:

  ```typescript
  // Before
  expect(res.body.message).toBe('Not a member of this tenant');

  // After
  expect(res.body.message).toBe(ErrorCode.NOT_TENANT_MEMBER);
  // or, tolerant of both versions
  expect(res.body.message).toContain('Not a member of this tenant');
  ```

  Substring matches (`toContain`, log filters) keep working unchanged — the original wording stays behind the
  code.
- **Your product does not call them tenants:** override the translations in your own error registry
  (`errorCode.additionalErrorRegistry`). It is registered after the core, and translations are merged per code,
  so your entry for `LTNS_0103` wins.

## 2. A finished TUS upload names the stored file (`X-File-Id`)

Until now a client knew only the TUS URL after an upload. Its last segment is the TUS **upload** id — a key of the
staging store, not of the file store — and `/files/id/<upload-id>` cannot answer with the file. The response that
completes an upload now carries the ID of the stored file:

```
HTTP/1.1 204 No Content
Upload-Offset: 52428800
X-File-Id: 6720c1f0a2b4c8e9d0f1a2b3
Access-Control-Expose-Headers: …, X-File-Id
```

- Sent on the completing request only: the last `PATCH`, or the `POST` of a creation-with-upload. Creation and
  partial `PATCH`es store nothing yet and carry no header.
- Listed in `Access-Control-Expose-Headers`, so a browser on a separate app origin can read it.
- The name is exported as `TUS_FILE_ID_HEADER`.

With `tus-js-client`:

```typescript
let fileId: string | undefined;
const upload = new Upload(file, {
  endpoint: '/tus',
  onAfterResponse: (_req, res) => {
    const id = res.getHeader('X-File-Id');
    if (id) {
      fileId = id;
    }
  },
  onSuccess: () => {
    // use `/files/id/${fileId}` — NOT the last segment of `upload.url`
  },
});
```

**What to check:**

- **Your frontend takes the last segment of the TUS URL as the file id:** read `X-File-Id` instead. Treat a
  missing header (an older server, see the next point) as "no file id known" — never fall back to the URL.
- **You override `onUploadComplete()`:** nothing to change as long as the override calls
  `super.onUploadComplete(upload)` with the `upload` it received — both `await super…` and `return super…` keep
  compiling and keep the header. An override that never calls `super` (it stores the file itself) completes the
  upload without `X-File-Id`. The method's signature did not change.

## 3. `GET /files/id/:id` answers 404 for an id that is not an ObjectId

An id that is not a 24-character hex string — typically a TUS upload id (32 hex characters) taken for the file id,
see §2 — reached `new ObjectId()` and threw a `BSONError`, so the route answered **500**. It now answers exactly
like an unknown id: `404` with `ErrorCode.FILE_NOT_FOUND`.

The guard sits in `CoreFileService` (`getFileInfo`, `resolveFile`, `getFileStream`, `getBuffer`,
`getDownloadUrl`, `getRawFileInfo`, `deleteFile`, `duplicateById`), so every route built on those methods
benefits — including a project's own `GET /files/info/:id` / `DELETE /files/:id`. Only strings are judged; an
`ObjectId` instance keeps its previous path.

**What to check:**

- **Your files use ids that are not ObjectIds** (unusual — every core store keys by ObjectId): override the new
  protected `isMalformedFileId(id)` in your `FileService` to accept them.
- **A monitor or test expected the 500:** it now gets 404.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| npm-mode and vendor-mode projects without tenant-message comparisons or TUS overrides | Nothing to do |
| Tests or frontends matching tenant refusals with `toContain` / a substring | Compatible |
| Tests comparing a tenant refusal message with `toBe` / `===` | Compare against `ErrorCode.*` (§1) |
| `TusService extends CoreTusService` overriding `onUploadComplete()` and calling `super` | Compatible, header included |
| `onUploadComplete()` override that does not call `super` | Compatible, no `X-File-Id` (§2) |
| `FileService extends CoreFileService` with a `checkRights()` that reads `getRawFileInfo()` | Compatible; a malformed id now reaches it as `null` |

## Troubleshooting

**The browser never sees `X-File-Id` although the server sends it**
The header is exposed by the tus server itself. If a proxy rewrites `Access-Control-Expose-Headers`, add
`X-File-Id` there as well.

**`X-File-Id` is missing on the completing response**
Check for an `onUploadComplete()` override that does not call `super.onUploadComplete(upload)`, or that passes it a
copy of `upload` (§2).

**A tenant refusal shows in English although the frontend translates errors**
The frontend translation loads the catalog from `GET /i18n/errors/:locale`. Make sure the error-code module is
registered (it is by default) and the catalog contains `LTNS_0103`–`LTNS_0107`.
