# Migration Guide: 12.7.0 → 12.7.1

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None |
| **Bugfixes** | Security: revoking a session by id could leave a live session in place for a user with many stored sessions (§1). The first second-factor check while enabling 2FA answered with the token of the session it had just replaced (§2) |
| **Documentation** | 12.6.x-to-12.7.x §2: `lt dev up` with an exported `NODE_ENV` (§3). 12.5.x-to-12.6.x: the E2E helper `findVerificationToken()` in project copies (§4) |
| **Migration Effort** | None on the server. Check a project's `start` script (§3) and its copy of the E2E auth helper (§4) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.7.1
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. `revoke-session` by id looks among the active sessions only

**Why:** since 12.7.0, `POST /iam/revoke-session` accepts `{ sessionId }` and resolves the id among the caller's own
sessions. It asked Better-Auth for every stored session of the user. Better-Auth returns at most 100 rows for such a
query, and MongoDB keeps expired session rows until something removes them. For a user with more than 100 stored
sessions, the session to revoke could fall outside the answer. The request then revoked nothing and still answered
successfully, so a device the user meant to sign out stayed signed in.

**What changed:** the id is resolved among the user's **active** sessions only. An expired session has nothing left to
revoke, and an unknown or foreign id still revokes nothing and discloses nothing.

**Your project:** nothing to do. The same fix ships in 12.6.2 and 11.43.8.

## 2. The first second-factor check while enabling 2FA hands out no replaced token

**Why:** enabling 2FA rotates the session. The first `POST /iam/two-factor/verify-totp` creates a new session, sets
its cookie and deletes the old one, and Better-Auth answered with the token of the old session. That token was dead
by then, so it gave no access, but the rule is that no response body carries an opaque session token. The token policy
(12.6.1) did not recognise it, because neither the new cookie nor the session store named it any more.

**What changed:** a response that sets a new session cookie while its body names another opaque token counts as a
session rotation. Cookie mode removes the token. With `cookies: false` or `exposeTokenInBody`, the body carries the JWT
of the **new** session, as sign-in does.

**Your frontend:** nothing to do. In cookie mode the session cookie authenticates after enabling 2FA, as before. In
token-in-body mode the `token` of this response now belongs to the session the client actually holds.

## 3. Correction in 12.6.x-to-12.7.x §2: `lt dev up` with an exported `NODE_ENV`

The 12.7.x guide said that `lt dev up` and `lt dev test` set `NODE_ENV=local`. They do for the API server. A
`migrate:up` in the project's `start` script runs with whatever `NODE_ENV` the shell exported, so with
`NODE_ENV=development` exported, that step stops since 12.7.0. Pin the environment in the script, as
nest-server-starter 12.7.0 does:

```json
"start": "cross-env NODE_ENV=local pnpm run migrate:up && pnpm run start:local"
```

## 4. Addition to 12.5.x-to-12.6.x: the E2E helper `findVerificationToken()`

Since 12.6 the verification token is sealed. Projects created from nuxt-base-starter 2.37 or earlier keep their own
copy of `tests/e2e/helpers/auth-backend.ts` (in a fullstack project under `projects/app/`), and its
`findVerificationToken()` reads the address out of the token's JWT. It finds no token any more, and every E2E test that
verifies an address fails or times out. Updating the starter does not reach that copy: replace
`findVerificationToken()`, `userKey()` and `jwtEmail()` with the versions from nuxt-base-starter 2.38.1. Those match the
development log line by `UserKey` and still read the JWT of a server older than 12.6. This affects every project
copy.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `POST /iam/revoke-session` with `{ sessionId }` or `{ token }` | Unchanged API. By id, only an active session is found (§1) |
| Enabling 2FA in cookie mode | Unchanged: the new session cookie authenticates; the body carries no token (§2) |
| Enabling 2FA with `cookies: false` / `exposeTokenInBody` | The body's `token` is the JWT of the new session (§2) |
| A project subclass of `CoreBetterAuthService` overriding `sessionTokenOfUser()` | Keep the active-sessions restriction (`onlyActiveSessions: true`) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `lt dev up` stops in the migration step | `migrate:up` inherits an exported `NODE_ENV` without a block | `cross-env NODE_ENV=local` in the `start` script (§3) |
| E2E tests that verify an address find no token | The project's copy of the E2E helper still decodes the JWT | Take the helper from nuxt-base-starter 2.38.1 (§4) |
