# Migration Guide: 12.9.3 → 12.9.4

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None in nest-server. NestJS 12.5.0, which `pnpm run update` installs, adds startup errors for configurations it used to ignore (§2) |
| **New Features** | None |
| **Bugfixes** | Every S3 download the client aborted mid-transfer logged `ERROR File download failed: aborted` with a stack trace (§1) |
| **Security** | NestJS 12.5.0 closes three high advisories of the Express stack (process crashes; §2). `ws` GHSA-37g9-w4hg-h9qr (high, unauthenticated memory-exhaustion DoS through the GraphQL WebSocket) — add one override to your `pnpm-workspace.yaml` (§3) |
| **Migration Effort** | `pnpm run update`, one override (§3), a test run against NestJS 12.5.0 (§2) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.9.4
pnpm run update   # nest-server-starter based projects
# add the ws override from §3 to pnpm-workspace.yaml, then: pnpm install
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. No ERROR for downloads the client aborts

A client that leaves while an S3 download is still streaming is normal traffic, and with 12.9.3 a frequent one: a video
player aborts the running range on every seek. Each of them logged

```
ERROR [CoreFileController] File download failed: aborted
Error: aborted
    at Socket.socketCloseListener (node:_http_client:…)
```

through the framework's download routes and every project route that delivers with `pipeFileToResponse()` — under the
load in which the `S3 socket pool exhausted:` line has to stand out.

The cause is an order of listeners. `downloadAbortSignal(res)` is created before the rights check (the client may leave
while it runs), so its listeners come first. On the event that reports the client gone it aborts the S3 request, and the
SDK fails the body with `aborted` inside that same dispatch, before `pipeFileToResponse()` has seen the client leave.
It shows through a Nest route, whose GET request is not read to its end, so the request's `close` reports the abort.

Since 12.9.4 `pipeFileToResponse()` reads a stream error while the client is gone (`isResponseGone(res)`, or one of its
own client-gone signals) as the end of an aborted download: nothing is sent, one debug line is logged, the socket was
already released. A store error while the client is still connected is an ERROR as before.

Nothing to change in a project. A route that delivers with its own code instead of `pipeFileToResponse()` should switch
to it (see the 12.8.9 guide).

## 2. Dependencies: NestJS 12.5.0

12.9.4 declares NestJS 12.5.0. `pnpm run update` raises these pins of a nest-server-starter based project:

| Package | From | To |
|---|---|---|
| `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express` | 12.4.2 | 12.5.0 |
| `@nestjs/graphql` | 14.2.0 | 14.2.1 |
| `@nestjs/schedule` | 12.0.3 | 12.0.4 |
| `@nestjs/swagger` | 12.1.1 | 12.1.2 |
| `@nestjs/cli` (dev) | 12.0.12 | 12.0.13 |
| `@nestjs/testing` (dev) | 12.4.2 | 12.5.0 |
| `oxlint-tsgolint` (dev) | 7.0.2006 | 7.0.2007 |
| `vite` (dev) | 8.3.7 | 8.3.8 |

Update `@nestjs/core` and the platform package together: the adapter passes new route-matching options to the core.

**Why now: NestJS 12.5.0 is a security release.** Its advisories of 2026-11-12 include three high ones for an
application on Express, all fixed only in 12.5.0:

| Advisory | Package | What |
|---|---|---|
| [GHSA-q223-fc7f-xg75](https://github.com/nestjs/nest/security/advisories/GHSA-q223-fc7f-xg75) | `@nestjs/core` 12.4.x | Process crash when a handler returns a stream that fails before it is read |
| [GHSA-c8fr-c7pf-58pf](https://github.com/nestjs/nest/security/advisories/GHSA-c8fr-c7pf-58pf) | `@nestjs/platform-express` < 12.5.0 | Process crash via a multipart request with many fields |
| [GHSA-jgpx-8x6j-fcpf](https://github.com/nestjs/nest/security/advisories/GHSA-jgpx-8x6j-fcpf) | `@nestjs/common` < 12.5.0 | Process crash via many files validated at once by `ParseFilePipe` |

They were not in GitHub's global advisory database on 2026-11-14, so `pnpm audit` does not report them yet. A project
that pins `@nestjs/*` itself below 12.5.0 stays affected whatever nest-server version it runs.

NestJS 12.5.0 changes behaviour that a REST / GraphQL application on Express can meet (full list in its
[release notes](https://github.com/nestjs/nest/releases/tag/v12.5.0)):

- **New startup errors.** A guard, interceptor or pipe that cannot run (an abstract class as token, a class given as
  the `useValue` of `APP_GUARD`) and an invalid `forRoutes()` / `exclude()` entry now stop the application at startup.
  They did nothing before, so the fix is to correct or remove the entry — boot the application once after the update.
- Middleware passed to `forRoutes()` is now also mounted on routes excluded from the global prefix.
- Multipart requests are capped at 1000 parts by default (`limits.parts` raises it), which also caps a `maxCount` above 1000.
- A `SyntaxError` / `URIError` without a status thrown by an `app.use()` middleware answers 500 instead of 400.
- An `@Optional()` dependency that exists but fails to build now fails its consumer instead of arriving as `undefined`.
- A limit given as `NaN` (`Number(process.env.UNSET)`) now gets its default instead of switching the limit off.

`@apollo/server` stays at 5.5.1. 5.5.2 caps `@graphql-tools/utils` below 12.0.2 for Node 20 installs and thereby brings
back GHSA-c4qx-w738-7hr3 (high); this framework requires Node >= 22.15, so 5.5.2 adds nothing. Do not raise it in a
project either.

**better-auth** is your project's own pin; nest-server 12.9.4 is tested with 1.7.23 and its peer range is unchanged.
If you raise it past 1.7.21, two changes from better-auth apply: a throw from `sendVerificationEmail` no longer rejects
a sign-up (it is logged, the sign-up succeeds — the user stays unverified and can request the mail again), and the
MongoDB adapter builds indexes for fields marked `unique` / `index` at startup — one that fails (duplicate e-mail
addresses, a conflicting index) has to be fixed before the application starts cleanly.

## 3. Security: one override for `ws`

[GHSA-37g9-w4hg-h9qr](https://github.com/websockets/ws/security/advisories/GHSA-37g9-w4hg-h9qr) (high): a client floods
ping frames without reading the replies, the server buffers the automatic pongs, and the process runs out of memory. It
needs no authentication, and every application with GraphQL subscriptions accepts the WebSocket. Patched in `ws`
8.23.0. The GraphQL WebSocket server runs on the `ws` copy of `@nestjs/graphql`, which 14.2.1 — the newest release —
exact-pins at 8.22.1. nest-server's own `overrides:` do not reach your install (`docs/security-overrides.md`), so put the
entry into your project's `pnpm-workspace.yaml` and run `pnpm install`. A nest-server-starter based project already has
an 8.x entry, `'ws@>=8.0.0 <8.22.1': 8.22.1`: **replace** it, do not only raise its target — its key does not match
the exact `8.22.1` that `@nestjs/graphql` requests, so the vulnerable copy would stay. The 7.x entry stays as it is.

```yaml
overrides:
  # GHSA-37g9-w4hg-h9qr (high): @nestjs/graphql 14.2.1 exact-pins ws 8.22.1. Keep the target in lockstep with the
  # ws version @lenne.tech/nest-server declares (8.23.0 since 12.9.4). Remove once @nestjs/graphql pins ws >= 8.23.0.
  'ws@>=8.0.0 <8.23.0': '8.23.0'
```

`pnpm why ws` must then show a single `ws@8.23.0`. Until GitHub's global advisory database lists the advisory,
`pnpm audit` does not report the vulnerable version — a green audit does not mean the project is not affected. A
vendor-mode project adds the same entry.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ERROR [CoreFileController] File download failed: aborted` with `socketCloseListener` in the stack, one per aborted download | 12.8.9 – 12.9.3 on S3 | Update to 12.9.4 |
| The application stops at startup after the update, naming a guard, interceptor, pipe or a `forRoutes()` / `exclude()` entry | NestJS 12.5.0 refuses what 12.4 ignored (§2) | Correct or remove the entry; it never took effect |
| `pnpm why ws` lists `ws@8.22.1` under `@nestjs/graphql` | The override from §3 is missing, or the old `<8.22.1` key was kept with only its target raised | Use exactly `'ws@>=8.0.0 <8.23.0': '8.23.0'`, `pnpm install` |
