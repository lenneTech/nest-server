# Migration Guide: 11.46.5 → 11.46.6

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None. New exports for the fix below: `processGraphQlUploadRequest`, `GRAPHQL_UPLOAD_MAX_PATH_KEYS`, `GRAPHQL_UPLOAD_MAX_MAP_KEYS` |
| **Bugfixes** | None |
| **Security** | GraphQL multipart uploads (§1): graphql-upload GHSA-5vm7-vc2x-p3w2 (high, one anonymous request crashed the process), GHSA-qwwm-252j-9whw (medium, duplicate file fields leaked temporary files), and an unbounded `map` (one anonymous request with a deep path exhausted the heap, one with many entries blocked the event loop and took hundreds of MB, one with a numeric key like `4294967294` handed GraphQL an array of 2^32 − 1 elements). Invalid variables, documents of many operations, fragments spread thousands of times and tens of thousands of variables, a plain JSON POST included, blocked the event loop in the complexity check (§3). A PEM private key under a key such as `certificate` is masked in the Hub config panel (§4) |
| **Migration Effort** | `pnpm run update`. Projects that register `graphqlUploadExpress()` themselves pass the framework's parser (§1); vendor-mode projects add four dependencies (§2) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@11.46.6
pnpm run update   # nest-server-starter based projects
grep -rn "graphqlUploadExpress(" src/   # own registrations: pass processGraphQlUploadRequest (§1)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual, then add the dependencies from §2.

## 1. Security: GraphQL multipart uploads

**No action needed** unless the project registers `graphqlUploadExpress()` itself (below).

`CoreModule` registers graphql-upload's `graphqlUploadExpress()` for `/graphql`, in front of every guard. Up to 11.46.5
it ran graphql-upload 15.0.2's own `processRequest`, which accepted any object path and any number of entries in the
multipart `map` field:

- **GHSA-5vm7-vc2x-p3w2 (high):** a path into an upload placed by an earlier entry replaced one of its methods. A
  request with `map={"1":["variables.file"],"2":["variables.file.reject"]}` and no file fields made the parser throw
  `TypeError: upload.reject is not a function` outside any request — an uncaught exception, on which the process
  exits (`installProcessDiagnostics()` exits 1, as Node does without it). **One anonymous request took the server
  down.** A path with a `__proto__` key let a client-supplied object pass the `GraphQLUpload` scalar's check.
- **GHSA-qwwm-252j-9whw (medium):** a second file field with the name of an already resolved upload created another
  temporary file and dropped the reference to the first, which was never deleted — temporary files and file
  descriptors leaked per request.
- **Unbounded path depth (no advisory; graphql-upload 15.0.2 and 18.0.2 have the same flaw):** the parser places each
  upload with object-path's `set()`, which recurses once per key and copies the remaining keys each time — O(n²) memory
  and time for a path of n keys, in one synchronous call. Measured on this line (Node 24) with
  `map={"1":["variables.a.a.a…"]}`: 8,000 keys (16 KB) took 330 MB; 40,000 keys (80 KB) exhausted a 1 GB heap and
  ended the process. The default `maxFieldSize` of 1 MB leaves room for 400,000 keys.
- **Unbounded number of entries (no advisory; graphql-upload 15.0.2 and 18.0.2 have the same flaw):** every `map` entry
  becomes an upload, and one whose file never arrives is rejected at the end of the request with an error of its own,
  stack trace included. 1 MB of entries without any path (83,000 of them) took 230 MB and blocked the event loop for
  410 to 770 ms.
- **Numeric keys (no advisory; graphql-upload 15.0.2 and 18.0.2 have the same flaw):** object-path reads a key like
  `4294967294` as a NUMBER and sets that index of an array it creates. The 258-byte request
  `map={"1":["variables.f.4294967294"]}` handed GraphQL an array of 4,294,967,295 elements, and GraphQL's list coercion
  walks every hole: the complexity plugin did, before any guard, until a 1 GB heap ran out (10 s). With a nullable list
  item (`[Upload]`) every hole is a valid `null`, so execution would walk them too.

graphql-upload fixed the two advisories in 18.0.2, an ESM-only release that requires graphql 17; this line runs
graphql 16 with graphql-upload 15.0.2. 11.46.6 therefore ships `processGraphQlUploadRequest`
(`common/helpers/graphql-upload.helper.ts`): graphql-upload 15.0.2's parser with both upstream fixes and two bounds of
its own, and `CoreModule` passes it to `graphqlUploadExpress()`. It answers with 400:

- a path into another upload or with a `__proto__` key — "Invalid object path",
- a path with more than `GRAPHQL_UPLOAD_MAX_PATH_KEYS` (64) keys — "Invalid object path",
- a `map` with more than `GRAPHQL_UPLOAD_MAX_MAP_KEYS` (10,000) units. Every entry counts one, every key of its paths
  one more, and every array element a numeric key creates one more, holes included: `{"1":["variables.files.0"]}`
  counts 5, or 4 when the operations already hold `files: [null]`; `variables.f.4294967294` counts more than four
  billion. The path that goes over the bound is answered with "Invalid object path", an entry with "Invalid ‘map’
  multipart field entry key …" before its upload is created.

A duplicate file field is ignored. Each of these requests is now answered within about 50 ms (the 83,000 entries:
~50 ms, +50 MB; `variables.f.4294967294`: ~15 ms, +4 MB). A path a client library builds has a handful of keys
(`variables.file` 2, `variables.input.files.3` 4, batched `0.variables.file` 3); 10,000 units are at least 2,000 files
at `variables.files.N`. The most expensive request
the bounds still accept — 10,000 entries without a path — blocks the event loop for about 80 ms with +35 MB.
graphql-upload stays at 15.0.2 for its scalar and middleware.

**A project that registers `graphqlUploadExpress()` itself** (its own route, its own limits) passes the framework's
parser — graphql-upload's default is the vulnerable one:

```typescript
import { processGraphQlUploadRequest } from '@lenne.tech/nest-server';
import graphqlUploadExpress = require('graphql-upload/graphqlUploadExpress.js');

consumer
  .apply(graphqlUploadExpress({ maxFiles: 10, maxFileSize: 10_000_000, processRequest: processGraphQlUploadRequest }))
  .forRoutes('graphql');
```

Find such registrations with `grep -rn "graphqlUploadExpress(" src/`. A project that calls graphql-upload's
`processRequest` directly switches to `processGraphQlUploadRequest` (same signature and options).

**Behaviour change:** a GraphQL variable literally named `__proto__` that receives a file is refused with 400 (input
object fields cannot use that name; names starting with `__` are reserved).

## 2. Dependencies

New direct `dependencies` for the multipart parser (§1): `busboy` 1.6.0, `fs-capacitor` 6.2.0, `http-errors` 2.0.1 and
`object-path` 0.11.8 — the versions graphql-upload 15.0.2 already installs, so an npm-mode project gets no new package.

A **vendor-mode** project declares them in `dependencies`: the core imports them directly, and a pnpm project does not
see graphql-upload's own copies. A project that compiles with `noImplicitAny` (part of `strict`) also adds
`@types/busboy` 1.5.4, `@types/http-errors` 2.0.5 and `@types/object-path` 0.11.4 to `devDependencies`.

## 3. Security: the complexity check is bounded

`ComplexityPlugin` (registered by `CoreModule` whenever GraphQL is on) computes every operation's cost in Apollo's
`didResolveOperation`, after parsing and validation, before any guard. It called graphql-query-complexity's
`getComplexity()`, and these requests made that call itself the denial of service — each one anonymous, a plain JSON
POST to `/graphql` included:

- **Invalid variables.** `getComplexity()` coerces the variables with graphql's `getVariableValues()` without an error
  cap, so a list of invalid items (`"variables":{"f":[0,0,…]}` for `$f: [Upload!]!`) created one `GraphQLError` per item.
- **Many operations, no `operationName`.** Apollo resolves no operation and still calls the hook. `getComplexity()`
  then evaluated EVERY operation of the document and coerced the variables for each.
- **Fragment spreads.** graphql-query-complexity evaluates a fragment again at every spread, coercing its literal
  arguments each time. Its node cap (10,000 visits) bounds the visits, not what one costs:
  `{...F …×3300} fragment F on Query { findUsers(filter: { singleFilter: { …, value: [0,0,…] } }) { __typename } }`.
- **Many declared variables.** At every field it visits, the library walks every declared variable.
- **Many failing arguments.** The library catches the coercion error of every field's arguments and goes on, and every
  error locates itself by scanning the query up to its field: `query($x: String = "a") { a: getUser(id: $x) { id } … }`
  with `{"x": null}` is valid and fails at every field.

| Request | 11.46.5 | 11.46.6 |
|---|---|---|
| 100 KB of invalid list items | event loop blocked 1.6 s, +320 MB | ~5 ms, +1 MB |
| 1 MB of invalid list items | event loop blocked 17 s, +1.8 GB | ~10 ms, +14 MB |
| 860 operations sharing one 16,000-item variable (100 KB) | event loop blocked 5.9 s | < 1 ms, refused by execution |
| the same with 1,720 operations (200 KB multipart) | event loop blocked 25.5 s | < 1 ms, refused by execution |
| a 41,667-item literal in a fragment spread 3,300 times (100 KB) | event loop blocked 2.2 s | ~15 ms, "Query is too complex" |
| the same with a 490,000-item literal (990 KB multipart) | event loop blocked 22.5 s | ~100 ms, "Query is too complex" |
| 38,000 declared variables and 4,900 spreads (1.2 MB) | event loop blocked 17 s | ~100 ms, "Query is too complex" |
| 2,300 fields failing their argument, after 25,000 line breaks (98 KiB) | event loop blocked 1.4 s | ~6 ms, refused with the first error |
| 9,999 such fields after 395,000 line breaks (993 KiB multipart) | event loop blocked 86 s | ~16 ms, refused with the first error |

What is left for the large literal and the many variables is linear in the request: graphql's validation and
execution walk the same literal and the same variables once themselves.

The rows after the first two were measured on the development line, which has the same plugin and the same
graphql-query-complexity 2.0.0.

Since 11.46.6 the plugin:

1. does nothing when Apollo resolved no operation — graphql's `execute()` then refuses the request ("Must provide
   operation name…") before it coerces a single variable;
2. coerces the resolved operation's variables, stopping at the first error, and skips the complexity check when they
   do not coerce: `execute()` refuses such variables itself, with graphql's cap of 50, before any resolver runs, so
   there is no operation whose cost could matter;
3. refuses an operation whose fields (and `@skip` / `@include`) times declared variables exceed 250,000, with
   `Query is too complex: too many fields for its number of variables` — measured at most about 23 ms of analysis.
   With the default cost of 1 per field, a query `maxComplexity: 1000` accepts has at most 1,000 fields; with 30
   variables that is at most 30,000;
4. computes graphql-query-complexity's number with each fragment evaluated once and reused at every further spread.
   The number is the one `getComplexity()` returns, and the 10,000-node cap still counts every spread. A field's
   `complexity` extension that is a function runs once per fragment instead of once per spread, so it must depend only
   on its arguments and `childComplexity`;
5. stops the analysis at its first error and refuses the request with it — `getComplexity()` collected every error and
   threw the last one.

For valid variables the result is what it was: `Query is too complex: …` above `graphQl.maxComplexity`, and
`Query exceeds the maximum allowed number of nodes.` above 10,000 nodes.

**What clients see:** a request with invalid variables gets execution's errors (up to 50 messages, then "Too many
errors processing variables, error limit reached. Execution aborted.") instead of the single coercion error the plugin
threw before. The status changes with it: HTTP 400 with the code `BAD_USER_INPUT` (Apollo 5 default
`status400ForVariableCoercionErrors`) instead of HTTP 500 with `INTERNAL_SERVER_ERROR`.

## 4. Security: PEM private keys are masked in the Hub config panel

The Hub config panel's masker (`maskConfigDeep()`) decided by the key name alone. A certificate login usually keeps
certificate and private key in one PEM under a name such as `certificate`, which no name rule may treat as secret, so
the panel showed the private key to administrators in clear text. Since 11.46.6 every string and `Buffer` that holds
a PEM private key (`-----BEGIN … PRIVATE KEY-----`, PGP's `PRIVATE KEY BLOCK` included) is masked as a whole, whatever
its key is called. A certificate without a key stays readable.

No action needed. A project's own `GET /config` route does not use this masker on 11.x; if it returns the
configuration, it masks with its own rules — check them for the same case.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Uploads through `CoreModule`'s `/graphql` registration | Protected with the update |
| `graphqlUploadExpress()` registered by the project | Pass `processRequest: processGraphQlUploadRequest` (§1) |
| Vendor mode, GraphQL uploads | Add the four dependencies (and the `@types/*` under `noImplicitAny`) from §2 |
| A project's own Apollo plugin that calls `getComplexity()` with the request's variables | Same flaws as §3 — skip a request without a resolved operation, check the variables with `getVariableValues(…, { maxErrors: 50 })` first, and bound fragment spreads and variables, or rely on the framework's plugin |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Vendor mode: `Cannot find module 'busboy'` (or `fs-capacitor`, `http-errors`, `object-path`) at start | The core imports them since 11.46.6 | Add them to `dependencies` (§2) |
| Vendor mode: `TS7016: Could not find a declaration file for module 'busboy'` (or `http-errors`, `object-path`) | `noImplicitAny` without the type packages | Add the `@types/*` packages from §2 |
| A file upload answers 400 `Invalid object path for the ‘map’ multipart field …` | The `map` names a path into another upload, with a `__proto__` key or with more than 64 keys | Send each file at its own flat variable path (`variables.files.0`, `variables.input.files.3`) |
| An upload answers 400 `Invalid object path …` for a path with a large number in it | The index creates more array elements than the bound allows | Number the files from 0 (`variables.files.0`, `variables.files.1`) |
| An upload of very many files answers 400 `Invalid object path …` or `Invalid ‘map’ multipart field entry key …` | The `map` has more than 10,000 units | Split the upload into several requests |
| A request with invalid variables answers with several variable errors instead of one | Execution reports them now (§3) | Fix the variables; the messages are graphql's own |
| A query answers `Query is too complex: too many fields for its number of variables` | Its fields × declared variables exceed 250,000 (§3) | Split the query, or pass related values as one input-object variable |
