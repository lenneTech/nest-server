# Migration Guide: 11.45.x → 11.46.x

## 11.46.0 changes behaviour

The version number moves only the MINOR digit (the MAJOR follows NestJS). Read §1 before you update: a deployed
instance that creates its first administrator through `POST /system-setup/init` (a setup page in the frontend) is
refused from now on until it is configured. This is the 11.x backport of 12.4.0; 12.x projects have it since then.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | `POST /system-setup/init` is closed outside `local`, `ci` and `e2e` unless `systemSetup.httpInit` opens it (§1) |
| **New Features** | `systemSetup.httpInit` (`true` or `{ token }`), the `X-System-Setup-Token` header, `httpInitEnabled` / `httpInitTokenRequired` in `GET /system-setup/status`, error codes `LTNS_0053` / `LTNS_0054`, a boot report for a deployment that cannot be set up (§1) |
| **Bugfixes** | A deployed instance without users and without `initialAdmin` could be taken over through the anonymous init (§1). A creation that failed after the user was written left a user without the admin role behind and locked the setup for good (§2). An all-digit `initialAdmin` password from the environment crashed the boot, and camelCase ENV names for it were ignored silently (§3) |
| **Migration Effort** | None for a deployment that provisions its first admin through `initialAdmin`, none for one whose users already exist, and none locally. A NEW deployed stage set up through the UI: one ENV variable (§1) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@11.46.0
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

Local development and the e2e suites of a starter-based project keep working without a change: `local`, `ci` and
`e2e` keep the init open. A deployment whose database already has users is not affected either: the init was locked
there before, and stays locked.

## 1. The HTTP init is fail-closed outside the local environments

`POST /system-setup/init` is anonymous (`S_EVERYONE`). Until 11.46.0 its only guard was "no user exists yet", in every
environment. So every deployed instance that went live without `systemSetup.initialAdmin` — a new deployment, or one
whose database was reset — could be taken over by whoever called the route before the first person signed up: an
administrator account for anybody who found the API.

**What changes:** outside `local`, `ci` and `e2e` the init answers **403 `LTNS_0053`** unless `systemSetup.httpInit`
opens it. The environment is the configured `env` (else `NODE_ENV`); the deployed `develop` and `test` stages of a
starter-based project, `production`, `staging` and any unknown or missing name count as deployed.

| `systemSetup.httpInit` | `local` / `ci` / `e2e` | every other environment |
|---|---|---|
| not set | open | **closed** — 403 `LTNS_0053` |
| `true` | open | open, without a token |
| `{ token: '<at least 16 characters>' }` | open, token required | open, token required — 403 `LTNS_0054` without it |
| `false` / `{ enabled: false }` | closed | closed |

`systemSetup.initialAdmin` is not affected: the configured admin is still created at boot in every environment.

**How a new 11.x deployment gets its first admin**, preferred first:

1. **Provision the admin via ENV** — created on the next start, no setup page needed:

   ```bash
   NSC__SYSTEM_SETUP__INITIAL_ADMIN__EMAIL=admin@example.com
   NSC__SYSTEM_SETUP__INITIAL_ADMIN__PASSWORD=<strong password>
   NSC__SYSTEM_SETUP__INITIAL_ADMIN__NAME=Admin   # optional
   ```

   The admin is created only while no user exists, so the variables can stay; change the password after the first
   sign-in.

2. **Open the init with a token** when the setup must happen through the UI:

   ```bash
   NSC__SYSTEM_SETUP__HTTP_INIT__TOKEN=<secret of at least 16 characters, with letters>
   ```

   The frontend sends it in the `X-System-Setup-Token` header. Remove the variable once the admin exists.

3. **Open the init without a token** (`NSC__SYSTEM_SETUP__HTTP_INIT=true`) only where nobody else can reach the API
   before you do: whoever calls it first becomes the administrator. The boot warns about it while no user exists.

**A misconfiguration closes, it never opens.** `httpInit: { token: process.env.SETUP_TOKEN }` with the variable unset,
an empty or short token, or an empty / all-digit `NSC__SYSTEM_SETUP__HTTP_INIT__TOKEN` (the environment reader turns
it into a number) keep the init closed and log an error at boot naming the problem. A string `"true"` from
`NEST_SERVER_CONFIG` counts as not set.

**Frontend:** `GET /system-setup/status` additionally returns `httpInitEnabled` and `httpInitTokenRequired`, always,
whatever `needsSetup` says. Show the setup form only when `needsSetup && httpInitEnabled`, with a token field when
`httpInitTokenRequired`. A backend older than 11.46.0 sends neither field; treat that as "available" (as before).

```typescript
const { needsSetup, httpInitEnabled = true, httpInitTokenRequired = false } = await status.json();
if (needsSetup && httpInitEnabled) {
  await fetch('/system-setup/init', {
    body: JSON.stringify({ email, name, password }),
    headers: {
      'Content-Type': 'application/json',
      ...(httpInitTokenRequired ? { 'X-System-Setup-Token': setupToken } : {}),
    },
    method: 'POST',
  });
}
```

**Boot report.** A deployed instance that starts with zero users, no usable `initialAdmin` and a closed init now logs
an error that names both ways in — before, it stayed silent until somebody tried to sign in.

**Swagger:** while the init is closed, `POST /system-setup/init` is left out of the document `setupSwagger()` builds.

**A project controller** that extends `CoreSystemSetupController` and overrides `createInitialAdmin()` must call
`this.systemSetupService.assertHttpInitAllowed(token)` first (the token read with
`@Headers(SYSTEM_SETUP_TOKEN_HEADER)`); otherwise the override keeps the init open in every environment. A project's
own endpoint that calls `CoreSystemSetupService.createInitialAdmin()` directly does the same.

## 2. A failed creation no longer leaves a user behind

When a step after creating the user failed (linking the credential account, the user sync, the role update, the legacy
password), only the setup claim was released. The user stayed — without the admin role — so `needsSetup` turned
`false` and the init was refused for good: a deployment with a user and no administrator, recoverable only by editing
the database.

**What changes:** the partially created user is removed again (`internalAdapter.deleteUser()`: sessions, accounts and
the `users` document), `needsSetup` stays `true`, and the setup can be retried. The caller still gets 403 `LTNS_0050`,
and the server log names the original failure. If the removal itself fails, the log says which user to delete by hand.

**What to check on an instance that hit this before 11.46.0:** a `users` document without the admin role and no
administrator anywhere. Delete that document and its `account` documents, then provision the admin as in §1.

## 3. `initialAdmin` from the environment

- An all-digit `NSC__SYSTEM_SETUP__INITIAL_ADMIN__PASSWORD` arrives as a number (the environment reader converts
  numeric strings) and crashed the boot. It is now skipped with a warning naming the cause; use a password with
  letters.
- A variable with a camelCase segment (`NSC__systemSetup__initialAdmin__email`) is not read: the environment reader
  lowercases every segment it does not split at `_`. The boot now warns about such a variable and names the correct
  spelling (names only, never values). The documented names are the SCREAMING_SNAKE ones in §1.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `systemSetup.initialAdmin` via config or (SCREAMING_SNAKE) ENV | Unchanged |
| Setup page used locally / in e2e suites (`local`, `ci`, `e2e`) | Unchanged |
| A deployed stage whose users already exist | Unchanged (the init was locked there before) |
| Setup page on a NEW deployed stage without configuration | **403 `LTNS_0053`** — see §1 |
| `systemSetup: { enabled: false }` | Unchanged (no endpoints at all) |
| `CoreSystemSetupService.createInitialAdmin()` called by project code | Not gated — call `assertHttpInitAllowed()` first on an HTTP path |
| A frontend reading `GET /system-setup/status` | Two additional fields; existing fields unchanged |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| 403 `LTNS_0053` on a deployed stage | The init is closed there by default | `initialAdmin` via ENV, or `NSC__SYSTEM_SETUP__HTTP_INIT__TOKEN` (§1) |
| 403 `LTNS_0054` | Token missing or different | Send the configured value in `X-System-Setup-Token` |
| Boot error "POST /system-setup/init stays closed" | The token configuration is unusable (missing, empty, short, a number) | Set a token of at least 16 characters with letters |
| Boot error "No users exist and this instance cannot be set up" | Deployed, no users, no usable `initialAdmin`, init closed | One of the ways in §1 |
| Boot warning "Environment variable NSC__systemSetup__… is not read" | camelCase ENV names | Rename as in §3 |
