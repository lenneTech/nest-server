# Migration Guide: 12.1.0 → 12.1.1

## Overview

| Category             | Details                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bugfixes**         | Multi-replica fixes: a BullMQ cron schedule lost in Redis is registered again (§1), a cron tick no longer runs twice when replicas fire on either side of a second boundary and `runParallel: false` holds across replicas (§2), Redis channels are subscribed again after an outage (§3), a withdrawn Better-Auth role stops working on every replica at once (§4). `synchronizedUp()` works (it threw on every call) (§5) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.1.1
pnpm run update   # nest-server-starter based projects: aligns the pins the framework raised
pnpm run build && pnpm test
```

Vendor-mode projects pick it up with the core update (`/lt-dev:backend:update-nest-server-core`).

## 1. A BullMQ cron schedule lost in Redis comes back

With `redis` configured and `bullmq` installed, cron jobs run as BullMQ job schedulers. The schedule was written once
at bootstrap, so a Redis restart without persistence, a `FLUSHDB` or an eviction removed it, and no replica ran the
job again until the next deploy. `CoreCronJobs` now registers the schedules the queue no longer lists — after every
reconnect of the queue connection and every `bullSchedulerCheckIntervalMs` (protected, 60000 ms; `0` switches only the
timer off) — and logs a warning naming each one. A schedule removed on purpose stays removed, also while replicas of
the previous version are still running. A tick that fell due while the schedule was missing is not run.

## 2. Cron jobs across replicas

**The tick lease is keyed on the scheduled instant.** A job on a local timer took its lease under the time its timer
fired. Two replicas firing a few milliseconds apart on either side of a second boundary computed different keys and
both ran the tick. The key is now the tick's scheduled instant; a manual run (the Hub's "Run now") gets a key of its
own.

**`runParallel: false` holds across replicas.** It used to hold within one process only, so a long run on replica A
did not stop replica B from starting the next tick. A distributed job with `runParallel: false` (or `1`) now holds a
`<job>:running` lease for the duration of the run (60 s, renewed every 20 s, released when the run ends) — on Redis,
else the SQL lease table, else `cron-locks` — and a replica that finds it held skips its tick. Like the tick lease it
fails open: an unreachable lease store runs the tick.

**What to check:** a run that never ends now holds the job on **every** replica while its process lives, not only on
its own. If a job of yours can hang, give it a timeout.

**BullMQ jobs no longer pile up in Redis.** Scheduler jobs carry `attempts: 1`, `removeOnComplete: { count: 100 }` and
`removeOnFail: { count: 500 }` (protected `bullJobOptions`); before, every completed and failed tick stayed in Redis.
The first bootstrap after the update removes the backlog an earlier version kept, oldest first, in batches — a tool
that reads old job history from Redis (Bull Board and the like) shows the last 100 / 500 from then on.

Without `redis`, startup logs one info line naming the jobs that run on every replica because they do not set
`distributed` (silent with `log: false`). A failed TTL index on `cron-locks` is retried on the next tick.

## 3. Redis outages

`CoreRedisService.isReady()` says whether the shared connection is up (`enabled` only says Redis is configured). At
boot the service pings once (3 s) and warns when Redis does not answer, then boots anyway.

Channels on the shared subscriber now go through `subscribeChannel(channel)` / `releaseChannel(channel)`, counted per
holder, and are subscribed again on every reconnect. ioredis re-subscribes only what once succeeded, so a subscribe
that failed at boot left that replica deaf for its whole life — the framework's own tenant-cache invalidation was one
such channel.

**What to check:** code of your own that calls `getSubscriber().subscribe(…)` keeps working, but is not re-subscribed
after a failed first attempt. Switch to `subscribeChannel()` / `releaseChannel()` for that.

GraphQL subscriptions and TUS upload locks still have no fallback while Redis is down — see the "Central Redis" row
of `.claude/rules/configurable-features.md`.

## 4. Better-Auth roles across replicas

`CoreBetterAuthUserMapper` caches a user's roles and verification state for 15 s. `invalidateUserCache()` cleared
that cache on the replica that called it only, so a withdrawn role kept working on the others until the entry
expired. With `redis` configured the invalidation is now broadcast to every replica, which also re-checks the user's
open WebSockets there.

**What to check:** a subclass of `CoreBetterAuthUserMapper` that implements `onApplicationBootstrap()` or
`onModuleDestroy()` must call `super`, or the broadcast is neither subscribed nor released.

## 5. `synchronizedUp()`

`synchronizedUp()` threw on every call until 12.1.0: it called `up` on the loaded migration state, which has none. It
now runs the `MigrationRunner` — the same runner as `migrate up` — under the state store's lock, takes
`migrationsDirectory` (default `migrations` in the working directory, as for the CLI) and `pattern`, and refuses a
`MongoStateStore` without `lockCollectionName` rather than running unsynchronized. A relative `migrationsDirectory`
given to `MigrationRunner` is resolved against the working directory (it failed with `MODULE_NOT_FOUND` before).

## 6. Better-Auth on MySQL and MariaDB

12.1.0 refused to boot with the user model on a MySQL or MariaDB source while Better-Auth was enabled. It now runs
there: Better-Auth's Kysely adapter on the source's `mysql2` pool, its migrations applied as the owner under the
database's `GET_LOCK`. Better-Auth names no collation, and MariaDB refuses a foreign key to `users.id` across
collations, so while it creates a table the framework switches the database's default collation to `utf8mb4_bin` and
restores it afterwards — only on such a run, with a 5 s lock wait, because `ALTER DATABASE` locks every table.

Nothing to do for a project on MongoDB or PostgreSQL.

## Smaller fixes

- Upload file names from `multerRandomFileName()` come from `crypto.randomBytes()` instead of `Math.random()`.
- The Hub's log and trace panels answer an empty page with the cursor unchanged when the shared Redis buffer cannot
  be read, instead of the replica's local buffer under a cursor that belongs to the shared one.

## Compatibility Notes

| Pattern                                                                  | Status                                                                     |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Single replica, no Redis                                                 | Unchanged apart from the info line naming non-distributed cron jobs (§2)   |
| `CronJobs extends CoreCronJobs` without overrides                        | Unchanged                                                                  |
| A cron job with `runParallel: false` on several replicas                 | Now exclusive fleet-wide (§2)                                              |
| Own `getSubscriber().subscribe()` calls                                  | Work; switch to `subscribeChannel()` for re-subscription (§3)              |
| `CoreBetterAuthUserMapper` subclass with own lifecycle hooks             | Call `super` (§4)                                                          |
| Better-Auth with users on MySQL / MariaDB                                | New — boots now (§6)                                                       |
