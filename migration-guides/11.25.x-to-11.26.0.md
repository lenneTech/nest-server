# Migration Guide: 11.25.x → 11.26.0

## Overview

| Category        | Effort     | Notes                                                            |
|-----------------|-----------|------------------------------------------------------------------|
| Breaking        | None       | Fully backward compatible — feature is opt-in.                   |
| New Features    | Medium     | Offline sync support (REST + WebSocket hint + plugin).            |
| Bug Fixes       | None       | None in this release.                                            |
| Deprecations    | None       | None.                                                            |

**Bottom line**: existing projects update with zero changes. The new
offline sync feature is fully opt-in via `config.sync`.

## Quick Migration

For projects that do **not** want to enable offline sync:

```bash
pnpm update @lenne.tech/nest-server@11.26.0
```

That's it. No code changes required. The new sync plugin is registered
in `connectionFactory` only when `config.sync` is truthy. All existing
schemas, indexes, services, and tests remain unchanged.

## What's New: Offline Sync Module

11.26.0 ships generic offline-sync support designed for mobile clients
(typically React Native + SQLite). It provides:

- **Soft-delete tombstones** with a Mongoose plugin that adds `version`
  and `deletedAt` fields (only on schemas marked `syncable: true`).
- **Optimistic-concurrency CAS** in `CrudService.update()` via optional
  `expectedVersion` service option.
- **Cursor-paginated delta pulls** via `CrudService.findChangesSince()`.
- **REST endpoints**: `GET /sync/:model` (pull) and `POST /sync/:model`
  (bulk push with idempotency, conflict detection, field-level LWW).
- **GraphQL subscription** `syncHint` for "changes available" notifications,
  filtered per tenant.
- **Rate-limit guard** for sync routes.

See [`src/core/modules/sync/README.md`](../src/core/modules/sync/README.md)
and [`src/core/modules/sync/INTEGRATION-CHECKLIST.md`](../src/core/modules/sync/INTEGRATION-CHECKLIST.md)
for activation details.

### Activating the feature

```typescript
// config.env.ts
export const config: IServerOptions = {
  // ... existing config ...
  sync: {
    enabled: true,
    models: [
      {
        name: 'Note',
        service: NoteService,
        createDto: NoteCreateInput,
        updateDto: NoteInput,
      },
    ],
  },
};
```

```typescript
// note.model.ts
@Schema({ syncable: true, timestamps: true })
export class Note extends CorePersistenceModel {
  // ... existing properties ...
}
```

## Breaking Changes

None. The release adds new optional fields and methods without modifying
any existing public API contracts:

- `CrudService.update(id, input, serviceOptions)` — `serviceOptions` is
  unchanged for callers that do not pass `expectedVersion` or `hardDelete`.
- `CrudService.delete(id, serviceOptions)` — unchanged for non-syncable
  schemas. For syncable schemas it now soft-deletes by default, but
  existing projects do not have any syncable schemas yet.
- `CrudService.findChangesSince()` — newly added, no impact on existing
  callers.
- `IServerOptions.sync` — newly added optional field.
- `ICoreModuleOverrides.sync` — newly added optional field.

## Compatibility Notes

### Existing Mongoose schemas

- Schemas without `syncable: true` are completely untouched.
- The plugin is registered in `connectionFactory` only when
  `config.sync` is truthy. Without it, the plugin function is never
  even imported into the connection.
- No new indexes are created on existing collections.

### Existing tests

- All 429 unit tests pass unchanged.
- The mongoose-plugins.e2e-spec.ts (24 tests) and tenant-guard.e2e-spec.ts
  (187 tests) and multi-tenancy.e2e-spec.ts (38 tests) all pass unchanged.
- The new `tests/sync-backward-compat.e2e-spec.ts` verifies that with
  the plugin loaded but a non-syncable schema, behaviour is bit-for-bit
  identical to the pre-11.26.0 baseline.

### Existing models with `version` or `deletedAt` fields

If a project already has a `version` or `deletedAt` field on a schema
that it intends to mark `syncable: true`, two options:

1. **Use the project field names**: configure `sync.fields` to point
   at the existing field names instead of the defaults.

   ```typescript
   sync: {
     fields: {
       version: 'docVersion',
       deletedAt: 'softDeletedAt',
     },
   };
   ```

2. **Migrate**: rename the existing fields to the sync defaults via a
   one-shot migration script (see Step 4 in
   [`INTEGRATION-CHECKLIST.md`](../src/core/modules/sync/INTEGRATION-CHECKLIST.md)).

## Troubleshooting

**Q: I enabled `sync: true` but `GET /sync/Note` returns 404.**
A: The model needs to be registered. Add an entry to `sync.models[]`
with `name`, `service`, `createDto`, and `updateDto`.

**Q: Bulk push items return `invalid` status.**
A: The DTO validation rejected the payload. Verify that the registered
`createDto` / `updateDto` includes `@UnifiedField` decorators for all
fields the client sends. Read the `message` field in the result for
details.

**Q: After enabling sync, my existing tests fail with "Updating the
path 'version' would create a conflict".**
A: This indicates that an existing schema is already syncable and the
caller's update body includes a `version` field. Check that you are
not mixing application-managed versioning with the sync plugin's
versioning.

**Q: I get `Sync model "X" is not registered` despite calling
`CoreSyncModule.forRoot({ models })`.**
A: The DI resolution happens in `onApplicationBootstrap`. Make sure
the model's CrudService is also imported into a module that the
`CoreSyncModule` consumer can resolve via `ModuleRef.get(...)`.

**Q: Hints arrive on one server instance but not on others.**
A: The default in-memory PubSub is single-instance. Override
`ICoreModuleOverrides.sync.pubSub` with a Redis-backed PubSub for
multi-instance deployments.
