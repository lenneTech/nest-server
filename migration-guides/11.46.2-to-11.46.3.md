# Migration Guide: 11.46.2 → 11.46.3

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None in the API. **Behaviour change:** a download stream that makes no read progress for 30 s is now closed — code that opens a stream and reads it much later (a ZIP export that appends every file first) must open it right before reading or opt out per call (§5). A download that cannot get a store connection answers `503` instead of waiting without end (§2) |
| **New Features** | `s3.maxSockets`, `s3.connectionTimeoutMs`, `s3.socketTimeoutMs`, `s3.downloadIdleTimeoutMs`, `file.downloadIdleTimeoutMs`, `file.downloadCaching`; `ETag`, `304` and `Content-Length` on downloads; `CoreS3Service.getSocketPoolStats()`; `guardIdleStream()`, `isResponseGone()`, `downloadAbortSignal()`; `abortSignal` and `downloadIdleTimeoutMs` in `FileServiceOptions`, `abortSignal` and `idleTimeoutMs` in `CoreS3Service.getObject()` |
| **Bugfixes** | S3 downloads could exhaust the S3 client's socket pool for good (§1) |
| **Migration Effort** | `pnpm run update`. A project with its OWN download route replaces `stream.pipe(res)` with `pipeFileToResponse(stream, res)` (§3). Check code that reads file streams late (§5). Alert on the new error log line (§4) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@11.46.3
pnpm run update   # nest-server-starter based projects
grep -rn "\.pipe(res" src/   # own download routes: switch them to pipeFileToResponse() (§3)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. What happened

A project delivered S3 downloads with a bare `stream.pipe(res)`. When a client aborted, `pipe()` only unpiped: the S3
body was never read and never destroyed, and it kept one socket of the S3 client's pool. The pool had the SDK's default
size of 50 and no timeout that frees an unread body. After 50 aborted downloads every S3 request waited without end;
the health check stayed green because it does not touch S3, and the process ran out of heap hours later. Under load it
became an avalanche: slow downloads made waiting clients give up, and every one of them leaked the next socket.

11.46.3 makes that impossible in several layers, each effective on its own:

| Layer | What it does |
|---|---|
| Idle guard on every download stream | `CoreS3Service.getObject()`, `CoreFileService.getFileStream()` and `getFileStreamByName()` return a stream that destroys its source after `downloadIdleTimeoutMs` (30 s) without read progress. A slow reader that keeps reading is never cut off |
| `pipeFileToResponse()` | destroys the source when the client goes — on the response's `close`, the request's `close` before its end or the socket's `end`/`close` (under an abort storm about one in six aborted downloads reported it only through the request or the socket) — and at once when the client had already gone (a client that gave up while waiting for a socket) |
| Download routes | pass an `abortSignal` to the store (an S3 request still waiting for a socket is dropped when the client leaves), skip the store when the client has gone, destroy a stream that arrives late |
| S3 client | own agents with `maxSockets` 200, `connectionTimeoutMs` 15 000, `socketTimeoutMs` 120 000 |
| Visibility | an exhausted pool is logged as an ERROR once per minute with numbers |

## 2. Configuration

All optional; the defaults are what 11.46.3 runs with.

```typescript
s3: {
  bucket: 'files',
  maxSockets: 200,               // SDK default was 50
  connectionTimeoutMs: 15_000,   // per attempt: wait for a free socket + connect; 3 attempts → 503 after ~46 s
  socketTimeoutMs: 120_000,      // inactivity backstop for every S3 request
  downloadIdleTimeoutMs: 30_000, // S3 download stream without read progress is closed
},
file: {
  downloadIdleTimeoutMs: 30_000, // the same for GridFS and filesystem streams
  downloadCaching: 'none',       // or 'revalidate' (see below)
},
```

Environment: `NSC__S3__MAX_SOCKETS`, `NSC__S3__CONNECTION_TIMEOUT_MS`, `NSC__S3__SOCKET_TIMEOUT_MS`,
`NSC__S3__DOWNLOAD_IDLE_TIMEOUT_MS`, `NSC__FILE__DOWNLOAD_IDLE_TIMEOUT_MS`, `NSC__FILE__DOWNLOAD_CACHING`.

A non-positive or non-numeric value uses the default; the guards cannot be switched off globally (§5 has the per-call
exception). `connectionTimeoutMs` bounds the wait for a free socket too (the SDK starts it when the request is created),
and the SDK retries a timed-out attempt — 3 attempts in all, so the `503` comes after up to about 3 × `connectionTimeoutMs`
plus a short backoff (about 46 s with the default). Keep 3 × the value below your reverse proxy's read timeout (60 s for
nginx and AWS ALB by default; otherwise the proxy answers `504` first) and well above normal queue waits — a short value
fails healthy downloads under load.

**`file.downloadCaching: 'revalidate'`** sends `Cache-Control: private, no-cache`: the browser keeps the file but asks
again on every use; that request runs the full role and rights check and is answered `304 Not Modified` without reading
the store. For image-heavy apps it removes most store reads. The default `'none'` keeps `private, no-store` (nothing is
kept on the device). Both modes send a weak `ETag` (`W/"<file id>"` — weak because a `compression` middleware may
deliver the same file gzip-encoded or not) and `Content-Length`.

**Compression:** a `compression({ filter: () => true })` gzips already compressed downloads (JPEG, PNG, PDF, ZIP) and only
burns CPU under many parallel downloads. nest-server's reference `main.ts` now uses `filter: compression.filter` (the
package default); nest-server-starter follows.

## 3. Own download routes

Replace every `stream.pipe(res)` that delivers a file with `pipeFileToResponse(stream, res)`, and pass an abort signal:

```typescript
import { downloadAbortSignal, pipeFileToResponse } from '@lenne.tech/nest-server';

@Get('image/:id')
async image(@Param('id') id: string, @Res() res: Response, @CurrentUser() currentUser) {
  // Fires when the client goes (response or request close), so a store request waiting for a socket is dropped
  const abortSignal = downloadAbortSignal(res);
  const stream = await this.fileService.getFileStream(id, { abortSignal, currentUser });
  if (!stream) {
    throw new NotFoundException();
  }
  res.header('Content-Type', 'image/png');
  return pipeFileToResponse(stream, res);
}
```

The idle guard would release a bare-piped stream after 30 s as well, but under load 30 s per aborted download is enough
to fill a pool.

## 4. Monitoring

Alert on `S3 socket pool exhausted:` in the log (level ERROR, at most once per minute per process). It names the
sockets in use, the waiting requests and the download streams closed for lack of progress. Genuine load → raise
`s3.maxSockets`; a growing count without load → a download path that does not use `pipeFileToResponse()`.
`CoreS3Service.getSocketPoolStats()` returns the same numbers for a metrics endpoint.

Downloads the idle guard closed are reported as ONE warning per minute (`N file download(s) closed after no read
progress …`), split into clients that stopped reading without closing and stores that delivered nothing. A client that
stops reading is not a server error, so it never produces an ERROR line per download. A store that delivered nothing
before the first byte answers `503` with `Retry-After`. The health check deliberately does
not fail on it: a short S3 disturbance would take the whole API, sign-in included, out of the load balancer.

## 5. Streams that are read late

Every stream from `getFileStream()`, `getFileStreamByName()` and `CoreS3Service.getObject()` must be read within
`downloadIdleTimeoutMs` (30 s) of being obtained and keep making progress. Code that collects streams first and reads
them later breaks: a ZIP export with `archiver.append(await getFileStream(id), …)` in a loop pipes each source into a
buffer at once but reads it only when that entry's turn comes. A stream the guard closes ends WITHOUT `end`: a `.pipe()`
consumer waits forever, `pipeline()` and `for await` reject (`ERR_STREAM_PREMATURE_CLOSE` / `StreamIdleTimeoutError`).

| Fix | How |
|---|---|
| Open each stream right before it is read (preferred) | archiver: append the next file only after the previous entry finished (`entry` event) |
| Raise the idle time | `file.downloadIdleTimeoutMs` / `s3.downloadIdleTimeoutMs` (capped at 2^31 − 1 ms, about 24.8 days) |
| Opt out for one call | `getFileStream(id, { downloadIdleTimeoutMs: false, … })` / `getObject(key, { idleTimeoutMs: false })` — only when the code is certain to read the stream to the end or destroy it; until then it holds its socket, file handle or cursor |

For S3 both have a second limit: a socket without traffic for `s3.socketTimeoutMs` (120 s) is closed by the SDK, so an
S3 stream that is not read for that long ends with an error even with the opt-out — raise `s3.socketTimeoutMs` as well
for exports that let an entry wait longer. The opt-out keeps the guard's error handling, so that error never ends the
process.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Downloads answer `503` with `Retry-After` | no store connection within `s3.connectionTimeoutMs` — the pool is exhausted | genuine load: raise `s3.maxSockets`; otherwise look for downloads that do not go through `pipeFileToResponse()` |
| A very slow client gets a truncated file | it read nothing for `downloadIdleTimeoutMs` | raise `s3.downloadIdleTimeoutMs` / `file.downloadIdleTimeoutMs` |
| A ZIP export or batch job hangs or produces truncated entries | it opens file streams first and reads them later (§5) | open each stream right before reading it, or opt out per call (§5) |
| The proxy answers `504` while the pool is exhausted, the API never shows its `503` | 3 × `connectionTimeoutMs` (SDK retries) exceeds the proxy's read timeout | lower `s3.connectionTimeoutMs` (§2) |
| `S3 socket pool exhausted` in the log | see §4 | see §4 |
