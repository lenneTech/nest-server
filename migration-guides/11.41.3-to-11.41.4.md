# Migration Guide: 11.41.3 → 11.41.4

## Overview

| Category                 | Effort                  | Applies to                                                                                             |
| ------------------------ | ----------------------- | ------------------------------------------------------------------------------------------------------ |
| **New feature (opt-in)** | config + a thin controller | API tokens: USER tokens and — with multi-tenancy — TENANT tokens, signed assertions for embedded pages |
| Improvement              | none, optional clean-up | `mountAiMcpOAuth(app)` takes the OAuth issuer from the server config                                   |
| **Security fix**         | none, verify once       | Role guards hand non-system roles to the tenant guard only while one is REGISTERED                     |
| Dependencies             | `pnpm run update`       | `@nestjs/*` 11.2.6, mongoose 9.10.2 / mongodb 7.6.0, multer 2.4.0 — align your own pins (§4)           |

No breaking change for a standard setup. Without an `apiTokens` block the token feature does nothing; the security fix only changes behaviour where `multiTenancy` is configured but no tenant guard is registered (see §3).

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm run update            # starter-based projects: aligns the framework's ecosystem (see §4)
pnpm run build && pnpm test
```

Vendor-mode projects adopt the new `src/core/modules/api-token/` directory and the touched guards
through the core update.

## What's New in 11.41.4

### 1. API tokens

Bearer credentials for machine clients, scripts and embedded pages that cannot carry a session cookie.

|                     | USER token                                          | TENANT token           |
| ------------------- | --------------------------------------------------- | ---------------------- |
| Belongs to          | one user                                            | one tenant             |
| Acts with           | the user's current rights, **without** global roles | the lowest tenant role |
| Optional limits     | scopes, one tenant, `maxTenantRole`, expiry         | scopes, expiry         |
| Needs multi-tenancy | no                                                  | yes                    |

```typescript
// config.env.ts
apiTokens: {
  scopes: ['upload', 'read', 'export'],
  encryptionKey: process.env.API_TOKEN_ENCRYPTION_KEY, // required in production/staging
},

// a route a token may call — tokens are denied on every other route, public ones included
@ApiTokenScopes('upload')
@Roles(RoleEnum.S_USER)
@Post('documents')
```

Management goes through `CoreApiTokenService` (`createUserToken`, `createTenantToken`, …); the project
writes a thin controller. Full integration: `src/core/modules/api-token/INTEGRATION-CHECKLIST.md`.

Security properties worth knowing before you open a route:

- A token only reaches routes that declare `@ApiTokenScopes()`; every guard enforces that.
- A prefixed credential that fails answers **401 on every route** — it is never silently anonymous.
- Tenant boundaries hold for both kinds: a tenant token only in its tenant, a user token only in its
  user's active memberships (and in one of them, if restricted).
- A tenant token is no person: a route guarded only by `S_SELF` / `S_CREATOR` refuses it, and
  `@CurrentUser()` carries no `email` / `verified`.
- Tokens never manage tokens — `CoreApiTokenService` refuses a token caller even on a route you
  released; a platform admin's user token is not a platform admin. Protected fields (`tenant`, `user`,
  `kind`, `revokedAt`, …) cannot be set through a management input, dotted paths included.
- The MCP OAuth consent step (`mountAiMcpOAuth`) refuses token-authenticated requests: a consent
  mints an access token with the user's full rights. An override of `authorizeConsent()` keeps this check.
- A password reset that ends the user's sessions ends their user tokens too: the legacy reset always,
  the IAM reset while `betterAuth.emailAndPassword.revokeSessionsOnPasswordReset` is on (recommended).
  Tenant tokens are not affected — they belong to the tenant.

What your project has to take care of itself:

| Topic                               | What to do                                                                                                                                                                                                        |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deleting or off-boarding a tenant   | Call `CoreApiTokenService.deleteAllForTenant(tenantId)`. The core has no tenant model to notice the deletion, and a tenant token depends on no member — until you call it, the tenant's tokens keep authenticating                         |
| Account compromise without a reset  | Call `CoreApiTokenService.revokeAllForUser(userId)`. With `revokeSessionsOnPasswordReset` off, an IAM reset leaves user tokens alive, like personal access tokens elsewhere; a password CHANGE never revokes them |
| Routes mounted with `app.use()`     | They run outside the Nest guards, so `@ApiTokenScopes()` does not protect them and `req.user` may be a token. Check `getApiTokenContext(req.user)` there                                                          |
| `@CurrentUser()` on an opened route | For a tenant token it is not a person: no `email`, no `verified`. Code that mails or notifies "the current user" must check `getApiTokenContext()` first                                                          |
| Better-Auth admin plugin (`banned`) | Not used by the framework. If you add it, override `CoreApiTokenService.loadTokenUser()` so a banned user's tokens are refused too                                                                                |
| Brute force against tokens          | Tokens carry 256 bits of secret, so guessing is not the risk — but failed attempts are not rate-limited per IP. Put an IP limit in front (reverse proxy / WAF) if the API is exposed                              |
| Secret scanning                     | Register the shape `<prefix>_<24 hex>_<64 hex>` as a custom pattern                                                                                                                                               |

### 2. `mountAiMcpOAuth(app)` without `baseUrl`

The OAuth issuer — and with it every URL in the discovery metadata that MCP clients follow — now
defaults to the server's `baseUrl` (`NSC__BASE_URL`), resolved like BetterAuth and CORS resolve it.
`local` / `ci` / `e2e` fall back to `http://localhost:3000`; any other environment without a
`baseUrl` fails the call instead of advertising a guessed localhost URL. The resolved issuer is logged
once at boot.

```typescript
// Before
await mountAiMcpOAuth(app, { baseUrl: envConfig.baseUrl || `http://localhost:${envConfig.port}` });

// After
await mountAiMcpOAuth(app);
```

An explicit `baseUrl` still wins. Remove a hand-written `localhost` fallback: it is exactly what made a
deployed API advertise `http://localhost:3000` and send MCP clients to the user's own machine.

### 3. Role guards delegate only to a registered tenant guard (security fix)

`RolesGuard` and `BetterAuthRolesGuard` hand every non-system role to `CoreTenantGuard`, which
resolves it against the membership. They used to decide that from CONFIGURATION alone: with
`multiTenancy` set but no tenant guard actually registered, a role such as `RoleEnum.ADMIN` went to
a guard that never ran, and every authenticated caller passed. They now delegate only while a tenant
guard is registered, and otherwise check the roles against `user.roles` themselves (with a one-time
warning).

A project that lets `CoreModule` register the tenant module — the normal setup — sees no difference.
If your project replaces the tenant module with its own registration, make sure a tenant guard is
still registered, either through `CoreTenantModule.forRoot({ guard })` or as `CoreTenantGuard`
itself.

### 4. Dependency updates

A maintenance pass ships with this release. No major version moved in `dependencies` or
`peerDependencies`; `better-auth` stays on its `>=1.7.1 <1.8.0` peer range.

| Package | 11.41.3 | 11.41.4 |
| ------- | ------- | ------- |
| `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express` | 11.2.1 | 11.2.6 |
| `mongoose` / `mongodb` | 9.9.3 / 7.5.0 | 9.10.2 / 7.6.0 |
| `multer` | 2.3.0 | 2.4.0 |
| `graphql` | 16.14.0 | 16.14.2 |
| `jose` | 6.2.9 | 6.2.12 |
| `@modelcontextprotocol/sdk` | 1.30.0 | 1.30.1 |
| `@tus/server` | 2.4.4 | 2.4.5 |
| `compression` | 1.8.1 | 1.8.2 |
| `supertest` | 7.2.2 | 7.3.0 |

**What to do:** if your project pins any of these itself — most do for `@nestjs/common`,
`@nestjs/core`, `@nestjs/platform-express` and `mongoose` — raise the pins to the versions above.
A pin that lags behind the framework puts a second copy into the tree, and with `@nestjs/*` that
surfaces as type errors about classes that "incorrectly extend" their base class. Starter-based
projects get this from `pnpm run update`, which also raises the tooling devDependencies a project
shares with the framework: `@nestjs/testing` 11.2.6, `@swc/core` 1.16.2, `@types/node` 26.6.2,
`oxfmt` 0.70.0, `oxlint` 1.85.0 and `unplugin-swc` 2.0.0 (a major, whose only breaking change is
dropping Node 18).

**Security overrides:** `@nestjs/platform-express` 11.2.6 pins `multer` 2.4.0 itself, so the
`multer` override from `docs/security-overrides.md` is inert on this version. Keep it as insurance
and raise its target in lockstep: `'multer@>=2.0.0 <2.4.0': '2.4.0'`. The `ws` and `js-yaml`
entries are likewise inert on the `@nestjs/graphql` / `@nestjs/swagger` versions this framework
declares; they only matter where your own `package.json` pins older ones.

## Compatibility Notes

| Pattern                                                                           | Status                                                                                                                                                                                                                                                                                                               |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Projects without `apiTokens`                                                      | Unchanged                                                                                                                                                                                                                                                                                                            |
| Custom guards extending `RolesGuard` / `BetterAuthRolesGuard` / `CoreTenantGuard` | Unchanged as long as they call `super.canActivate()`. A guard that replaces the logic entirely skips the token rules in THAT guard: route release and scopes are still enforced by the role guard, but a user token's tenant restriction and `maxTenantRole` are applied only by `CoreTenantGuard` — keep calling it |
| A project using the `x-api-key` header for its own keys                           | Only values carrying the token prefix are claimed; everything else passes through                                                                                                                                                                                                                                    |
| `mountAiMcpOAuth(app, { baseUrl })`                                               | Unchanged; the argument is optional now                                                                                                                                                                                                                                                                              |
| `multiTenancy` configured without any registered tenant guard                     | Non-system roles are now checked against `user.roles` instead of being waved through — a route that relied on the gap starts answering 403                                                                                                                                                                           |

## Troubleshooting

| Symptom                                                        | Cause                                                                              | Fix                                                           |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Boot error mentioning `apiTokens.manageRole` or "a role below" | The manage role is not a declared tenant role, or the hierarchy has a single level | Declare the role / add a lower role, or `tenantTokens: false` |
| Boot error "encryptionKey … required in production/staging"    | No key configured                                                                  | Set `apiTokens.encryptionKey` or `SECRETS_ENCRYPTION_KEY`     |
| A token gets 403 on a route                                    | Route not opened, scope missing, role too high, foreign tenant                     | `@ApiTokenScopes()`, token scopes, `X-Tenant-Id`              |
| `mountAiMcpOAuth: no public server URL` at boot                | Deployed without `baseUrl`                                                         | Set `NSC__BASE_URL`                                           |
