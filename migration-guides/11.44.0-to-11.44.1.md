# Migration Guide: 11.44.0 → 11.44.1

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None in the API. Non-canonical paths under the Better-Auth base path answer 400, the IAM rate limit counts per route (§2). `emailAndPassword.disableSignUp: true` closes social sign-up too (§3) |
| **New Features** | `CoreBetterAuthService.isPersistedUser()`, `CoreBetterAuthUserMapper.mapUnstoredSessionUser()` and `equalizeLegacyPasswordSync()` (§1). `socialProviders.<name>.disableSignUp` (§3). `CoreBetterAuthPathGuardMiddleware`, `canonicalRequestPath()`, error code `LTNS_0305` (§2) |
| **Bugfixes** | Security: a sign-up for an already registered address changed the existing account (§1). Dot segments under the IAM base path bypassed the controller and the rate limiter (§2). Social login created accounts while sign-up was switched off (§3) |
| **Migration Effort** | Update. Projects that had `requireEmailVerification: true` or `autoSignIn: false` with open sign-up check their accounts (§1). A deployment with a tight `betterAuth.rateLimit.max` checks the value (§2). A project that closed sign-up but wants new users through one social provider sets one flag (§3) |

11.44.1 is a security patch for 11.44.0 (`latest-11`). §1 ships in 12.8.1 and 12.6.6 as well. §2 and §3 are backports
of 12.3.0, where 12.x has had them since.

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@11.44.1
pnpm run update   # nest-server-starter based projects (release/11.x)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. A sign-up for an already registered address changes nothing

**Why:** with `emailAndPassword.requireEmailVerification: true` or `emailAndPassword.autoSignIn: false` (set through
`betterAuth.options`), Better-Auth 1.5.0 and later answers a sign-up for a known address like a new one, so the
response does not reveal which addresses have an account. That answer carries a placeholder user: a generated id and
the given address, stored nowhere. The core's sign-up paths took it for the new user:

- **REST `POST /iam/sign-up/email`** (`CoreBetterAuthController.signUp()`, also without a project override) linked the
  placeholder to the real account it found by address. That account's `iamId` then pointed at the placeholder, it got
  `verified: false`, its **legacy password was set to the one the caller chose**, and the answer carried its roles.
- **GraphQL `betterAuthSignUp`** linked it the same way and answered with the real account's id and roles.
- **The legacy sign-up with IAM enabled** (`/auth/signup`, GraphQL `signUp`) linked it, overwrote the password and
  returned the real account, and the caller received its tokens.

With the legacy endpoints open, the overwritten legacy password let the caller sign in as the account owner. For a
legacy user without an IAM credential account, the next IAM sign-in with that password migrated the account to it.

**What changed:** a user Better-Auth returns from a sign-up is written only once `CoreBetterAuthService.isPersistedUser()`
confirmed it through Better-Auth's own adapter. For a placeholder, nothing is linked and no password is synced. The
answer stays that of a new sign-up: its own id, no roles, not verified, and the same bcrypt round as a real sign-up,
so neither the body nor the response time tells the address exists. The legacy sign-up answers a known address with
`Email address already in use`, as it always did without IAM.

**Who was affected:** a project running better-auth 1.5.0 or later (nest-server 11.18.0 and later pin it) whose
Better-Auth options set `requireEmailVerification: true` or `autoSignIn: false`, with sign-up open
(`emailAndPassword.disableSignUp: true` refused the request before it reached Better-Auth). Without those options
Better-Auth answers a known address with an error, and the core answered `EMAIL_ALREADY_EXISTS` without writing.

**Your project:** update. If the conditions above applied, the traces an attack leaves on an account do not list every
affected one: `iamId` no longer matching the account's own id, and `verified: false` next to `emailVerified: true`, are
written back by the owner's next IAM sign-in, while the overwritten legacy password stays. Take the time the options
were active as the window and:

- **Accounts that still carry a trace:** remove the legacy `password`, end their sessions (IAM sessions and legacy
  refresh tokens) and send a password reset.
- **Every account with a Better-Auth credential account:** remove the legacy `password`. IAM sign-in does not read it,
  only the legacy endpoints do. Where `auth.legacyEndpoints` keeps those open (closed by default since 11.38.0), send
  these accounts a password reset instead.
- **Credential accounts created in the window for a user who existed before it:** a legacy user's first IAM sign-in
  creates one with the password used for that sign-in, after an attack the caller's. End those sessions and send a
  password reset.

Better-Auth logs a sign-up for a known address ("Sign-up attempt for existing email") only at `logger.level: 'info'` or
lower. Its default is `warn`, so there is usually no log trail. A project test that stubs `CoreBetterAuthService` for
the sign-up needs `isPersistedUser`.

## 2. Requests under the Better-Auth base path

### Non-canonical paths answer 400

Every check under the base path (`/iam` by default) — rate limiter, controller routes, the forwarding to Better-Auth —
read the path as sent, while Better-Auth routes the path after `new URL()` resolved it. `/iam/sign-up/%2e/email`
therefore reached Better-Auth's own sign-up past the controller and every project override, and
`/iam/callback/../sign-in/email` passed the rate limiter as a skipped OAuth callback and ran as a sign-in.

`CoreBetterAuthPathGuardMiddleware` now runs first under the base path and answers **400** (`#LTNS_0305: Invalid
request path`) for a path with a `.` or `..` segment (also `%2e`-encoded), a backslash, an encoded `/` or `\`, or a
`#`. No Better-Auth route needs any of them; a client that sends one has a bug. It is registered by
`CoreBetterAuthModule` itself, so there is nothing to add. `CoreBetterAuthApiMiddleware` and the rate limiter decide on
the same canonical path (`canonicalRequestPath()`) as well, so they stay right where the guard is not registered.

### The IAM rate limit tells routes apart

The rate-limit middleware read `req.path`, which is `/` for a middleware Nest mounts under the base path. So every IAM
request of a client shared one counter with the full limit, and the skip list (`/session`, `/callback`) and the halved
limit for sign-in, sign-up and the password routes never applied over HTTP.

Now a client IP has one counter per route NAME — the last path segment — so `/sign-in/email` and `/sign-up/email` (both
`email`) share one counter. `/session` and `/callback` are not counted, and the strict routes (sign-in, sign-up, the
password reset and change routes) get half of `betterAuth.rateLimit.max`, rounded up. The skip and strict lists match
whole path segments, case-insensitively, as Express routes.

**What to check:** a deployment that set `betterAuth.rateLimit.max` (the nest-server-starter reads it from
`IAM_RATE_LIMIT_MAX`) gets half of it for the e-mail sign-in and sign-up now, and the two count together: with
`max: 10`, five attempts per window for both combined. Behind a shared NAT or proxy, sign-ups use up the same budget as
sign-ins. Raise the value if that is too tight.

## 3. Social login creates no account while sign-up is switched off

Only with `betterAuth.emailAndPassword.disableSignUp: true` and at least one social provider. The flag closed
`/sign-up/email` only. Better-Auth decides a social sign-up per provider, and each provider got only its `clientId` and
`clientSecret`, so whoever signed in with Google, GitHub etc. for the first time got an account in a project that had
closed self-registration.

**What changes:** every configured provider now receives the flag, so `disableSignUp: true` closes sign-up through
every social provider as well, unless that provider sets its own `disableSignUp`. A first sign-in through a provider by
somebody who has no account is refused (the OAuth callback redirects with `error=signup_disabled`, `/sign-in/social`
with an `idToken` answers 401 `signup disabled`). Users who already have an account keep signing in, also through a
provider they have not used before: Better-Auth checks the flag only when no user exists for the address.

**What to check:** a project that closed sign-up on purpose needs nothing. A project that closed e-mail sign-up but
wants new users through a provider opens that one deliberately:

```typescript
// config.env.ts
betterAuth: {
  emailAndPassword: { disableSignUp: true },
  socialProviders: {
    google: { clientId: '...', clientSecret: '...', disableSignUp: false }, // new users through Google
    github: { clientId: '...', clientSecret: '...' },                       // follows disableSignUp: closed
  },
},
```

`disableSignUp: true` on a provider closes sign-up for that provider alone, while sign-up stays open elsewhere. Only a
boolean counts there: any other value, such as the string `"false"` in `NEST_SERVER_CONFIG`, follows
`emailAndPassword.disableSignUp`. Plugins a project registers itself through `betterAuth.options.plugins` are not
covered; set their own sign-up options.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| 400 `#LTNS_0305` on an IAM request | The path carries a dot segment, a backslash, an encoded separator or a `#` | Fix the client's URL |
| 429 on sign-in or sign-up earlier than before | The strict routes get half of `betterAuth.rateLimit.max`, and sign-in and sign-up share one counter (§2) | Raise `betterAuth.rateLimit.max` |
| New users land on the error page with `error=signup_disabled` after a social login | `disableSignUp: true` covers social providers (§3) | Expected; or set `disableSignUp: false` on the provider |
| A project test fails with `SIGNUP_FAILED` | Its stub of `CoreBetterAuthService` has no `isPersistedUser` (§1) | Add `isPersistedUser: async () => true` to the stub |
