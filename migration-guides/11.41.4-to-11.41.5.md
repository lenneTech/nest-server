# Migration Guide: 11.41.4 → 11.41.5

## Overview

| Category              | Details                                                                                                          |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Breaking Changes**  | None in the package                                                                                              |
| **Bugfix**            | `migrate down` now holds the migration lock, like `migrate up` already did                                       |
| **Template change**   | nest-server-starter's `docker-entrypoint.sh` now aborts the start when a migration RAN AND FAILED (§2)           |
| **New option**        | `MIGRATIONS_ALLOW_FAILURE=true` — start anyway for one deploy (starter and this repo's entrypoint)               |
| **Dependencies**      | nodemailer 9 → 10 (security; the only break is Node >= 20), js-yaml override now needed in your project (§3)     |
| **Migration Effort**  | Raise two overrides in your `pnpm-workspace.yaml` (§3); decide once whether to adopt the strict entrypoint (§2)  |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm run update            # starter-based projects: aligns the framework's ecosystem (see §3)
pnpm run build && pnpm test
```

Vendor-mode projects pick up `migration-runner.ts` through the core update.

## What's New in 11.41.5

### 1. `migrate down` holds the migration lock

Since 11.33.0, `migrate up` (`MigrationRunner.up()`) runs under the lock of the state store's lock
collection — `migrations_lock` by default for stores built by `createMigrationStore()` — so replicas
booting together serialize instead of each applying the same pending migration. `migrate down`
did not. A rollback is typically run while a deploy is failing, i.e. exactly while replicas restart
and each boots into `migrate up`; outside the lock the two read and rewrote the migration state
concurrently. `MigrationRunner.down()` now takes the same lock. `migrate list` only reads and stays
unlocked.

Nothing to do: projects using `createMigrationStore()` get it automatically. A store built with an
empty lock collection name (`createMigrationStore(uri, 'migrations', '')`) still runs unlocked, as
before.

### 2. The starter's entrypoint aborts on a migration that ran and failed

This concerns `docker-entrypoint.sh` in **nest-server-starter** (and therefore in projects created
from it), not the npm package. Until now the starter's entrypoint logged a failed migration and
started the server anyway. A failed schema migration is then indistinguishable from a good deploy
on every level anyone watches — health check 200, the right commit on `/meta`, drift detection
green, `turbo deploy --wait` converging — over an app that works against the empty collections
Mongoose created at boot while the data still sits under the old names.

| Situation | Before | Now |
| --------- | ------ | --- |
| A migration ran and threw | warning, server starts | **start aborted** (exit 1); the container runtime retries |
| `MIGRATIONS_ALLOW_FAILURE=true` | — | warning, server starts — a deliberate exception for ONE deploy |
| `MIGRATE_FAILURE_POLICY=warn` / `abort` | `warn` was the default | still honoured; wins over `MIGRATIONS_ALLOW_FAILURE` |
| Unknown value in either variable | fell back to `warn` | falls back to `abort`, with a warning |
| A recorded migration whose FILE is gone | warning, server starts | unchanged: warning, server starts |
| No migrations bundled / no CLI in the image | skipped | unchanged: skipped |

The last-but-one row is deliberate: migrations that ran everywhere may simply be deleted once a new
instance no longer needs them (git history restores them). The migrate CLI reports such a file as a
warning, and the entrypoint passes no `--strict`. A project that wants the opposite sets
`NSC__MIGRATE__STRICT=true` explicitly — that stays available, it is just not the default.

**What to do in an existing project:** your `docker-entrypoint.sh` is your own file, so nothing
changes until you adopt the new one. To adopt it, copy `docker-entrypoint.sh` from
nest-server-starter 11.41.5. If a deploy must go out with a migration known to fail, set
`MIGRATIONS_ALLOW_FAILURE=true` for that deploy and unset it again once the migration is fixed.

This repository's own `docker-entrypoint.sh` already defaulted to `abort`; it gained the
`MIGRATIONS_ALLOW_FAILURE` alias.

### 3. Dependency updates

| Package | 11.41.4 | 11.41.5 |
| ------- | ------- | ------- |
| `nodemailer` | 9.1.1 | **10.0.13** |
| `mongoose` | 9.10.2 | 9.10.3 |
| `@modelcontextprotocol/sdk` | 1.30.1 | 1.31.0 |
| dev: `@swc/core`, `@types/multer`, `@types/node`, `oxfmt`, `oxlint` | 1.16.2, 2.2.0, 26.6.2, 0.70.0, 1.85.0 | 1.16.12, 2.3.0, 26.6.3, 0.71.0, 1.86.0 |

**nodemailer 10 is a major, and it ships in a patch on purpose.** Five advisories cover 9.1.1 — two
of them high (GHSA-v53p-9fqp-m79j, GHSA-prgh-xp8r-p3m5), three moderate — and they are fixed only in
10.x; there is no 9.x backport. The single breaking change of 10.0.0 is "Node.js 20 or newer is
required", and this package already requires Node >= 22.12. 10.x is a TypeScript rewrite that ships
its own declarations; `@types/nodemailer` is no longer read. Only one thing changes for code that
uses nodemailer's types directly:

```typescript
import type * as SMTPTransport from 'nodemailer/lib/smtp-transport';

let transport: SMTPTransport;          // before: the namespace WAS the class
let transport: SMTPTransport.default;  // nodemailer 10: the class is the default export
let options: SMTPTransport.Options;    // unchanged
```

`MailTransportOptions` in `IServerOptions` was adjusted the same way; a project that only passes a
plain options object (`email.smtp`) is unaffected.

**What to do:**

1. Starter-based projects: `pnpm run update` raises `mongoose` and the dev tooling to the versions above.
2. Two overrides `pnpm run update` does NOT touch — edit `overrides:` in your `pnpm-workspace.yaml`:

   ```yaml
   # The lockstep entry from nest-server-starter. Left at 9.1.1 it forces the framework's
   # nodemailer back DOWN to 9.1.1 — and keeps all five advisories.
   nodemailer: 10.0.13

   # @nestjs/swagger 11.4.7 (the newest 11.x) exact-pins js-yaml 5.3.0, covered by
   # GHSA-r3ph-w7gj-g6xm (moderate, patched >=5.4.1). Replaces an older `<5.2.2` entry, which no
   # longer reaches that pin. Background: docs/security-overrides.md.
   'js-yaml@>=5.0.0 <5.4.2': '5.4.2'
   ```

3. Run `pnpm install` and `pnpm audit` — both advisories must be gone.

Overrides in this repository never reach your project (pnpm applies them only to the root of an
install), which is why the js-yaml entry has to be repeated there.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| `createMigrationStore(uri)` / `createMigrationStore(uri, 'migrations')` | Lock active for `up` and now `down` |
| A custom `MongoStateStore` without `lockCollectionName` | Unchanged: runs unlocked |
| `NSC__MIGRATE__STRICT=true` | Unchanged: a missing recorded migration file fails the run |
| A `nodemailer: 9.1.1` override (starter-derived projects) | Pins nodemailer 9.1.1 under the framework — raise it to `10.0.13` (§3) |
| Code typing `import * as X from 'nodemailer/lib/…'` as `X` | Use `X.default` (§3) |
| Your own `docker-entrypoint.sh` | Unchanged until you adopt the starter's (§2) |

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| Container restarts in a loop, log: `refusing to start against a possibly half-applied schema` | A migration ran and failed (new entrypoint) | Fix the migration; for one deploy, `MIGRATIONS_ALLOW_FAILURE=true` |
| `migrate down` waits with `Waiting for migration lock release …` | Another replica is running `migrate up` | Wait; a lock whose holder died is broken after 60 s without heartbeat |
| `Strict mode: N recorded migration file(s) missing` | `NSC__MIGRATE__STRICT=true` and a migration file was deleted | Restore the file from git, or unset `NSC__MIGRATE__STRICT` |
| `pnpm audit` still reports nodemailer advisories after the update | A `nodemailer: 9.1.1` override pins the old version | Raise it to `10.0.13` |
| `pnpm audit` reports GHSA-r3ph-w7gj-g6xm (js-yaml) | No (or an old `<5.2.2`) js-yaml override | Add `'js-yaml@>=5.0.0 <5.4.2': '5.4.2'` |
| `TS2709` / `Cannot use namespace 'SMTPTransport' as a type` | nodemailer 10 types | Use `SMTPTransport.default` |
