# Migration Guide: 11.42.0 → 11.42.1

## Overview

| Category             | Details                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------- |
| **Bugfix**           | Browser uploads through TUS work with cookie authentication and separate app/API origins (§1) |
| **New option**       | `tus.allowedOrigins` overrides the derived origins (§1)                                       |
| **Migration Effort** | None — `pnpm update`                                                                          |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick up the core update; nothing else to change.

## 1. TUS answered a credentialed request with `Access-Control-Allow-Origin: *`

The tus handler writes its responses itself, past the API's CORS layer, and `@tus/server` answers
`Access-Control-Allow-Origin: *` unless it is given `allowedOrigins`. The core gave it none. With cookie
authentication and separate app and API origins (`lt dev up`, or `app.example.com` /
`api.example.com`), the request is credentialed and the API adds
`Access-Control-Allow-Credentials: true` — a combination every browser refuses:

> The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*'
> when the request's credentials mode is 'include'.

So every browser upload failed, while the server answered `201`. Preflights and unauthenticated
requests were fine, which is why no test noticed — only an **authenticated** request with an `Origin`
reaches the header.

Since 11.42.1 the tus server takes its origins from `buildCorsConfig()`, the decision REST, GraphQL and
Better-Auth already share (`appUrl`, `baseUrl`, `cors.allowedOrigins`, `cors.allowAll`), and mirrors an
allowed `Origin`. A foreign origin gets no `Access-Control-Allow-Origin` at all. To use different
origins for uploads:

```typescript
tus: {
  allowedOrigins: ['https://uploads.example.com'];
}
```

Without credentialed CORS configured — cookies off, or no origin resolvable — nothing changes; the tus
default `*` stays.

## 2. Dependencies

Updated within their majors: `@modelcontextprotocol/sdk` 1.32.0, `mongoose` 9.10.4, `supertest` 7.3.1, and
the `@aws-sdk/*` S3 packages 3.1146.0 (dev). NestJS stays on 11.

`@modelcontextprotocol/sdk` 1.32.0 lets its CLIENT transports follow redirects only within the same
origin. The framework uses the server side only, so this matters only to a project that builds its own MCP
client transport and relied on a cross-origin redirect.

## Troubleshooting

| Symptom                                                                                            | Cause                                          | Fix                                                          |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| Browser: "must not be the wildcard '*' when the request's credentials mode is 'include'" on `/tus` | 11.42.0 or older                               | Update to 11.42.1                                            |
| Upload from an origin that is not the app refused by CORS                                          | Origin not in `appUrl` / `cors.allowedOrigins` | Add it to `cors.allowedOrigins`, or set `tus.allowedOrigins` |
