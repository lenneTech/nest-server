# Migration Guide: 12.8.5 → 12.8.6

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None. Both additions are opt-in; without `ai.mcp.roles` MCP behaves as before |
| **New Features** | `ai.mcp.roles` / `CoreAiMcpOAuthService.mayUseMcp()`: who may use MCP at all, checked on every way in (§1). `sendConsentNotice()`: a notice page on the MCP OAuth consent route with the consent page's security headers (§2) |
| **Security** | Until 12.8.5 there was no account-level MCP rule. A refusal a project built into `authorizeConsent()` was bypassed with the user's own session token or JWT as bearer, and earlier grants kept refreshing (§1) |
| **Migration Effort** | None, unless the project limits MCP to some accounts — then move that rule into `ai.mcp.roles` or `mayUseMcp()` (§1). Projects that deep-import `mcpOAuthConsentHeaders()` switch to `sendConsentNotice()` (§2) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.6
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Who may use MCP: `ai.mcp.roles` and `mayUseMcp()`

**The gap.** `/ai/mcp` accepts three credentials: the user's own Better-Auth session token or JWT as bearer, and an MCP
OAuth access token. Only the last one passes the consent route `/authorize`. A project that refused some accounts in its
own `authorizeConsent()` override (only administrators may connect MCP clients, say) therefore refused a new OAuth grant
only: a refused user put their own session token into an MCP client (`Authorization: Bearer …`) and used MCP anyway —
with their own rights, so the tools' roles, policies and `authorize()` still applied, but the rule "only administrators"
did not. A grant issued before a refusal also kept producing access tokens through its refresh token.

**What is new.** One rule, checked wherever a credential arrives:

```typescript
// config.env.ts
ai: { mcp: { oauth: true, roles: ['admin'] } }   // or NSC__AI__MCP__ROLES=admin,support
```

| Where | A refused user gets |
|---|---|
| every request to `/ai/mcp` (POST, GET, DELETE), session token, JWT and OAuth token alike | 403 — an open session ends with its next request |
| the consent route `/authorize` | a refusal notice (403) instead of the consent form |
| `/token` (authorization code, refresh token) | `invalid_grant`; the refresh token the rotation issued is revoked |

- Unset: every signed-in user may use MCP, exactly as before.
- The roles are compared with the user's own (global) roles, never a tenant membership role. List every role that may
  use MCP, `admin` included if administrators should.
- A value that names no role (`[]`, `''`, an empty entry, a non-string) or a system role (`s_…`) fails the boot.
- For a rule roles cannot express, override `mayUseMcp(user, req)` in the `CoreAiMcpOAuthService` subclass registered
  via `CoreModule.forRoot(env, { ai: { mcpOAuthService } })`. Only an explicit `true` admits; a throw refuses.
- The refusal's wording comes from `consentRefusal(req)` (German / English by `Accept-Language`), its look from
  `renderConsentNoticePage(view)`.

**What to do.** Nothing, unless the project limits MCP to some accounts. A project that refused accounts in its own
`authorizeConsent()` moves the rule:

```typescript
// Before (12.8.5): refused a new grant only — /ai/mcp stayed open to the user's own session or JWT
protected override async authorizeConsent(client: any, params: any, res: any): Promise<void> {
  const user = await this.consentUser(res.req);
  if (user && !isAdmin(user)) {
    /* own refusal page */
    return;
  }
  return super.authorizeConsent(client, params, res);
}

// After (12.8.6): the whole override goes; the rule is configuration
ai: { mcp: { roles: ['admin'] } }

// …or, for a rule roles cannot express, in the same subclass:
override async mayUseMcp(user: { id: string; roles?: string[] }): Promise<boolean> {
  return this.mcpAccounts.isEnabled(user.id);
}

// Own wording of the refusal (optional)
protected override consentRefusal(req: any): IMcpOAuthConsentNotice {
  return { locale: 'de', message: 'Nur Administratoren dürfen MCP-Clients verbinden.', title: 'Zugriff nicht möglich' };
}
```

A unit test that constructs `CoreAiMcpController` with a stub instead of a `CoreAiMcpOAuthService` now needs
`checkMcpAccess` on the stub (`checkMcpAccess: async () => true`); without it every request is refused.

## 2. A notice of your own on the consent route: `sendConsentNotice()`

For any other case where a project answers `/authorize` itself (maintenance, a closed beta), the page needs the same
protection as the consent page: a CSP with a per-response nonce, `frame-ancestors 'none'`, `X-Frame-Options: DENY`,
`Cache-Control: no-store`. Those headers are deliberately not exported (a project that copies them stops receiving
their fixes), so until now such a page either went without them or deep-imported `mcpOAuthConsentHeaders()` from
`core/modules/ai/helpers/ai-mcp-oauth-consent.helper` — which vendor-mode projects can reach, but which is not API.

`this.sendConsentNotice(res, notice)` answers with a notice page; the framework sets the status, a fresh nonce and the
security headers, the project supplies plain text:

```typescript
protected override async authorizeConsent(client: any, params: any, res: any): Promise<void> {
  if (await this.maintenance.isActive()) {
    return this.sendConsentNotice(res, {
      locale: 'de',
      message: ['Wir warten gerade das System.', 'Bitte versuche es in einer Stunde noch einmal.'],
      status: 503,
      title: 'Wartung',
    });
  }
  return super.authorizeConsent(client, params, res);
}
```

| Field | Meaning |
|---|---|
| `title`, `message` | Plain text, escaped; an array of messages renders one paragraph each |
| `status` | 400–599, default 403; anything else sends 403 with a warning |
| `switchAccount` | Shows the signed-in account with "use another account" (sign-out through Better-Auth, then the same `/authorize` again); default `true` |
| `link` | `{ href, label }` below the message: an absolute `http(s)` URL or a path on this origin; anything else is left out with a warning |
| `locale` | `'de'` / `'en'` for `<html lang>` and the built-in labels; default from `Accept-Language` |

The page issues nothing — no code, no redirect. Its wording and look change like the consent page's: override
`renderConsentNoticePage(view)` and call `renderMcpOAuthConsentNoticePage(view, { texts, styles })`. A notice decides
nothing about MCP access itself (§1).

**What to do:** nothing, unless the project sends such a page itself. A project that applies
`mcpOAuthConsentHeaders(nonce)` from a deep import and renders its own HTML replaces that code with
`sendConsentNotice()` — or, when the page refuses accounts, with `ai.mcp.roles` / `mayUseMcp()` and an overridden
`consentRefusal()` (§1). Its own colours move into `styles` of an overridden `renderConsentNoticePage()`. The deep import
keeps working in vendor mode for now, but the helper's internals may change in any release.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Boot fails with `ai.mcp.roles must name at least one role` | `[]`, `''`, an empty entry or a non-string | List the roles, or remove `ai.mcp.roles` to let every signed-in user use MCP |
| Boot fails with `ai.mcp.roles names system roles` | `s_user`, `S_EVERYONE` … | System roles are runtime checks no user holds; list real roles |
| `/ai/mcp` answers 403 `this account may not use MCP` | The user holds none of `ai.mcp.roles`, or `mayUseMcp()` refused | Expected for that user; check the user's own roles (tenant membership roles do not count) |
| MCP client must sign in again after a role change | `/token` answers `invalid_grant` for a refused user | Expected — grants of refused users end |
| Every request of a controller unit test answers 403 | The test's OAuth service stub has no `checkMcpAccess` | Add `checkMcpAccess: async () => true` to the stub |
