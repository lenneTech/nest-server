# Migration Guide: 11.42.1 → 11.42.2

## Overview

| Category             | Details                                                                  |
| -------------------- | ------------------------------------------------------------------------ |
| **Bugfix**           | Finished TUS uploads answer 204 behind the `compression` middleware (§1) |
| **Migration Effort** | None — `pnpm update`                                                     |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick up the core update; nothing else to change.

## 1. A finished TUS upload never got an answer although the file was stored

`@tus/server` finishes its responses with `res.end(callback)`, a documented Node signature. The
`compression` middleware patches `res.end(chunk, encoding)` and treats the first argument as a chunk,
so the callback reached `Buffer.byteLength()` and threw:

```
TypeError [ERR_INVALID_ARG_TYPE]: The first argument must be of type string or an instance of Buffer … Received function
```

The starter's `main.ts` — and therefore every generated project — registers `compression` with
`filter: () => true` and `threshold: 0`, which removes the two checks that would otherwise skip a
bodyless 204. The failure hit the final `PATCH`, AFTER the upload had been migrated into the file
store: the request hung — the headers were already sent, so no error response could follow — the
client never saw a 2xx, `tus-js-client` never fired `onSuccess`, and no log named `compression`.

Since 11.42.2 `CoreTusService` normalises `res.end(callback)` before the tus server writes
(`normalizeEndCallback()`, wrapped around `getServer().handle()`), so it holds for the core controller
and for any project controller that calls the tus server. No change to `main.ts` is needed; a project
that worked around it by excluding `/tus` from the compression filter can keep or drop that filter.

## 2. TUS request errors are logged with their stack

`CoreTusController` logged only `error.message` for a failed TUS request. A `TypeError` thrown by a
middleware's patched `res.end` then read like a tus failure, with nothing pointing at the middleware —
the defect in §1 took several rounds to find for exactly that reason. The stack is now logged too.
