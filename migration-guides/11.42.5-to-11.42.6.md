# Migration Guide: 11.42.5 → 11.42.6

## Overview

| Category             | Details                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Correction**       | The 11.42.3 → 11.42.4 guide told every project to drop `useBodyParser()` from `main.ts`. With a path-scoped parser in `main.ts` that removes JSON parsing everywhere else (§1) |
| **Improvement**      | The server warns at boot when NestJS skipped its global body parser because of such a path-scoped one (§1)   |
| **Tooling**          | `check:overrides` no longer reports a failed audit as clean, and its probe follows `pnpm_config_registry` (§2) |
| **Breaking Changes** | None                                                                                                         |
| **Migration Effort** | None for most projects. Projects that removed `useBodyParser()` while registering a path-scoped parser in `main.ts` must add it back (§1) |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Then check `main.ts` as described in §1. Vendor-mode projects pick up the core update and need the
same check.

## 1. Keep `useBodyParser()` next to a path-scoped parser

§1 of the [11.42.3 → 11.42.4 guide](./11.42.3-to-11.42.4.md) recommended moving the body limit from
`main.ts` into `bodyParser.json.limit` and deleting the `useBodyParser()` call. That is right, with one
exception the guide did not name.

NestJS registers its own global JSON and URL-encoded parsers inside `app.init()`, but only when no
layer with the same function name exists yet. It compares the NAME and nothing else. A path-scoped
parser registered in `main.ts` before `listen()` carries that name:

```typescript
// main.ts
server.use('/diagnostics', json({ limit: '256kb' })); // a layer named `jsonParser`
```

With `useBodyParser()` removed, NestJS treats the JSON parser as already applied and registers none.
Every request outside `/diagnostics` then reaches its handler with an empty body. A sign-in fails with
a validation error such as "Missing input", and before this release nothing was logged.

**Check `main.ts`.** If it registers `json(...)` or `urlencoded(...)` on a path, keep or restore the
global parser next to it:

```typescript
// main.ts
server.use('/diagnostics', json({ limit: '256kb' }));
server.useBodyParser('json'); // the configured bodyParser.json.limit is applied to it
```

Keep the limit itself in the config (`bodyParser.json.limit`), where it also holds under
`Test.createTestingModule()`. The e2e suite cannot catch the missing parser: the testing module never
runs `main.ts`, so it never registers the path-scoped parser either.

Since 11.42.6 the server logs a warning at boot in exactly this situation:

```
No global json body parser is registered: NestJS skips its own when a layer named `jsonParser`
already exists, and a path-scoped `json()` parser registered before `app.init()` counts as one. …
```

The framework only reports it. It does not register the missing parser itself: NestJS would have put
it after everything `main.ts` registered, and that position is no longer known during module init. A
raw-body webhook or a proxy registered after the path-scoped parser must keep receiving the unread
request stream.

## 2. `check:overrides`: a failed audit is no longer reported as clean

Two fixes in `scripts/check-overrides.mjs` (and the shared registry block in `scripts/check.mjs`):

- When pnpm 11 cannot reach the registry, `pnpm audit --json` prints
  `{"error": {"message": "fetch failed"}}` instead of a report. The guard read that as "0 advisories"
  and printed `ok — N override(s) checked … none is failing`. It now prints
  `could not obtain an audit report` (exit 0) on a live run, and fails (exit 1) when the failed report
  was passed in with `--audit-file`, which is the CI path. The suppression checks still run in that
  case, because they ask the GitHub Advisory API rather than the audit: a suppressed advisory that
  gained a fix still fails with `FIX AVAILABLE`.
- The clean-tree probe reads `pnpm_config_registry`, the variable pnpm 11 audits against. It used to
  read `npm_config_registry`, which pnpm 11 ignores, and could then ask a registry the audit never used.

`scripts/` is not part of the npm package. Projects created from nest-server-starter or lt-monorepo
receive these fixes with their template update.

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| Boot warning "No global json body parser is registered" | `main.ts` registers a path-scoped `json()` and no global parser | Add `server.useBodyParser('json')` to `main.ts` (§1) |
| Requests arrive with an empty body outside one path; sign-in reports "Missing input" | Same cause, on a version before 11.42.6 | Same fix (§1) |
| `check:overrides` prints `could not obtain an audit report (fetch failed)` | The npm registry was not reachable during the audit | Re-run with network access, or pass a captured report with `--audit-file` |
| `check:overrides` fails with `records a failed audit, not a result` | The report passed with `--audit-file` is a pnpm error, not an audit | Capture the report again once the registry answers |
