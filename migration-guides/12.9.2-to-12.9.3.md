# Migration Guide: 12.9.2 → 12.9.3

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | Byte ranges from every file store: `getFileStream(id, { range })`, `CoreS3Service.getObject(key, { range })`, `resolveDownloadRange()`, `setDownloadRangeHeaders()`, `parseRangeHeader()`; `TestDownloadOptions.headers` |
| **Bugfixes** | `GET /files/id/:id` and `GET /files/:filename` answered every `Range` request with `200` and the whole file — Safari does not play a video from such a server (§1) |
| **Migration Effort** | Projects with their OWN route for video, audio or large downloads: answer `Range` (§2). Everyone else: `pnpm run update` |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.9.3
pnpm run update   # nest-server-starter based projects
grep -rn "pipeFileToResponse(" src/   # own download routes: serve ranges where media is delivered (§2)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The framework's download routes answer ranges

Safari refuses to play a video, and stalls audio, from a server that answers a `Range` request with `200` and the
whole file. Chrome plays it anyway, so the problem showed neither locally nor in a Chromium-based Playwright run — it
showed on the first iPhone. Until 12.9.2 the core could not read a byte range at all: `CoreS3Service.getObject()` sent
no `Range`, and `getFileStream()` always opened the whole file. A project could serve ranges from GridFS and the
filesystem with its own code, but not from S3, which every deployed stage with `s3` configured uses.

Since 12.9.3 both download routes answer ranges on every store, without any change in the project:

| Request | Answer |
|---|---|
| `Range: bytes=0-1` (one range inside the file) | `206`, `Content-Range: bytes 0-1/<length>`, `Content-Length: 2`, only those bytes |
| `Range: bytes=1000-` / `bytes=-500` | `206` with the rest of the file / its last 500 bytes |
| A range starting at or past the end of the file | `416`, `Content-Range: bytes */<length>`, `#LTNS_0503` |
| Several ranges, an invalid header, `If-Range` | `200` with the whole file, as before |
| No `Range` | `200` as before, now with `Accept-Ranges: bytes` |

The rights check runs first, as before: a refused or unknown file is `404` whatever the `Range` says. A `206` carries
`no-transform` in `Cache-Control` (`private, no-store, no-transform` by default), which keeps a `compression`
middleware from gzipping the partial body.

## 2. Own download routes

A route of your own that delivers media (or large files a client may resume) answers ranges with three calls:

```typescript
import {
  downloadAbortSignal,
  openDownloadStream,
  pipeFileToResponse,
  resolveDownloadRange,
  RESPONSE_GONE,
  setDownloadRangeHeaders,
} from '@lenne.tech/nest-server';

@Get('video/:id')
async video(@Param('id') id: string, @Res() res: Response, @CurrentUser() currentUser) {
  const serviceOptions = { abortSignal: downloadAbortSignal(res), currentUser };
  const resolved = await this.fileService.resolveFile(id, serviceOptions); // rights check, length, store
  if (!resolved) {
    throw new NotFoundException();
  }
  const range = resolveDownloadRange(res, resolved.info.length); // throws 416 past the end
  const stream = await openDownloadStream(res, () =>
    this.fileService.getFileStream(id, { ...serviceOptions, range }, resolved.store),
  );
  if (stream === RESPONSE_GONE) {
    return res;
  }
  if (!stream) {
    throw new NotFoundException();
  }
  res.header('Content-Type', resolved.info.contentType || 'video/mp4');
  res.header('Cache-Control', 'private, no-store');
  setDownloadRangeHeaders(res, range, resolved.info.length); // 206 + Content-Range, or Accept-Ranges only
  return pipeFileToResponse(stream, res);
}
```

- `resolveDownloadRange()` must run AFTER the rights check: a `416` confirms that the file exists.
- `setDownloadRangeHeaders()` goes after your own headers — it replaces `Content-Length` with the length of the range
  and appends `no-transform` to `Cache-Control`.
- The range reaches every store: S3 with a ranged `GetObject`, GridFS from the chunk holding the first byte, the
  filesystem from that offset — with the same idle guard and abort signal as a whole file, so an aborted range
  releases its S3 socket at once.

**A project that reads ranges itself** (GridFS `openDownloadStream(id, { start, end })`, `createReadStream({ start,
end })`, a hand-written Range parser) can switch to these functions and drop its own code — and gets S3, which such
code could not reach. Mind the end: `range.end` is INCLUSIVE, like HTTP and `createReadStream()`; GridFS counts it
exclusive, which `getFileStream()` translates.

Lower-level pieces, for code that does not go through `CoreFileService`:

- `CoreS3Service.getObject(key, { range: { start, end } })` — the result carries `contentRange` (S3's
  `bytes <start>-<end>/<total>`) and the range's `contentLength`.
- `parseRangeHeader(header, length)` — the pure parser (`{ start, end }`, `'unsatisfiable'` or `undefined`), for a
  route that decides `If-Range` with a strong validator of its own.
- A malformed range (`start > end`, negative, not an integer) throws a `RangeError` before any store is asked.

## 3. Tests

`testHelper.download()` / `downloadBuffer()` take request headers:

```typescript
const res = await testHelper.download(`/files/id/${id}`, { headers: { Range: 'bytes=0-1' }, token });
expect(res.statusCode).toBe(206);
expect(res.headers['content-range']).toBe(`bytes 0-1/${length}`);
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| A video plays in Chrome but not in Safari (iPhone, macOS) | The route answers `Range` with `200` and the whole file | Framework routes: update. Own route: §2 |
| `416` with `#LTNS_0503` | The client asked for bytes past the end of the file; `Content-Range: bytes */<length>` names the real size | Usually a player with a cached, outdated length — reload |
| `RangeError: Invalid byte range` | A `range` with `start > end`, a negative or fractional value reached `getFileStream()` / `getObject()` | Produce it with `resolveDownloadRange()` |
| `InvalidRange` from S3, or a GridFS stream error `Stream end (…) must not be more than the length of the file` | A `range` past the end of the file reached the store | Resolve it against the file's `length` with `resolveDownloadRange()`, which cuts it at the last byte |
