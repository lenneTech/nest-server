# Migration Guide: 11.42.3 → 11.42.4

## Overview

| Category             | Details                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **New option**       | `bodyParser.json.limit` / `bodyParser.urlencoded.limit` — the request body limit, configurable for the first time (§1) |
| **Improvement**      | A request over the body limit is answered with `#LTNS_0304` plus size and limit, and logged with the route (§2) |
| **Security**         | `proxy-addr` 2.0.8 (critical) and `@graphql-tools/utils` 12.0.1 (high) — your project needs a lockfile refresh and one override (§3) |
| **Bugfix**           | Without `betterAuth.secret` and with JWT secrets shorter than 32 characters, native Better-Auth endpoints rejected the session right after sign-in (§4) |
| **Dependencies**     | `nodemailer` 10.0.14 (patch: address-parser and DKIM header fixes) — no action needed |
| **Migration Effort** | Small — `pnpm update` plus one override in `pnpm-workspace.yaml` (§3). Projects that raise the body limit in `main.ts` can move it into the config (§1) |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
pnpm update --depth Infinity proxy-addr
```

Then add the `@graphql-tools/utils` override from §3 to `pnpm-workspace.yaml`, run `pnpm install`,
and check §3 for an older `@graphql-tools/utils` 11.x copy, which the override does not reach.
Vendor-mode projects pick up the core update and need the same two dependency steps. The body limit
needs no configuration: unset, both parsers keep the 100 kB they had.

## 1. The request body limit is configurable

NestJS registers a JSON and a URL-encoded body parser on every application, and until now neither had
a limit anybody chose: body-parser's default of **100 kB** applied, and nothing in the framework or the
starter could change it. A request over it is refused in middleware — before authentication, before
routing, GraphQL included — so a document that grew past 100 kB could no longer be saved, and every
retry failed the same way.

```typescript
// config.env.ts — documents carry HTML: allow 2 MB of JSON, keep form posts at the default
bodyParser: {
  json: { limit: '2mb' },
},
```

| Value                  | Meaning                                                              |
| ---------------------- | -------------------------------------------------------------------- |
| unset                  | 100 kB, exactly as before                                            |
| `2097152`              | bytes                                                                |
| `'500kb'`, `'2mb'`     | 1024-based size; units `b` / `kb` / `mb` / `gb`, case-insensitive    |
| `0`, negative, `'lots'` | refused with an error log at boot; the parser keeps its limit       |

The JSON and URL-encoded limits are separate on purpose: raising one does not raise the other.

**Raise it only where the data model needs it, and only as far.** The parser runs before
authentication, and `JSON.parse` blocks the event loop for the whole body — measured on a realistic
document shape, about 0.5 ms for 100 kB, 16 ms for 1 MB and 55 ms for 2 MB per request. That is why
the default stays at 100 kB.

**If you raise the limit in `main.ts` today**, move it into the config:

```typescript
// main.ts — before: not applied in the e2e suite
server.useBodyParser('json', { limit: '2mb' });

// config.env.ts — after: applied in production AND under Test.createTestingModule()
bodyParser: { json: { limit: '2mb' } },
```

The config is applied during module init, so it holds in every test that builds the app with
`Test.createTestingModule(...).createNestApplication()` — which never runs `main.ts`, so a
`useBodyParser()` call there never reached the e2e suite. Once configured, the value also replaces a
global parser your `main.ts` registered; keeping both is harmless, but the config wins.

A **path-scoped** parser is left alone: `server.use('/upload', json({ limit: '20mb' }))` in `main.ts`
still gives that one path its own limit. The parser runs before routing, so a per-route limit can only
key on the path — and all GraphQL operations share one.

**`rawBody: true`:** `req.rawBody` is kept for apps created with `NestFactory.create(…, { rawBody:
true })`. Under `Test.createTestingModule()` the options passed to `createNestApplication()` are not
visible to providers, so a test app created with `{ rawBody: true }` gets no `req.rawBody` once a limit
is configured.

## 2. An oversized request says what happened

Before, the caller received:

```json
{ "statusCode": 413, "message": "request entity too large" }
```

and the server logged the same text as an error with a stack trace. Now, configured or not:

```json
{ "statusCode": 413, "message": "#LTNS_0304: Request body too large [137270 bytes, limit 102400 bytes]", "error": "Payload Too Large" }
```

The size is present when the client sent a `Content-Length`. Frontends using the error translation of
`@lenne.tech/nuxt-extensions` show the translated `LTNS_0304` text. The server logs one warning per
refused request, with method, path (without query string) and the config key to raise:

```
413 PATCH /offers/6650…: json body of 137270 bytes exceeds the limit of 102400 bytes. If payloads of this size are legitimate here, raise `bodyParser.json.limit` in the server options.
```

The status code is unchanged. Only clients that compare the message text against
`'request entity too large'` need adjusting — branch on the status or on `LTNS_0304` instead.

## 3. Two dependency advisories your project must fix itself

`pnpm` overrides apply only to the project that runs the install, so the framework's own fixes do not
reach your tree — see [docs/security-overrides.md](../docs/security-overrides.md).

| Package | Advisory | What your project needs |
| ------- | -------- | ----------------------- |
| `proxy-addr` | [GHSA-jqcg-44mw-7w3h](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) — **critical**: IP spoofing through an IPv4-mapped IPv6 address in a trusted subnet. Patched `>=2.0.8` | A lockfile refresh. `express` requests `^2.0.7`, so `2.0.8` is in range, but an existing lockfile stays on `2.0.7` |
| `@graphql-tools/utils` | [GHSA-7mx3-vvmw-hjmv](https://github.com/advisories/GHSA-7mx3-vvmw-hjmv) — high: prototype pollution in `mergeDeep` (schema assembly). Covers `<=12.0.0` — **11.x included, with no 11.x fix**. Patched `>=12.0.1` | An override for the copy `@nestjs/graphql` 13.4.5 exact-pins (`12.0.0`), and — in an older lockfile — a refresh of `@graphql-tools/schema` / `merge`, which can still pull in 11.x (see below) |

`proxy-addr` is what Express uses to compute `request.ip` from `X-Forwarded-For` as far as
`trustProxy` allows. With `trustProxy` set, every IP-keyed rate limit — the framework's own and any of
yours — depends on it.

```bash
pnpm update --depth Infinity proxy-addr
```

```yaml
# pnpm-workspace.yaml
overrides:
  # @nestjs/graphql 13.4.5 exact-pins @graphql-tools/utils@12.0.0 — GHSA-7mx3-vvmw-hjmv (high, patched >=12.0.1).
  # 12.0.2+ requires Node >=22.15; take the newest 12.x instead if your engines floor allows it.
  '@graphql-tools/utils@>=12.0.0 <12.0.1': '12.0.1'
```

**Check for a second, older copy.** `@apollo/server` 5.x requests `@graphql-tools/schema` `^10.0.0`. A
lockfile resolved before schema 10.1.0 (published 2026-08-12) holds a 10.0.x, which requests utils
`^11.1.0` — vulnerable, outside the override key above, and with no fix in the 11.x line. Look for it:

```bash
grep -n "'@graphql-tools/utils@11" pnpm-lock.yaml
```

If it is there, lift the requesters into their current lines, which ask for utils 12:

```bash
pnpm update --depth Infinity @graphql-tools/schema @graphql-tools/merge
```

The current releases (schema 10.1.3, merge 9.2.6) request utils `^12.0.3`, which depends on
`@whatwg-node/promise-helpers` 2 and therefore needs **Node >=22.15**. Current Node 22 LTS images
(22.22) and Node 24 satisfy that; if your `engines.node` still declares a lower floor, raise it — the
override above cannot hold this copy back, because `^12.0.3` does not intersect its key.

Then `pnpm install` and `pnpm audit` — both advisories must be gone.

## 4. Native Better-Auth endpoints accept the session when the secret is auto-generated

**Affects only** projects that configure no `betterAuth.secret` and whose fallback secrets
(`jwt.secret`, `jwt.refresh.secret`) are shorter than 32 characters — typically a local `.env`.
Better-Auth then generates a secret at startup and signs with it, while the NestJS layer (cookie
helper, API middleware, `CoreBetterAuthService`) still signed with the configured value or none. The
session cookie went out unsigned, so every endpoint Better-Auth serves itself and that reads the
cookie — `/iam/token`, the MCP `/iam/mcp/authorize`, passkey, 2FA — answered **401 right after a
successful sign-in**, and an MCP OAuth login looped back to the login page.

Since 11.42.4 the NestJS layer signs with exactly the secret Better-Auth uses. No action is needed.
It is still the wrong setup for anything but local development: a generated secret changes on every
restart and differs per replica, so sessions do not survive either — set `betterAuth.secret` (at
least 32 characters), as the boot warning says.

## Troubleshooting

| Symptom                                                          | Cause                                                        | Fix                                                        |
| ---------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| `413 … exceeds the limit` warnings for a route that should accept it | The 100 kB default is too small for that data              | Set `bodyParser.json.limit` (§1)                           |
| `bodyParser.json.limit … is not a positive size` at boot         | A typo or unit the parser does not know (`'2 megabytes'`)    | Use bytes or `'2mb'`                                       |
| `no global json body parser is registered` at boot               | The app was created with `bodyParser: false`                 | Remove the option, or register your own parser             |
| A webhook test loses `req.rawBody` after configuring a limit     | Test app created via the testing module with `rawBody: true` | See the `rawBody` note in §1                               |
| A path still answers a bare `request entity too large`           | A path-scoped parser of your own refused it                  | Raise that parser's limit in `main.ts`                     |
| `pnpm audit` still reports `@graphql-tools/utils` 12.0.0          | The override is missing, or its key was copied without the range | Add the entry from §3 verbatim                              |
| `pnpm audit` still reports `@graphql-tools/utils` 11.x            | An older `@graphql-tools/schema` 10.0.x requests `^11.1.0`, outside the override key | `pnpm update --depth Infinity @graphql-tools/schema @graphql-tools/merge` (§3) — needs Node >=22.15 |
| `pnpm audit` still reports `proxy-addr` 2.0.7                     | The lockfile was not refreshed                              | `pnpm update --depth Infinity proxy-addr` (§3)              |
| `/iam/token` or MCP authorize answers 401 right after sign-in   | 11.42.3 or older without `betterAuth.secret` and with short JWT secrets | Update to 11.42.4 (§4); for anything beyond local development set `betterAuth.secret` |
