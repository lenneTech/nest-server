# Migration Guide: 12.10.0 → 12.10.1

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None. Two exported constants name the new limits: `GRAPHQL_UPLOAD_MAX_PATH_KEYS`, `GRAPHQL_UPLOAD_MAX_MAP_KEYS` |
| **Bugfixes** | None |
| **Security** | Unauthenticated denial of service, every one fixed in the framework — no action needed: GraphQL multipart requests with a deep `map` path, with many `map` entries or with a numeric path key like `4294967294` (§1); the GraphQL complexity check on invalid variables, documents of many operations, fragments spread thousands of times and tens of thousands of variables, a plain JSON POST included (§2). A PEM private key under a key such as `certificate` is masked in `GET /config`, the Hub config panel and the `ConfigService` debug output (§3) |
| **Migration Effort** | Package update |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.10.1
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. Security: a bounded `map` in GraphQL multipart uploads

**No action needed** unless the project registers `graphqlUploadExpress()` itself with graphql-upload's default parser
(below).

`CoreModule` registers graphql-upload's `graphqlUploadExpress()` for `/graphql`, in front of every guard, and since
12.10.0 passes it the framework's `processGraphQlUploadRequest` (see the 12.9.x → 12.10.x guide, "Security: GraphQL
multipart uploads"). That parser creates an upload for every entry of the multipart `map` field and places it at each
path the entry names, with object-path's `set()`. Nothing bounded what that builds:

- `set()` recurses once per key and copies the remaining keys each time, so a path of n keys costs O(n²) memory and
  time, all of it in one synchronous call.
- An entry whose file never arrives is rejected at the end of the request with an error of its own, stack trace
  included — a `map` can name tens of thousands of entries without a single path.
- object-path reads a key like `4294967294` as a NUMBER and sets that index of an array it creates. The 258-byte
  request `map={"1":["variables.f.4294967294"]}` handed GraphQL an array of 4,294,967,295 elements, and GraphQL's list
  coercion walks every hole: the complexity plugin did, before any guard, until the heap ran out. With a nullable
  list item (`[Upload]`) every hole is a valid `null`, so execution would walk them too.

Measured on Node 24, one anonymous request each:

| `map` | Before 12.10.1 | 12.10.1 |
|---|---|---|
| one path of 8,000 keys (16 KB) | +310 MB, event loop blocked 0.5 s | 400, ~10 ms |
| one path of 40,000 keys (80 KB), 1 GB heap | heap exhausted, the process ends | 400, ~15 ms |
| one path of 400,000 keys (800 KB, inside the default 1 MB `maxFieldSize`) | heap exhausted after ~13 s (default heap) | 400, ~20 ms |
| 1 MB of 64-key paths | event loop blocked 150–640 ms | 400, ~20 ms |
| 1 MB of entries without a path (83,000 entries) | +230 MB, event loop blocked 410 ms | 400, +50 MB, ~35 ms |
| `{"1":["variables.f.4294967294"]}` (258 bytes), 1 GB heap | heap exhausted after 9 s, the process ends | 400, +2 MB, ~12 ms |

graphql-upload's own parser has the same flaws, 17.1.0 as well as 18.0.2.

Since 12.10.1 `processGraphQlUploadRequest` refuses with 400:

- a path with more than `GRAPHQL_UPLOAD_MAX_PATH_KEYS` (64) keys — "Invalid object path",
- a `map` with more than `GRAPHQL_UPLOAD_MAX_MAP_KEYS` (10,000) units. Every entry counts one, every key of its paths
  one more, and every array element a numeric key creates one more, holes included: `{"1":["variables.files.0"]}`
  counts 5, or 4 when the operations already hold `files: [null]`; `variables.f.4294967294` counts more than four
  billion. The path that goes over the bound is answered with "Invalid object path", an entry with "Invalid ‘map’
  multipart field entry key …" before its upload is created.

A path a client library builds has a handful of keys: `variables.file` has 2, `variables.input.files.3` has 4, a
batched `0.variables.file` has 3. 10,000 units are at least 2,000 files at `variables.files.N`. The most expensive
request the bounds still accept — 10,000 entries without a path — blocks the event loop for about 60 ms with +45 MB.

**A project that registers `graphqlUploadExpress()` itself** already passes `processRequest: processGraphQlUploadRequest`
since 12.10.0 and gets the bounds with the update. One that still passes graphql-upload's default has neither these
bounds nor the 12.10.0 fixes:

```typescript
import { processGraphQlUploadRequest } from '@lenne.tech/nest-server';
import graphqlUploadExpress from 'graphql-upload/graphqlUploadExpress.mjs';

consumer
  .apply(graphqlUploadExpress({ maxFiles: 10, maxFileSize: 10_000_000, processRequest: processGraphQlUploadRequest }))
  .forRoutes('my-upload-route');
```

Find such registrations with `grep -rn "graphqlUploadExpress(" src/`. `maxFiles` stays graphql-upload's option: it
limits the files of a request, which the `map` bound does not replace.

## 2. Security: the complexity check is bounded

`ComplexityPlugin` (registered by `CoreModule` whenever GraphQL is on) computes every operation's cost in Apollo's
`didResolveOperation`, after parsing and validation, before any guard. It called graphql-query-complexity's
`getComplexity()`, and these requests made that call itself the denial of service — each one anonymous, a plain JSON
POST to `/graphql` included:

- **Invalid variables.** `getComplexity()` coerces the variables with graphql's `getVariableValues()` without an error
  cap, so a list of invalid items (`"variables":{"f":[0,0,…]}` for `$f: [Upload!]!`) created one `GraphQLError` per item.
- **Many operations, no `operationName`.** Apollo resolves no operation and still calls the hook. `getComplexity()`
  then evaluated EVERY operation of the document and coerced the variables for each.
- **Fragment spreads.** graphql-query-complexity evaluates a fragment again at every spread, coercing its literal
  arguments each time. Its node cap (10,000 visits) bounds the visits, not what one costs:
  `{...F …×3300} fragment F on Query { findUsers(filter: { singleFilter: { …, value: [0,0,…] } }) { __typename } }`.
- **Many declared variables.** At every field it visits, the library walks every declared variable.
- **Many failing arguments.** The library catches the coercion error of every field's arguments and goes on, and every
  error locates itself by scanning the query up to its field: `query($x: String = "a") { a: getUser(id: $x) { id } … }`
  with `{"x": null}` is valid and fails at every field.

| Request | Before 12.10.1 | 12.10.1 |
|---|---|---|
| 100 KB of invalid list items | event loop blocked 1.5 s, +300 MB | ~5 ms, +1 MB |
| 1 MB of invalid list items | event loop blocked 15 s, +2 GB | ~10 ms, +13 MB |
| 860 operations sharing one 16,000-item variable (100 KB) | event loop blocked 5.9 s | < 1 ms, refused by execution |
| the same with 1,720 operations (200 KB multipart) | event loop blocked 25.5 s | < 1 ms, refused by execution |
| a 41,667-item literal in a fragment spread 3,300 times (100 KB) | event loop blocked 2.2 s | ~15 ms, "Query is too complex" |
| the same with a 490,000-item literal (990 KB multipart) | event loop blocked 22.5 s | ~100 ms, "Query is too complex" |
| 38,000 declared variables and 4,900 spreads (1.2 MB) | event loop blocked 17 s | ~100 ms, "Query is too complex" |
| 2,300 fields failing their argument, after 25,000 line breaks (98 KiB) | event loop blocked 1.4 s | ~6 ms, refused with the first error |
| 9,999 such fields after 395,000 line breaks (993 KiB multipart) | event loop blocked 86 s | ~16 ms, refused with the first error |

What is left for the large literal and the many variables is linear in the request: graphql's validation and
execution walk the same literal and the same variables once themselves.

Since 12.10.1 the plugin:

1. does nothing when Apollo resolved no operation — graphql's `execute()` then refuses the request ("Must provide
   operation name…") before it coerces a single variable;
2. coerces the resolved operation's variables, stopping at the first error, and skips the complexity check when they
   do not coerce: `execute()` refuses such variables itself, with graphql's cap of 50, before any resolver runs, so
   there is no operation whose cost could matter;
3. refuses an operation whose fields (and `@skip` / `@include`) times declared variables exceed 250,000, with
   `Query is too complex: too many fields for its number of variables` — measured at most about 23 ms of analysis.
   With the default cost of 1 per field, a query `maxComplexity: 1000` accepts has at most 1,000 fields; with 30
   variables that is at most 30,000;
4. computes graphql-query-complexity's number with each fragment evaluated once and reused at every further spread.
   The number is the one `getComplexity()` returns, and the 10,000-node cap still counts every spread. A field's
   `complexity` extension that is a function runs once per fragment instead of once per spread, so it must depend only
   on its arguments and `childComplexity`;
5. stops the analysis at its first error and refuses the request with it — `getComplexity()` collected every error and
   threw the last one.

For valid variables the result is what it was: `Query is too complex: …` above `graphQl.maxComplexity`, and
`Query exceeds the maximum allowed number of nodes.` above 10,000 nodes.

**What clients see:** a request with invalid variables gets execution's errors (up to 50 messages, then "Too many
errors processing variables, error limit reached. Execution aborted.") instead of the single coercion error the plugin
threw before. The status changes with it: HTTP 400 with the code `BAD_USER_INPUT` (Apollo 5 default
`status400ForVariableCoercionErrors`) instead of HTTP 500 with `INTERNAL_SERVER_ERROR`.

## 3. Security: PEM private keys are masked by their value

`redactSecrets()` — behind `GET /config`, the Hub config panel and the `ConfigService` output with `warn: true` —
decided by the key name alone. A certificate login usually keeps certificate and private key in one PEM under a name
such as `certificate`, which no name rule may treat as secret, so the private key reached an administrator's response
and the debug output in clear text. Since 12.10.1 every string and `Buffer` that holds a PEM private key
(`-----BEGIN … PRIVATE KEY-----`, PGP's `PRIVATE KEY BLOCK` included) is masked as a whole, whatever its key is called.
A certificate without a key stays readable. Keys named `pfx` or `pkcs12` are masked too: a PKCS#12 container carries
no text marker.

No action needed. A project that worked around it with `security.secretFields: ['certificate']` can keep that entry.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Uploads through `CoreModule`'s `/graphql` registration | Bounded with the update |
| `graphqlUploadExpress()` registered by the project with `processRequest: processGraphQlUploadRequest` | Bounded with the update |
| `graphqlUploadExpress()` registered by the project without `processRequest` | Not protected — pass `processGraphQlUploadRequest` (§1) |
| A project's own Apollo plugin that calls `getComplexity()` with the request's variables | Same flaws as §2 — skip a request without a resolved operation, check the variables with `getVariableValues(…, { maxErrors: 50 })` first, and bound fragment spreads and variables, or rely on the framework's plugin |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| An upload answers 400 `Invalid object path for the ‘map’ multipart field …` for a path with many keys | The path has more than 64 keys | Place the file at a flatter variable (`variables.input.files.3`) |
| An upload answers 400 `Invalid object path …` for a path with a large number in it | The index creates more array elements than the bound allows | Number the files from 0 (`variables.files.0`, `variables.files.1`) |
| An upload of very many files answers 400 `Invalid object path …` or `Invalid ‘map’ multipart field entry key …` | The `map` has more than 10,000 units | Split the upload into several requests |
| A request with invalid variables answers with several variable errors instead of one | Execution reports them now (§2) | Fix the variables; the messages are graphql's own |
| A query answers `Query is too complex: too many fields for its number of variables` | Its fields × declared variables exceed 250,000 (§2) | Split the query, or pass related values as one input-object variable |
