# Migration Guide: 12.8.2 → 12.8.3

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | `betterAuth.emailVerification.appName`: the application name in the verification and password-reset mails, independent of `package.json` (§2) |
| **Bugfixes** | Under Node 26 every start and every migration run from source printed `[DEP0205] DeprecationWarning: module.register() is deprecated`. The TypeScript loader now registers its import hooks with `module.registerHooks()` where Node supports it (§1) |
| **Migration Effort** | None. Optional: set `appName` when the mails should not carry the `package.json` name (§2) |

12.8.3 is a patch for 12.8.2. Nothing has to change in a project.

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.3
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. The TypeScript loader without `module.register()` on Node 26

**Why:** the framework's TypeScript loader (`migrate/helpers/ts-compiler.js`) runs the dev server from source
(`node -r …/ts-compiler.js src/main.ts`), the migrate CLI (`--compiler ts:…/ts-compiler.js`) and `config.env.ts`. For
`import`ed TypeScript (an ESM project, a `.mts` file) it registered Node module hooks through `module.register()`.
Node 26 deprecates that function at runtime, so every one of those runs printed DEP0205, in npm and vendor projects
alike.

**What changed:** the loader picks the hook API per Node line:

| Node | API | Why |
|---|---|---|
| 24.12+ and 26+ | `module.registerHooks()`, in-thread | hands a CommonJS module imported from ESM back to the CommonJS loader, as the loader needs |
| 22.x, 24.0–24.11, 25.x | `module.register()` with `ts-compiler-hooks.mjs`, as before | these lines refuse that hand-back in synchronous hooks; none of them deprecates `module.register()` |

Both paths share one implementation in `ts-compiler.cjs`. The behaviour is the same on every line: decorators with
metadata, `./x.js` specifiers resolving to `x.ts`, JSON imports with attributes, CommonJS-scoped `.ts` / `.cts` files
compiled by the `require` hook with a real `require` (`require.cache`, `require.extensions`). The CommonJS path
(`require()` of a `.ts` file, every migration) is unchanged.

`engines.node` stays `>= 22.15`. Nothing to do: the loader path, its function export and `--compiler ts:…` are the same.

## 2. `betterAuth.emailVerification.appName`

**Why:** the verification and password-reset mails name the application in the subject
(`<appName> - Verify your email address`), in the EJS templates (`appName`) and in the Brevo parameters (`appName`).
That name came from the `name` of the `package.json` in the working directory, formatted (`my-app` → `My App`). In a
monorepo the working directory is the API package: one named `api` sent `Api - Verify your email address`. Changing it
needed an override of `getAppName()`.

**What changed:** an optional setting:

```typescript
// config.env.ts
betterAuth: {
  emailVerification: {
    appName: 'Kundenportal',
  },
},
```

or `NSC__BETTER_AUTH__EMAIL_VERIFICATION__APP_NAME=Kundenportal`. The value is trimmed. Unset or empty, the mails keep
the `package.json` name. A value that is not a string is ignored with one warning. An override of `getAppName()` or
`resolveAppName()` still wins.

**A project with email verification switched off** (`emailVerification: false`) still sends password-reset mails, so
the name matters there too. Write it with `enabled: false`:

```typescript
betterAuth: {
  emailVerification: { enabled: false, appName: 'Kundenportal' },
},
```

With environment variables, set `NSC__BETTER_AUTH__EMAIL_VERIFICATION__ENABLED=false` next to
`NSC__BETTER_AUTH__EMAIL_VERIFICATION__APP_NAME`. `false` keeps no settings, so `appName` would be ignored; an object
without `enabled: false` (which is what the variable alone turns `false` into) switches verification ON, and every
sign-in of a user whose address was never verified is then answered with 401 `EMAIL_VERIFICATION_REQUIRED`.

Authenticator apps and passkey prompts are not affected: they read `betterAuth.twoFactor.appName` and
`betterAuth.passkey.rpName`, as before.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `node -r …/ts-compiler.js src/main.ts`, `migrate … --compiler ts:…` | unchanged, without DEP0205 on Node 26 |
| A project calling `require('…/ts-compiler.js')()` itself | unchanged (idempotent function export) |
| A subclass overriding `getAppName()` / `resolveAppName()` | unchanged, still wins over the setting |
| Own email templates using `appName` | receive the configured name when it is set |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `[DEP0205] DeprecationWarning: module.register() is deprecated` after the update | a second loader in the project (`tsx`, `ts-node/esm`, a `--loader` / `--import` flag) still calls `module.register()` | remove or update that loader; the framework's own no longer calls it on Node 26 |
| The mail subject still shows the package name | `appName` is set at the wrong level, or empty, or `emailVerification` is `false` (keeps no settings) | it belongs under `betterAuth.emailVerification`; with verification off write `{ enabled: false, appName }`; check the boot log for the "must be a string" warning |
| After setting `appName`, unverified users get 401 `EMAIL_VERIFICATION_REQUIRED` at sign-in | the project had `emailVerification: false`; the object (or `NSC__…__APP_NAME` alone) switched verification on | add `enabled: false` (`NSC__BETTER_AUTH__EMAIL_VERIFICATION__ENABLED=false`) |
