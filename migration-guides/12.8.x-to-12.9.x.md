# Migration Guide: 12.8.x → 12.9.x

## 12.9.0 refuses fields without a declared type at boot

The version number moves only the MINOR digit (the MAJOR follows NestJS). This release contains a breaking change:

- `@UnifiedField` **throws at boot** for a field that sets none of `type`, `isAny` or `enum` and whose compiler
  metadata (`design:type`) is only `Object`. 12.8.7 warned about the same fields.

This affects the dev start (SWC) and the deployed build (tsc) alike: under tsc it covers `any`, `unknown`, `object`,
`Record<…>`, an interface or a mixed enum; under SWC also `null | number`, a type alias and `boolean | null`. Run the
check of **12.9.0** to know (Quick Migration): the 12.8.7 check passes two kinds of field this release refuses — one
typed with an enum that mixes string and number members, and one in a `*.spec.ts` / `*.test.ts` file.

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | A `@UnifiedField` field without `type` / `isAny` / `enum` whose `design:type` is `Object` fails the boot with `[@UnifiedField] "<Class>.<field>" has no explicit type …` (§1) |
| **New Features** | `nest-check-unified-field-types` also reports a field typed with a mixed enum (string and number members), which the boot refuses as well, and reads `*.spec.ts` / `*.test.ts` files (§2) |
| **Bugfixes** | None. Tested against better-auth 1.7.19 (with `@better-auth/core` and `@better-auth/passkey`); the peer range stays `>=1.7.16 <1.8.0`, and a project pins the three together as before |
| **Migration Effort** | Run the 12.9.0 `nest-check-unified-field-types --fix` once and declare the fields it names by hand (§2). Usually minutes |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.9.0
pnpm run update   # nest-server-starter based projects

# The 12.9.0 check — a static check, it runs before anything boots. Write the declared types, then declare what it names
pnpm exec nest-check-unified-field-types --fix
pnpm exec nest-check-unified-field-types --include tests --fix   # test fixtures with @UnifiedField, see §2

pnpm run build
pnpm test
```

Run it with 12.9.0, not with the 12.8.7 check: that one passes fields with a mixed enum and every field in a `*.spec.ts`
/ `*.test.ts` file, and 12.9.0 refuses both at boot (§2).

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual. A `bin/check-unified-field-types.js` in the
project may still be the 12.8.7 copy the lt CLI placed there, so run the 12.9.0 check as a one-off in the API project:
`npx -p @lenne.tech/nest-server@12.9.0 nest-check-unified-field-types --fix` (and once more with `--include tests`).

## 1. What is refused, and what to declare

Without `type`, `@UnifiedField` takes a field's type from `design:type`. `Object` there names no type: the field was
validated as a nested object (`IsObject`, `ValidateNested`), documented as `type: object` and typed
`{ [key: string]: unknown }` in a generated client — and for a union with `null` or a type alias only under the SWC dev
start, while the tsc build validated the declared type. Since 12.9.0 the field has to say what it holds, as an array
field without `type` always had to.

| Field | What to declare | Behaviour of the deployed build |
|---|---|---|
| `max?: null \| number`, `count?: Count` (alias of `number`) | `type: () => Number` (written by `--fix`) | unchanged, unless `strictNullChecks` (below) |
| `kind?: Kind` (alias of a string union), `flag?: boolean \| null` | `type: () => String` / `Boolean` (written by `--fix`) | unchanged |
| `address?: Address \| null` (a class) | `type: () => Address` (written by `--fix`) | unchanged |
| `meta?: Record<string, unknown>`, an interface, `object` | `type: () => Object` — keeps today's validation exactly | unchanged |
| `value?: any` / `unknown`, `string \| number` | `isAny: true` for any value, or `type: () => Object` to keep today's behaviour | `isAny` drops the object validation the build applied |
| `level?: Mixed` (enum with string and number members) | `enum: Mixed` | the build validated it as an object; `enum` validates the members |
| a class imported with `import type` | import it as a value, then `type: () => X` | unchanged |

Fields with `type`, `isAny` or `enum`, and fields typed `number`, `string`, `boolean`, `Date`, a value-imported class,
an enum of strings or of numbers, or an in-place union of string literals load as before.

**`strictNullChecks`**: there the tsc build also writes `Object` for `null | number`, so such a field was validated as
an object in production too. `--fix` writes the declared type and marks the line `[changes the deployed build]`: the
deployed API now validates it as a number. Review those fields.

## 2. Finding the fields

`nest-check-unified-field-types` (package bin since 12.8.7, `check:unified-field-types` in nest-server-starter's
`check`) uses the project's type checker and reports every field the boot refuses:

- `--fix` writes `type: () => Number` / `String` / `Boolean` / `Date` / the class wherever the field's type resolves to
  one, and names the rest with what to declare (§1).
- New in 12.9.0: a field typed with a **mixed enum** is reported too (`(an enum)`).
- The default scope is `src`. Fixture classes in a project's tests are refused at boot as well: run it once with
  `--include tests`. Since 12.9.0 the check also reads `*.spec.ts` and `*.test.ts` files (12.8.7 skipped them).

## Compatibility Notes

| Pattern | Status |
|---|---|
| Project with the **12.9.0** `check:unified-field-types` green (scope including its tests) | Compatible |
| Project green only with the 12.8.7 check | Run the 12.9.0 check: a mixed enum or a field in a `*.spec.ts` / `*.test.ts` file still fails the boot |
| Fields with `type`, `isAny` or `enum` | Compatible |
| `@UnifiedField()` on `any` / `Record` / an interface without `type` | Fails the boot → `type: () => Object` keeps today's behaviour |
| Vendor-mode core | Compatible (the framework's own fields all declare their type) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `[@UnifiedField] "X.y" has no explicit type, and the compiler metadata says only "Object" …` at boot or in a test run | §1 | `nest-check-unified-field-types --fix`, then declare what it names |
| The check passes, the boot still refuses a field | the file is outside `--include` (default `src`) or not part of the tsconfig's program | run the check with `--include <dir>` (or `--project <tsconfig>`), or declare it by hand |
| A fixed field is marked `[changes the deployed build]` | `strictNullChecks` (§1) | review it; the written type is the one the field declares |
| The check passes, the boot refuses a field typed with a class (`owner?: User`) | an import cycle: the class is not defined yet when the decorator runs, so the SWC dev start writes `Object` for it — the check cannot see a cycle | `type: () => User` — the arrow resolves the class later, after the cycle |
