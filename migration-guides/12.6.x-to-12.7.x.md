# Migration Guide: 12.6.x → 12.7.x

## 12.7.0 contains a breaking change

The version number moves only the MINOR digit (the MAJOR follows NestJS). `getEnvironmentConfig()` now refuses to
load a configuration when `NODE_ENV` is empty or names an environment that has no block in `config.env.ts`. Until
12.7.0 both cases silently got the `local` block. A stage or job that relied on that stops at startup after the
update. That is intended: the `local` block on a deployed stage is the hole this release closes (§1).

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | An empty `NODE_ENV`, or one without a block in `config.env.ts`, throws at startup instead of loading the `local` block (§1) |
| **New Features** | None |
| **Bugfixes** | A deployed stage can no longer run on the `local` block by a missing block or an unset host variable (§1) |
| **Migration Effort** | Check the boot line of every stage and job before updating and add a block for each `NODE_ENV` that has none (§1); check scripts and process files that set `NODE_ENV` (§2); know what your platform does with a refused start (§3) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.7.0
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. A NODE_ENV without a block no longer starts

**Why:** `getEnvironmentConfig()` used `config[NODE_ENV || 'local'] || config.local`. A stage started with
`NODE_ENV=development`, `dev` or `staging` in a project that defines none of them, or with an empty `NODE_ENV`, ran on
the `local` block. Its `env` then claims `local`, which opens what the framework keeps to laptops: the anonymous
`POST /system-setup/init`, `GET /config`, private outbound targets for user-entered URLs, the development MCP OAuth
secret, and the auth links in the log — on top of whatever dummy secrets the `local` block carries.

**What changed:**

| `NODE_ENV` | Until 12.6.x | From 12.7.0 |
|---|---|---|
| unset | the `local` block (or `defaultEnv`) | unchanged |
| names a block | that block | unchanged |
| names no block (`staging`, `development`, a typo) | the `local` block | throws `NODE_ENV='<value>' has no block in the configuration (known: …)` |
| empty or blank (`''`, `'  '`) | the `local` block | throws `NODE_ENV is set but empty (known: …)` |
| `test` with no `test` block, under vitest or jest (`VITEST` / `JEST_WORKER_ID`) | the `local` block | the `local` block, with one warning |
| `test` with no `test` block, anywhere else | the `local` block | throws |

**Am I affected?**

- **A stage or job on an env without a block.** Its boot log shows `Configured for: local (requested: <NODE_ENV>)`.
  Look at every place that starts the application or loads `config.env.ts`, not only deployed stages: compose files,
  CI jobs, `package.json` scripts (`migrate:<env>:up`, seeds), cron containers.
- **An empty `NODE_ENV`.** `NODE_ENV=${NODE_ENV}` in a compose file passes `''` when the host does not set the
  variable. The boot line then reads a plain `Configured for: local`, which looked correct. Check the environment of
  the running container instead (`NODE_ENV` present but empty).
- **A test suite under vitest or jest without a `test` block** keeps working and prints
  `NODE_ENV='test' has no block in the configuration; a test runner is active, so the local block is used.` once per
  module instance. Add a `test` block to silence it.

**What to do, before the update:**

- For each `NODE_ENV` without a block, **add a block** rather than renaming `NODE_ENV`. Other libraries read
  `NODE_ENV` themselves (Express and many others switch behaviour on `production` / `development`), so renaming it
  changes them too. In a starter-based project: `staging: deployedConfig('staging', { brandSuffix: 'Staging' }),`.
  A stage that moves off the `local` block needs every variable its new block requires — in a starter-based project
  the ones `.env.example` lists as required — and its `migrate:<env>:up` job too.
- For an empty `NODE_ENV`, set the value on the host or in the compose file, or remove the line so the variable is
  really unset.
- Check the scripts that set a `NODE_ENV` of their own, not only the stages (§2): they fail at the first run after the
  update, which may be weeks later.
- Know what your platform does with a refused start before you deploy the update (§3).

**Starter-based projects:** nest-server-starter refuses both cases itself since its 12.6.0 release, before
`getEnvironmentConfig()` runs (see `12.5.x-to-12.6.x.md` §3). That check lives in your project's own
`src/config.env.ts`, and `pnpm run update` does not touch that file, so a project created from an earlier starter has
it only if it was taken over by hand. Check for both messages of the starter's checks:

```bash
grep -nE "has no block in src/config.env.ts|is set but empty" src/config.env.ts
```

- Both found: 12.7.0 changes nothing about `NODE_ENV` for you; the starter has a `test` block, so its test runs see no
  warning either.
- Only `has no block…`: the check of an earlier starter change without the empty-value rule. An empty `NODE_ENV` is
  refused from 12.7.0 on; check your stages for it (§1).
- Neither: your project is affected like any other, §1–§3 apply in full.

## 2. Scripts and process files that name an environment

A refused start is not limited to deployed stages. Every script that sets `NODE_ENV` loads `config.env.ts` the same
way, and a scan of existing projects found three recurring cases:

- **`migrate:preview:up`.** The lt CLI writes it into every project, usually without a `preview` block; until now it
  migrated silently against the local database URI. Take over the `preview` block of nest-server-starter
  (`preview: deployedConfig('preview', { brandSuffix: 'Preview' }),`), or remove the script if nothing runs it.
- **A pm2 default of `development`.** Many `pm2.config.js` files set `NODE_ENV` to `development` in their default
  `env`. Set it to a block that exists, or add a `development` block if pm2 really runs a development stage.
- **Block names that differ from the script names.** A project whose blocks are called `dev` or `productive` while its
  scripts set `NODE_ENV=develop` or `NODE_ENV=production` (`migrate:develop:up`, `start:prod`, `migrate:prod:up`) gets
  the `local` block today and a refused start after the update. Make both use the same name: let the script set the
  block's name, or add the name the script uses as a further block (a `production` key next to `productive`). Where a
  deployed stage relies on the value for other libraries (`production`), keep the value and add the block.

Nothing changes on a developer machine: a missing `NODE_ENV` still means `local`, and `lt dev up` / `lt dev test` set
`NODE_ENV=local`.

## 3. What happens on deploy?

The refusal is an error thrown while the configuration loads, so the API process exits before it listens. What the
stage does then depends on the platform:

| Platform | Running stage | What you see |
|---|---|---|
| TurboOps | The previous version keeps running (start-first update with a health check, `failure_action: rollback`) | The deployment ends `failed` with a completed rollback, the pipeline turns red |
| STACKIT (Argo Rollouts canary) | The previous version keeps running: the rollout is aborted at its progress deadline | `RolloutAborted` after the deadline (300 s); **the pipeline stays green** |
| deploy.party | **The stage goes down**: there is no health check and no check after the deploy | **Nothing**: the build reports success |

On every platform, the **first** deploy of a new stage goes down, because there is no previous version to keep.
TurboOps can go down too when an api service runs without a health check or updates stop-first (because of a named
volume, or `updateOrder` set to stop-first).

Before you deploy the update:

- **deploy.party:** check the stage's `NODE_ENV` against the blocks of `config.env.ts` first. A refused start goes
  unnoticed there until somebody opens the application.
- **STACKIT:** look at the rollout status after the deploy rather than at the pipeline, which stays green.
- **TurboOps:** a red pipeline with a rollback is the signal; the previous version keeps serving.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `NODE_ENV` unset on a developer machine | Unchanged: the `local` block |
| `lt dev up` / `lt dev test` | Unchanged: they start the API with `NODE_ENV=local` |
| A starter-based project whose `src/config.env.ts` contains both starter 12.6.0 checks (`has no block…`, `is set but empty`) | Already refuses both cases itself; nothing changes |
| A starter-based project created earlier, without those checks | Affected like any other project: `pnpm run update` does not change `config.env.ts` (§1–§3) |
| vitest / jest suites without a `test` block | Keep the `local` block, with one warning per module instance |
| A project that calls `getEnvironmentConfig({ defaultEnv })` | `defaultEnv` still applies when `NODE_ENV` is unset |
| A `local` `env` from `NSC__ENV`, `NEST_SERVER_CONFIG` or a project's own loader on a deployed stage | Not caught here; the auth-link log line keeps its own `NODE_ENV` check (12.6.0) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `NODE_ENV='<value>' has no block in the configuration (known: …)` at startup | The stage ran on the `local` block until now | Add a block for `<value>` to `config.env.ts` (§1) |
| `NODE_ENV is set but empty` at startup | An empty variable, often `NODE_ENV=${NODE_ENV}` in a compose file | Set the value or remove the line (§1) |
| `NODE_ENV='test' has no block in the configuration; a test runner is active` in a test run | vitest sets `NODE_ENV=test` | Nothing to do, or add a `test` block |
| A job (migration, seed) fails after the update while the application starts | The job runs with its own `NODE_ENV` | Give that `NODE_ENV` a block too (§2) |
| A deploy.party stage is down after the update, the build was green | The API refused to start; the platform has no health check | Check the stage's `NODE_ENV` and its logs (§3) |
| A STACKIT pipeline is green but the stage still serves the previous version | The canary was aborted at its progress deadline | Look at the rollout status and the API's logs (§3) |
