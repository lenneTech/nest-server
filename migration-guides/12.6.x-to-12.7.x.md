# Migration Guide: 12.6.x → 12.7.x

## 12.7.0 contains breaking changes

The version number moves only the MINOR digit (the MAJOR follows NestJS). Two defaults change:

- `getEnvironmentConfig()` now refuses to load a configuration when `NODE_ENV` is empty or names an environment that
  has no block in `config.env.ts`. Until 12.7.0 both cases silently got the `local` block. A stage or job that relied
  on that stops at startup after the update. That is intended: the `local` block on a deployed stage is the hole this
  release closes (§1).
- `setupSwagger()` serves the API documentation only in `local`, `ci` and `e2e` unless `swagger: true` is set. A
  deployed stage that showed `/swagger` until now answers 404 there after the update (§4).
- In JWT mode (`cookies: false`) CORS answers the configured origins with credentials instead of every origin with
  `*`. A browser page on an origin that is neither `appUrl`, `baseUrl` nor in `cors.allowedOrigins` can no longer
  call the API (§5).
- `GET /iam/list-sessions` names the sessions by `id` and hands out no session token any more; revoke a session with
  `POST /iam/revoke-session` and `{ sessionId }` (§6).

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | An empty `NODE_ENV`, or one without a block in `config.env.ts`, throws at startup instead of loading the `local` block (§1). Swagger is off outside `local` / `ci` / `e2e` unless `swagger: true` (§4). JWT mode answers only the configured origins, with credentials, instead of `*` (§5). `list-sessions` hands out no tokens (§6) |
| **New Features** | `POST /iam/revoke-session` accepts `{ sessionId }` (§6); `swagger` server option (§4); `includeDisabled` for the AI prompt list (§7) |
| **Bugfixes** | A deployed stage can no longer run on the `local` block by a missing block or an unset host variable (§1). A JWT-mode API on a separate origin can finish a 2FA sign-in in the browser (§5). A disabled AI prompt can be managed again (§7). A `j:` session cookie no longer signs a request in as somebody else (§8, 12.7.3) |
| **Migration Effort** | Check the boot line of every stage and job before updating and add a block for each `NODE_ENV` that has none (§1); check scripts and process files that set `NODE_ENV` (§2); know what your platform does with a refused start (§3); set `swagger: true` on the stages that must keep showing the API documentation (§4); in JWT mode, list every browser origin that calls the API (§5); a session management screen revokes by `sessionId` (§6); an AI prompt management screen lists with `includeDisabled` (§7) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.7.0
pnpm run update   # nest-server-starter based projects
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual.

## 1. A NODE_ENV without a block no longer starts

**Why:** `getEnvironmentConfig()` used `config[NODE_ENV || 'local'] || config.local`. A stage started with
`NODE_ENV=development`, `dev` or `staging` in a project that defines none of them, or with an empty `NODE_ENV`, ran on
the `local` block. Its `env` then claims `local`, which opens what the framework keeps to laptops: the anonymous
`POST /system-setup/init`, `GET /config`, private outbound targets for user-entered URLs, the development MCP OAuth
secret, and the auth links in the log — on top of whatever dummy secrets the `local` block carries.

**What changed:**

| `NODE_ENV` | Until 12.6.x | From 12.7.0 |
|---|---|---|
| unset | the `local` block (or `defaultEnv`) | unchanged |
| names a block | that block | unchanged |
| names no block (`staging`, `development`, a typo) | the `local` block | throws `NODE_ENV='<value>' has no block in the configuration (known: …)` |
| empty or blank (`''`, `'  '`) | the `local` block | throws `NODE_ENV is set but empty (known: …)` |
| `test` with no `test` block, under vitest or jest (`VITEST` / `JEST_WORKER_ID`) | the `local` block | the `local` block, with one warning |
| `test` with no `test` block, anywhere else | the `local` block | throws |

**Am I affected?**

- **A stage or job on an env without a block.** Its boot log shows `Configured for: local (requested: <NODE_ENV>)`.
  Look at every place that starts the application or loads `config.env.ts`, not only deployed stages: compose files,
  CI jobs, `package.json` scripts (`migrate:<env>:up`, seeds), cron containers.
- **An empty `NODE_ENV`.** `NODE_ENV=${NODE_ENV}` in a compose file passes `''` when the host does not set the
  variable. The boot line then reads a plain `Configured for: local`, which looked correct. Check the environment of
  the running container instead (`NODE_ENV` present but empty).
- **A test suite under vitest or jest without a `test` block** keeps working and prints
  `NODE_ENV='test' has no block in the configuration; a test runner is active, so the local block is used.` once per
  module instance. Add a `test` block to silence it.

**What to do, before the update:**

- For each `NODE_ENV` without a block, **add a block** rather than renaming `NODE_ENV`. Other libraries read
  `NODE_ENV` themselves (Express and many others switch behaviour on `production` / `development`), so renaming it
  changes them too. In a starter-based project: `staging: deployedConfig('staging', { brandSuffix: 'Staging' }),`.
  A stage that moves off the `local` block needs every variable its new block requires — in a starter-based project
  the ones `.env.example` lists as required — and its `migrate:<env>:up` job too.
- For an empty `NODE_ENV`, set the value on the host or in the compose file, or remove the line so the variable is
  really unset.
- Check the scripts that set a `NODE_ENV` of their own, not only the stages (§2): they fail at the first run after the
  update, which may be weeks later.
- Know what your platform does with a refused start before you deploy the update (§3).

**Starter-based projects:** nest-server-starter refuses both cases itself since its 12.6.0 release, before
`getEnvironmentConfig()` runs (see `12.5.x-to-12.6.x.md` §3). That check lives in your project's own
`src/config.env.ts`, and `pnpm run update` does not touch that file, so a project created from an earlier starter has
it only if it was taken over by hand. Check for both messages of the starter's checks:

```bash
grep -nE "has no block in src/config.env.ts|is set but empty" src/config.env.ts
```

- Both found: 12.7.0 changes nothing about `NODE_ENV` for you; the starter has a `test` block, so its test runs see no
  warning either.
- Only `has no block…`: the check of an earlier starter change without the empty-value rule. An empty `NODE_ENV` is
  refused from 12.7.0 on; check your stages for it (§1).
- Neither: your project is affected like any other, §1–§3 apply in full.

## 2. Scripts and process files that name an environment

A refused start is not limited to deployed stages. Every script that sets `NODE_ENV` loads `config.env.ts` the same
way, and a scan of existing projects found three recurring cases:

- **`migrate:preview:up`.** The lt CLI writes it into every project, usually without a `preview` block; until now it
  migrated silently against the local database URI. Take over the `preview` block of nest-server-starter
  (`preview: deployedConfig('preview', { brandSuffix: 'Preview' }),`), or remove the script if nothing runs it.
- **A pm2 default of `development`.** Many `pm2.config.js` files set `NODE_ENV` to `development` in their default
  `env`. Set it to a block that exists, or add a `development` block if pm2 really runs a development stage.
- **Block names that differ from the script names.** A project whose blocks are called `dev` or `productive` while its
  scripts set `NODE_ENV=develop` or `NODE_ENV=production` (`migrate:develop:up`, `start:prod`, `migrate:prod:up`) gets
  the `local` block today and a refused start after the update. Make both use the same name: let the script set the
  block's name, or add the name the script uses as a further block (a `production` key next to `productive`). Where a
  deployed stage relies on the value for other libraries (`production`), keep the value and add the block.

On a developer machine a missing `NODE_ENV` still means `local`. **One exception, corrected in 12.7.1:** `lt dev up`
and `lt dev test` start the API server with `NODE_ENV=local`, but a migration step in the project's `start` script
(`pnpm run migrate:up && …`) runs with the `NODE_ENV` the shell exported. With `NODE_ENV=development` (or any other
value without a block) exported, that migration now stops. Pin the environment in the script, as nest-server-starter
12.7.0 does:

```json
"start": "cross-env NODE_ENV=local pnpm run migrate:up && pnpm run start:local"
```

## 3. What happens on deploy?

The refusal is an error thrown while the configuration loads, so the API process exits before it listens. What the
stage does then depends on the platform:

| Platform | Running stage | What you see |
|---|---|---|
| TurboOps | The previous version keeps running (start-first update with a health check, `failure_action: rollback`) | The deployment ends `failed` with a completed rollback, the pipeline turns red |
| STACKIT (Argo Rollouts canary) | The previous version keeps running: the rollout is aborted at its progress deadline | `RolloutAborted` after the deadline (300 s); **the pipeline stays green** |
| deploy.party | **The stage goes down**: there is no health check and no check after the deploy | **Nothing**: the build reports success |

On every platform, the **first** deploy of a new stage goes down, because there is no previous version to keep.
TurboOps can go down too when an api service runs without a health check or updates stop-first (because of a named
volume, or `updateOrder` set to stop-first).

Before you deploy the update:

- **deploy.party:** check the stage's `NODE_ENV` against the blocks of `config.env.ts` first. A refused start goes
  unnoticed there until somebody opens the application.
- **STACKIT:** look at the rollout status after the deploy rather than at the pipeline, which stays green.
- **TurboOps:** a red pipeline with a rollback is the signal; the previous version keeps serving.

## 4. Swagger only where it is switched on

**Why:** `setupSwagger()` mounted the Swagger UI and the JSON document on every stage a project called it on,
production included. The full API description — every route, the roles it requires, every input shape — was public
there.

**What changed:** `setupSwagger()` asks `isSwaggerEnabled()` first (new server option `swagger`):

| `swagger` | `local` / `ci` / `e2e` | every other environment (`develop`, `test`, `production`, …) |
|---|---|---|
| not set | served | **off** |
| `true` | served | served |
| `false` | off | off |

Off mounts nothing: neither `/swagger` and `/swagger-api-tokens` nor `/api-docs-json` and `/api-docs-api-tokens-json`
(or the paths you gave `setupSwagger()`); they answer 404. One line in the boot log says Swagger is off. A value that
is not a boolean counts as not set.

**Your project:** nothing to do if the documentation should stay local. To keep it on a stage, set it in that
stage's block of `config.env.ts`, or through the environment:

```typescript
// config.env.ts — only the stage that should show the documentation
develop: {
  // …
  swagger: true,
},
```

```bash
NSC__SWAGGER=true
```

A client generator that reads `/api-docs-json` from a deployed stage (`openapi-typescript`, `orval`, …) needs the
switch on that stage, or reads the document from a local or CI run instead.

## 5. CORS with credentials in JWT mode

**Why:** with `cookies: false` the API answered every origin with `Access-Control-Allow-Origin: *` and no
credentials. Browsers refuse `*` on a credentialed request, and a JWT-mode frontend makes them: the stack's client
sends `credentials: 'include'`, and after a second factor it turns the session cookie Better-Auth set into a JWT
through `/iam/token`. With app and API on separate origins, a 2FA sign-in in JWT mode failed in every browser while
the server answered 200.

**What changed:** `buildCorsConfig()` no longer distinguishes the cookie mode. REST (through `main.ts`), GraphQL and
the tus uploads answer the same origin list in both modes:

| `cookies: false`, origins | Until 12.6.x | From 12.7.0 |
|---|---|---|
| `appUrl` / `baseUrl` / `cors.allowedOrigins` resolvable | `*`, no credentials, every origin | those origins, with credentials; any other origin gets no CORS grant |
| `cors.allowAll: true` | `*`, no credentials | the request origin mirrored, with credentials (as in cookie mode) |
| nothing resolvable | `*`, no credentials | unchanged |

Credentialed CORS decides which origins may READ a credentialed response; it does not change what a browser sends.
The list is the one cookie mode has always trusted, so no other origin gains anything.

**Your project:** nothing to change in `main.ts` — it already applies what `buildCorsConfig()` returns. If browser
pages on further origins call your JWT-mode API (a second frontend, a partner widget), list them:

```typescript
cors: {
  allowedOrigins: ['https://admin.example.com'],
},
```

Server-to-server calls and native apps send no `Origin` and are not affected.

## 6. list-sessions names sessions by id; revoke-session takes the id

**Why:** `GET /iam/list-sessions` answered every session of the user with its `token` — the bearer credential of every
device the user is signed in on, readable by any script on the page. 12.6.1 took the session token out of the other
forwarded answers; this was the last one.

**What changed:**

| | Until 12.6.x | From 12.7.0 |
|---|---|---|
| `GET /iam/list-sessions` | `[{ id, token, userId, expiresAt, … }]` | `[{ id, userId, expiresAt, … }]` — no `token`, in every mode |
| `POST /iam/revoke-session` | `{ token }` | `{ sessionId }` (new) or `{ token }` (unchanged) |

`{ sessionId }` is resolved among the sessions of the signed-in user. An unknown id, or the id of another user's
session, revokes nothing — the answer is the same as for a foreign token, so it discloses nothing. Revoking by
`token` stays for clients that hold one; nothing in the stack's frontends uses either route directly.

**Your frontend:** a "signed-in devices" screen that revokes a session by the `token` from `list-sessions` sends the
`id` instead:

```typescript
await fetch(`${api}/iam/revoke-session`, {
  body: JSON.stringify({ sessionId: session.id }),
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  method: 'POST',
});
```

Better-Auth's client (`authClient.revokeSession({ token })`) types the body as `{ token }`; send the request yourself
as above.

## 7. Disabled AI prompts in the management list

**Why:** `GET /ai/prompts` (GraphQL `findAiPrompts`) answered enabled prompts only, for every caller. That is right
for the chat's prompt picker and wrong for the management screen: a prompt saved with "enabled" switched off
disappeared from it and could no longer be edited or deleted.

**What changed:** a new, optional switch. Without it nothing changes.

| Call | Lists |
|---|---|
| `GET /ai/prompts` · `findAiPrompts` | enabled prompts — the chat picker (unchanged) |
| `GET /ai/prompts?includeDisabled=true` · `findAiPrompts(includeDisabled: true)` | enabled and disabled prompts — the management screen |

Visibility is the same in both: the user's own prompts and the prompts of the user's tenant.

**Your frontend:** the screen that edits and deletes prompts adds the parameter; the chat picker keeps its call.

## 8. A session token must be a string (12.7.3, security)

**Why:** cookie-parser turns a cookie value starting with `j:` into the parsed JSON. A request with
`Cookie: iam.session_token=j:{"$ne":null}` and no other credential therefore carried an object. The role guards'
fallback (`BetterAuthTokenService.extractTokenFromRequest()`) passed it on, and `getSessionByToken()` used it as
MongoDB filter value, which MongoDB read as an operator: the request was answered as the owner of a stored session.
Affected since 11.10.0 on MongoDB, and since 12.1.1 on MySQL / MariaDB with a number (`j:7`: MySQL compares
`token = 7` numerically, so every token starting with `7` and a letter matches); the same applies to the legacy
`token` cookie. PostgreSQL is not affected.

**What changed:** `extractTokenFromRequest()` takes only a non-empty string from a cookie and skips anything else, and
`getSessionByToken()` answers `{ session: null, user: null }` for a value that is not a non-empty string, before it
queries. Nothing changes for a string token.

**Your project:** update; no code change is needed. Project code that calls `getSessionByToken()` with a cookie value
is covered by the check in that method. Code of your own that puts a cookie, query or body value into a database
filter itself checks it with `isQueryableString()` (exported from `@lenne.tech/nest-server`) first, as the framework's
token lookups do.

## Compatibility Notes

| Pattern | Status |
|---|---|
| `NODE_ENV` unset on a developer machine | Unchanged: the `local` block |
| `lt dev up` / `lt dev test` | They start the API with `NODE_ENV=local`; a `migrate:up` in the `start` script inherits the shell's `NODE_ENV` — pin it (§2, corrected in 12.7.1) |
| A starter-based project whose `src/config.env.ts` contains both starter 12.6.0 checks (`has no block…`, `is set but empty`) | Already refuses both cases itself; nothing changes |
| A starter-based project created earlier, without those checks | Affected like any other project: `pnpm run update` does not change `config.env.ts` (§1–§3) |
| vitest / jest suites without a `test` block | Keep the `local` block, with one warning per module instance |
| A project that calls `getEnvironmentConfig({ defaultEnv })` | `defaultEnv` still applies when `NODE_ENV` is unset |
| A `local` `env` from `NSC__ENV`, `NEST_SERVER_CONFIG` or a project's own loader on a deployed stage | Not caught here; the auth-link log line keeps its own `NODE_ENV` check (12.6.0) |
| `setupSwagger()` in `main.ts` | Unchanged call; it decides itself whether to mount (§4) |
| A generator fetching `/api-docs-json` from a deployed stage | 404 there unless `swagger: true` on that stage (§4) |
| JWT mode, frontend on `appUrl` | Works cross-origin with credentials now, 2FA sign-in included (§5) |
| JWT mode, a browser page on an origin not listed anywhere | Blocked by the browser; list it in `cors.allowedOrigins` (§5) |
| A client reading `token` from `list-sessions` | Gets none; use `id` and `revoke-session` with `{ sessionId }` (§6) |
| `revoke-session` with `{ token }` | Unchanged (§6) |
| `GET /ai/prompts` / `findAiPrompts` without the new parameter | Unchanged: enabled prompts only (§7) |
| Project code calling `getSessionByToken()` with a cookie value | Protected since 12.7.3: a value that is not a string finds no session (§8) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `NODE_ENV='<value>' has no block in the configuration (known: …)` at startup | The stage ran on the `local` block until now | Add a block for `<value>` to `config.env.ts` (§1) |
| `NODE_ENV is set but empty` at startup | An empty variable, often `NODE_ENV=${NODE_ENV}` in a compose file | Set the value or remove the line (§1) |
| `NODE_ENV='test' has no block in the configuration; a test runner is active` in a test run | vitest sets `NODE_ENV=test` | Nothing to do, or add a `test` block |
| A job (migration, seed) fails after the update while the application starts | The job runs with its own `NODE_ENV` | Give that `NODE_ENV` a block too (§2) |
| `lt dev up` stops in the migration step, the server would start | `migrate:up` inherits an exported `NODE_ENV` without a block (`development`) | `cross-env NODE_ENV=local pnpm run migrate:up` in the `start` script (§2) |
| A deploy.party stage is down after the update, the build was green | The API refused to start; the platform has no health check | Check the stage's `NODE_ENV` and its logs (§3) |
| A STACKIT pipeline is green but the stage still serves the previous version | The canary was aborted at its progress deadline | Look at the rollout status and the API's logs (§3) |
| `/swagger` answers 404 on a deployed stage | Swagger is off outside `local` / `ci` / `e2e` | `swagger: true` in that stage's block, or `NSC__SWAGGER=true` (§4) |
| A browser reports a CORS error for the API in JWT mode after the update | The page's origin is not `appUrl`, `baseUrl` or in `cors.allowedOrigins` | Add it to `cors.allowedOrigins` (§5) |
| Revoking a device does nothing after the update | The screen sends the `token` from `list-sessions`, which is gone | Send `{ sessionId: session.id }` (§6) |
| A disabled AI prompt is missing from the management screen | The screen lists without `includeDisabled` | `GET /ai/prompts?includeDisabled=true` (§7) |
