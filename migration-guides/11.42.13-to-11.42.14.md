# Migration Guide: 11.42.13 → 11.42.14

## Overview

| Category             | Details                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| **Bugfixes**         | A route-level `@UseGuards(AuthGuard(...))` no longer refuses every API token with 401 on a route released via `@ApiTokenScopes()` (§1) |
| **New Features**     | None                                                                                                     |
| **Framework API**    | Unchanged — no new exports, no changed signatures                                                        |
| **Dependencies**     | None for the package (development tooling only)                                                          |
| **Breaking Changes** | None. Tokens on routes that do not release them are refused exactly as before                            |
| **Migration Effort** | None. Projects that removed an `AuthGuard` to make tokens work may keep it removed (§1)                   |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required.

## 1. An explicit `AuthGuard` no longer closes a released route to API tokens

Many projects put `@UseGuards(AuthGuard(AuthGuardStrategy.BETTER_AUTH))` (or `AuthGuard(AuthGuardStrategy.JWT)`) on
routes next to `@Roles()`. nest-server-starter's `UserController` does so on six routes. The guard is redundant
there, because `@Roles()` already authenticates, but it was not harmless: it re-verified every request unless the
user came from Better-Auth, and a user authenticated by an API token does not. So it read the `ltt_…` credential as a
session or a JWT, failed, and answered **401** — on a route the role guard had just admitted via
`@ApiTokenScopes()`. Opening such a route for tokens therefore never worked while the guard was on it.

The guard now accepts the token `CoreApiTokenMiddleware` already authenticated, for the `JWT` and `BETTER_AUTH`
strategies. It applies the same route policy as the role guards (`enforceApiTokenRoute()`: deny by default, scopes,
tenant binding) itself, so it never admits a token on a route that does not release it — also in a setup where it
runs without a framework role guard in front of it.

```typescript
@ApiTokenScopes('read')
@Get(':id')
@Roles(RoleEnum.S_USER)
@UseGuards(AuthGuard(AuthGuardStrategy.BETTER_AUTH)) // 11.42.13: 401 for every token; 11.42.14: works
async getUser(@CurrentUser() currentUser: User, @Param('id') id: string): Promise<User> { … }
```

`AuthGuard(AuthGuardStrategy.JWT_REFRESH)`, `RefreshTokenGuard` and project-defined strategies never accept a token.

**What to check:**

- **You removed an `AuthGuard` from a route to make tokens work:** nothing to do. The guard stays redundant next to
  `@Roles()`; restoring it is optional.
- **A test expected 401 for a token on a released route that carries an `AuthGuard`:** it now gets the route's
  answer. A token on a route WITHOUT `@ApiTokenScopes()` is still refused with 403, as before.

## Compatibility Notes

| Pattern | Status |
| ------- | ------ |
| Routes with `@Roles()` only | Unchanged |
| Routes with `@Roles()` + `@UseGuards(AuthGuard(BETTER_AUTH \| JWT))` + `@ApiTokenScopes()` | Tokens now pass (§1) |
| Routes with `@UseGuards(AuthGuard(...))` but no `@ApiTokenScopes()` | Tokens refused with 403, as before |
| `refreshToken` / `AuthGuard(JWT_REFRESH)` / custom Passport strategies | Never accept a token, as before |
| A project guard that extends `AuthGuard(...)` and overrides `handleRequest()` | Compatible; the override also runs for token users |

## Troubleshooting

**A token still gets 401 on a route with an `AuthGuard`**
Check that the route (or its class) declares `@ApiTokenScopes()` with a scope the token holds — without it, the role
guard refuses the token with 403 before the `AuthGuard` runs. A 401 means the token itself did not authenticate
(revoked, expired, wrong prefix); the token middleware answers that before any guard.
