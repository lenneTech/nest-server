# Migration Guide: 11.43.2 → 11.43.3

## Overview

| Category             | Details                                                                                                                                                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bugfixes**         | An MCP OAuth access token reaches the tenant context: tenant-scoped AI tools answered "Tenant context required" to every OAuth client, members included (§1). The OAuth user is the current user of the request, so audit fields and the role guard plugin apply to tool writes (§2) |
| **New Features**     | None                                                                                                                                                                                                                                                                                 |
| **Framework API**    | `CoreTenantGuard.resolveMembershipContext()` (new, public), the optional `resolveMembership()` on the exported `TenantContextResolver` interface, `CoreAiMcpController.resolveScopedUser()` / `scopeLateResolvedUser()` (new, protected)                                             |
| **Dependencies**     | Unchanged                                                                                                                                                                                                                                                                            |
| **Breaking Changes** | None                                                                                                                                                                                                                                                                                 |
| **Migration Effort** | None. Check §2 if MCP tools of your project write data                                                                                                                                                                                                                               |

## Quick Migration

```bash
pnpm update @lenne.tech/nest-server
```

Vendor-mode projects pick it up with the core update. No code or configuration change is required.

## 1. MCP OAuth clients got no tenant context

`CoreTenantGuard` turns the tenant header (`X-Tenant-Id`) into a tenant context only for a user it sees on the
request. A session cookie and a Better-Auth JWT are resolved by the middleware before the guards. An MCP OAuth
access token is not: nothing but `CoreAiMcpController` accepts it, so it is resolved after the guards. The request
therefore never got a tenant, and `mongooseTenantPlugin` refused every tenant-scoped read — a generic MCP client
could discover, register, pass the consent page, open a session and list its tools, and then every tenant-scoped
tool answered `Tenant context required`, even with a header naming a tenant the user is an active member of.

The controller now asks the guard's own membership check (`CoreTenantGuard.resolveMembershipContext()`, the same
decision as its `@Roles(S_EVERYONE)` branch) for a user it resolved itself. The result does not depend on the
credential:

| Request                                               | Session cookie / JWT | MCP OAuth token (11.43.2) | MCP OAuth token (11.43.3) |
| ----------------------------------------------------- | -------------------- | ------------------------- | ------------------------- |
| Header names a tenant the user is an active member of | that tenant          | none — refused            | that tenant               |
| Header names a tenant the user is not a member of     | none — refused       | none — refused            | none — refused            |
| No header                                             | none — refused       | none — refused            | none — refused            |

The header alone never establishes a tenant, which is what keeps a freely chosen `X-Tenant-Id` harmless.

## 2. The OAuth user is the current user of the request

For the same reason `req.user` stayed unset for an OAuth request, and `RequestContext.currentUser` is read from
it. The Mongoose plugins read an empty current user as work the server does on its own:

- `createdBy` / `updatedBy` were not written for data an MCP tool created or changed,
- `mongooseRoleGuardPlugin` let a tool's write change `roles` without checking the caller,
- `assertTenantRole()` refused the call as anonymous.

Since 11.43.3 the controller sets `req.user` for a user it resolved itself, so all three behave as for a cookie or
JWT request.

**What to check:**

- **An MCP tool of your project writes `roles` and relied on the role guard plugin letting it through:** under an
  OAuth token that write is now checked against the user, as it always was under a cookie or a JWT. Run such a
  write inside `RequestContext.runWithBypassRoleGuard()` when the tool is meant to assign roles.
- **A test in your project pins the old refusal** ("Tenant context required" for an OAuth member): flip it to
  assert the data, and keep the cases for a non-member and for a missing header refused.
- **You override `CoreAiMcpController.handlePost()` or `handleGet()` / `handleDelete()`** without calling
  `super`: resolve the user through `resolveScopedUser(req)` instead of `resolveUser(req)`, or the fix does not
  reach your controller.

## Compatibility Notes

| Pattern                                                                      | Status                                                                                                        |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| MCP over a session cookie or a Better-Auth JWT                               | Unchanged — the guards saw the user before                                                                    |
| MCP OAuth without `multiTenancy`                                             | Unchanged apart from §2                                                                                       |
| Your own `TenantContextResolver` registered via `setTenantContextResolver()` | Compiles unchanged — `resolveMembership()` is optional; without it an OAuth request gets no tenant, as before |
| An override of `resolveUser()`                                               | Still used — `resolveScopedUser()` calls it                                                                   |
