# Migration Guide: 12.6.12 → 12.6.13

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None |
| **New Features** | None. New exports for the fixes below: `processGraphQlUploadRequest`, `GRAPHQL_UPLOAD_MAX_PATH_KEYS`, `GRAPHQL_UPLOAD_MAX_MAP_KEYS`, `isAgentCallContext()`, `resolveAgentCallRequest()` |
| **Bugfixes** | `HttpExceptionLogFilter` threw on `@nestjs/ai` / `@nestjs/mcp` calls, so the model read "Internal server error" for every refusal (§2) |
| **Security** | GraphQL multipart uploads (§1): graphql-upload GHSA-5vm7-vc2x-p3w2 (high, one anonymous request crashed the process), GHSA-qwwm-252j-9whw (medium, duplicate file fields leaked temporary files), and an unbounded `map` (one anonymous request with a deep path exhausted the heap, one with many entries blocked the event loop and took hundreds of MB). With `@nestjs/ai` or `@nestjs/mcp` installed, the global guards decided agent function and MCP tool calls on the tool ARGUMENTS (§2) |
| **Migration Effort** | `pnpm run update`. Projects that register `graphqlUploadExpress()` themselves pass the framework's parser (§1); vendor-mode projects add four dependencies (§3) |

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.6.13
pnpm run update   # nest-server-starter based projects
grep -rn "graphqlUploadExpress(" src/   # own registrations: pass processGraphQlUploadRequest (§1)
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual, then add the dependencies from §3.

## 1. Security: GraphQL multipart uploads

**No action needed** unless the project registers `graphqlUploadExpress()` itself (below).

`CoreModule` registers graphql-upload's `graphqlUploadExpress()` for `/graphql`, in front of every guard. Up to 12.6.12
it ran graphql-upload's own `processRequest`, which accepted any object path and any number of entries in the
multipart `map` field:

- **GHSA-5vm7-vc2x-p3w2 (high):** a path into an upload placed by an earlier entry replaced one of its methods. A
  request with `map={"1":["variables.file"],"2":["variables.file.reject"]}` and no file fields made the parser throw
  `TypeError: upload.reject is not a function` outside any request — an uncaught exception, on which the process
  exits (`installProcessDiagnostics()` exits 1, as Node does without it). **One anonymous request took the server
  down.** A path with a `__proto__` key let a client-supplied object pass the `GraphQLUpload` scalar's check.
- **GHSA-qwwm-252j-9whw (medium):** a second file field with the name of an already resolved upload created another
  temporary file and dropped the reference to the first, which was never deleted — temporary files and file
  descriptors leaked per request.
- **Unbounded path depth (no advisory; graphql-upload 18.0.2 has the same flaw):** the parser places each upload with
  object-path's `set()`, which recurses once per key and copies the remaining keys each time — O(n²) memory and time
  for a path of n keys, in one synchronous call. Measured on Node 24 with `map={"1":["variables.a.a.a…"]}`: 8,000 keys
  (16 KB) took 310 MB and blocked the event loop for half a second; 40,000 keys (80 KB) exhausted a 1 GB heap and
  ended the process. The default `maxFieldSize` of 1 MB leaves room for 400,000 keys.
- **Unbounded number of entries (no advisory; graphql-upload 18.0.2 has the same flaw):** every `map` entry becomes an
  upload, and one whose file never arrives is rejected at the end of the request with an error of its own, stack trace
  included. 1 MB of entries without any path (83,000 of them) took 230 MB and blocked the event loop for 410 ms.

graphql-upload fixed the two advisories in 18.0.2, which requires graphql 17; this framework runs graphql 16. 12.6.13
therefore ships `processGraphQlUploadRequest` (`common/helpers/graphql-upload.helper.ts`): graphql-upload 17.1.0's
parser with both upstream fixes and two bounds of its own, and `CoreModule` passes it to `graphqlUploadExpress()`. It
answers with 400:

- a path into another upload or with a `__proto__` key — "Invalid object path",
- a path with more than `GRAPHQL_UPLOAD_MAX_PATH_KEYS` (64) keys — "Invalid object path",
- a `map` with more than `GRAPHQL_UPLOAD_MAX_MAP_KEYS` (10,000) entries and path keys together. Every entry counts one,
  every key of its paths one more, so `{"1":["variables.file"]}` counts 3. The path that goes over the bound is
  answered with "Invalid object path", an entry with "Invalid ‘map’ multipart field entry key …" before its upload is
  created.

A duplicate file field is ignored. Each of these requests is now answered within about 40 ms, most of it parsing the
field's JSON (the 83,000 entries: ~35 ms, +50 MB). A path a client library builds has a handful of keys
(`variables.file` 2, `variables.input.files.3` 4, batched `0.variables.file` 3); 10,000 is some 2,000 files at
`variables.input.files.N`. The most expensive request the bounds still accept — 10,000 entries without a path — blocks
the event loop for about 60 ms with +45 MB. graphql-upload stays at 17.1.0 for its scalar and middleware.

**A project that registers `graphqlUploadExpress()` itself** (its own route, its own limits) passes the framework's
parser — graphql-upload's default is the vulnerable one:

```typescript
import { processGraphQlUploadRequest } from '@lenne.tech/nest-server';
import graphqlUploadExpress from 'graphql-upload/graphqlUploadExpress.mjs';

consumer
  .apply(graphqlUploadExpress({ maxFiles: 10, maxFileSize: 10_000_000, processRequest: processGraphQlUploadRequest }))
  .forRoutes('graphql');
```

Find such registrations with `grep -rn "graphqlUploadExpress(" src/`. A project that calls graphql-upload's
`processRequest` directly switches to `processGraphQlUploadRequest` (same signature and options).

**Behaviour change:** a GraphQL variable literally named `__proto__` that receives a file is refused with 400 (input
object fields cannot use that name; names starting with `__` are reserved).

## 2. Guards on `@nestjs/ai` and `@nestjs/mcp` calls

Only relevant to a project that installs `@nestjs/ai` (`@AgentFunction()`) or `@nestjs/mcp` (`@Tool()`, `@Resource()`,
`@Prompt()`). Both run every global guard, interceptor and filter of the application around their methods, with the
context types `'ai'` / `'mcp'` and the arguments `[input, call]`. Index 0 is what the model or the MCP client wrote.
Up to 12.6.12 the framework's guards fell back to `switchToHttp().getRequest()` there — index 0. Tool arguments
`{ "user": { "roles": ["admin"] } }` were the caller a guard decided on.

Since 12.6.13 the framework resolves the request of such a call from the call object (`caller.request`,
`McpContext.request`):

- `@Roles()` on an agent function or MCP tool is decided against the request's user exactly as over HTTP, tenant
  header included — in `RolesGuard`, `BetterAuthRolesGuard`, `CoreTenantGuard`, the auth guard and the legacy
  rate-limit guard.
- A **request-less** caller — `caller: { user, scopes }` (a queue job), a durable run, MCP over stdio — is
  **anonymous**: public methods run, every other one is refused with 401. To run a role-gated agent function from a job,
  authenticate there and pass a request (`caller: { request }`).
- `@CurrentUser()` / `@RESTUser()` and the response interceptors (`@Restricted`, secret fields) use the request's user.
- `HttpExceptionLogFilter` hands the exception back to the package instead of writing an HTTP response, so the model
  or MCP client reads the refusal's message instead of "Internal server error".

**Not in 12.6.13** — these parts of the 12.10.x work stay on the 12.10 line: the `MCP_VERIFIED_USER` token,
`CoreAiMcpOAuthService.createMcpTokenVerifier()` for a `@nestjs/mcp` endpoint, the AI SDK transport
(`providerType: 'nestjs-ai'`), agent functions as AI tools, and the removal of secret fields from AI tool results.
Update to 12.10.x for them.

**A guard of your own** that reads the request with `switchToHttp().getRequest()` (or `GqlExecutionContext`'s `req`
with that fallback) has the same flaw on these calls. Resolve the request through the framework:

```typescript
import { resolveGuardRequest } from '@lenne.tech/nest-server';
import { GqlExecutionContext } from '@nestjs/graphql';

canActivate(context: ExecutionContext): boolean {
  // undefined for a request-less agent / MCP call: treat it as anonymous
  const request = resolveGuardRequest(context, (ctx) => GqlExecutionContext.create(ctx).getContext());
  // …
}
```

Nothing to do otherwise, unless the project relied on the old behaviour.

## 3. Dependencies

New direct `dependencies` for the multipart parser (§1): `busboy` 1.6.0, `fs-capacitor` 8.0.0, `http-errors` 2.0.1 and
`object-path` 0.11.8 — the versions graphql-upload 17.1.0 already installs, so an npm-mode project gets no new package.

A **vendor-mode** project declares them in `dependencies`: the core imports them directly, and a pnpm project does not
see graphql-upload's own copies. A project that compiles with `noImplicitAny` (part of `strict`) also adds
`@types/busboy` 1.5.5, `@types/http-errors` 2.0.5 and `@types/object-path` 0.11.4 to `devDependencies`.

## Compatibility Notes

| Pattern | Status |
|---|---|
| Uploads through `CoreModule`'s `/graphql` registration | Protected with the update |
| `graphqlUploadExpress()` registered by the project | Pass `processRequest: processGraphQlUploadRequest` (§1) |
| Vendor mode, GraphQL uploads | Add the four dependencies (and the `@types/*` under `noImplicitAny`) from §3 |
| Projects without `@nestjs/ai` / `@nestjs/mcp` | Unchanged — the guards take the new branch only for the context types `'ai'` / `'mcp'` |
| A guard of the project's own on agent / MCP calls | Resolve the request with `resolveGuardRequest()` (§2) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Vendor mode: `Cannot find package 'busboy'` (or `fs-capacitor`, `http-errors`, `object-path`) at start | The core imports them since 12.6.13 | Add them to `dependencies` (§3) |
| Vendor mode: `TS7016: Could not find a declaration file for module 'busboy'` (or `http-errors`, `object-path`) | `noImplicitAny` without the type packages | Add the `@types/*` packages from §3 |
| A file upload answers 400 `Invalid object path for the ‘map’ multipart field …` | The `map` names a path into another upload, with a `__proto__` key or with more than 64 keys | Send each file at its own flat variable path (`variables.files.0`, `variables.input.files.3`) |
| An upload of very many files answers 400 `Invalid object path …` or `Invalid ‘map’ multipart field entry key …` | The `map` has more than 10,000 entries and path keys together | Split the upload into several requests |
| A role-gated agent function answers 401 from a queue job | Request-less callers are anonymous | Authenticate in the job and pass `caller: { request }` |
