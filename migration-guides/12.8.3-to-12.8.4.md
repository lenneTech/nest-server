# Migration Guide: 12.8.3 → 12.8.4

## Overview

| Category | Details |
|---|---|
| **Breaking Changes** | None for the application. The minimum versions of the optional peers rise: mongodb `>= 7.8.0`, mongoose `>= 9.12.0` (§1) |
| **New Features** | None |
| **Bugfixes** | Security: mongodb 7.8.0 closes GHSA-77w5-j825-v4qm (`timeoutMS`) and a flaw in the host-name check of SRV lookups (`mongodb+srv://`) (§1) |
| **Migration Effort** | `pnpm run update`. A project that pins mongoose / mongodb itself — vendored cores included — raises them (§1). A test setup that registers the Better-Auth resolver twice gets an error from @nestjs/graphql 14.2 (§2) |

12.8.4 is a maintenance release: dependencies only, the framework's code is unchanged.

## Quick Migration

```bash
pnpm add @lenne.tech/nest-server@12.8.4
pnpm run update   # nest-server-starter based projects: raises mongoose / mongodb and the NestJS pins with the framework
pnpm run build
pnpm test
```

**Vendor mode**: run `/lt-dev:backend:update-nest-server-core` as usual, and raise mongoose / mongodb in the project's own
`package.json` (§1).

## 1. mongoose 9.12.0 and mongodb 7.8.0 (security)

mongoose 9.12.0 moves to the mongodb driver 7.8.0. That driver closes two flaws present in every earlier 7.x:

- **GHSA-77w5-j825-v4qm / CVE-2026-119179** (high): with `timeoutMS`, a connection-pool desynchronization after an
  operation timeout could hand one user's data to another. Only projects that set `timeoutMS` themselves are affected —
  the framework never sets it. Since 7.8.0 `timeoutMS` is a no-op; use `serverSelectionTimeoutMS`, `socketTimeoutMS`,
  `waitQueueTimeoutMS` and `maxTimeMS` instead.
- **SRV host-name verification** (mongodb `>= 3.3.3 < 7.8.0`, no GHSA): a host returned by the SRV lookup of a
  `mongodb+srv://` URL was not verified properly, so whoever controlled the DNS answer could redirect the driver to a
  host outside your domain. Projects with `mongodb://host1,host2` URLs are not affected.

Neither appears in `pnpm audit` — GHSA-77w5 is a repository advisory of the driver, the SRV flaw has no GHSA at all — so
the update is the only signal.

**What changed:** the optional peers now require mongodb `>= 7.8.0` and mongoose `>= 9.12.0` (before: `>= 7.7.0` /
`>= 9.11.4`). mongoose 9.11 pins the driver to `~7.7`, so raising mongodb alone leaves mongoose's own copy vulnerable —
raise both.

**What to do:** nest-server-starter based projects get both through `pnpm run update`. A project that pins mongoose and
mongodb itself — every vendor-mode project on MongoDB does — sets them to `9.12.0` / `7.8.0`:

```bash
pnpm add mongoose@9.12.0 mongodb@7.8.0
```

## 2. @nestjs/graphql 14.2: a field resolved by two unrelated resolvers fails the start

12.8.4 raises NestJS to 12.4 and `@nestjs/graphql` to 14.2. `@nestjs/graphql` 14.2 now refuses a GraphQL field that two
resolver classes resolve when neither extends the other. The symptom, at application start:

```
"Query.betterAuthSession" is resolved by both "DefaultBetterAuthResolver.betterAuthSession" and
"BetterAuthResolver.betterAuthSession", which do not override one another, so the order in which the modules are
scanned would decide which one runs.
```

**Where it appears:** in a test setup that imports `CoreModule.forRoot(envConfig)` (IAM-only signature, which registers
the default Better-Auth module) **and** the project's own `BetterAuthModule.forRoot(…)` with its resolver. Outside tests
the framework's duplicate-registration safety net keeps the second registration out; under vitest (`VITEST` set) that
net is off on purpose, so both resolvers reached the schema — before 14.2 one of them won silently.

**Fix — use one of the documented registration patterns:**

```typescript
// Pattern 3: the project registers Better-Auth itself
const config = { ...envConfig, betterAuth: { ...envConfig.betterAuth, autoRegister: false } };
CoreModule.forRoot(config);
BetterAuthModule.forRoot({ config: config.betterAuth, … });

// or Pattern 2: let CoreModule register the project's classes
CoreModule.forRoot(envConfig, { betterAuth: { controller: BetterAuthController, resolver: BetterAuthResolver } });
```

## 3. Further updates

better-auth, `@better-auth/core` and `@better-auth/passkey` 1.7.18 (bug fixes, no advisory against 1.7.16; the peer
range `>= 1.7.16 < 1.8.0` is unchanged), `@nestjs/swagger` 12.1.1, `@nestjs/jwt` 12.0.4, `@nestjs/schedule` 12.0.3,
`@nestjs/passport` 12.0.1, `@nestjs/mongoose` 12.0.1, nodemailer 10.4.0, graphql-ws 6.4.1, ws 8.22.1 and development
tooling. Majors are left for later (graphql 17, graphql-upload 18, TypeScript 7, undici 8).

## Compatibility Notes

| Pattern | Status |
|---|---|
| nest-server-starter based project, `pnpm run update` | Unchanged — pins follow the framework |
| Project pinning mongoose 9.11 / mongodb 7.7 itself | Peer warning; raise to 9.12.0 / 7.8.0 (§1) |
| `timeoutMS` in a connection option | Now a no-op (mongodb 7.8.0) — use the per-stage timeouts (§1) |
| Test setup with `CoreModule.forRoot(envConfig)` + `BetterAuthModule.forRoot()` | Fails at start under vitest — §2 |
| Production app with the same registration | Unchanged (the safety net registers Better-Auth once) |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `"Query.betterAuthSession" is resolved by both "DefaultBetterAuthResolver…" and "BetterAuthResolver…"` | Better-Auth registered twice in a test setup (§2) | `autoRegister: false`, or the `overrides` parameter of `CoreModule.forRoot()` |
| Peer warning for mongoose / mongodb | The project pins 9.11 / 7.7 | `pnpm add mongoose@9.12.0 mongodb@7.8.0` |
| Operations no longer time out after `timeoutMS` | `timeoutMS` is a no-op since mongodb 7.8.0 | `serverSelectionTimeoutMS`, `socketTimeoutMS`, `maxTimeMS` |
